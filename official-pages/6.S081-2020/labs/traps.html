回溯

对于调试来说，回溯通常很有用：堆栈上错误发生点上方的函数调用列表。

实施一个 backtrace() 函数于 kernel/printf.c。插入对此函数的调用 sys_sleep，然后运行 bttest，这称为 sys_sleep。您的输出应如下所示： 

backtrace:
0x0000000080002cda
0x0000000080002bb6
0x0000000080002898
之后 bttest 退出 qemu。在您的终端中：地址可能略有不同，但如果您运行 addr2line -e kernel/kernel （或 riscv64-unknown-elf-addr2line -e kernel/kernel）并剪切并粘贴上述地址，如下所示： 
    $ addr2line -e kernel/kernel
    0x0000000080002de2
    0x0000000080002f4a
    0x0000000080002bfc
    Ctrl-D
你应该看到这样的东西： 
    kernel/sysproc.c:74
    kernel/syscall.c:224
    kernel/trap.c:85

编译器在每个堆栈帧中放入一个帧指针，该指针保存调用者的帧指针的地址。你的 backtrace 应该使用这些帧指针来遍历堆栈并打印每个堆栈帧中保存的返回地址。

一些提示：

  • 添加回溯原型 kernel/defs.h 这样你就可以调用 backtrace 在 sys_sleep.
  • GCC编译器将当前执行函数的帧指针存储在寄存器中 s0。添加以下函数 kernel/riscv.h: 
    static inline uint64
r_fp()
{
  uint64 x;
  asm volatile("mv %0, s0" : "=r" (x) );
  return x;
}
    并在中调用这个函数 backtrace 读取当前帧指针。该函数使用 在线组装 阅读 s0.
  • 这些 讲义 有堆栈帧布局的图片。请注意，返回地址位于距堆栈帧的帧指针的固定偏移量 (-8) 处，并且保存的帧指针位于距帧指针的固定偏移量 (-16) 处。
  • xv6 为 xv6 内核中页对齐地址的每个堆栈分配一页。您可以使用以下方法计算堆栈页的顶部和底部地址 PGROUNDDOWN(fp) 和 PGROUNDUP(fp) （见 kernel/riscv.h。这些数字有帮助 backtrace 终止其循环。

一旦你的回溯开始工作，就可以从 panic 在 kernel/printf.c 这样你就可以在内核崩溃时看到它的回溯。

报警

在本练习中，您将向 xv6 添加一项功能，该功能会在进程使用 CPU 时间时定期发出警报。这对于想要限制其消耗的 CPU 时间的计算密集型进程，或者想要计算但也想要执行一些定期操作的进程可能很有用。更一般地说，您将实现用户级中断/故障处理程序的原始形式；例如，您可以使用类似的方法来处理应用程序中的页面错误。如果您的解决方案通过了警报测试和用户测试，则它是正确的。

你应该添加一个新的 sigalarm(interval, handler) 系统调用。如果应用程序调用 sigalarm(n, fn)，然后每次之后 n 程序消耗的CPU时间的“滴答声”，内核应该引起应用程序功能 fn 被召唤。当 fn 返回时，应用程序应从中断处恢复。时钟周期是 xv6 中相当任意的时间单位，由硬件计时器生成中断的频率决定。如果应用程序调用 sigalarm(0, 0)，内核应该停止生成周期性警报调用。

你会发现一个文件 user/alarmtest.c 在您的 xv6 存储库中。将其添加到 Makefile 中。在添加之前它不会正确编译 sigalarm 和 sigreturn 系统调用（见下文）。

alarmtest 来电 sigalarm(2, periodic) 在 test0 要求内核强制调用 periodic() 每 2 个刻度，然后旋转一段时间。你可以在user/alarmtest.asm中看到alarmtest的汇编代码，这可能会方便调试。当以下情况时，您的解决方案是正确的： alarmtest 产生这样的输出，并且 usertests 也可以正确运行：

test0：调用处理程序

首先修改内核以跳转到用户空间中的警报处理程序，这将导致 test0 打印“alarm!”。不用担心“警报”之后会发生什么！输出;如果您的程序在打印“alarm!”后崩溃，现在没关系。以下是一些提示：

  • 您需要修改 Makefile 才能导致 alarmtest.c 编译为 xv6 用户程序。
  • 放置正确的声明 user/user.h are: 
        int sigalarm(int ticks, void (*handler)());
    int sigreturn(void);
  • 更新 user/usys.pl （生成 user/usys.S）、kernel/syscall.h 和 kernel/syscall.c 以允许 alarmtest 调用 sigalarm 和 sigreturn 系统调用。
  • 现在，您的 sys_sigreturn 应该只返回零。
  • 你的 sys_sigalarm() 应将警报间隔和指向处理函数的指针存储在新字段中 proc 结构（在 kernel/proc.h).
  • 您需要跟踪自上次调用进程的警报处理程序以来已经经过了多少个滴答声（或直到下一次调用为止）；你需要一个新领域 struct proc 也为此。你可以初始化 proc 领域在 allocproc() 在 proc.c.
  • 每个滴答声，硬件时钟都会强制产生一个中断，该中断在 usertrap() 在 kernel/trap.c.
  • 如果存在计时器中断，您只想操纵进程的警报滴答声；你想要类似的东西 
        if(which_dev == 2) ...
  • 仅当进程有未完成的计时器时才调用警报函数。请注意，用户警报函数的地址可能为 0（例如，在 user/alarmtest.asm 中， periodic 位于地址 0)。
  • 你需要修改 usertrap() 这样当进程的警报间隔到期时，用户进程就会执行处理函数。当 RISC-V 上的陷阱返回到用户空间时，什么决定了用户空间代码恢复执行的指令地址？
  • 如果您告诉 qemu 仅使用一个 CPU，那么使用 gdb 查看陷阱会更容易，您可以通过运行 
        make CPUS=1 qemu-gdb
  • 如果alarmtest打印出“alarm!”，那么你就成功了。

test1/test2()：恢复中断的代码

有可能alarmtest 在打印“alarm!”后在test0 或test1 中崩溃，或者alarmtest（最终）打印“test1 失败”，或者alarmtest 退出而不打印“test1 通过”。要解决此问题，必须确保当警报处理程序完成时，控制返回到用户程序最初被定时器中断中断的指令。您必须确保寄存器内容恢复到中断时所保存的值，以便用户程序在报警后可以不受干扰地继续运行。最后，您应该在每次警报计数器响起后“重新启动”警报计数器，以便定期调用处理程序。

作为起点，我们为您做出了一个设计决策：用户警报处理程序需要调用 sigreturn 当他们完成时系统调用。看看 periodic 在 alarmtest.c 举个例子。这意味着您可以将代码添加到 usertrap 和 sys_sigreturn 它们相互配合，使用户进程在处理警报后正确恢复。

一些提示：

  • 您的解决方案将要求您保存和恢复寄存器——您需要保存和恢复哪些寄存器才能正确恢复中断的代码？ （提示：会很多）。
  • 有 usertrap 保存足够的状态 struct proc 当计时器响起时 sigreturn 可以正确返回被中断的用户代码。
  • 防止对处理程序的重入调用——如果处理程序尚未返回，内核不应再次调用它。 test2 测试这个。

一旦你通过了 test0, test1, 和 test2 跑 usertests 确保您没有破坏内核的任何其他部分。
