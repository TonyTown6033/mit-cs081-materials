回溯

在调试时，查看回溯信息通常非常有用：回溯是从错误发生点向上追溯，列出调用栈上各函数调用的列表。

请实现一个 backtrace() 中的函数 kernel/printf.c函数。并在以下位置插入对该函数的调用： sys_sleep，然后运行 bttest，它调用 sys_sleep。你的输出应如下所示： 

backtrace:
0x0000000080002cda
0x0000000080002bb6
0x0000000080002898
在 bttest 退出 qemu。在你的终端中：地址可能略有不同，但如果你运行 addr2line -e kernel/kernel （或 riscv64-unknown-elf-addr2line -e kernel/kernel）并按如下方式粘贴上述地址： 
    $ addr2line -e kernel/kernel
    0x0000000080002de2
    0x0000000080002f4a
    0x0000000080002bfc
    Ctrl-D
你应该会看到类似如下的内容： 
    kernel/sysproc.c:74
    kernel/syscall.c:224
    kernel/trap.c:85

编译器在每个栈帧中存放一个帧指针，用于保存调用者栈帧的地址。你的 backtrace 应利用这些帧指针沿栈向上遍历，并打印每个栈帧中保存的返回地址。

一些提示：

  • 将 backtrace 的函数原型添加到 kernel/defs.h 以便你可以在 backtrace 中 sys_sleep.
  • GCC 编译器将当前正在执行的函数的帧指针存储在寄存器 s0。将以下函数添加到 kernel/riscv.h: 
    static inline uint64
r_fp()
{
  uint64 x;
  asm volatile("mv %0, s0" : "=r" (x) );
  return x;
}
    并在 backtrace 中调用此函数以读取当前帧指针。该函数使用 内联汇编 来读取 s0.
  • 这些 课程笔记 中有栈帧布局的示意图。注意，返回地址位于栈帧帧指针的固定偏移量（-8）处，而保存的帧指针位于帧指针的固定偏移量（-16）处。
  • xv6 在 PAGE 对齐的地址处为 xv6 内核中的每个栈分配一页内存。你可以使用 PGROUNDDOWN(fp) 和 PGROUNDUP(fp) 中查看其使用示例（参见 kernel/riscv.h来计算栈页的顶部和底部地址。这些数值有助于 backtrace 终止其循环。

一旦你的回溯功能正常运行，请从 panic 中 kernel/printf.c 以便在内核发生 panic 时看到其回溯信息。

警报

在本练习中，你将为 xv6 添加一项功能，使其能够在进程使用 CPU 时间时周期性地发出提醒。这对于希望限制自身 CPU 占用时间的计算密集型进程，或那些在执行计算的同时还需要定期执行某些操作的进程，都十分有用。更广泛地说，你将实现一种用户态中断/故障处理程序的基础形式；例如，你可以用类似的机制在应用程序中处理缺页错误。若你的解答能通过 alarmtest 和 usertests，则视为正确。

您应该添加一个新的 sigalarm(interval, handler) 系统调用。如果应用程序调用 sigalarm(n, fn)，然后在每 n 程序消耗的 CPU 时间"滴答数"，内核应触发应用程序函数 fn 被调用。当 fn 返回时，应用程序应从中断处继续执行。时钟节拍（tick）是 xv6 中一个相当任意的时间单位，由硬件定时器产生中断的频率决定。如果应用程序调用 sigalarm(0, 0)，内核应停止生成周期性的告警调用。

您将找到一个文件 user/alarmtest.c 在你的 xv6 代码仓库中。将其添加到 Makefile。在你添加之前，它无法正确编译 sigalarm 和 sigreturn 系统调用（见下文）。

alarmtest 调用 sigalarm(2, periodic) 中 test0 请求内核强制调用 periodic() 每 2 个时钟滴答调用一次，然后自旋一段时间。你可以在 user/alarmtest.asm 中查看 alarmtest 的汇编代码，这对调试很有帮助。当 alarmtest 产生如下输出且 usertests 也能正确运行时，你的解答即为正确：

test0：调用处理程序

首先修改内核，使其跳转到用户态中的告警处理程序，从而让 test0 打印出 "alarm!"。暂时不用关心打印 "alarm!" 之后会发生什么；程序在打印 "alarm!" 后崩溃目前是可以接受的。以下是一些提示：

  • 你需要修改 Makefile，使 alarmtest.c 被编译为 xv6 用户程序。
  • 需要放入 user/user.h are: 
        int sigalarm(int ticks, void (*handler)());
    int sigreturn(void);
  • 更新 user/usys.pl（该文件用于生成 user/usys.S）、kernel/syscall.h 以及 kernel/syscall.c，以允许 alarmtest 以调用 sigalarm 和 sigreturn 系统调用。
  • 目前，你的 sys_sigreturn 只需返回零即可。
  • 你的 sys_sigalarm() 应将报警间隔和处理函数的指针存储在 proc 结构体（在 kernel/proc.h).
  • 你需要记录自上次调用进程的报警处理函数以来（或距下次调用还剩）经过了多少个时钟滴答；为此你还需要在 struct proc 中新增一个字段。你可以在 proc 中初始化 allocproc() 中 proc.c.
  • 每个时钟滴答，硬件时钟会强制触发一次中断，该中断由 usertrap() 中 kernel/trap.c.
  • 只有在发生时钟中断时，才需要操作进程的报警计数；你需要类似这样的逻辑： 
        if(which_dev == 2) ...
  • 仅在进程有待触发的定时器时才调用报警函数。注意，用户报警函数的地址可能为 0（例如，在 user/alarmtest.asm 中， periodic 位于地址 0）。
  • 你需要修改 usertrap() 以便在进程的报警间隔到期时，用户进程能够执行处理函数。当 RISC-V 上的陷阱返回到用户态时，是什么决定了用户态代码恢复执行的指令地址？
  • 如果你告诉 qemu 只使用一个 CPU，用 gdb 查看陷阱会更容易，你可以通过运行以下命令来实现 
        make CPUS=1 qemu-gdb
  • 如果 alarmtest 打印出 "alarm!"，则说明你已经成功。

test1/test2()：恢复被中断的代码

alarmtest 很可能在打印 "alarm!" 后崩溃于 test0 或 test1，或者 alarmtest（最终）打印 "test1 failed"，或者 alarmtest 在未打印 "test1 passed" 的情况下退出。要解决此问题，你必须确保当警报处理程序执行完毕后，控制流能够返回到用户程序最初被计时器中断所打断的那条指令处。你必须确保寄存器内容恢复为中断发生时所保存的值，以便用户程序能够在中断后继续正常运行。最后，每次警报触发后，你应当重新"装填"警报计数器，以便处理程序能够被周期性地调用。

作为起点，我们已经为你做出了一个设计决策：用户告警处理程序必须调用 sigreturn 系统调用完成后返回。请看 periodic 中 alarmtest.c 作为示例。这意味着你可以向 usertrap 和 sys_sigreturn 这些函数协同工作，确保用户进程在处理完警报后能够正确恢复执行。

一些提示：

  • 您的解决方案需要保存和恢复寄存器——为了正确恢复被中断的代码，您需要保存和恢复哪些寄存器？（提示：数量会很多）。
  • 确保 usertrap 在以下位置保存足够的状态： struct proc 当计时器触发时， sigreturn 能够正确返回到被中断的用户代码。
  • 防止对处理程序的重入调用——如果一个处理程序尚未返回，内核不应再次调用它。 test2 对此进行了测试。

一旦通过 test0, test1，以及 test2 运行 usertests 以确保你没有破坏内核的其他任何部分。
