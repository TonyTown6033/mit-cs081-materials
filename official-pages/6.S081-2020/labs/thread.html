# 使用线程

在本作业中，你将使用哈希表探索基于线程和锁的并行编程。你应该在一台真实的 Linux 或 MacOS 计算机（而非 xv6，也非 qemu）上完成本作业，该计算机需具备多核处理器。目前大多数笔记本电脑均配备了多核处理器。

本作业使用 UNIX pthread 线程库。你可以通过以下手册页找到相关信息： man pthreads，你也可以在网上查阅相关资料，例如 这里, 这里，以及 这里.

该文件 notxv6/ph.c 包含一个简单的哈希表，在单线程使用时是正确的，但在多线程使用时则不正确。在你的 xv6 主目录中（也许是 ~/xv6-labs-2020），请输入： 

$ make ph
$ ./ph 1
注意，构建时需要 ph Makefile 使用的是你操作系统的 gcc，而非 6.S081 的工具链。传递给 ph 指定在哈希表上执行 put 和 get 操作的线程数量。运行一段时间后， ph 1 将产生类似如下的输出： 
100000 puts, 3.991 seconds, 25056 puts/second
0: 0 keys missing
100000 gets, 3.981 seconds, 25118 gets/second

您看到的数字可能与此示例输出相差两倍或更多，这取决于您的计算机速度、是否具有多个核心，以及是否正在忙于处理其他任务。

ph 运行两个基准测试。首先，通过调用 put()，并打印每秒 puts 操作的实际速率。然后它从哈希表中获取键，使用 get()。它打印出因 puts 操作而本应存在于哈希表中但却丢失的键的数量（此处为零），并打印出每秒完成的 gets 操作数量。

您可以看出 ph 通过给定大于一的参数，使多个线程同时使用其哈希表。试试 ph 2: 

$ ./ph 2
100000 puts, 1.885 seconds, 53044 puts/second
1: 16579 keys missing
0: 16579 keys missing
200000 gets, 4.322 seconds, 46274 gets/second
这段文字的第一行是 ph 2 输出表明，当两个线程并发地向哈希表中添加条目时，它们的总插入速率达到每秒 53,044 次。这大约是运行单线程时速率的两倍 ph 1。这是一个出色的"并行加速"效果，约达 2 倍，这也是所能期望的最大值（即两倍的核心数带来每单位时间两倍的工作量）。

然而，这两行写道 16579 keys missing 表明哈希表中应该存在的大量键实际上并不在其中。也就是说，put 操作本应将这些键添加到哈希表中，但出现了问题。请查看 notxv6/ph.c，尤其是在 put() 和 insert().

为什么使用 2 个线程时会出现键缺失的情况，而使用 1 个线程时不会？请找出一个使用 2 个线程时可能导致键缺失的事件序列，并将你的事件序列及简短说明提交至 answers-thread.txt

为了避免这一系列事件的发生，请在以下位置插入加锁和解锁语句： put 和 get 中 notxv6/ph.c 这样在使用两个线程时，缺失的键的数量始终为 0。相关的 pthread 调用如下： 

pthread_mutex_t lock;            // declare a lock
pthread_mutex_init(&lock, NULL); // initialize the lock
pthread_mutex_lock(&lock);       // acquire lock
pthread_mutex_unlock(&lock);     // release lock

你已完成当 make grade 表示你的代码通过了 ph_safe 测试，该测试要求在使用两个线程时零缺失键。此时未通过 ph_fast 测试。

不要忘记调用 pthread_mutex_init(). 首先用 1 个线程测试你的代码，然后用 2 个线程测试。结果是否正确（即你是否消除了键丢失的问题）？双线程版本相对于单线程版本是否实现了并行加速（即单位时间内完成更多的总工作量）？

在某些情况下，并发 put()s在哈希表中读写的内存没有重叠，因此不需要用锁来相互保护。你能否修改 ph.c 以利用这类情况，从而在某些 put()每个哈希桶一个锁如何？

修改你的代码，使得某些 put 操作在保持正确性的同时并行运行。完成后， make grade 表示您的代码通过了这两项 ph_safe 和 ph_fast 测试。该 ph_fast 该测试要求两个线程每秒的 put 次数至少是单个线程的 1.25 倍。

屏障

在本次作业中，你将实现一个 屏障：应用程序中的一个点，所有参与的线程必须在此等待，直到其他所有参与的线程也到达该点。你将使用 pthread 条件变量，这是一种类似于 xv6 的 sleep 和 wakeup 的序列协调技术。

你应该在真实计算机上完成本作业（不是 xv6，不是 qemu）。

该文件 notxv6/barrier.c 包含一个存在缺陷的屏障。 

$ make barrier
$ ./barrier 2
barrier: notxv6/barrier.c:42: thread: Assertion `i == t' failed.
2 指定了在屏障处同步的线程数量（ nthread 中 barrier.c）。每个线程执行一个循环。在每次循环迭代中，线程调用 barrier() 然后随机休眠若干微秒。由于一个线程在另一个线程到达屏障之前就已离开屏障，断言被触发。期望的行为是每个线程在 barrier() 直到所有 nthreads 它们都已调用了 barrier().

您的目标是实现所需的屏障行为。除了您在 ph 在本作业中，您将需要以下新的 pthread 原语；请查阅 这里 和 这里 详情请参阅。 

pthread_cond_wait(&cond, &mutex);  // go to sleep on cond, releasing lock mutex, acquiring upon wake up
pthread_cond_broadcast(&cond);     // wake up every thread sleeping on cond

确保你的解决方案通过 make grade的 barrier 测试。

pthread_cond_wait 释放 mutex 当被调用时，并重新获取 mutex 在返回之前。

我们已为你提供了 barrier_init()。你的任务是实现 barrier() 以使 panic 不会发生。我们已经定义了 struct barrier 供你使用；其字段供你自行使用。

有两个问题会使你的任务变得复杂：

  • 你需要处理一系列连续的 barrier 调用，我们将每次调用称为一轮。 bstate.round 记录当前轮次。你应该递增 bstate.round 每当所有线程都到达 barrier 时执行一次。
  • 你需要处理这种情况：一个线程在其他线程尚未退出 barrier 之前就抢先绕回循环。特别地，你在不同轮次中重复使用了 bstate.nthread 变量。请确保一个已离开 barrier 并抢先绕回循环的线程不会增加 bstate.nthread 而此时上一轮仍在使用它。

uthread 的可选挑战

用户级线程包在多个方面与操作系统存在不良交互。例如，如果一个用户级线程在系统调用中阻塞，另一个用户级线程将无法运行，因为用户级线程调度器不知道其某个线程已被 xv6 调度器取消调度。又如，两个用户级线程无法在不同核心上并发运行，因为 xv6 调度器并不知道存在多个可并行运行的线程。请注意，如果两个用户级线程真正并行运行，由于存在若干竞争条件，该实现将无法正常工作（例如，运行在不同处理器上的两个线程可能同时调用 thread_schedule 同时选择同一个可运行线程，并在不同处理器上分别运行它。）

有几种方法可以解决这些问题。其中一种是使用 调度程序激活（scheduler activations） 另一种是为每个用户级线程使用一个内核线程（如 Linux 内核所做的那样）。在 xv6 中实现其中一种方式。这并不容易做到正确；例如，当为多线程用户进程更新页表时，你需要实现 TLB 击落（TLB shootdown）。

向你的线程包中添加锁、条件变量、屏障（barrier）等。
