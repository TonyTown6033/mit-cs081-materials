实验：系统调用

在上一个实验中，你使用系统调用编写了一些实用程序。在本实验中，你将向 xv6 添加一些新的系统调用，这将帮助你理解系统调用的工作原理，并让你接触 xv6 内核的部分内部实现。你将在后续实验中添加更多系统调用。

在开始编写代码之前，请阅读 xv6 书的第 2 章，以及第 4 章的 4.3 节和 4.4 节，以及相关源文件：

  • 系统调用的用户态代码位于 user/user.h 和 user/usys.pl.
  • 内核态代码位于 kernel/syscall.h, kernel/syscall.c.
  • 进程相关代码位于 kernel/proc.h 和 kernel/proc.c.

要开始本实验，请切换到 syscall 分支： 

  $ git fetch
  $ git checkout syscall
  $ make clean

如果你运行 make grade，你会发现评分脚本无法执行 trace 和 sysinfotest。你的任务是添加必要的系统调用及其桩函数，使其正常运行。

系统调用追踪

在本任务中，你将添加一个系统调用追踪功能，该功能可能会在调试后续实验时为你提供帮助。你需要创建一个新的 trace 系统调用来控制追踪。它应接受一个参数，即整数"mask"，其二进制位指定要追踪哪些系统调用。例如，若要追踪 fork 系统调用，程序需调用 trace(1 << SYS_fork)，其中 SYS_fork 是来自 kernel/syscall.h。你需要修改 xv6 内核，使其在每个系统调用即将返回时打印一行信息——前提是该系统调用的编号已在掩码中设置。该行信息应包含进程 ID、系统调用名称以及返回值；你不需要打印系统调用的参数。该 trace 系统调用应为调用它的进程及其后续 fork 的所有子进程启用追踪，但不应影响其他进程。

我们提供了一个 trace 用户态程序，该程序在启用追踪的情况下运行另一个程序（参见 user/trace.c）。完成后，你应该看到如下输出： 

$ trace 32 grep hello README
3: syscall read -> 1023
3: syscall read -> 966
3: syscall read -> 70
3: syscall read -> 0
$
$ trace 2147483647 grep hello README
4: syscall trace -> 0
4: syscall exec -> 3
4: syscall open -> 3
4: syscall read -> 1023
4: syscall read -> 966
4: syscall read -> 70
4: syscall read -> 0
4: syscall close -> 0
$
$ grep hello README
$
$ trace 2 usertests forkforkfork
usertests starting
test forkforkfork: 407: syscall fork -> 408
408: syscall fork -> 409
409: syscall fork -> 410
410: syscall fork -> 411
409: syscall fork -> 412
410: syscall fork -> 413
409: syscall fork -> 414
411: syscall fork -> 415
...
$

在上面的第一个示例中，trace 调用 grep，仅追踪 read 系统调用。32 是 1<<SYS_read。在第二个示例中，trace 在追踪所有系统调用的同时运行 grep；2147583647 的低 31 位全部置为 1。在第三个示例中，程序未被追踪，因此不会打印任何追踪输出。在第四个示例中，所有 forkforkfork 测试输入 usertests 正在被追踪。如果您的程序行为与上面所示一致（尽管进程 ID 可能有所不同），则您的解决方案是正确的。

一些提示：

  • 添加 $U/_trace 到 Makefile 中的 UPROGS

  • 运行 make qemu 你会发现编译器无法编译 user/trace.c，因为系统调用的用户态存根尚不存在：请在 user/user.h，一个供 user/usys.pl，以及一个系统调用号给 kernel/syscall.h。Makefile 调用了 perl 脚本 user/usys.pl，其输出为 user/usys.S，实际的系统调用存根，它们使用 RISC-V ecall 修复编译错误后，运行用于切换到内核的指令。一旦你修复了编译问题，运行 trace 32 grep hello README；因为你还没有在内核中实现该系统调用，所以它会失败。

  • 添加一个 sys_trace() 中的函数 kernel/sysproc.c 通过在 proc 结构体中（参见 kernel/proc.h）中的新变量来记录其参数，从而实现新的系统调用。从用户态获取系统调用参数的函数位于 kernel/syscall.c，你可以在 kernel/sysproc.c.

  • 修改 fork() 中查看其使用示例（参见 kernel/proc.c），将跟踪掩码从父进程复制到子进程。

  • 修改 syscall() 中的函数 kernel/syscall.c 以打印跟踪输出。你需要添加一个系统调用名称数组以供索引。

Sysinfo

在本实验中，你将添加一个系统调用， sysinfo，用于收集正在运行的系统的信息。该系统调用接受一个参数：指向 struct sysinfo 中查看其使用示例（参见 kernel/sysinfo.h的指针。内核应填写该结构体的字段：其中 freemem `field` 应设置为空闲内存的字节数，以及 nproc `p_sz` 字段应设置为 state 不是 UNUSED。我们提供了一个测试程序 sysinfotest；如果打印出 "sysinfotest: OK"，则视为通过本作业。

一些提示：

  • 添加 $U/_sysinfotest 到 Makefile 中的 UPROGS

  • 运行 make qemu; user/sysinfotest.c 将无法编译。按照与上一个作业相同的步骤，添加系统调用 sysinfo。要声明 sysinfo() 的原型 in user/user.h 你需要预先声明 struct sysinfo: 

        struct sysinfo;
    int sysinfo(struct sysinfo *);
    一旦你修复了编译错误，运行 sysinfotest；因为你还没有在内核中实现该系统调用，所以它会失败。

  • `sysinfo` 需要将一个 struct sysinfo 返回用户态；参见 sys_fstat() (kernel/sysfile.c）和 filestat() (kernel/file.c）作为相关示例，了解如何使用 copyout().

  • 要收集空闲内存的数量，请向以下文件添加一个函数： kernel/kalloc.c

  • 要收集进程数量，请向以下文件添加一个函数： kernel/proc.c
