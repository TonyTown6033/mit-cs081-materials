OOM
  问题饼干，Windows、Linux、FreeBSD等都面临
  （交换并不能解决这个问题，但可能会降低 OOM 的可能性）
  许多内核操作分配内存
    open(2) 分配一个文件对象
    socket(2) 分配一个套接字对象
  用户程序决定何时释放资源/释放内存
  => User prog determines how much heap memory kernel uses
  但机器内存有限

  问题：如果用户程序导致内核分配所有内存怎么办？
    为什么会出现这种情况呢？
      越野车程序
      数据库服务器有意使用大部分内存
        + 分配数量不幸激增
    结果：在内存释放之前几乎没有操作可以成功
      用户程序很难或不可能合理地处理
      即 printf() 失败
      即使 exit(2) 也失败了！
      其他进程使用的内存
    没有用户编程可以取得进展

  如何恢复？需要释放内存
    通过杀死内存占用进程来恢复内存
    不能简单地杀掉
      exit(2) 必须分配以关闭文件并保持 FS 一致
    结果：内核必须为退出（2）保留足够的内存
      Linux 和 Biscuit 都是这样做的

  内核如何杀猪很重要
    Linux的做法：
      分配器中的阻塞很诱人
        那么调用者就不必处理失败
      但这可能会陷入僵局
        例如：Good prog 锁定 FS 中的目录
          内存占用等待锁定
            内核无法杀猪
            猪等待好的节目
            好的 prog 等待 hog 退出
            死锁
      Avoid deadlock by failing alloc of good prog
      结果：内核必须处理几乎所有分配的失败
        困难且充满错误
        “太小而不能失败”规则

    饼干的做法
      无法使用Linux的方法
      在执行op之前，等待足够的mem
        无需在操作中等待
        没有持有锁
        因此不会出现死锁
      如何计算最大内存？
        事实证明 Go 的静态分析很容易
        编写工具：MAXLIVE
          高级：花哨的逃逸分析
          不准确，但保守
            高估所需的内存，永远不会低估
          检查调用图
          查找每个系统调用的所有分配
          两种对象：
            1) 可以写入全局
            2）仅由堆栈指针引用
          类型 1 对象始终存在
          某些堆栈帧破坏时释放的类型 2 对象
          Mem = 每个调用图叶子处类型 1 的总和 + 类型 2 的最大值
      结果：没有死锁，几乎没有分配失败的处理

      GC 的成本由两个因素决定：
        1）对象数量（成本随着对象的增加而增加）
          GC必须标记/读取每个对象中的指针
        2) 可用堆内存量（成本随着可用内存的增加而降低）
          每次空闲内存耗尽时进行GC
      应用程序最多使用 5GB 内存

        但内核对象的数量很小

            文件内容页面
            套接字缓冲区

          减少#个内核对象
          增加可用堆内存
      一般来说：
        使用 mem 来减少大型堆的 CPU 开销
