6.S081 2020 第10讲：锁

为什么要讲锁？
  应用程序希望利用多核处理器实现并行加速
  因此内核必须处理并行的系统调用
  进而需要并行访问内核数据（缓冲区缓存、进程等）
  锁有助于正确共享数据
  锁可能限制并行加速效果

如果没有锁会出现什么问题
  案例分析：删除 kalloc.c 中的 acquire/release
  启动
    内核正常运行！
  运行 usertests
    所有测试通过！
    但我们丢失了一些页面
  为什么会丢失页面？
    共享内存多处理器的示意图
    两个核心同时调用 kfree() 时产生竞争
  糟糕：
    我们需要锁来保证正确性
    但会损失性能（kfree 被串行化）
        
锁的抽象：
  锁 l
  acquire(l)
    x = x + 1 -- "临界区"
  release(l)
  锁本身是一个对象
  若多个线程调用 acquire(l)
    只有一个会立即返回
    其余线程将等待 release() —— "阻塞"
  程序通常有大量数据和大量锁
    若不同线程使用不同数据，
    则它们可能持有不同的锁，
    从而可以并行执行——完成更多工作。
  注意锁 l 并不与数据 x 显式绑定
    程序员自行规划两者之间的对应关系

一条保守的规则，用于判断何时需要加锁：
  只要两个线程访问同一内存位置，且其中至少一个是写操作
  不持有正确的锁就不要操作共享数据！
  （过于严格：程序逻辑有时可排除共享的情况；无锁编程）
  （过于宽泛：printf()；并非总存在简单的锁与数据的对应关系）

锁能否自动化？
  或许编程语言可以为每个数据对象关联一把锁
    编译器在每次使用时自动添加 acquire/release
    程序员更难遗漏！
  这种思路往往过于死板：
    rename("d1/x", "d2/y"):
      lock d1, erase x, unlock d1
      lock d2, add y, unlock d2
    问题：文件在一段时间内不存在！
      rename() 应当是原子的
        其他系统调用应看到操作之前或之后的状态，而非中间状态
      否则编写程序将极为困难
    我们需要：
      lock d1 ; lock d2
      erase x, add y
      unlock d2; unlock d1
  也就是说，程序员通常需要对以下方面进行显式控制：
    锁被持有期间的代码区域
    以便隐藏尴尬的中间状态

关于锁的作用的几种理解方式
  锁有助于避免更新丢失
  锁有助于创建原子性的多步操作——隐藏中间状态
  锁有助于操作维护数据结构上的不变式
    假设操作开始时不变式成立
    操作利用锁来隐藏对不变式的临时违反
    操作在释放锁之前恢复不变式

问题：死锁
  注意 rename() 持有两把锁
  如果出现以下情况：
    core A              core B
    rename(d1/x, d2/y)  rename(d2/a, d1/b)
      lock d1             lock d2
      lock d2 ...         lock d1 ...
  解决方案：
    程序员为所有锁规定一个获取顺序
    所有代码必须按该顺序获取锁
    即：预判所需的锁，排序，再获取——较为复杂！

锁与模块化
  锁使得在模块内部隐藏细节变得困难
  为避免死锁，我需要了解所调用函数会获取哪些锁
  并且可能需要在调用之前就获取这些锁，即使我自己并不使用它们
  即：锁通常不是各个模块的私有事务

锁与并行性
  锁会*阻止*并行执行
  为了获得并行性，通常需要对数据和锁进行拆分
    使每个核心可以使用不同的数据和不同的锁
    "细粒度锁"
  如何最优地划分数据与锁是一个设计难题
    整个文件系统；目录/文件；磁盘块
    整个内核；各子系统；各对象
  你可能需要重新设计代码，使其在并行环境下运行良好
    示例：将单一空闲内存链表拆分为每个核心各自的空闲链表
      若线程频繁在单一空闲链表的锁上等待，此方法有助于改善性能
    这类重写工作可能需要大量投入！

锁粒度建议
  从粗粒度锁开始，例如用一把锁保护整个模块
    死锁风险更低，因为同时持有两把锁的机会更少
    对不变量/原子性的分析要求也更低
  通过测量判断是否存在性能问题
    粗粒度锁通常已经足够——该模块可能只占用很少的时间
  仅在必要时才重新设计以采用细粒度锁

让我们来看看 xv6 中的锁机制。

锁的典型用法：uart.c
  这是许多操作系统设备驱动程序的典型组织方式
  示意图：
    用户进程、内核、UART、uartputc、从 uart_tx_buf 中移除数据、
    uartintr()
  并发来源：进程、中断
  uart.c 中只有一把锁：uart_tx_lock——粒度较粗
  uartputc()——uart_tx_lock 保护的是什么？
    1. uart_tx_buf 操作中不存在竞争条件
    2. 若队列非空，UART 硬件正在执行队列头部的任务
    3. 对 UART 写寄存器不存在并发访问
  uartintr()——中断处理程序
    获取锁——可能需要在中断级别等待！
    从 uart_tx_buf 中移除字符
    将下一个排队字符交给 UART 硬件（对应条件 2）
    访问 UART 硬件寄存器（对应条件 3）

如何实现锁？
  为什么下面这种方式不可行：
    struct lock { int locked; }
    acquire(l) {
      while(1){
        if(l->locked == 0){ // A
          l->locked = 1;    // B
          return;
        }
      }
    }
  问题：A 行与 B 行之间存在竞争条件
  我们如何才能原子地完成 A 和 B？

原子交换指令：

  a5 = 1
  s1 = &lk->locked
  amoswap.w.aq a5, a5, (s1)

  在硬件层面执行以下操作：
    全局锁定该地址（其他核心无法使用）
    temp = *s5
    *addr = a5
    a5 = temp
    解锁该地址
  RISC-V 硬件提供了锁定内存位置的机制
    不同 CPU 有不同的实现方式
    示意图：核心、总线、RAM、锁定单元
    因此我们实际上是将问题下推给了硬件
    硬件以缓存行或整条总线为粒度实现锁定
  内存锁强制并发交换操作逐一执行，而非交错执行

查看 xv6 自旋锁的实现
  acquire(l){
    while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
  }
  若 l->locked 原本为 1，sync_lock_test_and_set 会将其再次设为 1 并返回 1，
    循环继续自旋
  若 l->locked 原本为 0，至多一个 lock_test_and_set 会读到 0；它将其设为 1 并返回 0；其他 test_and_set 则返回 1
    它将其设为 1 并返回 0；其他 test_and_set 则返回 1
  这是一种"自旋锁"，因为等待的核心在 acquire 循环中"自旋"

    将 lk->locked 设为 0

细节：内存读写顺序
  假设两个核心使用一个锁来保护计数器 x
  且我们有一个朴素的锁实现
  核心 A：          核心 B：
    locked = 1
    x = x + 1      while(locked == 1)
    locked = 0       ...
                   locked = 1
                   x = x + 1
                   locked = 0
  编译器和 CPU 都会对内存访问进行重排序
    即它们不遵循源程序中内存引用的顺序
    例如，编译器可能为核心 A 生成如下代码：
      locked = 1
      locked = 0
      x = x + 1
      即把自增操作移到临界区之外！
    合法的行为集合称为"内存模型"
  release() 中对 __sync_synchronize() 的调用可防止指令重排
    编译器不会将内存访问移到 __sync_synchronize() 之后
    并（可能）发出"内存屏障"指令以通知 CPU
  acquire() 中对 __sync_synchronize() 的调用具有类似的效果：
  如果使用锁，则无需理解内存排序规则
    只有在编写特殊的"无锁"代码时才需要了解

为什么使用自旋锁？
  等待时不会浪费 CPU 吗？
  为何不放弃 CPU 并切换到另一个进程让其运行？
  如果持锁线程需要运行，等待线程是否应该让出 CPU？
  自旋锁使用准则：
    持有自旋锁的时间应非常短暂
    持有自旋锁时不要让出 CPU
  系统为较长的临界区提供"阻塞"锁
    等待线程会让出 CPU
    但开销通常更高
    后续你将看到一些 xv6 的阻塞方案

建议：
  能不共享就不共享
  从少量粗粒度锁开始
  对代码进行性能分析——哪些锁妨碍了并行性？
  仅在需要并行性能时才使用细粒度锁
  使用自动化数据竞争检测工具
