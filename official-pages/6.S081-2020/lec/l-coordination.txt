why hold p->lock across swtch()?
   这是很重要的一点，影响 xv6 中的许多情况
   [图：P1、STACK1、swtch、STACK_SCHED]
   yield:
     acquire(&p->lock);
     p->state = RUNNABLE;
     开关（）；
   scheduler:
     开关（）；
     release(&p->lock);

the main point of holding p->lock across swtch():
  prevent another core's scheduler from seeing p->state == RUNNABLE
  直到原始核心停止执行线程之后
  在原始核心停止使用线程堆栈之后

为什么 sched() 在让出 CPU 时禁止持有自旋锁？
   (other than p->lock)
   i.e. sched() checks that noff == 1
   在单核机器上，想象一下：
     P1 P2
     捕获量(L)
     安排（）
                  捕获量(L)
   这是一个僵局：
     P2 将旋转直到 P1 释放 - 并且 P2 不会让出 CPU
     但P1在再次运行之前不会释放
   多核的情况下，也会出现死锁；必须涉及更多的自旋锁
   解决方案：不要持有自旋锁并让出CPU！

让我们看看proc.c中的wakeup(chan)
  它扫描进程表，寻找 SLEEPING 和 chan
  it grabs each p->lock
  还请记住，调用者在调用wakeup()之前获取了条件锁
  so wakeup() holds BOTH the condition lock and each p->lock

让我们看看 proc.c 中的 sleep()
  sleep *必须*释放条件锁
    since we can't hold locks when calling swtch(), other than p->lock
  问：sleep() 释放条件锁后如何阻止wakeup() 运行？
  A: acquire p->lock before releasing condition lock
  由于wakeup()持有*两个*锁，所以sleep()持有*任一*就足够了
    为了强制wakeup()旋转而不是查看这个过程
  现在，在 swtch() 完成之前，wakeup() 无法继续
    so wakeup() is guaranteed to see p->state==SLEEPING and p->chan==chan
  因此：不会丢失唤醒！

请注意，uartwrite() 将 sleep() 包装在循环中
  即在 sleep() 返回后重新检查条件，可能会再次睡眠
  两个原因：
    也许有多个服务员，另一个线程可能已经消耗了该事件
    即使条件不成立，kill() 也会唤醒进程
  sleep 的所有使用都包含在循环中，因此它们重新检查

# what about kill(pid)?
  问题：强行终止进程可能不安全
    它可能在内核中执行
      使用其内核堆栈、页表、proc[] 条目、trapframe
    它可能持有锁
      例如在 fork() 一个新进程的过程中
      并且必须完成才能恢复不变量
    所以：kill()不能直接摧毁目标！
  solution: 
    kill() sets p->killed flag, nothing else
    the target process itself checks for p->killed
      并调用 exit() 本身
    look for "if(p->killed) exit(-1);" in usertrap()
      此时没有持有锁
      所以退出（）是安全的

# what if kill() target is sleep()ing?
  在这种情况下，它不会持有锁，并且不会执行！

# xv6 solution to kill() of sleep()ing process
  参见 proc.c 中的kill()
    将 SLEEPING 更改为 RUNNABLE - 就像wakeup()
    所以 sleep() 可能会在条件成立之前返回
  some sleep loops check for p->killed
    例如管道读取()、控制台读取()
    否则 read 可能会因被终止的进程而无限期挂起
  some sleep loops don't check p->killed
    例如virtio_disk.c
    OK not to check p->killed since disk reads are pretty quick
  所以一个被kill()ed的进程可能会持续一段时间
    但 usertrap() 将在系统调用完成后 exit()

# xv6 spec for kill
  如果目标位于用户空间
    将在下次进行系统调用或进行定时器中断时死亡
  如果目标在内核中
    目标永远不会执行另一个用户指令
    但可能会在内核中花费相当长的时间
