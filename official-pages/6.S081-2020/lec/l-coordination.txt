为什么在 swtch() 期间持有 p->lock？
   这是一个重要问题，影响 xv6 中的许多情况
   [图示：P1, STACK1, swtch, STACK_SCHED]
   yield:
     acquire(&p->lock);
     p->state = RUNNABLE;
     swtch();
   scheduler:
     swtch();
     release(&p->lock);

在 swtch() 期间持有 p->lock 的主要目的：
  防止另一个核心的调度器在原始核心停止执行该线程之前
  以及在原始核心停止使用该线程的栈之前
  看到 p->state == RUNNABLE

为什么 sched() 禁止在让出 CPU 时持有自旋锁？
   （p->lock 除外）
   即 sched() 检查 noff == 1
   在单核机器上，设想如下情形：
     P1           P2
     acq(L)
     sched()
                  acq(L)
   这是一个死锁：
     P2 将自旋等待直到 P1 释放锁 —— 而 P2 不会让出 CPU
     但 P1 要再次运行后才能释放锁
   在多核情况下，死锁同样可能发生；但需要涉及更多自旋锁
   解决方案：不要在持有自旋锁的同时让出 CPU！

# 主题：顺序协调
  线程需要等待特定事件或条件：
    等待磁盘读取完成（事件来自中断）
    等待管道写入方产生数据（事件来自线程）
    等待任意子进程退出

# 协调是线程编程的基本构建块。
  通常使用起来较为直接。
  但（与锁类似）受制于某些规则，有时会带来棘手的难题。

# 为什么不直接用一个自旋等待事件发生的 while 循环？
  管道读取：
    while 缓冲区为空 {
    }
  管道写入：
    将数据放入缓冲区

# 更好的方案：使用让出 CPU 的协调原语
  有很多种，例如屏障、信号量、事件队列。
  xv6 使用 sleep 与 wakeup

# 示例：uart.c 中的 uartwrite() 和 uartintr()
  我已修改了这些函数！
    与默认的 xv6 不同
    请参见课程表页面上的"code"链接
  基本思路：
    UART 每次只能接受一个（实际上是少数几个）字节的输出
      发送每个字节需要较长时间，可能长达毫秒级
    向控制台写入的进程必须等待 UART 发送完上一个字符
    UART 在发送完每个字符后会产生中断
      写入线程应在此之前让出 CPU
  write() 调用 uartwrite()
    uartwrite() 写入第一个字节（如果可以的话）
    uartwrite() 调用 sleep() 等待 UART 的中断
    uartintr() 调用 wakeup()
    参数 "&tx_chan" 用于将 sleep 和 wakeup 关联起来
  简单而灵活：
    sleep/wakeup 无需了解你在等待什么
    无需显式分配协调对象

# 为什么 sleep() 需要锁参数？
  遗憾的是，你无法像期望的那样简洁地设计 sleep()
  sleep() 不能简单地实现为"等待某个事件"
  这个问题被称为"丢失唤醒"
    它潜伏于所有时序协调方案中，令人头疼
  以下是详细说明

# 假设只有 sleep(chan)；我们该如何实现？
  以下是一个有缺陷的 sleep/wakeup
  broken_sleep(chan)
    在某个"channel"上睡眠，channel 是一个数字/地址
      用于标识我们等待的条件/事件
    p->state = SLEEPING;
    p->chan = chan;
    sched();
  wakeup(chan)
    wakeup 唤醒所有在 chan 上睡眠的线程
    可能唤醒多个线程
    对每个 p：
      if p->state == SLEEPING && p->chan == chan:
        p->state = RUNNABLE

# uart 代码如何使用这个（有缺陷的）sleep/wakeup？
  int done
  uartwrite(buf):
    对每个字符 c：
      while not done:
        sleep(&done)
      send c
      done = false
  uartintr():
    done = true
    wakeup(&done)
  done==true 是我们等待的条件
  &done 是睡眠通道（与条件本身并无直接关联）

# 但加锁怎么办？
  - 驱动程序的数据结构，例如 done
  - UART 硬件
  uartwrite()() 和 uartintr() 都需要加锁
  uartwrite()() 应该在整个操作序列中持有锁吗？
    不行：这样 uartintr() 就无法获取锁并设置 done
  也许 uartwrite() 可以在调用 sleep() 之前释放锁？
  我们来试试——修改 uart.c 以调用 broken_sleep()
    release(&uart_tx_lock);
    broken_sleep(&tx_chan);
    acquire(&uart_tx_lock);

当 uartwrite() 在调用 broken_sleep() 之前释放锁时会出什么问题？
  uartwrite() 发现上一个字符尚未发送完毕
  中断在 release() 之后、broken_sleep() 之前发生
  uartwrite() 进入睡眠，尽管 UART TX 已经完成
  此时没有任何东西能唤醒 uartwrite()，它将永远睡眠

这就是"丢失唤醒"问题。

我们需要消除 uartwrite() 检查条件与 sleep() 将进程标记为睡眠状态
  之间的时间窗口。
  我们将使用锁来防止 wakeup() 在整个时间窗口内运行。

我们将修改 sleep() 的接口及其使用方式。
  我们要求必须有一把锁来保护该条件，
    并且 sleep() 和 wakeup() 的调用者都必须
    持有"条件锁"。
  sleep(chan, lock)
    调用者必须持有锁
    sleep 释放锁，返回前重新获取
  wakeup(chan)
    调用者必须持有锁
  （修复 uart.c）

让我们看看 proc.c 中的 wakeup(chan)
  它扫描进程表，查找处于 SLEEPING 状态且 chan 匹配的进程
  它获取每个进程的 p->lock
  还要记住，调用者在调用 wakeup() 之前已经获取了条件锁
  因此 wakeup() 同时持有条件锁和每个 p->lock

让我们看看 proc.c 中的 sleep()
  sleep *必须* 释放条件锁
    因为调用 swtch() 时不能持有除 p->lock 之外的锁
  问：sleep() 如何在释放条件锁之后阻止 wakeup() 运行？
  答：在释放条件锁之前先获取 p->lock
  由于 wakeup() 需要持有*两把*锁，sleep() 只需持有*其中一把*就足够了
    从而迫使 wakeup() 自旋而不去检查该进程
  这样 wakeup() 必须等到 swtch() 完成后才能继续
    因此 wakeup() 一定能看到 p->state==SLEEPING 且 p->chan==chan
  从而：不会有唤醒丢失！

注意 uartwrite() 将 sleep() 包裹在一个循环中
  即在 sleep() 返回后重新检查条件，可能再次进入睡眠
  原因有两点：
    可能有多个等待者，另一个线程可能已经消费了该事件
    kill() 会唤醒进程，即使条件并不成立
  所有 sleep 的使用都包裹在循环中，以便重新检查条件

# 问题：线程无法释放自身的所有资源
  例如它自己的栈，它仍在使用中
  例如它的 struct context，调用 swtch() 时可能还需要用到

# xv6 有两种方式终止进程：exit() 和 kill()

# 普通情况：进程通过 exit() 系统调用主动退出
  部分资源在 exit() 中释放，部分在父进程的 wait() 中释放
  proc.c 中的 exit()：
    关闭已打开的文件
    将子进程的父进程改为 PID 1（init）
    唤醒正在 wait() 的父进程
    p->state = ZOMBIE
      即将死亡但尚未真正死亡
      不会再次运行
      也不会（尚未）被 fork() 重新分配
    （注意栈和 proc[] 条目仍处于已分配状态……）
    调用 swtch() 切换到调度器
  proc.c 中的 wait()（父进程或 init 最终会调用）：
    通过 sleep() 等待任意子进程调用 exit()
    扫描 proc[] 表，查找 p->state==ZOMBIE 的子进程
    调用 freeproc()
      （持有 p->lock……）
      trapframe、pagetable、……、p->state=UNUSED
  因此：wait() 不仅是为了应用程序的便利，也是操作系统自身所需
    *每一个*进程都必须被 wait()
    这正是退出进程的子进程需要被重新挂载到其他父进程的原因
  部分复杂性源于
     子进程与其父进程并发退出
     需遵循先父后子的加锁顺序以避免死锁

# kill(pid) 怎么处理？
  问题：强制终止一个进程可能并不安全
    它可能正在内核中执行
      正在使用其内核栈、页表、proc[] 条目、trapframe
    它可能持有锁
      例如正处于 fork() 新进程的过程中
      必须执行完毕才能恢复不变量
    因此：kill() 不能直接销毁目标进程！
  解决方案：
    kill() 仅设置 p->killed 标志位，不做其他任何操作
    目标进程自身检查 p->killed
      并自行调用 exit()
    在 usertrap() 中查找 "if(p->killed) exit(-1);"
      此时未持有任何锁
      因此可以安全地调用 exit()

# 如果 kill() 的目标进程正在 sleep() 中怎么办？
  在这种情况下，它不持有锁，也没有在执行！
  kill() 立即销毁目标进程可以吗？
  可能没问题：
    等待控制台输入
  可能有问题：
    在文件创建过程中等待磁盘

# xv6 对 kill() 处于 sleep() 中的进程的解决方案
  参见 proc.c 中的 kill()
    将 SLEEPING 改为 RUNNABLE —— 类似于 wakeup()
    因此 sleep() 将返回，可能在条件为真之前就返回了
  某些 sleep 循环会检查 p->killed
    例如 piperead()、consoleread()
    否则已被 kill 的进程的读操作可能会无限期挂起
  某些 sleep 循环不检查 p->killed
    例如 virtio_disk.c
    可以不检查 p->killed，因为磁盘读取速度相当快
  因此被 kill() 的进程可能还会继续运行一段时间
    但 usertrap() 会在系统调用完成后调用 exit()

# kill 的 xv6 规范
  如果目标进程在用户态
    下次发起系统调用或触发定时器中断时将会终止
  如果目标进程在内核中
    目标进程将不再执行任何用户态指令
    但可能还会在内核中继续运行相当长一段时间

# 总结
  sleep/wakeup 让线程等待特定事件
  并发意味着我们必须关注唤醒丢失的问题
  在线程系统中，进程终止是一个棘手的问题
