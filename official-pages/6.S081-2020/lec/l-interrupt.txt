6.S081 2020 第9讲：中断

中断
  硬件现在需要关注！
    例如，数据包到达、时钟中断
  软件必须暂停当前工作并作出响应
    在 RISC-V 上使用与系统调用和异常相同的陷阱机制
  新的问题/复杂性：
    异步性
      中断正在运行的进程
      中断处理程序可能不在引发中断的进程上下文中运行
    并发性
      设备与进程并行运行
    设备编程
      设备可能难以编程

内核如何知道是哪个设备发出了中断？
  每个设备都有唯一的源编号/IRQ（中断请求）编号
    由硬件平台定义
    UART0 在 qemu 上的编号为 10（参见 kernel/memlayout.h）
    在 SiFive 开发板上编号不同

RISC-V 中断相关寄存器
  sie --- 监督级中断使能寄存器
    每个软件中断、外部中断、定时器中断各占一位
  sstatus --- 监督级状态寄存器
    一位用于使能中断
  sip --- 监督级中断挂起寄存器
  scause --- 监督级原因寄存器
  stvec --- 监督级陷阱向量寄存器
  mdeleg --- 机器级委托寄存器

  shell 调用 sys_read() 等待输入（见下文）

  UART 完成字符发送并触发中断
    PLIC 将中断转发给某个 CPU
    CPU 在收到中断时执行以下步骤：
    - 若该陷阱为设备中断，且 SIE 位
      为零，则不执行以下任何操作。
    - 通过清除 SIE 禁用中断。
      防止中断被再次中断
    - 将 pc 复制到 sepc
    - 将当前模式（用户态或内核态）保存在 sstatus 的 SPP 位中。
    - 设置 scause 以反映中断的原因。
    - 将模式设置为内核态。
    - 将 stvec 复制到 pc。
      stvec 包含 kernelvec 或 usertrap，取决于中断
      发生在用户态还是内核态
    - 从新的 pc 处开始执行。
    与我们之前见过的系统调用、页错误等机制相同。

    kernelvec/usertrap 都会调用 devintr() 来检查中断
      UART 的外部中断
        plic_claim()
        uartintr()
          如果还有更多字符则发送它们
	  可能发送多个字符
        plic_complete()
      从 kernelvec/usertrap 返回
        恢复被中断的计算

如果多个中断同时到来怎么办？
  PLIC 将中断分发给各个核心
    中断可以并行处理
  如果没有 CPU 认领该中断，中断将保持挂起状态
    最终每个中断都会被分发到某个 CPU
        
中断暴露了几种形式的并发
  1. 设备与 CPU 之间
    生产者/消费者并行
  2. 中断可能打断正在返回到 shell 的 CPU（仍在内核中）
    当代码必须原子执行时需禁用中断
  3. 中断可能在不同 CPU 上与 shell（或返回 shell 的过程）并行运行
    锁；周三的主题

生产者/消费者并行
  以打印为例
    shell 是生产者
    设备是消费者
  为了解耦两者：
    驱动程序中有一个缓冲区
      上半部将字符放入缓冲区
        若无空间则等待
	在调用进程的上下文中运行
      下半部从缓冲区取出字符
        中断处理程序唤醒生产者
	可能不在 shell 的上下文中运行
  注意：下半部分和上半部分可能在不同 CPU 上并行运行
    我们将在后续讲座中讲到这一点

中断的演变
  中断曾经相对较快；现在变慢了
    旧方式：每个事件触发一次中断，硬件简单，软件复杂
    新方式：硬件完成大量工作后再发出中断
  某些设备产生事件的速率超过每微秒一次
    例如：千兆以太网每秒可传输 150 万个小数据包
  一次中断大约耗费一微秒的量级
    保存/恢复状态
    缓存缺失
    如果中断频率超过每微秒一次该怎么办？
    
轮询：与设备交互的另一种方式
  处理器持续循环，直到设备需要响应
    若设备速度慢，会浪费处理器周期
    xv6 中的一个示例：uartputc_sync()
  但若设备速度快，开销则很小
    无需保存寄存器等
  若事件始终处于等待状态，无需持续通知软件

轮询与中断的比较
  对高速率设备采用轮询而非中断
  对低速率设备使用中断，例如键盘
    持续轮询会浪费 CPU
  在轮询与中断之间自动切换
    速率低时使用中断（此时轮询会浪费 CPU 周期）
    速率高时使用轮询（此时中断会浪费 CPU 周期）
  更快地将中断转发至用户态
    用于页面错误和用户态处理的设备
    硬件直接交付给用户，无需内核介入？
    更快速地通过内核的转发路径？
  这些主题我们将在课程后续部分逐一深入探讨
