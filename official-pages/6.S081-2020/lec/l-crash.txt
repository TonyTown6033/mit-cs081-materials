# 为什么需要崩溃恢复

什么是崩溃恢复？
  你正在写入文件系统
  然后电源故障
  你重新启动
  你的文件系统还能正常使用吗？

问题所在：
  在多步骤操作过程中发生崩溃
  可能导致文件系统不变量被破坏
  重启后：
    坏的情况：由于文件系统损坏再次崩溃
    更坏的情况：没有崩溃，但读写了错误的数据

示例：
  创建文件：
    
    $ echo hi > x
    // 上节课的创建操作追踪：
    bwrite: block 33 by ialloc   // 在 inode 块 33 中分配 inode
    bwrite: block 33 by iupdate  // 更新 inode（例如，设置 nlink）
    bwrite: block 46 by writei   // 写入目录项，通过 dirlink() 添加 "x"
    bwrite: block 32 by iupdate  // 更新目录 inode，因为 inode 可能已发生变化

    在 iupdate 和 writei 之间发生崩溃
      已分配文件 inode
      崩溃：inode 未释放但未使用 —— 还不算太糟

    如果文件系统先写入 46 和 32，再写入 33 会怎样
      如果在写入 32 和 33 之间崩溃，则目录项指向空闲 inode —— 灾难！
      再次崩溃，或者更糟：该 inode 被分配给了其他内容

  写入文件：
    inode 的 addrs[] 和 len
    间接块
    块内容
    块空闲位图
    崩溃：inode 引用了空闲块——灾难性错误！
    崩溃：块未空闲但也未被使用——影响不大
        
  unlink：
    块空闲位图
    释放 inode
    清除目录项

我们能期望什么？
  重启并运行恢复代码后
  1. 文件系统内部不变量得到维护
     例如，没有块同时出现在空闲列表和某个文件中
  2. 除最后几个操作外，其余操作均已持久化到磁盘
     例如，昨天写入的数据得以保留
     但崩溃时正在写入的数据可能未保留
     因此用户可能需要检查最后几个操作
  3. 无操作顺序异常
     echo 99 > result ; echo done > status

正确性与性能往往相互冲突
  磁盘写入很慢！
  安全性 => 尽快写入磁盘
  速度 => 避免写磁盘（批量写入、回写缓存、按磁道排序等）

崩溃恢复是一个反复出现的问题
  在所有存储系统中均会出现，例如数据库
  多年来已有大量研究投入其中
  存在许多巧妙的性能与正确性权衡方案

# 日志方案

最流行的方案：日志记录（== 日志式文件系统）
  目标：系统调用相对于崩溃具有原子性
  目标：快速恢复（无需耗时数小时的 fsck）

将分两步介绍日志机制
  首先介绍 xv6 的日志，它仅提供安全性和快速恢复
  然后介绍 Linux EXT3，它在正常运行时同样高效

日志机制的基本思想
  你需要原子性：系统调用的所有写操作要么全部完成，要么全不执行
    我们将这种原子操作称为"事务"
  将系统调用*将要*执行的所有写操作记录到磁盘上的日志中（log）
  然后在磁盘上记录"完成"标记（commit）
  再执行实际的文件系统磁盘写入（install）
  崩溃并恢复时：
    若日志中存在"完成"标记，则重放日志中的所有写操作
    如果没有"done"，忽略日志
  这是一个预写日志（WRITE-AHEAD LOG）

预写日志规则
  在一个事务的*所有*写入都已记录到磁盘日志中，
  且已标记为已提交之前，
  不得将该事务的*任何*写入安装到磁盘。

为什么要遵守此规则？
  一旦我们将某个写入安装到磁盘上的文件系统，
  就必须完成该事务的*所有*其他写入——
  这样事务才是原子的。我们必须
  做好在第一次安装写入之后发生崩溃的准备，
  因此其他写入在崩溃后必须仍然可用——
  即保存在日志中。

日志是一种神奇的机制
  复杂可变数据结构的崩溃恢复通常很困难
  日志往往可以叠加在现有存储系统之上
  并且与高性能兼容（下周的主题）

# xv6 日志概述

xv6 日志的表示方式
  [图示：缓冲区缓存、内存中的日志块号数组，
            磁盘上的文件系统树、磁盘上的日志头和日志块]
  写入时将块号添加到内存数组中
  将数据本身保留在缓冲区缓存中（已固定）
  提交时：
    将缓冲区写入磁盘上的日志
    等待磁盘完成写入（"同步"方式）
    将日志头扇区写入磁盘
      块号
      非零的"n"值
  提交后：
    将日志中的块安装（写入）到其在文件系统中的原始位置
    解除块的固定（unpin）
    将磁盘日志头中的"n"写为零

磁盘日志头中的"n"值表示提交状态
  非零 == 已提交，日志内容有效且是一个完整的事务
  零 == 未提交，内容可能不完整，恢复时应忽略日志
  写入非零"n"值的操作即为"提交点"
    
xv6 磁盘布局及对应块号
   2: 日志头
   3: 日志块
  32: inode
  45: 位图
  46: 数据块

让我们看一个例子。
  我修改了 bwrite()，使其打印底层磁盘写入操作，
  即事务提交期间发生的磁盘写入。

  $ echo a > x
    
  // 创建
  bwrite 3    // inode，33
  bwrite 4    // 目录内容，46
  bwrite 5    // 目录 inode，32
  bwrite 2    // 提交（块号与块数）
  bwrite 33   // 安装 x 的 inode
  bwrite 46   // 安装目录内容
  bwrite 32   // 安装目录 inode
  bwrite 2    // 将日志标记为"空"
  // 写入
  bwrite 3
  bwrite 4
  bwrite 5
  bwrite 2
  bwrite 45   // 位图
  bwrite 595  // a（注意：bzero 已被吸收）
  bwrite 33   // inode（文件大小）
  bwrite 2
  // 写入
  bwrite 3
  bwrite 4
  bwrite 2
  bwrite 595  // \n
  bwrite 33   // inode
  bwrite 2

让我们来看第 2 个事务，即一次 write()
  首先是 file.c:syswrite
    计算在日志写满之前可以写入多少块
    在一个事务中写入那么多块

  结合 fs.c:writei
    begin_op()
      bmap() -- 可以写位图、间接块
        log_write 将新块清零
      bread()
      修改 bp->data
      log_write()
        吸收 bzero
      iupdate() -- 写入 inode
    end_op()

  log.c 中的 begin_op()：
    需要指明哪组写操作必须是原子的！
    需要检查日志是否正在提交
    需要检查我们的写操作是否能放入日志的剩余空间
  log_write()：
    将扇区号添加到内存数组中
    bpin() 将把块固定在缓冲区缓存中，使 bio.c 不会将其驱逐
  end_op()：
    如果没有未完成的操作，则提交
  commit()：
    将缓存中已更新的块复制到磁盘上的日志
    在磁盘日志头中记录扇区号及"done"标志
    安装写操作 —— 将磁盘日志中的数据复制到磁盘文件系统
      bunpin() 将从缓存中取消固定 —— 此后该块可被驱逐
    从日志中清除"done"标志

如果我们在事务进行中崩溃会发生什么？
  内存中的数据丢失，仅剩下崩溃时刻的磁盘状态
  内核在启动时、使用文件系统之前会调用 recover_from_log()
    如果日志头块显示"done"：
      将日志中的块复制到磁盘上的实际位置
  磁盘上的日志中有什么？
    提交前崩溃
    提交过程中崩溃 —— 提交点在哪里？
    install_trans() 执行过程中崩溃
    重启后在 recover_from_log() 执行期间崩溃
  注意：多次重放日志是允许的！
    只要期间没有其他操作介入

注意：xv6 假设磁盘是故障停止型的
  它要么正确完成写操作，要么根本不执行写操作
    即，例如因断电导致最后一次写操作无法完成
  因此：
    不存在部分写入（每次扇区写入是原子的）
    不存在乱写
    不存在扇区数据损坏（无读取错误）
    不存在读取错误扇区的情况

# 挑战
    
挑战：防止缓存写回
  系统调用可以安全地更新*缓存中的*块，
    但该块在事务提交之前
    不能被写入文件系统
  这很棘手，因为例如缓存可能耗尽空间，
    并可能试图驱逐某些条目
    以便读取和缓存其他数据。
  考虑 create 的示例：
    将脏 inode 写入日志
    将目录块写入日志
    驱逐脏 inode
    提交
  xv6 的解决方案：
    确保缓冲区缓存足够大
    将脏块固定在缓冲区缓存中
    提交后，解除块的固定
    
挑战：系统调用的数据必须能放入日志
  xv6 的解决方案：
  - 计算每个系统调用写入块数的上界
    将日志大小设置为 >= 上界
  - 将某些系统调用拆分为多个事务
    例如，大型 write()
    因此：大型 write() 不是原子的
      但崩溃后会留下写入内容正确的前缀
		
挑战：允许并发系统调用
  必须允许来自多个调用的写入同时存在于日志中
  提交时必须全部写入
  但不能写入仍处于事务中的调用的数据

xv6 的解决方案
  若新系统调用的数据可能放不下日志，则不允许其启动
    必须等待当前调用完成并提交
  当进行中的调用数量降为零时
    提交
    释放日志空间
    唤醒等待中的调用

挑战：一个块可能在一个事务中被多次写入
  写入仅影响内存中已缓存的块
  因此一个缓存块可能反映多个未提交的事务
  但安装操作仅在没有进行中的事务时才发生
    所以已安装的块只反映已提交的事务
  有利于性能："写入合并"

# 总结

xv6 的日志设计有哪些优点？
  由于写前日志（write-ahead log）保证了正确性
  良好的磁盘吞吐量：日志天然地将写入批量处理
    但数据磁盘块会被写入两次
  并发性
    
xv6 的日志机制有什么问题？
  效率不高：
    每个块被写入两次（写日志和安装）
    即使只修改了几个字节，也要记录整个块
    每个日志块都是同步写入的
      可以批量写入，只同步写入日志头
    日志写入和安装写入都是急切的
      两者都可以是惰性的，以吸收更多写操作
      但仍必须先写日志
  操作超出日志容量时会出现问题
    unlink 在截断文件时可能会弄脏许多块
