*** 虚拟机

什么是虚拟机？
  对计算机的模拟，精确度足以运行操作系统

示意图：硬件、宿主机/VMM、客户内核、客户进程
  VMM 可以独立运行，或
  VMM 可以运行在宿主操作系统中，例如 Linux

为什么使用虚拟机？
  在单台物理机上运行大量客户机
    通常单个服务只需要适量资源
    若使用独占服务器则会浪费大量资源
    适用于云计算和企业计算
    需要在现有操作系统内核下新增一层来管理多个客户机
  虚拟机提供比进程更强的隔离
  一台计算机，多个操作系统（OSX 与 Windows）
  内核开发环境（如 qemu）
  技巧：检查点、迁移、监控

虚拟机有着悠久的历史
  1960 年代：IBM 使用虚拟机共享大型机
  1990 年代：VMWare 重新推广了虚拟机，用于 x86 硬件
  2000 年代：广泛应用于云计算和企业环境

我们为什么要讨论虚拟机？
  操作系统设计中最有趣的进展已逐渐转移到虚拟机领域
    与传统操作系统内核有大量重叠
    同时也带来了一些新的挑战与机遇
  某些问题通过在操作系统下插入新的一层可以更容易解决
  虚拟机对上层操作系统和下层硬件都产生了影响

虚拟机需要多精确？
  通常目标是：
    客户机完全感知不到自己运行在虚拟机中
    宿主机能够支持任意客户操作系统
  因此我们希望：
    访客无法区分虚拟机与真实计算机
    访客无法逃出其所在的虚拟机
  必须允许标准操作系统启动和运行
  必须能遏制恶意软件
    不能让访客逃脱虚拟机！
  实践中，许多虚拟机有所妥协
    访客操作系统知道自己运行在虚拟机上，
    并为提高效率进行了相应修改

我们可以通过编写软件来模拟机器指令，从而构建虚拟机
  虚拟机监控器逐条解释执行访客指令
  为访客维护虚拟机状态
    32个寄存器、satp、模式、RAM、磁盘等
  优点：可行性显而易见
  缺点：速度慢

思路：在真实 CPU 上直接执行访客指令——速度快！
  如果访客内核执行了特权指令会怎样？
    例如访客将新页表加载到 satp
    不能让访客内核直接访问监督模式寄存器等！

思路：在用户态运行访客内核
  类似于将访客内核作为一个 xv6 进程来运行
  当然，访客内核假设自己处于监督模式
  普通指令可以正常执行
    两个寄存器相加、函数调用等
  RISC-V 特权指令在用户态中是非法的
    将触发陷阱，陷入虚拟机监控器
  虚拟机监控器的陷阱处理程序模拟特权指令
    可能将该特权操作应用于虚拟状态
      例如读写 sepc
    可能转换后应用于真实硬件
      例如对 satp 的赋值
  "陷阱与模拟"
  优点在于可以完全用软件构建此类虚拟机
    你可以修改 xv6，使其成为针对 RISC-V 的陷阱与模拟虚拟机监控器

陷阱与模拟虚拟机监控器需要"虚拟化"哪些 RISC-V 状态？
  因为不能允许访客查看或修改真实的机器状态。
  所有 s* 寄存器（sepc、stvec、scause、satp 等）
  模式
  hart 编号

RISC-V 在陷阱与模拟虚拟化方面表现非常友好
  所有特权指令在用户态下尝试执行时都会触发陷阱
  并非所有 CPU 都如此友好——例如 32 位 x86
    某些特权指令不会触发陷阱；x86 在用户态下运行时会直接忽略

对于 RISC-V 陷阱与模拟，当以下情况发生时需要做什么：

... 客户内核执行 sret（返回用户态）？
    [图示：VMM、客户内核、客户用户态、虚拟状态、实际硬件状态]
    CPU 陷入 VMM
      这实际上是一次从用户态到超级用户态的陷阱
      客户的 PC 保存在 epc 中（以及可能的 trapframe）
    VMM 陷阱处理程序：
      虚拟模式 = 用户态
      实际 sepc = 虚拟 sepc
      [切换页表以处理 PTE_U]
      从陷阱返回

... 客户用户代码执行 ecall 以发起系统调用？
    CPU 陷入 VMM（ecall 始终会产生陷阱）
    VMM 陷阱处理程序：
      虚拟 sepc = 实际 sepc
      虚拟模式 = 超级用户态
      虚拟 scause = "系统调用"
      实际 sepc = 虚拟 stvec
      [切换页表以处理 PTE_U]
      从陷阱返回

... 客户内核读取 scause，例如 csrr a0, scause
    陷入 VMM
    trapframe a0 = 虚拟 scause
    实际 sepc += 4
    从陷阱返回

... 客户内核写入 satp？
  VMM 必须确保客户只能访问其自身的内存
    并且必须重新映射客户的物理地址
  客户的页表：
    客户虚拟地址 -> 客户物理地址
  VMM 为该客户维护的映射
    客户物理地址 -> 宿主物理地址
  VMM 的"影子"页表
    客户虚拟地址 -> 宿主物理地址
  VMM 将影子页表装载到实际的 satp 中

... 客户内核修改当前活跃页表中的某个 PTE？
  VMM 无需做任何事情
  RISC-V 规范规定，PTE 的修改在执行 sfence.vma 之前不会生效
  sfence.vma 会导致陷入 VMM
    VMM 生成一个新的影子页表

如何模拟设备？
  例如磁盘、网卡、显示器
  一大挑战！
  策略：模拟一种常见的现有真实设备
    这是运行无感知客户操作系统所必需的
    拦截内存映射控制寄存器的读/写操作
      通过将这些页标记为无效，使 VMM 获得页错误
    VMM 将页错误转换为对（不同）真实设备的操作
    例如 qemu 为 xv6 模拟 uart/console
      qemu 将 uart 的读/写转换为显示器或 ssh 上的字符
  策略：为效率而专门设计的虚拟设备
    需要客户操作系统驱动程序——即客户系统知道自己运行在虚拟机中
    可以比在控制寄存器读/写上陷入更为精简高效
    例如 xv6 的 virtio_disk.c；qemu 将其转换为对文件 fs.img 的读/写
  策略：直通访问真实硬件设备
    客户操作系统直接访问设备硬件，无需陷入
    通常需要设备提供特定支持
      现代网卡具备此支持
    可以非常高效

陷入并模拟的方式效果良好——但速度可能较慢！
  需要大量陷入 VMM

*** 硬件支持的 x86 虚拟化

VT-x/VMX/SVM：硬件支持的虚拟化
  Intel（以及 AMD）CPU 具有硬件虚拟化支持
    CPU 直接支持虚拟状态与真实状态的区分
    因此客户系统可以执行特权指令而无需陷入
  比陷入并模拟的方式更快
  更易于为 VMM 实现相应软件
  被广泛用于实现虚拟机

VT-x 根模式与非根模式
  [图示：两组寄存器，以及 EPT]
  宿主机（VMM）运行在"根模式"——无特殊之处
  客户系统运行在"非根模式"
    拥有完整的"虚拟"控制寄存器集合
      x86 中与 satp、stvec、用户态/监督态等价的寄存器
    客户监督态可以执行操作系统内核所期望的一切操作
      切换到（客户）用户态、处理系统调用、陷阱等
    非根模式*看起来*就像一台普通计算机
    但 VT-x 非根模式在某些关键方面限制了客户系统
      主要通过页表实现，我们稍后将看到
  新增指令用于在根模式/非根模式之间切换
    VMLAUNCH/VMRESUME：根模式 -> 非根模式
    VMCALL：非根模式 -> 根模式
  设备中断（如定时器、磁盘）会导致退出非根模式
    VMM 默认负责处理设备
  虚拟机控制结构（VMCS）
    非根模式退出时，虚拟状态保存至 VMCS
    VMLAUNCH/VMRESUME 时，虚拟状态从 VMCS 中恢复

VT-x 页表
  问题：
    我们希望让客户机内核控制页表，
    并将客户机限制在其允许的物理内存范围内，
    但不希望在以下情况下付出陷入 VMM 的开销：
      客户机设置 %cr3（即 satp）或修改 PTE 时。
  EPT：VT-x 在非根模式下具有*两*层地址转换
    VMM 负责建立 EPT 页表
    其中仅包含客户机可使用的"客户机物理地址"
    映射到 VMM 为客户机分配的真实（宿主机）物理地址
    EPT = Extended Page Table（扩展页表）
  MMU 硬件查询 %cr3 以获取客户机物理地址，
    再通过 EPT 将客户机物理地址转换为宿主机物理地址
  EPT 对客户机不可见
  因此：
    客户机可以自由读写 %cr3、修改 PTE、读取 D 位等
    VMM 仍可通过 EPT 实现隔离
  典型配置：
    VMM 为客户机分配一部分 RAM
    VMM 在 EPT 中将客户机物理地址 0..size 映射到该 RAM
    客户机使用 %cr3 配置客户机进程的地址空间

*** Dune

核心思想：
  利用 VT-x 运行 Linux 用户进程（而非运行客户机内核）
  使用户代码能快速直接访问页表、异常等机制
  以便用户代码高效地实现：
    对不可信代码进行沙箱隔离
    修改页表并处理缺页错误

方案介绍
  [diagram]
  Dune 是 Linux 的一个"可加载内核模块"
  普通进程可以切换到"Dune 模式"
  Dune 模式下的进程仍然是一个进程
    拥有内存，可通过 VMCALL 发起 Linux 系统调用
  隔离机制略有不同
    VT-x 非根模式的超级用户模式
    通过 EPT 页表实现内存保护
    定时器中断发送给 Linux 而非进程，因此由 Linux 控制调度
  Dune 为进程提供了额外功能
    读写自身页表，包括 PTE D（脏）位
      比调用 Linux 的 mprotect() 系统调用更快
    自行处理缺页错误
      比让 Linux 将故障转化为向上调用更快
    切换到（客户）用户态
    拦截客户用户态的系统调用和缺页故障

示例：沙箱执行（论文第 5.1 节）
  假设你的网络浏览器想要运行一个第三方插件
    例如视频解码器或广告拦截器
    该插件可能是恶意的或有缺陷的
  浏览器需要一个"沙箱"
    执行插件，但限制其系统调用 / 内存访问
  假设浏览器以 Dune 进程运行：
    [图示：浏览器处于客户超级模式，插件处于客户用户态]
    为插件可使用的内存创建带有 PTE_U 映射的页表
      并为浏览器其余内存创建非 PTE_U 映射
    设置 %cr3
    通过 sret 进入不受信任的代码，处于客户用户态
    插件可通过页表读写图像内存
    插件可执行系统调用指令
      但其系统调用会陷入浏览器（而非底层内核）
      浏览器可以决定是否允许每个系统调用

示例：垃圾回收（GC）
  （改进的 Boehm 并发标记-清除回收器）
  GC 通过跟踪指针来找到所有存活（可达）的对象
    从寄存器开始
  但此 GC 是并发的——程序可能在 GC 追踪某对象后再次修改它
  GC 需要一种方式来获知哪些对象被修改了，
    以便重新访问被修改的对象
  Dune 如何提供帮助？
    使用 PTE 脏位（PTE_D）检测被写入的页
    GC 完成后清除所有脏位
    Dune 允许直接访问 PTE
      比通过 Linux 系统调用获取 PTE 快得多

快速的用户级虚拟内存访问可以惠及许多程序
  Appel 和 Li 的论文

Dune 总结
  核心思想：利用 VT-x 使进程能够访问特权硬件功能
  最终结论：在某些场景下比 Linux 系统调用快得多
