6.S081 2020 第11讲：线程切换

主题：深入了解 xv6 的底层机制
  前情回顾：系统调用、中断、页表、锁
  本讲内容：进程/线程切换

为什么要支持多任务？
  分时复用：多用户和/或多个运行中的程序。
  程序结构：质数筛。
  在多核硬件上实现并行加速。

线程是一种抽象，用于在存在多个任务时简化编程。
  线程 = 一个独立的串行执行单元 —— 包括寄存器、pc、栈
  线程系统将多个线程的执行交替进行
  两种主要策略：
    多个 CPU，每个 CPU 运行不同的线程
    每个 CPU 在多个线程之间"切换"，每次只运行一个

线程可以共享内存，也可以不共享
  xv6 内核线程：它们共享内核内存（因此需要锁）
  xv6 用户进程：每个进程只有一个线程，因此不存在共享
  linux：支持多个线程共享一个用户进程的内存

还有其他用于交替执行多个任务的技术
  可参阅事件驱动编程或状态机
  线程并非最高效的方式，但通常是最便捷的

线程设计的挑战
  如何在少数几个 CPU 上交替运行多个线程？
    如何让交替执行对线程透明？
    "调度" = 选择下一个要运行的线程的过程
  线程未运行时需要保存什么状态？
  如何应对计算密集型线程？

如何应对计算密集型线程？
  每个 CPU 都有定时器硬件，会周期性地产生中断
  内核利用定时器中断从陷入循环的线程中夺回控制权
  内核保存线程状态，执行切换，最终恢复执行，
    并还原已保存的状态以实现透明性
  RUNNING 与 RUNNABLE
  这就是"抢占式"调度 —— 强制剥夺毫不知情的代码的执行权
    与之相对的是协作式调度，在该模式下代码主动让出执行权

对于未在运行的线程该如何处理？
  需要暂存其状态：寄存器、栈、内存
    不过无需担心内存，它不会消失
  因此实现上需为每个线程提供一个栈和寄存器保存区
  需要追踪每个线程的状态
    运行中（RUNNING）vs 可运行（RUNNABLE）vs 睡眠中（SLEEPING）

在 xv6 中：
  [简图：进程、用户栈、陷阱帧、内核栈]
  每个进程有两个线程，一个用户线程，一个内核线程
    进程要么正在执行其用户线程，
    要么在其内核线程中处理系统调用或中断
  内核线程共享内核内存 / 数据结构
    因此内核是一个并行程序
  我们将"进程"、"内核线程"和"线程"作为同义词使用

xv6 中线程切换概述
  （要点：在线程间切换，使多个线程在每个 CPU 上交替执行）
  [图示：P1, TF1, STACK1, swtch(), CTX1;
            CTXs, swtch(), STACKs, scheduler(), &c]
  TF = trapframe = 保存的用户寄存器
  CTX = context = 保存的 RISC-V 寄存器
  从一个进程切换到另一个进程涉及多次状态转换：
    用户态 -> 内核态；将用户寄存器保存至陷阱帧
    内核线程 -> 调度器线程；将内核线程寄存器保存至上下文
    调度器线程 -> 内核线程；从上下文恢复内核线程寄存器
    内核态 -> 用户态；从陷阱帧恢复用户寄存器

"上下文切换"——从一个线程切换到另一个线程

调度器线程
  每个核心有一个调度器线程；每个调度器线程拥有自己的栈和一个 struct context
  内核线程（进程）始终切换到当前核心的调度器线程
    再由调度器线程切换到另一个内核线程（如果存在可运行的线程）
    内核线程之间永远不会直接切换
  原因：调度器拥有独立的栈，简化了
    诸如从退出中的进程切换走等边界情况的处理
  调度器线程持续扫描进程表，直到
    找到一个可运行（RUNNABLE）的线程（有可能一个都没有！）
  如果没有可运行的线程，调度器处于"空闲"状态

注意：
  每个核心要么运行其调度器线程，要么运行某个其他线程
    同一核心在同一时刻只运行一个线程
  每个线程要么恰好在某一个核心上运行，要么其寄存器
    已保存在其上下文中
  如果一个线程未在运行，其保存的上下文对应于一次
    对 swtch() 的调用

proc.h 中的 struct proc
  p->trapframe 保存用户线程的寄存器
  p->context 保存内核线程的寄存器
  p->kstack 指向线程的内核栈
  p->state 为 RUNNING、RUNNABLE、SLEEPING 等
  p->lock 保护 p->state（以及其他内容……）

记住 yield() 获取了进程的锁
  现在 scheduler 将其释放
  scheduler() 的代码*看起来*像是普通的加锁/解锁配对
    但实际上是 scheduler 加锁，yield 解锁

  特殊之处：锁由与获取它不同的线程释放！

Q: 为什么在 swtch() 执行期间要持有 p->lock？
   yield() 加锁
   scheduler() 解锁
   我们能否在调用 swtch() 之前就释放 p->lock？

p->lock 保护以下几件事：
  使这些步骤原子化：
    * p->state=RUNNABLE
    * 将寄存器保存到 p->context
    * 停止使用 p 的内核栈
    从而确保其他 CPU 的调度器在所有步骤完成前不会开始运行 p
  使这些步骤原子化且不可中断：
    * p->state=RUNNING
    * 将寄存器从 context 移入 RISC-V 寄存器
    从而防止中断触发 yield() 并将尚未初始化的
      RISC-V 寄存器保存到 context 中。

scheduler() 的循环遍历所有进程，找到一个处于 RUNNABLE 状态的进程
  持续循环直到找到为止——可能会空闲一段时间
  在本演示中，将找到另一个 spin 进程
让我们快进到 scheduler() 找到一个 RUNNABLE 进程的时刻

(gdb) tbreak proc.c:474
(gdb) c

scheduler() 锁定了新进程，然后将状态设置为 RUNNING
  这样其他 CPU 的 scheduler() 就不会再运行它了

  通过查看其上下文中的 $ra（返回地址）

查看 kernel/swtch.S（再次）

(gdb) tbreak swtch
(gdb) c
(gdb) stepi 28 -- 现在即将执行 swtch() 的 ret 指令
(gdb) print $ra

现在我们处于*另一个* spin 进程的时钟中断中
  在过去它被中断，调用了 yield() / sched() / swtch()
  但现在它将恢复执行，并返回到用户态

注意：只有 swtch() 负责写入上下文（初始化除外）
      只有 sched() 和 scheduler() 会调用 swtch()
      因此对于内核线程，context.ra 始终指向 sched() 内部
      而对于 scheduler 线程，context.ra 始终指向 scheduler() 内部

注意：sched() 调用 swtch()——然后 swtch() 返回到 sched()
      但通常是*另一个*线程在返回

sched() 和 scheduler() 是"协程"关系
   各自都清楚自己在 swtch() 到哪个目标
   各自都清楚 swtch() 的返回来自哪里
   例如 yield() 与 scheduler() 协同管理 p->lock 和 p->state
   这与普通的线程切换不同，在普通线程切换中，双方通常
     都不知道当前线程的前后是哪个线程

问：什么是"调度策略"？
   即当多个线程处于 RUNNABLE 状态时，xv6 如何决定下一个运行哪个？
   这是一个好的策略吗？

问：内核线程是否支持抢占式调度？
   是的——计时器中断和 yield() 可能在内核中执行时发生。
   yield() 由 kernel/trap.c 中的 kerneltrap() 调用
   被中断的内核代码的寄存器保存在哪里？
     不在 p->trapframe 中，因为那里已经保存了用户态寄存器。
     不在 p->context 中，因为我们即将调用 yield() 和 swtch()
     kernelvec.S 将它们压入内核栈（因为已经处于内核中）。
   内核中的抢占有用吗？
     在 xv6 中并不关键。
     若某些系统调用有大量计算，则很有价值。
     或者当我们需要严格的线程优先级概念时。

问：为什么 scheduler() 通过 intr_on() 短暂地开启中断？
   可能没有处于 RUNNABLE 状态的线程
     它们可能都在等待 I/O，例如磁盘或控制台
   开启中断，使设备有机会发出完成信号
     从而唤醒某个线程
   否则，系统将会冻结

问：为什么 sched() 禁止在持有锁的情况下让出 CPU？
   （p->lock 除外）
   即 sched() 会检查 noff == 1
   假设进程 P1 持有锁 L1 并让出 CPU
   进程 P2 运行，尝试 acquire(L1)
   P2 的 acquire 在关闭中断的情况下自旋
     因此计时器中断不会发生
     因此 P2 不会让出 CPU
     因此 P1 无法执行
     因此 P1 永远不会释放 L1

问：我们能否去掉独立的每 CPU 调度器线程？
   能否让 sched() 直接 swtch() 到新线程？
   从而让 sched() 自己查找下一个要运行的进程？
   那样会更快——避免了其中一次 swtch() 调用
   可以——但是：
     调度循环将运行在某个线程的内核栈上
     如果那个线程正在退出怎么办？
     如果另一个 CPU 想要运行该线程怎么办？
     如果线程数少于 CPU 数——即栈不够用怎么办？
     这些问题都可以解决——不妨试试！

总结
  xv6 为内核代码提供了一个便捷的线程模型
  通过计时器中断实现抢占
  通过切换寄存器和栈实现透明调度
  多核需要对栈和锁进行谨慎处理
