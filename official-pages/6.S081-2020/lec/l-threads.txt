6.S081 2020第11讲：线程切换

主题：xv6 的更多“幕后花絮”
  以前：系统调用、中断、页表、锁
  今天：进程/线程切换

为什么要支持多任务？
  分时：许多用户和/或许多正在运行的程序。
  程序结构：素数筛。
  多核硬件上的并行加速。

线程是一种抽象，用于在有许多任务时简化编程。
  线程=独立串行执行——寄存器、pc、堆栈
  线程系统交错执行多个线程
  两个主要策略：
    多个CPU，每个CPU运行不同的线程
    每个CPU在线程之间“切换”，一次运行一个

线程可以共享内存，也可以不共享内存
  xv6 内核线程：它们共享内核内存（因此有锁）
  xv6 用户进程：每个进程一个线程，因此不共享
  linux：支持多个线程共享用户进程的内存

还有其他技术可以交错执行多个任务
  查找事件驱动编程或状态机
  线程不是最高效的，但通常是最方便的

线程设计挑战
  如何在几个CPU上交错多个线程？
    如何使交错透明？
    “调度”=选择接下来运行哪个线程的过程
  线程未运行时要保存什么？
  如何应对计算密集型线程？

如何应对计算密集型线程？
  每个CPU都有定时器硬件，它周期性地中断
  内核使用定时器中断来从循环线程中获取控制权
  内核保存线程状态、切换、最终恢复，
    恢复保存的透明度状态
  运行与可运行
  这是“抢占式”调度——强制放弃不知情的代码
    与协作调度相反，协作调度中代码自愿产生

如何处理未运行的线程？
  我们需要留出它的状态：寄存器、堆栈、内存
    虽然不用担心内存，但它不会去任何地方
  所以实现为每个线程提供了一个堆栈和寄存器保存区域
  需要跟踪每个线程的状态
    运行、可运行、睡眠

在 xv6 中：
  【简单图：进程、用户栈、trapframe、内核栈】
  每个进程有两个线程，一个用户，一个内核
    进程*或者*执行它的用户线程，
    *或*在系统调用或内核线程中断中
  内核线程共享内核内存/数据结构
    因此内核是一个并行程序
  我们将使用“进程”和“内核线程”和“线程”作为同义词

xv6中线程切换概述
  （要点：在线程之间切换以在每个CPU上交错许多线程）
  [图：P1、TF1、STACK1、swtch()、CTX1；
            CTX、swtch()、STACK、调度程序() 等]
  TF = trapframe = 保存的用户寄存器
  CTX = 上下文 = 保存的 RISC-V 寄存器
  从一个进程到另一个进程涉及多个转换：
    user -> kernel; saves user registers in trapframe
    kernel thread -> scheduler thread; saves kernel thread registers in context
    scheduler thread -> kernel thread; restores kernel thread registers from ctx
    kernel -> user; restores user registers from trapframe

“上下文切换”——从一个线程切换到另一个线程

调度程序线程
  每个核心有一个；每个都有一个堆栈和一个结构体上下文
  内核线程（进程）总是切换到当前核心的调度程序线程
    如果一个内核线程处于可运行状态，则切换到另一个内核线程
    永远不会有直接的内核线程到内核线程的切换
  原因：调度程序的单独堆栈简化了
    例如从现有进程切换出去的情况
  调度程序线程不断扫描进程表，直到
    它找到一个 RUNNABLE 线程（可能没有一个！）
  如果没有 RUNNABLE 线程，则调度程序处于“空闲”状态

note:
  每个核心要么运行其调度程序线程，要么运行其他线程
    给定的核心一次仅运行一个线程
  每个线程要么运行在一个核心上，要么运行在它的寄存器上
    保存在其上下文中
  如果线程未运行，则其保存的上下文引用调用
    到 swtch()

proc.h 中的结构体 proc
  p->trapframe holds saved user thread's registers
  p->context holds saved kernel thread's registers
  p->kstack points to the thread's kernel stack
  p->state is RUNNING, RUNNABLE, SLEEPING, &c
  p->lock protects p->state (and other things...)

p->lock protects a few things:
  使这些步骤原子化：
    * p->state=RUNNABLE
    * save registers in p->context
    * 停止使用p的内核堆栈
    所以其他CPU的调度程序在所有步骤完成之前不会开始运行p

    所以中断不会yield()并保存尚未初始化的内容
      RISC-V 在上下文中进行寄存器。

Q：内核线程是否有抢占式调度？
   是的——定时器中断和yield()可以在内核中发生。
   kernel/trap.c 中的 kerneltrap() 调用的 Yield()
   中断的内核代码的寄存器保存在哪里？
     not in p->trapframe, since already has user registers.
     not in p->context, since we're about to call yield() and swtch()
     kernelvec.S 将它们推送到内核堆栈上（因为已经在内核中）。
   内核中的抢占有用吗？
     在 xv6 中并不重要。
     如果某些系统调用需要大量计算，则很有价值。
     或者如果我们需要严格的线程优先级概念。

问：为什么scheduler()用intr_on()短暂地启用中断？
   可能没有 RUNNABLE 线程
     他们可能都在等待 I/O，例如磁盘或控制台
   启用中断，以便设备有机会发出完成信号
     从而唤醒一个线程
   否则系统会死机

问：为什么 sched() 在让出 CPU 时禁止持有锁？
   (other than p->lock)
   i.e. sched() checks that noff == 1
   假设进程 P1 持有锁 L1，让出 CPU
   进程 P2 运行，尝试 acquire(L1)
   P2 的获取旋转并关闭中断
     所以定时器中断不会发生
     所以P2不会让出CPU
     所以P1无法执行
     所以 P1 永远不会释放 L1
