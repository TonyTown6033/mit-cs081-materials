Today: user -> kernel transition
  系统调用、故障、中断以同样的方式进入内核
  对于隔离和性能很重要
  许多精心设计和重要细节

当程序进行系统调用时需要发生什么，例如写（）？
  [CPU |用户/内核图]
  CPU 资源是为用户执行（而不是内核）而设置的
    32个寄存器，sp，pc，特权模式，satp，stvec，sepc，...
  需要发生什么？
    保存32个用户寄存器和PC
    切换到主管模式
    切换到内核页表
    切换到内核堆栈
    跳转到内核C代码
  高层次目标
    don't let user code interfere with user->kernel transition
      例如不要在超级用户模式下执行用户代码！
    对用户代码透明——恢复而不打扰

今天我们重点讨论用户/内核转换
  并忽略系统调用实现在内核中所做的事情
  但 sys 调用 impl 也必须小心且安全！

CPU的“模式”保护什么？
  即从用户到管理员的切换模式允许什么？
  Supervisor 可以使用 CPU 控制寄存器：
    satp——页表物理地址
    stvec——ecall 在内核中跳转到此处；指向蹦床
    sepc -- ecall 在此处保存用户电脑
    sscratch -- 陷阱帧的地址
  主管可以使用没有 PTE_U 标志的 PTE
  但主管没有其他权力！
    例如不能使用不在页表中的地址
    所以内核必须仔细设置才能工作

为什么 RISC-V 设计者没有让 ecall 为我们做这些事情？
  ecall 尽可能少做：
  为操作系统设计人员提供非常快速的系统调用/故障/中断的空间
    也许操作系统可以处理一些陷阱而无需切换页表
    也许我们可以将用户和内核都映射到一个页表中
       所以不需要页表切换
    也许有些寄存器不需要保存
    简单的系统调用可能不需要堆栈

保存 32 个用户寄存器的解决方案分为两部分：
  1) xv6 将第二个内核页面（trapframe）映射到每个用户页表中
     它有空间保存保存的寄存器
     内核为每个进程提供不同的 trapframe 页
     0x3fffffe000 处的页面是 trapframe 页面
     参见 kernel/proc.h 中的 struct trapframe
     （但我们仍然需要一个寄存器来保存陷阱帧的地址......）
  2）RISC-V提供sscratch寄存器
     内核将一个指向 trapframe 的指针放入 sscratch
       进入用户空间之前
     主管代码可以用 sscratch 交换任何寄存器
       因此两者都掌握了 sscratch 中的值，
       并同时保存寄存器的用户值

总结
  系统调用的进入/退出远比函数调用复杂
  大部分复杂性是由于隔离的要求造成的
    以及对简单快速的硬件机制的渴望
  需要思考的几个设计问题：
    邪恶程序可以滥用进入机制吗？
    你能想办法让硬件或软件变得更简单吗？
    你能想出让陷阱更快的方法吗？
