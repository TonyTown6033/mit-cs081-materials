6.S081 2020 第14讲：文件系统

文件系统有什么用？
  重启后数据持久保存
  命名与组织管理
  在程序和用户之间共享

为什么有趣？
  崩溃恢复
  性能/并发
  共享
  安全
  抽象很有用：pipes, devices, /proc, /afs, Plan 9
    因此面向文件系统的应用程序可以操作多种类型的对象
  两个实验的主题

API 示例 —— UNIX/Posix/Linux/xv6/&c：
  fd = open("x/y", -);
  write(fd, "abc", 3);
  link("x/y", "x/z");
  unlink("x/y");
  write(fd, "def", 3);
  close(fd);
  // file y/z contains abcdef
    
UNIX 文件系统 API 中体现的高层设计选择
  对象：文件（而非虚拟磁盘、数据库）
  内容：字节数组（而非 80 字节记录、BTree）
  命名：人类可读（而非对象 ID）
  组织：名称层次结构
  同步：无（而非加锁、版本控制）
    link()/unlink() 可以在 open() 的同时并发修改名称层次结构
  还存在其他文件系统 API，有时差异相当大！

API 的几点含义：
  fd 指向某个对象
    即使文件名发生变化该对象仍然存在
    或者文件在打开期间被删除也不受影响！
  一个文件可以有多个链接
    即出现在多个目录中
    其中没有哪一个出现是特殊的
    因此文件必须将信息存储在目录以外的地方
  因此：
    文件系统在磁盘上的 "inode" 中记录文件信息
    文件系统使用 i-number 引用 inode（即 FD 的内部版本）
    inode 必须有链接计数（用于判断何时释放）
    inode 必须有已打开 FD 的计数
    inode 的释放推迟到最后一个链接和 FD 均消失后才执行

数据存储在持久性介质上
  断电后数据仍保留在磁盘上
  常见存储介质：
    机械硬盘（容量大但速度慢，价格低廉）
    固态硬盘（容量较小，但速度快，价格更贵）
  历史上，磁盘通常以 512 字节为单位进行读写，这一单位称为扇区

机械硬盘（HDD）
  同心磁道
  每条磁道由一系列扇区组成
  磁头需要寻道，磁盘需要旋转
    随机访问速度慢（每次访问约 5 到 10 毫秒）
    顺序访问速度快得多（100 MB/秒）
  每个扇区具有 ECC 纠错码
  只能整扇区读写
  因此：子扇区写入代价高昂（需读取-修改-写回）

固态硬盘（SSD）
  非易失性"闪存"存储器
  随机访问：100 微秒
  顺序访问：500 MB/秒
  内部结构复杂——通常不可见，但有时会影响性能
    闪存在重新写入之前必须先擦除
    闪存块的写入次数有限制
    SSD 通过一层间接映射来应对——即重映射块

对于 HDD 和 SSD：
  顺序访问远快于随机访问
  大块读写比小块读写更快
  这两点都影响着文件系统的设计与性能
    
磁盘块
  大多数操作系统使用由多个扇区组成的块，例如 4 KB 块 = 8 个扇区
  以减少簿记开销和寻道开销
  xv6 使用 2 个扇区大小的块

磁盘布局
  xv6 将磁盘视为扇区数组（忽略磁盘的物理属性）
  0: 未使用
  1: 超级块（size、ninodes）
  2: 事务日志
  32: inode 数组，打包存入块中
  45: 块使用位图（0=空闲，1=已用）
  46: 文件/目录内容块
  磁盘末尾

xv6 的 mkfs 程序为空文件系统生成上述布局
  该布局在文件系统的整个生命周期内是静态的
  参见 mkfs 的输出

"元数据"
  磁盘上除文件内容以外的所有内容
  超级块、inode、位图、目录内容

磁盘上的 inode
  类型（空闲、文件、目录、设备）
  nlink
  size
  addrs[12+1]

直接块与间接块

示例：
  如何找到文件的第 8000 字节？
  逻辑块号 7 = 8000 / BSIZE（=1024）
  addrs 中的第 7 项

每个 inode 都有一个 inode 编号
  可以轻松地将 inode 编号转换为 inode
  inode 长度为 64 字节
  磁盘上的字节地址：32*BSIZE + 64*inum

目录内容
  目录与文件非常相似
    但用户不能直接写入
  内容为目录项（dirent）数组
  dirent：
    inum
    14 字节文件名
  若 inum 为零，则该 dirent 为空闲项

应将文件系统视为一种磁盘上的数据结构
  [树形结构：目录、inode、块]
  包含两个分配池：inode 池和块池

Q: 为什么有四次 iupdate？

文件系统中的并发
  xv6 的目标较为有限
    并行读写不同文件
    并行路径名查找
  但即便如此，这些操作也带来了有趣的正确性挑战

例如，如果有并发调用 ialloc 会怎样？
   它们会获得相同的 inode 吗？
   注意 ialloc 中的 bread / write / brelse
   bread 锁定块（可能需要等待），并从磁盘读取数据
   brelse 解锁该块

让我们来看 bio.c 中的块缓存
   块缓存仅保存少量最近使用的块
   bcache 位于 bio.c 的开头

文件系统调用 bread，bread 调用 bget
   bget 检查块是否已被缓存
   若已存在，则加锁（可能等待）并返回该块
     可能在 sleeplock 中等待，直到当前使用该块的进程释放它
     若已被锁定，sleep lock 会让调用者进入睡眠
   若不存在，则复用一个已有的缓冲区
   b->refcnt++ 防止在等待期间 buf 被回收
   不变量：磁盘块在内存中只保留一份副本

此处有两级锁
  bcache.lock 保护缓存内容的描述信息
  b->lock 仅保护单个缓冲区

问：块缓存的替换策略是什么？
   prev ... head ... next
   bget 复用 bcache.head.prev —— 即"尾部"块
   brelse 将块移动到 bcache.head.next

路径名查找
  逐个遍历路径名中的各个分量
  可能涉及多个块：
    顶层目录的 inode
    顶层目录的数据块
    下一层目录的 inode
    …… 以此类推 ……
  每次查找都可能导致缓存未命中
    磁盘访问代价高昂
  => 允许并行路径名查找
    若某进程因磁盘访问阻塞，另一个进程可继续执行查找
    挑战：unlink 可能与查找并发发生

让我们来看 namex()（kernel/fs.c）
  ilock()：对当前目录加锁
  查找下一个目录的 inode
  然后解锁当前目录
  另一个进程可能 unlink 下一个 inode
    但 inode 不会被删除，因为 inode 的 refcnt > 0
  风险：next 与 current 指向同一个 inode（查找"."时）
    在获取 next 的锁之前先解锁 current
    核心思想：将引用的获取与加锁分离
