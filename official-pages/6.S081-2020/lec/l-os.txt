Strawman设计不利于复用
  每个应用程序必须定期放弃硬件
  但是，隔离性较弱
    应用程序忘记放弃，没有其他应用程序运行
    应用程序有无限循环，没有其他应用程序运行
    你甚至无法从另一个应用程序中杀死这个糟糕的应用程序
  但由实时操作系统使用
    “协同调度”

Strawman设计不利于内存隔离
  所有应用共享物理内存
  一个应用程序可以覆盖另一个应用程序的内存
  一个应用程序可以覆盖操作系统库

Unix 界面有利于操作系统目标
  以实现目标的方式抽象硬件
  进程（而不是核心）：fork
     操作系统透明地将核心分配给进程
       保存和恢复寄存器
     强制进程放弃它们
       定期重新分配核心
  内存（而不是物理内存）：exec
     每个进程都有自己的内存
     操作系统可以决定将应用程序放置在内存中的位置
     操作系统可以强制不同应用程序的内存之间的隔离
     操作系统允许在文件系统中存储图像
  文件（而不是磁盘块）
     操作系统可以提供方便的名称
     操作系统可以允许进程/用户之间共享文件
  管道（而不是共享物理内存）
     操作系统可以停止发送者/接收者
  
操作系统必须具有防御性
  应用程序不应导致操作系统崩溃
  应用程序不应该能够打破它的隔离
  => need strong isolation between apps and OS
  方法：硬件支持
  - 用户/内核模式
  - 虚拟内存
  
处理器提供用户/内核模式
  内核模式：可以执行“特权”指令
    例如，设置内核/用户位
    例如，重新编程定时器芯片
  用户模式：无法执行特权指令
  操作系统运行在内核态，应用程序运行在用户态
  [RISC-V还有M模式，我们大多忽略]

处理器提供虚拟内存
  硬件提供将虚拟地址转换为物理地址的页表
  定义应用程序可以访问哪些物理内存
  操作系统设置页表，以便每个应用程序只能访问其内存

应用程序必须能够与内核通信
  Write to storage device, which is shared => must be protected => in kernel
  退出应用程序
  ...

内核是可信计算基础（TCB）
  内核必须“正确”
    内核中的错误可能允许用户应用程序绕过内核/用户
      在实践中经常发生，因为内核很复杂
      查看 CVE
  内核必须将用户应用程序视为可疑
    用户应用程序可能会欺骗内核做错误的事情
    内核必须仔细检查参数
    正确设置用户/内核
    Etc.
  内核也负责分离应用程序
    一个应用程序可能会尝试读取/写入另一应用程序的内存
  => Requires a security mindset
    内核中的任何错误都可能是安全漏洞

整体内核
  操作系统运行在内核空间
  xv6 就是这样做的。 Linux 等也是如此。
  kernel interface == system call interface
  一个包含文件系统、驱动程序等的大程序
  - 好：易于子系统协作
    文件系统和虚拟内存共享一个缓存
  - 不好：交互很复杂
    导致错误
    内部没有隔离

微内核设计
  许多操作系统服务作为普通用户程序运行
    文件服务器中的文件系统
  内核实现了在用户空间运行服务的最小机制
    有记忆的进程
    进程间通信（IPC）
  kernel interface != system call interface		
  - 好：更多隔离
  - 不好：可能很难获得良好的性能
  单片和微内核设计都广泛使用
