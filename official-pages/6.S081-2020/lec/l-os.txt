6.S081 2020 第3讲：操作系统组织

讲座主题：
  操作系统设计
    系统调用
    微内核/宏内核
  xv6中的第一个系统调用

操作系统全景
  应用程序：sh、echo、...
  系统调用接口（open、close、...）
        操作系统
    
操作系统的目标
  运行多个应用程序
  对它们进行隔离
  对它们进行多路复用
  共享资源

初步设计：无操作系统
  应用程序直接与硬件交互
    CPU核心与寄存器
    DRAM芯片
    磁盘块
    ...
  操作系统库或许对其中一部分进行抽象

初步设计不利于多路复用
  每个应用程序必须定期主动让出硬件
  但是，隔离性很弱
    应用程序忘记让出，其他应用程序将无法运行
    应用程序陷入死循环，其他应用程序将无法运行
    你甚至无法从另一个应用程序中终止行为异常的应用程序
  但实时操作系统会采用这种设计
    "协作式调度"

初步设计不利于内存隔离
  所有应用程序共享物理内存
  一个应用程序可以覆写另一个应用程序的内存
  一个应用程序可以覆写操作系统库

Unix接口有利于实现操作系统目标
  以实现目标的方式对硬件进行抽象
  进程（代替核心）：fork
     操作系统透明地将核心分配给进程
       保存并恢复寄存器
     强制要求进程主动让出核心
       定期重新分配核心
  内存（而非物理内存）：exec
     每个进程拥有"自己的"内存
     操作系统可以决定将应用程序放置在内存中的位置
     操作系统可以强制实现不同应用程序内存之间的隔离
     操作系统允许将镜像存储在文件系统中
  文件（而非磁盘块）
     操作系统可以提供便捷的名称
     操作系统可以允许进程/用户之间共享文件
  管道（而非共享物理内存）
     操作系统可以阻塞发送方/接收方
    
操作系统必须具有防御性
  应用程序不应能够使操作系统崩溃
  应用程序不应能够突破其隔离限制
  => 需要在应用程序与操作系统之间实现强隔离
  方法：硬件支持
  - 用户态/内核态
  - 虚拟内存
    
处理器提供用户态/内核态
  内核态：可以执行"特权"指令
    例如，设置内核/用户位
    例如，对定时器芯片重新编程
  用户态：不能执行特权指令
  操作系统运行在内核态，应用程序运行在用户态
  [RISC-V 还有一种 M 模式，我们基本上忽略不计]

处理器提供虚拟内存
  硬件提供页表，将虚拟地址转换为物理地址
  定义应用程序可以访问哪些物理内存
  操作系统设置页表，使每个应用程序只能访问其自身的内存

应用程序必须能够与内核通信
  向存储设备写入数据，该设备是共享的 => 必须受到保护 => 位于内核中
  退出应用程序
  ...

解决方案：添加指令以受控方式切换模式
  ecall <n>
  在预先约定的入口点进入内核态

修改操作系统示意图
  用户态 / 内核态（红线）
  app -> printf() -> write() -> SYSTEM CALL -> sys_write() -> ...
    用户态库是应用程序的私有事务
  内核内部函数不可被用户调用
    
  另一种绘制示意图的方式：
  syscall 1  -> system call stub -> kernel entry -> syscall -> fs
  syscall 2                                                 -> proc

  system call stub 执行特殊指令以进入内核
    硬件切换到内核态
    但只能在内核指定的入口点处进入

  系统调用需要某种方式来获取系统调用的参数

  [系统调用是本周实验的主题]
  
内核是可信计算基（TCB）
  内核必须是"正确的"
    内核中的漏洞可能允许用户应用程序绕过内核/用户的隔离
      这在实践中经常发生，因为内核非常复杂
      参见 CVEs
  内核必须将用户应用程序视为不可信的
    用户应用程序可能诱骗内核执行错误操作
    内核必须仔细检查参数
    正确配置用户态/内核态
    等等。
  内核也负责隔离各个应用程序
    某个应用程序可能试图读写另一个应用程序的内存
  => 需要具备安全意识
    内核中的任何漏洞都可能成为安全漏洞利用点

题外话：能否在没有硬件支持的
  内核/用户态模式和虚拟内存的情况下实现进程隔离？
  可以！使用强类型编程语言
  - 例如，参见 Singularity O/S
  编译器即为可信计算基（TCB）
  但硬件用户/内核态模式是最流行的方案

宏内核
  操作系统运行在内核空间
  xv6 采用此设计。Linux 等也是如此。
  内核接口 == 系统调用接口
  一个包含文件系统、驱动程序等的大型程序
  - 优点：子系统之间易于协作
    文件系统与虚拟内存共享同一缓存
  - 缺点：交互关系复杂
    容易引发漏洞
    内部缺乏隔离

微内核设计
  许多操作系统服务作为普通用户程序运行
    文件系统运行在文件服务器中
  内核实现最小化机制以在用户态运行服务
    带有内存的进程
    进程间通信（IPC）
  内核接口 != 系统调用接口
  - 优点：隔离性更强
  - 缺点：可能难以获得良好性能
  宏内核与微内核设计均被广泛使用

RISC-V 计算机
  一块非常简单的开发板（例如，无显示器）
  - 具有 4 个核心的 RISC-V 处理器
  - RAM（128 MB）
  - 支持中断（PLIC、CLINT）
  - 支持 UART
    允许 xv6 与控制台通信
    允许 xv6 从键盘读取输入
  - 支持 e1000 网卡（通过 PCIe）

使用 Qemu 进行开发
  比使用真实硬件更为便捷
  Qemu 模拟多种 RISC-V 计算机
  - 我们使用 "virt" 这款
    https://github.com/riscv/riscv-qemu/wiki
  - 与 SiFive 开发板（https://www.sifive.com/boards）相近
    但磁盘使用 virtio
