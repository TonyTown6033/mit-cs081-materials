以太网数据包格式
  [kernel/net.h, struct eth 打印输出]
  起始"标志"
  目标以太网地址 -- 48 位
  源以太网地址 -- 48 位
  以太网类型 -- 16 位
  有效载荷
  结束"标志"

[eth tcpdump 输出]

以太网地址
  简单以太网 LAN 采用广播方式：所有主机的 NIC 都能看到所有数据包
    主机通过目标地址判断该数据包是否真正发给自己
  现今的以太网 LAN 使用交换机，每台主机通过独立线缆连接
    交换机根据目标地址决定将数据包发送给哪台主机
  以太网地址由 NIC 制造商分配
    <24 位制造商 ID，24 位序列号>

ARP
  [kernel/net.h, struct arp]
  一种将 IP 地址转换为以太网地址的请求/响应协议
  "嵌套"在以太网数据包内，以太网类型为 0x0806
  ARP 头部指明是请求还是响应
  请求：目标 IP 地址
    请求数据包广播至交换机上的每台主机
    所有主机均处理该数据包，但只有拥有该 IP 地址的主机响应
  响应：对应的以太网地址

[arp tcpdump 输出]

注意：
  惯例是将高层数据包"嵌套"在低层数据包内
  例如：ARP 嵌套在以太网内
  因此通常会看到一系列首部（先是以太网首部，然后是 ARP 首部）
  一层的有效载荷即为下一层的首部

以太网头部足以将数据包传送到本地主机
  但若要将数据包路由到远程互联网主机，则需要更多信息

IP 头部
  [kernel/net.h, struct ip]
  以太网类型 0x0800
  包含许多字段，但地址是最关键的
  32 位 IP 地址足以路由到互联网上的任意计算机
  高位包含"网络号"，帮助路由器
    了解如何在互联网中转发数据包
  协议号告知目的主机如何处理该数据包
    即将其交给哪个上层协议（通常是 UDP 或 TCP）

[ip tcpdump output]

UDP 头部
  [kernel/net.h, struct udp]
  当数据包到达正确的主机后，应该交给哪个应用程序？
  UDP 头部位于 IP 数据包内部
  包含源端口号和目的端口号
  应用程序使用"socket API"系统调用告知
    内核它希望接收发送到特定端口的所有数据包
  某些端口是"众所周知"的，例如 53 号端口保留给 DNS 服务器
  其他端口按需分配给连接的客户端
  UDP 头部之后是载荷，例如 DNS 请求或响应

[udp tcpdump output]

TCP
  类似 UDP，但具有序列号字段，因此可以重传丢失的数据包，
    并将发送速率与网络及目的端容量相匹配

典型内核网络栈的分层视图
  应用层，如 Web 浏览器、DNS 服务器
  socket、端口到文件描述符表
  UDP | TCP
  IP、路由表 | ARP、ARP 表
  网络驱动
  -- 带分配器的数据包缓冲区（参见 net.h 中的 struct mbuf）
  -- 每一层在接收时解析、校验并剥除头部
     若发现问题则丢弃数据包
  -- 每一层在发送时在前部添加头部
  -- 软件层结构部分遵循头部的嵌套关系

典型内核网络栈的控制流视图
  多个独立的执行主体
  每个主体接收输入数据包、处理后产生输出
  以下是一种典型配置（变体众多；实验配置较为简单）
  网卡（NIC），具有内部缓冲或 DMA 缓冲
  接收中断处理程序，将数据从网卡复制到软件输入队列
  发送中断处理程序，将数据从软件输出队列复制到网卡
  "网络线程"
    从软件输入队列中读取数据包
    如何处理？ARP、转发、放入套接字队列
  应用程序——从各自的套接字队列中读取数据
    
为什么需要这么多缓冲队列？
  吸收临时的输入突发流量
  在计算期间保持输出网卡持续工作
  允许独立的控制流（网卡 vs 网络线程 vs 应用程序）

其他架构也是可行的，有时甚至更优
  例如：用户态协议栈
  例如：用户直接访问网卡（参见 Intel 的 DPDK）
  例如：轮询方式，如今天论文所述

网卡数据包缓冲
  论文中的网卡将数据包缓存在其自身内存中
    驱动软件必须将其复制到内存（RAM）
  实验作业中的网卡（Intel e1000）通过 DMA 直接写入主机内存
    软件为接收（rx）和发送（tx）各准备一个缓冲区指针"环"
    网卡通过 DMA 将每个数据包写入环中连续元素所指向的内存位置
    原因：DMA 比软件复制循环更快
         DMA 可与计算任务并发执行

为什么不始终使用轮询，而从不使用中断？

总体目标：
  一旦开始在某个数据包上消耗 CPU，就确保完整处理该数据包！
    即避免部分处理后因过载而丢弃
  针对转发的特殊情况：
    给予输出高于输入的优先级
  中断使我们无法进行任何控制

论文的解决方案是什么？
  不设 IP 输入队列
  网卡接收中断仅唤醒线程
    然后将该网卡的中断保持*禁用*状态
  线程负责所有处理，
    重新检查网卡是否有更多输入，
    仅在没有待处理输入时才重新启用中断

网卡中断：
  唤醒网络线程（但不读取任何数据包）
  禁用网卡中断

循环：
  如果网卡有待处理数据包
    从网卡读取若干数据包
    处理每个数据包
    （这是轮询部分）
  否则
    启用中断
    休眠

我们能否归纳出一些通用原则？
  在完成现有工作之前，不要在新工作上花费时间
  设计应使效率随负载增加而提升，
    而非下降。例如论文中在高负载下从
    中断切换为轮询的做法。

一个通用教训：复杂的（多阶段）系统若要在接近
  容量的负载下正常运行，可能需要对资源进行
  精细的调度
