6.S081 2020 L23：多核可扩展性和RCU

今天的主题：
  读取大量共享数据的多核内核性能。
  RCU（读-复制更新）：在 Linux 中非常成功。

Puzzle:
  并行执行对于多核性能至关重要。
  内核有很多天然的并行性。
    不同进程的系统调用在高层上通常是独立的。
    分叉，读/写缓存、管道、套接字等中的不同文件。
  但内核的共享资源常常抑制并行性。
    例如内存分配器、调度程序、磁盘缓存、i 节点缓存等。
    通常的症状是 CPU 时间浪费在 acquire() 中旋转。
  在生产内核中付出巨大努力来消除并行瓶颈。
  许多设计模式，适合不同的情况。

今天的焦点：读取密集型数据结构。

示例：单链表。
  例如进程列表； VMA；缓存块的数量；等。
  带有指向第一个元素的指针的全局变量。
  每个元素都有数据，例如一个短字符串和一个下一个指针。
  假设大多数用途是扫描列表的读取。
  偶尔作家会添加一些元素；删除元素；更改元素中的字符串。

xv6 需要列表读取器和写入器获取自旋锁。
  安全，但即使所有线程都是只读的，也没有并行性。
  我们可以有一个允许并行读取的锁吗？
  读/写锁似乎是一个完美的解决方案。

读/写锁API。
  r_lock(l) / r_unlock(l)
  w_lock(l) / w_unlock(l)
  语义：要么
    一位作者，没有读者或其他作者；或
    读者多，作者少。

这是 Linux 读/写锁的简化版本。
结构 rwlock { int n; };
  n=0  -> not locked
  n=-1 -> locked by one writer
  n>0  -> locked by n readers
r_lock（l）：
  而1：
    x = l->n
    如果 x < 0
      继续
    if CAS(&l->n, x, x + 1)
      返回
CAS(p, a, b) 是原子比较和交换指令
  if *p == a, set *p = b, return true
  否则返回 false
w_lock（l）：
  而1：
    if CAS(&l->n, 0, -1)
      返回

惊喜：如果在多个内核上多次调用，r_lock() 会非常慢：
  [图表：核心、缓存]
  假设有 N 个读者，没有作者。
  All N calls to r_lock() will read and cache l->n.
  Only one of the N CAS will succeed, and increment l->n.
    That CAS does O(N) work, since must invalidate N-1 cached copies of l->n.
  其他核心全部重试读取和CAS。
  所有 N 个核需要 N 次循环迭代才能完成 r_lock()。
    每个工作时间为 O(N)。
  总计：O(N^2) 工作。
Disappointing:
  如果缓存的话，列表本身读取可能需要几十个周期。
    即使有很多核心正在读取。
  但 r_lock() 可能需要 100 或 1000 的周期（如果它很流行的话）。

r_lock() 的根本问题是：它的*写入*成本很高。

我们可以对共享读写数据进行纯只读读取吗？
  即甚至避免需要锁定的写入？
  （尽管我们假设编写者仍然必须锁定。）

如果读者在没有锁定的情况下阅读列表会出现什么问题？
  [列表图，每个条目中都有字符串]
  如果没有作家，就不会出问题。
  是否有并发作家？
    1. 修改列表元素中的字符串？
    2. 插入一个新的列表元素？
    3. 删除元素？

所以读者单纯不加锁是行不通的。
  但具体问题是可以解决的！
  这就是 RCU 所做的。

读取-复制更新 (RCU)。
  快速读取：无锁（也无写入）。
  写入速度较慢：写入者需要锁定并做更多工作。
  在许多情况下可以帮助读取大量共享数据，但不是全部。
  在 Linux 中广泛使用，是其多核性能的很大一部分。

RCU理念1：不要就地修改数据；准备一份新副本。
  Head  ->  E1  ->  E2  ->  E3  ->  nil
  Suppose writer wants to change the string in E2->x.
  1. 锁
  2. e = 分配()
  3. e->next = E2->next
  4. e->x = "..."
  5. E1->next = e
  6. 解锁
  如果另一个核心上的读者遍历该列表呢？
    At some point reader will read E1->next.
    在步骤 5 之前或之后（这是一个简化，请参见下文）。
    如果之前，读者会看到未修改的 E2 和原始字符串。
    如果之后，读者会看到新元素和新字符串。
    Either way, reader will see ...->next pointing to E3.
  要点：读者不会看到部分更新的字符串。

思考这个想法的一个好方法是：
  Update of E1->next is a "committing write".
  以前，好像一切都没有改变。
  之后，所有更改都可见。
  RCU 最适合单指针写入提交的数据结构。
    例如列表和树。

RCU 想法 2：读取器和写入器必须使用内存屏障来强制执行顺序。
  我们不希望编译器或机器将步骤 3 或 4 移到步骤 5 之后。
  作家必须在第 5 步之前设置障碍。
  Reader needs a barrier between Rx = E1->next,
    并取消引用 Rx 以读取元素内容。

当作者释放列表元素时会发生什么？
  问题：读者可能正在查看要删除的元素。
  作者需要给读者时间来完成。
    之后它删除了对该元素的可见引用。
    但作者还要等多久呢？
  可以使用 GC 或引用计数，但它们很昂贵。

RCU 的理念 3：
  1. Reader 不允许跨上下文切换保存指向 RCU 数据的指针。
     类似于自旋锁不能跨上下文切换保持的规则。
  2. Writer 推迟释放，直到所有 CPU 都完成上下文切换。
  作者可能需要等待几毫秒，
    但假设写入很少。
  如何做到这一点？
    简单计划：writer 强制自己在每个 CPU 上进行调度。
    （有更有效的实现。）

供读者使用的Linux RCU接口：
  rcu_read_lock()
  rcu_read_unlock()
  rcu_取消引用(p)
对于作家：
  同步rcu()
  call_rcu(fn,x)
  rcu_分配_指针（pa，p）

rcu_read_lock/unlock 几乎不执行任何操作。
  禁用定时器中断以防止抢占。
  因为上下文切换意味着用 RCU 对象完成。

Synchronize_rcu() 可能需要很长时间，并且可能会占用 CPU。
call_rcu(fn,x) 立即返回；将 <fn,c> 添加到列表中。

使用 Linux 的 RCU 接口的列表阅读器：
  rcu_read_lock()
  e = 头
  而（p）{
    e = rcu_取消引用(e)
    look at e->x ...
    e = e->next
  }
  rcu_read_unlock()

注意：代码只能在rcu_read_lock/unlock中使用e！
  它不能例如返回(e)

替换第一个列表元素的代码：

  获取（锁定）
  老=头
  e = 分配()
  e->x = ...
  e->next = head->next
  rcu_assign_pointer(&head, e)
  释放（锁定）

  同步rcu()
  免费（旧）
   
RCU 性能与读/写锁的比较？
  致读者：
    RCU 的读取成本几乎为零。
    r/w 锁可能需要 100 秒或 1000 秒的周期（图 5，上面的线）。
    此外，RCU 可以在写入过程中进行读取！
  对于作家：
    由于synchronize_rcu()，RCU 可能需要更长的时间。
    因此，当写入很少或对时间不敏感时，RCU 就有意义。

示例：删除 NMI 处理程序；论文第 4.1 节；图 4.
  NMI 是无法禁用的中断。
    用于 CPU 分析、严重硬件错误、看门狗定时器。
  内核代码可以注册在 NMI 期间调用的处理程序。
  还可以取消注册处理程序，并释放包含代码的内存。
  NMI 很频繁；注册/注销很少见；因此读取 >> 写入。
  如果调用取消注册时某些核心位于 NMI 代码中怎么办？
  图4的解决方案，在unregister_nmi_handler()中：
    1. 删除 NMI 处理程序列表条目（这样以后的中断将看不到它）。
    2.synchronize_rcu()等待当前所有中断完成。
       因为核心在离开中断之前不会进行上下文切换。
    3.（未显示）释放保存 NMI 处理程序代码的内存。
  此示例使用 RCU 推迟释放，直到所有使用都完成。
  一个有趣的皱纹：
    NMI 无法禁用。
    所以自旋锁无法阻止 NMI。
    所以一般不能允许 NMI 获取锁（死锁...）。
    所以这里 RCU 不仅比读卡器锁定更快，
      但实际上在锁定不起作用的地方有效。

示例：IP 选项；第 4.2 节；图 6.
  IP 数据包标头可以包含选项（例如记录路由）。
  内核套接字具有（可选）选项，复制到每个传出数据包中。
  发送代码（udp_sendmsg()）复制套接字选项而不加锁。
  Options are read much more often than written -> good RCU candidate.
  setsockopt() 推迟使用 call_rcu(kfree,old) 释放被取代的选项。
  为什么读码安全？
    1. Writer 在发布指针之前完全准备好新选项。
    2. 写入器和读取器使用内存屏障。
    3. 作者将免费推迟到任何旧读者必须完成为止。
  该论文将其称为“引用计数”，但没有引用计数。
    “垃圾收集”可能是一个更好的术语，
    因为目标是在最后一个引用消失后释放。
  
RCU 并不普遍适用。
  对写作没有帮助。
  仅在读取>>写入时提高性能。
  不适用于必须在yield/sleep 中保存引用的代码。
    很像自旋锁。
  如果数据结构不适合单次提交写入，则不起作用。
    例如如果读者扫描双向链表的两个方向。
    或者如果需要就地更新。
  读者可以看到陈旧的数据。
    例如图 6 中的 udp_sendmsg() 可能会使用旧的 IP 选项进行发送。
    但前提是与setsockopt() 并发。
    这里不是问题；可能在少数情况下（论文提到了 Sys V IPC）。
  RCU 增加了编写者的复杂性。
    在网络上搜索“RCU 补丁审查清单”
  RCU 需要频繁进行上下文切换，并且需要了解它们。
    在内核中很容易，但在用户空间线程中则困难。

Synchronize_rcu() 能比“在每个CPU上调度”更高效吗？
  这是来自的设计
    http://www2.rdrop.com/users/paulmck/RCU/rclockpdcsproof.pdf
    第3.5.4节
  每核心数据：
    该核心的上下文切换计数。
    等待的synchronize_rcu()和call_rcu()列表。
  每个核心会定期处理整批（列表）的 RCU 编写器：
    保存列表，清空它。
    记录所有其他核心的计数。
    每次上下文切换，都会再次查看其他核心的计数。
    如果所有内容都已更改，则唤醒/运行已保存列表上的所有内容。

如果您共享写入量大的数据怎么办？
  最好：重新设计，不共享。
  第二佳：半私有每核分区。
  示例：锁定实验室中的 kalloc。
  示例：Linux 每核心调度列表。
  示例：统计计数器。
    每个核心在单独的自旋锁下保留自己的计数。
    要写入，获取本地锁，增加本地计数。
      如果仅从一个核心使用自旋锁，那么它很便宜。
    要读取，请获取“所有”锁，读取所有计数并对其求和。
      昂贵，但我们假设写入量很大。
  
RCU总结
  在加速对共享内核数据的读取访问方面非常成功。
    在现代 Linux 中广泛使用。
  完全消除了读者的锁定成本。
  允许读取器与写入器并行执行。
  关键思想是类似 GC 的宽限期来推迟释放对象。
