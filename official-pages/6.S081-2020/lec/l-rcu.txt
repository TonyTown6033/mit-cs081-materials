6.S081 2020 L23：多核可扩展性与 RCU

今日主题：
  多核内核中读密集型共享数据的性能优化。
  RCU（读-拷贝-更新）：在 Linux 中广泛应用且极为成功。

难题：
  在多核上，并行执行对性能至关重要。
  内核具有大量天然的并行性。
    不同进程的系统调用在高层往往是相互独立的。
    Fork、读写缓存中的不同文件、管道、套接字等。
  但内核的共享资源往往会抑制并行性。
    例如：内存分配器、调度器、磁盘缓存、i-node 缓存等。
    常见症状是 CPU 时间浪费在 acquire() 的自旋等待上。
  生产内核为消除并行瓶颈付出了大量努力。
  针对不同情况有许多设计模式可供选用。

今日重点：读密集型数据结构。

示例：单链表。
  例如：进程链表、VMA 链表、缓存块链表等。
  全局变量保存指向第一个元素的指针。
  每个元素包含数据（如一个短字符串）以及一个 next 指针。
  假设大多数操作是扫描链表的读操作。
  偶尔有写操作：添加元素、删除元素或修改元素中的字符串。

xv6 会要求链表的读者和写者都获取一个自旋锁。
  这样做是安全的，但即使所有线程都是只读的，也无法并行。
  我们能否使用一种允许并行读取的锁？
  读写锁看起来是一个完美的解决方案。

读写锁 API。
  r_lock(l) / r_unlock(l)
  w_lock(l) / w_unlock(l)
  语义：满足以下条件之一：
    一个写者，无读者也无其他写者；或
    多个读者，无写者。

以下是 Linux 读写锁的简化版本。
struct rwlock { int n; };
  n=0  -> 未加锁
  n=-1 -> 被一个写者持有
  n>0  -> 被 n 个读者持有
r_lock(l):
  while 1:
    x = l->n
    if x < 0
      continue
    if CAS(&l->n, x, x + 1)
      return
CAS(p, a, b) 是原子比较并交换指令
  若 *p == a，则设置 *p = b，返回 true
  否则返回 false
w_lock(l):
  while 1:
    if CAS(&l->n, 0, -1)
      return

意外发现：r_lock() 在多核上被频繁调用时非常慢：
  [示意图：多核、缓存]
  假设有 N 个读者，没有写者。
  所有 N 次 r_lock() 调用都会读取并缓存 l->n。
  N 次 CAS 中只有一次会成功，并将 l->n 加一。
    该 CAS 需要 O(N) 的开销，因为必须使 N-1 份 l->n 的缓存副本失效。
  其他核心全部重试读取和 CAS。
  所有 N 个核心完成 r_lock() 需要 N 次循环迭代。
    每次迭代消耗 O(N) 的开销。
  总计：O(N^2) 的开销。
令人失望的是：
  链表本身的读取在有缓存的情况下大概只需要几十个时钟周期。
    即使有大量核心同时读取也是如此。
  但若 r_lock() 被频繁调用，则可能耗费数百乃至数千个时钟周期。

r_lock() 的根本问题在于：它执行了代价高昂的*写操作*。

我们能否对共享的读写数据实现纯只读的读取？
  即，连加锁所需的写操作也完全避免？
  （不过我们仍假设写者需要加锁。）

读者在不加锁的情况下读取链表会出现什么问题？
  [链表示意图，每个节点中含有字符串]
  如果没有写者，则不会出现问题。
  如果存在并发写者呢？
    1. 修改链表节点中的字符串？
    2. 插入新的链表节点？
    3. 删除某个节点？

因此，读者简单地不加锁是行不通的。
  但上述具体问题是可以解决的！
  这正是 RCU 所做的事情。

读-拷贝-更新（RCU）。
  读取快速：无需加锁（也不执行写操作）。
  写入较慢：写者需要加锁，并执行更多工作。
  适用于许多以读为主的共享数据场景，但并非所有场景都适用。
  在 Linux 中被广泛使用，是其多核性能的重要组成部分。

RCU 思想一：不原地修改数据，而是准备一份新的副本。
  Head  ->  E1  ->  E2  ->  E3  ->  nil
  假设写者想修改 E2->x 中的字符串。
  1. 加锁
  2. e = alloc()
  3. e->next = E2->next
  4. e->x = "..."
  5. E1->next = e
  6. 解锁
  另一个核上正在遍历链表的读者会怎样？
    读者在某个时刻会读取 E1->next。
    这发生在第 5 步之前或之后（这是一种简化说法，详见下文）。
    若在之前，读者看到的是未修改的 E2 和原始字符串。
    若在之后，读者看到的是新元素和新字符串。
    无论哪种情况，读者都会看到 ...->next 指向 E3。
  关键点：读者不会看到字符串处于部分更新的状态。

理解这一思想的好方法：
  对 E1->next 的更新是一次"提交写"。
  在此之前，一切看起来都没有改变。
  在此之后，所有修改都变得可见。
  RCU 最适合用于单次指针写入即可提交的数据结构。
    例如链表和树。

RCU 思想二：读者和写者必须使用内存屏障来保证顺序。
  我们不希望编译器或硬件将第 3 步或第 4 步移到第 5 步之后执行。
  写者必须在第 5 步之前设置一道屏障。
  读者需要在执行 Rx = E1->next 之后、
    解引用 Rx 以读取元素内容之前设置一道屏障。

写者释放链表元素时会发生什么？
  问题在于：读者可能正在访问即将被删除的元素。
  写者需要给读者留出时间来完成操作。
    即在它移除对该元素的可见引用之后。
    但写者应该等待多久？
  可以使用垃圾回收或引用计数，但代价较高。

RCU 思想三：
  1. 读者不允许在上下文切换期间持有指向 RCU 数据的指针。
     类似于自旋锁不能在上下文切换期间持有的规则。
  2. 写者推迟释放操作，直到所有 CPU 都完成了一次上下文切换。
  写者可能需要等待几毫秒，
    但前提假设是写操作很少发生。
  如何实现？
    简单方案：写者强制自己在每个 CPU 上被调度一次。
    （还有更高效的实现方式。）

Linux RCU 读者接口：
  rcu_read_lock()
  rcu_read_unlock()
  rcu_dereference(p)
写者接口：
  synchronize_rcu()
  call_rcu(fn,x)
  rcu_assign_pointer(pa, p)

rcu_read_lock/unlock 几乎不做任何事情。
  禁用定时器中断以防止抢占。
  因为上下文切换意味着已完成对 RCU 对象的使用。

synchronize_rcu() 可能耗时较长，并可让出 CPU。
call_rcu(fn,x) 立即返回；将 <fn,c> 添加到一个列表中。

使用 Linux RCU 接口的链表读者：
  rcu_read_lock()
  e = head
  while(p){
    e = rcu_dereference(e)
    look at e->x ...
    e = e->next
  }
  rcu_read_unlock()

注意：代码只能在 rcu_read_lock/unlock 内部使用 e！
  例如不能执行 return(e)

替换链表首元素的代码：

  acquire(lock)
  old = head
  e = alloc()
  e->x = ...
  e->next = head->next
  rcu_assign_pointer(&head, e)
  release(lock)

  synchronize_rcu()
  free(old)
      
RCU 与读写锁的性能对比？
  对于读者：
    RCU 对读操作的开销几乎为零。
    读写锁可能需要数百甚至数千个时钟周期（图5，上方曲线）。
    此外，RCU 可以在写操作进行期间同时执行读操作！
  对于写者：
    RCU 由于 synchronize_rcu() 可能需要更长的时间。
    因此，RCU 在写操作较少或对时间不敏感时更为合适。

示例：移除 NMI 处理程序；论文第 4.1 节；图 4。
  NMI 是无法被禁用的中断。
    用于 CPU 性能分析、关键硬件错误、看门狗定时器。
  内核代码可以注册在 NMI 期间被调用的处理程序。
  也可以注销处理程序，并释放包含代码的内存。
  NMI 频繁发生；注册/注销操作较少；因此读操作 >> 写操作。
  如果某个核心在调用注销时正处于 NMI 代码中，会发生什么？
  图 4 在 unregister_nmi_handler() 中的解决方案：
    1. 删除 NMI 处理程序链表条目（使后续中断不再看到它）。
    2. 调用 synchronize_rcu() 等待所有当前中断完成。
       因为一个核心在离开中断之前不会发生上下文切换。
    3. （未展示）释放保存 NMI 处理程序代码的内存。
  此示例使用 RCU 将内存释放推迟到所有使用结束之后。
  一个有趣的特殊之处：
    NMI 无法被禁用。
    因此自旋锁无法阻止 NMI。
    因此通常不允许 NMI 获取锁（否则会死锁……）。
    因此在这里，RCU 不仅比加锁对读者更快，
      而且在加锁无法工作的场景下也能正常运行。

示例：IP 选项；第 4.2 节；图 6。
  IP 数据包头可以包含选项（例如记录路由）。
  内核套接字有（可选的）选项，会被复制到每个发出的数据包中。
  发送代码（udp_sendmsg()）在不加锁的情况下复制套接字选项。
  选项的读取频率远高于写入频率 -> 适合使用 RCU。
  setsockopt() 通过 call_rcu(kfree,old) 延迟释放被替换的旧选项。
  为什么读取代码是安全的？
    1. 写者在发布指针之前完整地准备好新选项。
    2. 写者和读者都使用内存屏障。
    3. 写者将释放推迟到所有读取旧选项的读者都已完成之后。
  论文将此称为"引用计数"，但实际上并没有引用计数器。
    "垃圾回收"可能是一个更贴切的术语，
    因为其目标是在最后一个引用消失后才释放内存。
    
RCU 并非普遍适用。
  对写操作没有帮助。
  仅在读操作 >> 写操作时才能提升性能。
  不适用于必须在 yield/sleep 之间持有引用的代码。
    与自旋锁类似。
  如果数据结构不适合单次提交写入，则此方法不可行。
    例如，如果读者需要双向扫描双向链表。
    或者需要就地更新的情况。
  读者可能看到过时的数据。
    例如，图6中的 udp_sendmsg() 可能使用旧的 IP 选项发送数据。
    但仅在与 setsockopt() 并发时才会发生。
    在此处不是问题；少数情况下可能存在问题（论文中提到了 Sys V IPC）。
  RCU 增加了写者的复杂性。
    在网上搜索 "review checklist for RCU patches"
  RCU 需要上下文切换频繁发生，并且需要感知上下文切换的时机。
    在内核中较容易实现，对用户态线程则较难。

synchronize_rcu() 能否比"在每个 CPU 上调度"更高效？
  以下是一种设计方案，来自
    http://www2.rdrop.com/users/paulmck/RCU/rclockpdcsproof.pdf
    第 3.5.4 节
  每核心数据：
    该核心的上下文切换计数。
    等待中的 synchronize_rcu() 和 call_rcu() 列表。
  每隔一段时间，每个核心批量处理一整批 RCU 写者：
    保存当前列表，并将其清空。
    记录所有其他核心的计数。
    每次上下文切换时，重新检查其他核心的计数。
    若所有计数均已变化，则唤醒/运行已保存列表中的所有任务。

如果你有写操作频繁的共享数据，该怎么办？
  最佳方案：重新设计以消除共享。
  次佳方案：使用半私有的每核心分区。
  示例：锁实验中的 kalloc。
  示例：Linux 的每核心调度列表。
  示例：统计计数器。
    每个核心维护自己的计数，使用独立的自旋锁保护。
    写入时，获取本地锁，递增本地计数。
      若自旋锁仅在单个核心上使用，其开销很低。
    读取时，获取*所有*锁，读取并汇总所有计数。
      开销较大，但我们假设写操作是主要场景。
    
RCU 总结
  在加速对共享内核数据的读访问方面非常成功。
    广泛应用于现代 Linux。
  完全消除了读者的加锁开销。
  允许读者与写者并行执行。
  核心思想是类似 GC 的宽限期机制，用于延迟释放对象。
