6.S081 2020 第22讲：Meltdown

为什么要学这篇论文？
  安全是操作系统的核心目标
  内核的主要策略：隔离
    用户态/特权态模式、页表、防御性系统调用，等等
  值得研究一些出错的典型案例

Meltdown
  一种对用户态/内核隔离的令人惊讶且令人不安的攻击
  近年来"微架构"攻击之一
    利用 CPU 隐藏的实现细节
  可以修复，但人们担忧此类相关漏洞会层出不穷

攻击的核心如下：
  char buf[8192]
  r1 = <a kernel virtual address>
  r2 = *r1
  r2 = r2 & 1
  r2 = r2 * 4096
  r3 = buf[r2]

以上代码从用户态代码中执行。

r2 最终会持有来自内核的数据吗？

假设内核已映射到用户态页表中，且 PTE_U 位被清除。
  在这些攻击被发现之前，这种做法几乎是普遍存在的。
  内核位于地址空间上半部分（高位置位），用户态位于下半部分（从零开始）。
  同时映射用户态和内核可以显著加快系统调用的速度。
  关键点：*r1 是有意义的，即使访问是被禁止的。

那么这段代码对攻击者究竟有何用处？
  答案与一系列大多隐藏的 CPU 实现细节有关。
  推测执行，以及缓存。

首先，谈谈推测执行。
  这部分暂时与安全无关。
  设想如下这段普通代码。
  这是类 C 代码；"r0" 等为寄存器，"*r0" 表示内存引用。

  r0 = <something>
  r1 = valid    // r1 is a register; valid is in RAM
  if(r1 == 1){
    r2 = *r0
    r3 = r2 + 1
  } else {
    r3 = 0
  }

  "r1 = valid" 可能需要从 RAM 加载数据，耗费数百个时钟周期。
  "if(r1 == 1)" 需要等待该数据就绪。
  如果 CPU 必须暂停直到 RAM 读取完成，那将大大降低效率。
  因此，CPU 会预测分支最可能走哪条路，
    并继续执行。
  这称为"推测执行"（speculation）。
  因此 CPU 可能会执行 "r2 = *r0"，
    然后执行 "r3 = r2 + 1"。

如果 CPU 错误预测了分支，例如 r1 == 0，会怎样？
  它会丢弃错误推测的结果。
  具体来说，CPU 会撤销 r2 和 r3 的内容。
  并在 "else" 分支重新开始执行。

推测执行对性能有极大提升，因为它
  允许 CPU 获得大量并行性——将
  耗时指令（除法、内存加载等）与后续
  指令重叠执行。

如果 CPU 推测执行了分支的前半部分，
  而 r0 持有一个非法指针，会怎样？
  若 valid == 1，"r2 = *r0" 应当触发异常。
  若 valid == 0，"r2 = *r0" 即使在推测执行时
    也不应触发异常。

CPU 只有在确认指令无需因错误推测而取消后，
  才会"提交"（retire）该指令。
  并且 CPU 按顺序提交指令，只有在所有
    先前指令都已提交之后才提交当前指令，因为只有到那时
    才能确认之前没有指令发生故障。
因此，由推测执行的指令所引发的故障，
  可能在该指令执行完成后过一段时间才会出现。

推测执行在原则上是不可见的——属于 CPU 实现细节，
  而非规范的一部分。
  也就是说，推测执行旨在提升性能，
    而不改变程序的计算结果——即对程序透明。
一些术语：
  "体系结构特性"（Architectural features）——CPU 手册中有记载，对程序员可见。
  "微体系结构"（Micro-architectural）——不在手册中，设计上对程序员不可见。

另一个微体系结构特性：CPU 缓存。
  core
  L1: va | data | perms
  TLB
  L2: pa | data
  RAM
如果加载缺失，数据将被取出并放入缓存。
L1（"一级"）缓存使用虚拟地址索引，以提高速度。
  一次系统调用在返回用户态后，会将内核数据留在 L1 缓存中。
  （假设页表同时包含用户和内核的映射）
每个 L1 缓存条目可能包含 PTE 权限位的副本。
L1 缺失时：进行 TLB 查找，再以物理地址查找 L2。
耗时：
  L1 命中 —— 数个时钟周期。
  L2 命中 —— 十几到二十几个时钟周期。
  RAM —— 300 个时钟周期。
  一个时钟周期为 1/时钟频率，例如 0.5 纳秒。

为什么在缓存中同时保存内核和用户数据是安全的？
  用户程序能直接从缓存中读取内核数据吗？

在现实中，微架构并非不可见。
  它会影响指令和程序的执行时间。
  编写性能敏感代码的人对此极为关注。
  编译器开发者也同样关注。
  Intel 等厂商发布了优化指南，但通常对细节语焉不详。

一个实用技巧：检测某内容是否已被缓存。
  这就是论文中的 Flush+Reload 方法。
  你想知道函数 f() 是否访问了地址 X 处的内存。
  1) 确保地址 X 处的内存未被缓存。
     Intel CPU 提供了 clflush 指令。
     或者可以加载足够多的无关内存，强制将其他内容从缓存中逐出。
  2) 调用 f()
  3) 记录当前时间。
     现代 CPU 允许你读取时钟周期计数器。
     对于 Intel CPU，使用 rdtsc 指令。
  4) 从地址 X 加载一个字节
     （需要内存屏障以确保加载真正发生）
  5) 再次记录当前时间。
  6) 如果两次时间之差 < （例如）50，则第 #4 步的加载命中缓存，
     这意味着 f() 必定访问了地址 X 处的内存。
     否则则未访问。

回到 Meltdown —— 这次更详细地介绍：

  char buf[8192]

  // the Flush of Flush+Reload
  clflush buf[0]
  clflush buf[4096]

  <some expensive instruction like divide>

  r1 = <a kernel virtual address>
  r2 = *r1
  r2 = r2 & 1      // 推测执行
  r2 = r2 * 4096   // 推测执行
  r3 = buf[r2]     // 推测执行

  <处理来自 "r2 = *r1" 的缺页故障>

  // Flush+Reload 中的 Reload 阶段
  a = rdtsc
  r0 = buf[0]
  b = rdtsc
  r1 = buf[4096]
  c = rdtsc
  if b-a < c-b:
    低位很可能为 1

也就是说，你可以根据哪条缓存行被加载（buf[0] 还是 buf[4096]）
推断出内核数据的低位。
    
要点：来自 "r2 = *r1" 的故障会延迟到该加载指令退休时才触发，
  这可能需要一段时间，从而为后续的推测执行指令
  提供了运行的机会。

要点：显然 "r2 = *r1" 会实际执行加载操作，尽管这是
  非法的，并将结果暂时写入 r2，但在指令退休时
  因故障而被回滚。

要点："r3 = buf[r2]" 将 buf[] 的部分内容加载到缓存中，
  即使对 r3 的修改因推测执行失误而被取消。
  这是因为 Intel 将缓存内容视为隐藏的微架构状态。

该攻击往往不能成功
  清单 3/4 中每个 XX 均表示一次失败
    为什么会失败？为何失败如此频繁？
  第 6.2 节指出，若内核数据未被缓存，读取速度仅为 10 字节/秒
    重试有帮助——为什么？
    可能需要数千次重试——为什么？
  成功所需的条件尚不明确。
  若内核数据在 L1 缓存中则攻击可能稳定奏效，否则则不然。

Meltdown 如何被用于现实世界的攻击？
  攻击者需要能在目标机器上运行自己的代码。
  分时系统：内核可能持有其他用户的敏感信息，例如密码、密钥。
    这些信息可能在 I/O 或网络缓冲区中，或者内核映射了物理内存。
  云环境：某些容器和虚拟机监控器（VMM）系统可能存在漏洞，
    攻击者可借此窃取其他云租户的数据。
  你的浏览器：它在沙箱中运行不受信任的代码，例如插件，
    某个插件可能会从你的内核中窃取你的密码。

然而，Meltdown 目前尚未被发现用于任何实际攻击。

防御措施有哪些？

软件修复方案：
  不在用户页表中映射内核。
    该论文将此称为"KAISER"；Linux 现在称其为 KPTI。
  每次系统调用进入/退出时需要进行页表切换。
    这就是 RISC-V xv6 的工作方式。
  页表切换可能较慢——可能需要刷新 TLB。
    PCID 可以避免刷新 TLB，但仍有一定开销。
  大多数内核在 Meltdown 被披露后不久便采用了 KAISER/KPTI。

硬件修复方案：
  投机加载时仅返回允许访问的数据！
    若 PTE_U 位未置位，则返回零，而非实际数据。
  这可能几乎没有代价，因为显然每条 L1
    缓存行都包含来自 PTE 的 PTE_U 位的副本。
  AMD CPU 显然一直以来都是这样工作的。
  最新的 Intel CPU 似乎也采用了这一做法（称为 RDCL_NO）。

这些防御措施已被部署，并被认为是有效的；但：
  令人不安的是，页保护机制竟然并不牢固！
  更多微架构层面的意外问题正在不断浮现。
  这一根本问题究竟只是可修复的漏洞？还是设计策略上的失误？
  请持续关注，此事仍在持续演进中。
