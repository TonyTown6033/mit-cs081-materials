崩溃
  对用户/内核隔离的令人惊讶且令人不安的攻击
  最近发生的一系列“微架构”攻击之一
    利用 CPU 隐藏的实现细节
  可以修复，但人们担心相关意外的无限供应

这是攻击的核心：
  字符缓冲区[8192]
  r1 = <内核虚拟地址>
  r2 = *r1
  r2 = r2 & 1
  r2 = r2 * 4096
  r3 = buf[r2]

从用户代码执行。

r2 最终会保存来自内核的数据吗？

假设内核映射到用户页表中，且 PTE_U 清零。
  在这些攻击被发现之前，这种情况几乎是普遍存在的。
  内核在上半部分（高位设置），用户在下半部分（从零开始）。
  映射用户和内核使系统调用速度显着加快。
  要点： *r1 是有意义的，即使被禁止。

那么这段代码怎么可能对攻击者有用呢？
  答案与一堆几乎隐藏的 CPU 实现细节有关。
  推测执行和缓存。

首先，投机执行。
  这还不是安全问题。
  想象一下这个普通的代码。
  这是类似 C 的代码； “r0”和c是寄存器，“*r0”是内存引用。

  r0 = <某物>
  r1 = valid // r1 是一个寄存器；有效在 RAM 中
  if(r1 == 1){
    r2 = *r0
    r3 = r2 + 1
  } 否则{
    r3 = 0
  }

  “r1 = valid”可能需要从 RAM 加载，需要 100 个周期。
  The "if(r1 == 1)" needs that data.
  如果 CPU 必须暂停直到 RAM 读取完成，那就太糟糕了。
  相反，CPU 会预测分支可能走向哪个方向，
    并继续执行。
  这就是所谓的“投机”。
  所以CPU可能会执行“r2 = *r0”，
    然后是“r3 = r2 + 1”。

What if the CPU mis-predicts a branch, e.g. r1 == 0?
  它冲掉了错误推测的结果。
  具体来说，CPU 恢复 r2 和 r3 的内容。
  并在“else”分支中重新开始执行。

推测执行对于性能来说是一个巨大的胜利，因为它
  让CPU获得大量的并行性——重叠
  长指令（除法、内存加载等）以及后续指令
  instructions.

如果 CPU 推测执行了第一部分怎么办？
  分支，并且 r0 持有非法指针？
  If valid == 1, the "r2 = *r0" should raise an exception.
  If valid == 0, the "r2 = *r0" should not raise an
    异常，即使是推测执行的。

CPU 仅在确定指令后才“退休”指令
  不会因为错误猜测而被取消。
  并且CPU按顺序退役指令，毕竟
    以前的指令已经失效，因为只有那时它才
    知道之前的指令没有错误。
因此，推测性指令的错误
  执行可能要等到指令完成后一段时间才会发生。

原则上，推测是不可见的——CPU 实现的一部分，
  但不是规范的一部分。
  也就是说，投机的目的是为了提高性能，而不需要
    改变程序计算的结果——使其透明。
一些行话：
  “架构特性”——CPU手册中的东西，程序员可见。
  “微架构”——手册中没有，旨在隐形。

另一个微架构特征：CPU 缓存。
  核心
  L1：VA |数据|烫发
  TLB
  L2: 帕 |数据
  内存
如果加载失败，则会获取数据并将其放入缓存中。
L1（“一级”）缓存实际上是索引的，以提高速度。
  系统调用返回用户空间后，将内核数据保留在一级缓存中。
  （假设页表有用户和内核映射）
每个 L1 条目可能包含 PTE 权限位的副本。
L1 缺失时：TLB 查找、使用 phys addr 进行 L2 查找。
Times:
  L1 命中——几个周期。
  L2 命中——十几个或两个周期。
  RAM——300 个周期。
  一个周期是 1/时钟频率，例如 0.5 纳秒。

为什么缓存中的内核数据和用户数据都是安全的？
  用户程序可以直接从缓存中读取内核数据吗？

在现实生活中，微建筑并不是看不见的。
  它影响指令和程序花费的时间。
  编写性能关键代码的人们对此非常感兴趣。
  以及编译器作者。
  英特尔&c发布优化指南，通常对细节含糊其辞。

一个有用的技巧：感知某些内容是否被缓存。
  这就是本文的Flush+Reload。
  您想知道函数 f() 是否使用地址 X 处的内存。
  1）确保X处的内存没有被缓存。
     Intel CPU 有一个 clflush 指令。
     或者您可以加载足够的垃圾内存以强制将其他所有内容从缓存中移出。
  2）调用f()
  3）记录时间。
     现代 CPU 允许您读取周期计数器。
     对于 Intel CPU，它是 rdtsc 指令。
  4）从地址X加载一个字节
     （你需要内存栅栏来确保负载确实发生）
  5) 再次记录时间。
  6) 如果时间差 <（例如）50，则 #4 中的负载达到，
     这意味着 f() 必须使用地址 X 处的内存。
     否则不会。

  // the Flush of Flush+Reload

  clflush 缓冲区[4096]

  a = rdtsc
  r0 = 缓冲区[0]
  b = rdtsc
  r1 = buf[4096]

  如果 b-a < c-b：

即可以根据该数据推导出内核数据的低位
加载了两个缓存行（buf[0] 与 buf[4096]）。
  
要点：“r2 = *r1”的故障被延迟到负载退出，
  这可能需要一段时间，为后续的投机留出时间
  执行的指令。

要点：显然“r2 = *r1”完成了负载，即使它是
  非法，并将结果放入 r2，尽管只是暂时的，因为
  退休时因过失而恢复。

要点：“r3 = buf[r2]”将一些 buf[] 加载到缓存中，
  即使由于错误推测而取消了对 r3 的更改。
  由于英特尔将缓存内容视为隐藏的微架构。

Meltdown 如何用于现实世界的攻击？
  攻击者需要在受害者机器上运行他们的代码。
  分时：内核可能有其他用户的秘密，例如密码、密钥。
    在 I/O 或网络缓冲区中，或者可能是内核映射物理内存。
  云：某些容器和 VMM 系统可能容易受到攻击，
    这样您就可以从其他云客户那里窃取数据。
  您的浏览器：它在沙箱中运行不受信任的代码，例如插件，

然而，Meltdown 尚未被用于任何实际攻击中。

防御呢？

软件修复：
  不要将内核映射到用户页表中。
    该报称此为“KAISER”； Linux 现在将其称为 KPTI。
  每个系统调用入口/出口都需要页表切换。
    这就是 RISC-V xv6 的工作原理。
  页表切换可能会很慢——它可能需要 TLB 刷新。
    PCID 可以避免 TLB 刷新，尽管仍然需要一些费用。
  Meltdown 出现后不久，大多数内核就采用了 KAISER/KPTI。

硬件修复：
  仅从推测负载返回允许的数据！
    如果 PTE_U 清零，则返回零，而不是实际数据。
  这可能几乎没有成本，因为显然每个 L1
    缓存行包含 PTE 中 PTE_U 位的副本。
  AMD CPU 显然一直都是这样工作的。
  最新的 Intel CPU 似乎可以做到这一点（称为 RDCL_NO）。
