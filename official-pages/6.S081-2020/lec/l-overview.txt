6.S081 2020 第1讲：操作系统概述

概述

* 6.S081 课程目标
  * 理解操作系统（O/S）的设计与实现
  * 亲手实践，扩展一个小型操作系统
  * 亲手实践，编写系统软件

* 操作系统的目的是什么？
  * 对硬件进行抽象，以提升易用性和可移植性
  * 在多个应用程序之间复用硬件资源
  * 对应用程序进行隔离，以限制错误的影响范围
  * 允许协作应用程序之间共享资源
  * 控制共享以保障安全性
  * 不阻碍高性能的实现
  * 支持多种多样的应用程序

* 组织结构：分层示意图
  [user/kernel diagram]
  - 用户应用程序：vi, gcc, DB, &c
  - 内核服务
  - 硬件：CPU, RAM, disk, net, &c
  * 我们非常关注接口设计以及内核的内部结构

* 操作系统内核通常提供哪些服务？
  * 进程（正在运行的程序）
  * 内存分配
  * 文件内容
  * 文件名、目录
  * 访问控制（安全性）
  * 其他许多服务：用户、IPC、网络、时间、终端

* 应用程序与内核之间的接口是什么？
  * "系统调用"
  * 示例，以 C 语言编写，来自 UNIX（如 Linux、macOS、FreeBSD）：

            fd = open("out", 1);
            write(fd, "hello\n", 6);
            pid = fork();

  * 这些看起来像函数调用，但实际上并不是

* 为什么操作系统的设计与实现既困难又有趣？
  * 环境严苛：硬件行为怪异，难以调试
  * 存在诸多设计上的权衡：
    - 高效性 vs 抽象性/可移植性/通用性
    - 功能强大 vs 接口简洁
    - 灵活性与安全性
  * 功能之间存在交互：`fd = open(); fork()`
  * 使用场景多样：笔记本电脑、智能手机、云计算、虚拟机、嵌入式系统
  * 硬件持续演进：NVRAM、多核处理器、高速网络

* 如果你有以下情况，你会庆幸自己选了这门课……
  * 对底层运行机制感兴趣
  * 喜欢基础设施
  * 需要追踪调试错误或安全问题
  * 关注高性能

UNIX 系统调用简介

* 应用程序通过系统调用与操作系统交互，该接口将是本课程的重点。
  我们先来看看程序如何使用系统调用。
  你将在第一个实验中使用这些系统调用。
  并在后续实验中对其进行扩展和改进。

* 我将展示一些示例，并在 xv6 上运行它们。
  xv6 与 Linux 等 UNIX 系统结构相似，
  但简单得多——你将能够完整理解 xv6
    配套教材解释了 xv6 的工作原理及其设计原因
  为什么选择 UNIX？
    开源、文档完善、设计简洁、广泛使用
    学习 xv6 将有助于你日后深入了解 Linux 内部机制
  xv6 在 6.S081 中承担两个角色：
    核心功能示例：虚拟内存、多核、中断等
    大多数实验的起点
  xv6 运行在 RISC-V 上，与当前 6.004 课程一致
  你将在 qemu 机器模拟器中运行 xv6

* 示例：copy.c，将输入复制到输出
  从输入读取字节，并将其写入输出
  $ copy
  copy.c 使用 C 语言编写
    Kernighan and Ritchie（K&R）一书非常适合学习 C 语言
  你可以通过网站上的课程安排找到这些示例程序
  read() 和 write() 是系统调用
  read()/write() 的第一个参数是"文件描述符"（fd）
    传递给内核，用于指定要读写的"已打开文件"
    该文件描述符必须事先已被打开
    一个 FD 连接到文件/设备/socket 等
    一个进程可以打开多个文件，拥有多个 FD
    UNIX 惯例：fd 0 为"标准输入"，1 为"标准输出"
  read() 的第二个参数是指向用于存放读取数据的内存区域的指针
  第三个参数是最多读取的字节数
    read() 实际读取的字节数可能少于该值，但不会超过
  返回值：实际读取的字节数，出错时返回 -1
  注意：copy.c 不关心数据的格式
    UNIX I/O 以 8 位字节为单位
    数据的解释由应用程序决定，例如数据库记录、C 源码等
  文件描述符从何而来？

* 示例：open.c，创建一个文件
  $ open
  $ cat output.txt
  open() 创建一个文件，返回文件描述符（出错时返回 -1）
  FD 是一个小整数
  FD 是内核为每个进程维护的表中的索引
  [用户态/内核态示意图]
  不同进程拥有各自独立的 FD 命名空间
    即 FD 1 对不同进程往往代表不同的含义
  这些示例忽略了错误处理——实际编程中切勿如此粗心！
  xv6 教材图 1.2 列出了系统调用的参数与返回值
    或查阅 UNIX man 手册，例如 "man 2 open"

* 当程序调用 open() 等系统调用时会发生什么？
  看起来像函数调用，但实际上是一条特殊指令
  硬件保存部分用户寄存器
  硬件提升特权级别
  硬件跳转到内核中已知的"入口点"
  现在在内核中运行 C 代码
  内核调用系统调用的具体实现
    open() 在文件系统中查找文件名
    可能会等待磁盘
    更新内核数据结构（缓存、文件描述符表）
  恢复用户寄存器
  降低特权级别
  跳回程序中的调用点，程序继续执行
  课程后续会详细介绍

* 我一直在使用 UNIX 的命令行界面——shell。
  shell 打印 "$" 提示符。
  shell 允许你运行 UNIX 命令行工具
    适用于系统管理、文件操作、开发和脚本编写
    $ ls
    $ ls > out
    $ grep x < out
  UNIX 也支持其他交互方式
    窗口系统、图形界面、服务器、路由器，等等。
  但通过 shell 进行分时操作是 UNIX 最初的核心功能。
  我们可以通过 shell 来实际使用许多系统调用。

* 示例：fork.c，创建一个新进程
  shell 为你输入的每条命令创建一个新进程，例如：
    $ echo hello
  fork() 系统调用用于创建新进程
    $ fork
  内核复制调用进程的内容
    包括指令、数据、寄存器、文件描述符、当前目录
    称为"父"进程和"子"进程
  唯一区别：fork() 在父进程中返回 pid，在子进程中返回 0
  pid（进程 ID）是一个整数，内核为每个进程分配不同的 pid
  因此：
    fork.c 中的 "fork() returned" 会在*两个*进程中都执行
    通过 "if(pid == 0)" 可以区分两个进程中的代码
  好的，fork 让我们可以创建新进程
    那如何在该进程中运行一个程序呢？

* 示例：exec.c，用可执行文件替换当前调用进程
  shell 是如何运行一个程序的，例如：
    $ echo a b c
  程序存储在文件中：包含指令和初始内存内容
    由编译器和链接器生成
  所以有一个叫 echo 的文件，其中包含指令
  $ exec
  exec() 用一个可执行文件替换当前进程
    丢弃指令和数据内存
    从文件中加载指令和内存
    保留文件描述符
  exec(filename, argument-array)
    argument-array 保存命令行参数；exec 将其传递给 main()
    cat user/echo.c
    echo.c 展示了程序如何查看其命令行参数

* 示例：forkexec.c，fork() 一个新进程，exec() 一个程序
  $ forkexec
  forkexec.c 包含一种常见的 UNIX 惯用写法：
    fork() 一个子进程
    在子进程中 exec() 一个命令
    父进程 wait() 等待子进程结束
  shell 对你输入的每条命令都执行 fork/exec/wait
    wait() 返回后，shell 打印下一个提示符
    若要在后台运行——&——shell 跳过 wait()
  exit(status) -> wait(&status)
    状态约定：0 = 成功，1 = 命令遇到错误
  注意：fork() 会复制内存，但 exec() 会丢弃已复制的内存
    这看起来可能有些浪费
    你将在"写时复制"实验中透明地消除这次复制

* 示例：redirect.c，重定向命令的输出
  shell 对此会做什么？
    $ echo hello > out
  答：fork，在子进程中修改 FD 1，exec echo
  $ redirect
  $ cat output.txt
  注意：open() 总是选择最小的未使用 FD；由于 close(1)，结果为 1。
  fork、FD 和 exec 良好地协作以实现 I/O 重定向
    先 fork 后 exec 的方式让子进程有机会在 exec 之前修改 FD
    FD 提供了间接性
      命令只使用 FD 0 和 1，无需知道它们具体指向哪里
    exec 保留了 sh 设置好的 FD
  因此：只有 sh 需要了解 I/O 重定向，而不是每个程序都需要

* 值得追问设计决策背后的"为什么"：
  为什么是这些 I/O 和进程抽象？为什么不用其他方式？
  为什么要提供文件系统？为什么不让程序以自己的方式使用磁盘？
  为什么用 FD？为什么不直接把文件名传给 write()？
  为什么文件是字节流，而不是磁盘块或格式化记录？
  为什么不把 fork() 和 exec() 合并？
  UNIX 的设计运行良好，但我们将会看到其他设计方案！

* 示例：pipe1.c，通过管道通信
  shell 如何实现
    $ ls | grep x
  $ pipe1
  一个文件描述符（FD）可以指向"管道"，也可以指向文件
  系统调用 pipe() 创建两个文件描述符
    从第一个文件描述符读取
    向第二个文件描述符写入
  内核为每个管道维护一个缓冲区
    [用户态/内核态示意图]
    write() 将数据追加到缓冲区
    read() 等待直到有数据可读

* 示例：pipe2.c，在进程间通信
  管道与 fork() 配合良好，可用于实现 ls | grep x
    shell 创建一个管道，
    然后（两次）调用 fork()，
    再将 ls 的文件描述符 1 连接到管道的写端，
    并将 grep 的文件描述符 0 连接到管道的读端
    [示意图]
  $ pipe2 -- 一个简化版本
  管道是一种独立的抽象，但与 fork() 配合使用效果很好

* 示例：list.c，列出目录中的文件
  ls 如何获取目录中的文件列表？
  可以打开一个目录并读取它 -> 文件名
  "." 是进程当前目录的伪名称
  更多细节请参见 ls.c

  * 这些抽象可以很好地组合使用，例如用于 I/O 重定向。
