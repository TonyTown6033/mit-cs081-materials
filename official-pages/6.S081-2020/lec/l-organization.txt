6.S081 2020 L18：操作系统组织结构，微内核

主题：
  内核应该做什么？
  它的抽象接口／系统调用应该是什么样的？

答案取决于具体应用场景和程序员的偏好！
  没有唯一的最佳答案
  本话题更侧重于思想，而非具体机制

传统方法
  1) 强大的抽象，以及
  2) "宏内核"实现
  UNIX、Linux、xv6

传统内核背后的理念是强大的抽象：
  可移植接口
    文件，而非磁盘控制器寄存器
    地址空间，而非直接访问 MMU
  隐藏复杂性的简单接口
    所有 I/O 通过文件描述符和 read/write 进行，而非针对每种设备单独处理等
    支持透明磁盘换页的地址空间
  抽象帮助内核管理和共享资源
    进程抽象使内核负责调度
    文件/目录抽象使内核负责磁盘布局
  抽象帮助内核实施安全策略
    文件权限
    具有私有地址空间的进程
  大量间接层
    例如文件描述符、虚拟地址、文件名、PID
    帮助内核实现虚拟化、隐藏、撤销、调度等功能

强大的抽象催生了庞大的"宏内核"
  内核是一个大型程序，如 xv6
  内核子系统之间易于协作——无烦人的边界限制
    exec() 和 mmap() 同时属于文件系统和虚拟内存系统
    相对容易添加符号链接、写时复制 fork、mmap 等功能
  所有内核代码以高特权级运行——内部无安全限制

传统内核的问题是什么？
  体积大 => 复杂 => 存在缺陷/不安全
  可能过于通用，因而性能较低
    通过 UNIX 管道发送一个字节需要执行多少代码？
    缓冲、锁、睡眠/唤醒、调度器
  许多设计决策已固化，无法更改，可能带来不便
    也许我想等待一个不是我子进程的进程
    也许我想修改另一个进程的地址空间
    也许数据库在磁盘上布局 B 树文件比内核文件系统做得更好
  难以创建可供他人使用的内核"扩展"
    新的设备驱动、文件系统等

微内核 —— 另一种方法
  核心思想：将大部分操作系统功能移至用户态服务进程
  [图示：硬件、内核、服务（文件系统 磁盘 虚拟内存 TCP 网卡 显示），应用程序]
  内核可以很小
    地址空间、线程、IPC（进程间通信）
    IPC 允许线程相互发送消息
  20 世纪 80 年代掀起了微内核设计研究的热潮
    CMU 的 Mach 或许是影响最为深远的
  如今用于嵌入式系统、手机芯片、车载娱乐系统
  其理念（尤其是用户态服务器和 IPC）对 Windows 和 MacOS 等系统产生了深远影响

为什么对微内核感兴趣？
  专注、优雅、全新设计
  体积小 -> 安全性更高 —— 代码越少，可被利用的漏洞越少
  体积小 -> 可验证（参见 seL4）
  体积小 -> 更易于优化
    无需为用不到的功能付出代价
  体积小 -> 避免将设计决策强加于应用程序
  用户态 -> 有助于推动操作系统服务的模块化
  用户态 -> 更易于扩展/定制/替换用户态服务
  用户态 -> 更健壮 —— 可单独重启各用户态服务
    大多数漏洞存在于驱动中，将它们移出内核！
  可运行/模拟多个操作系统，类似虚拟机监控器

微内核的挑战
  最小内核 API 是什么？
  需要简单的原语来构建 exec、fork、mmap 等
  需要在用户态构建操作系统的其余部分
  如何在使用 IPC 且集成度较低的情况下仍获得良好性能？

L4
  历经多次演进，衍生出许多版本和重新实现
  如今在手机和嵌入式控制器中已商业化应用
  是微内核方法的典型代表
  强调最小化原则：
    7 个系统调用（Linux 有 300 个以上，xv6 有 21 个）
    13,000 行代码

L4 基本抽象
  [图示]
  地址空间（"任务"）
  线程
  IPC

L4 系统调用：
  创建地址空间
  在[另一个]地址空间中创建/销毁线程
  通过 IPC 发送/接收消息（地址为线程 ID）
  将你的内存页映射到另一个地址空间
    必须经过对方同意
    这通过 IPC 实现 —— 一个任务可以修改另一个任务的页表
    用于创建新任务、共享内存
  拦截另一个地址空间的缺页异常 —— "pager"
    内核通过 IPC 传递
  访问设备硬件（不是系统调用，直接发生）
  处理设备中断
    内核通过 IPC 传递

注意：L4 内核几乎缺少 Linux 乃至 xv6 所具备的一切
  file system, fork(), exec(), pipes, device drivers, network stack, &c
  如果需要这些功能，必须以用户态代码实现
    库或服务进程

L4 的线程切换是如何工作的？
  当前用户态线程因以下 3 种原因主动让出 CPU：
    IPC 系统调用等待
    定时器中断
    yield() 系统调用
  L4 内核保存用户线程寄存器，
    选取一个 RUNNABLE 线程运行，
    恢复用户寄存器，
    切换页表，
    跳转至用户态
  没有什么出人意料的地方

L4 外部 pager 是如何工作的？
  每个任务都有一个 pager 任务
  1. 发生缺页异常
  2. 内核挂起该线程
  3. 内核通过 IPC 将缺页信息发送给 pager
  4. pager 从自身页面中选取一页
  5. pager 通过 IPC 回复将虚拟页地址发送给缺页线程
  6. 内核拦截 IPC，将目标页映射进去，恢复目标线程

L4 pager 可以用来做什么？
  分配内存 —— "sigma0" 在缺页时为早期任务按需分配
  写时复制 fork
    配合一个撤销访问权限的系统调用使用
  文件的 mmap

问题：IPC 性能
  微内核程序会进行大量 IPC 操作！
  在早期系统中开销极大
    多次内核穿越、TLB 缺失、上下文切换等
  IPC 的开销使许多人对微内核持否定态度
  L4 的设计者在 IPC 性能上投入了大量精力

以下是一种低效的 IPC 设计
  以 UNIX 管道为原型
  [图示：内核中的消息队列]
  send(id, msg)
    将 msg 追加到内核中的队列，然后返回
  recv(&id, &data)
    若队列中有待处理消息，则取出并返回
    否则调用 sleep()
  称为"异步"且"带缓冲"的方式
  现在常见的请求-响应模式（RPC）涉及：
    [图示：用于回复的第二条消息队列]
    4 次系统调用（用户态->内核->用户态）
      send() -> recv()
      recv() <- send
      每次调用都可能破坏 CPU 的缓存（TLB、数据缓存、指令缓存）
    四次消息拷贝（请求两次，回复两次）
    两次上下文切换，两次通用调度

L4 的快速 IPC
  "Improving IPC by Kernel Design," Jochen Liedtke, 1993
  * 同步方式
    [图示]
    send() 等待目标线程执行 recv()
    常见情况：目标线程已在 recv() 中等待
    send() 直接跳转到目标线程的用户态，如同从 recv() 返回
      无真正的上下文切换，无调度器循环
  * 无缓冲
    内核中无消息队列
    由于是同步方式，内核可直接在用户缓冲区之间拷贝数据
  * 小消息通过寄存器传递
    内核 send() 路径不会破坏大多数寄存器
      例如，无上下文切换
    小消息无需拷贝
      因为 send() 连同寄存器一起跳转到目标线程的用户态
  * 大消息以虚拟内存授权方式传递
    同样无需拷贝，但内核 send() 代码必须修改页表
  * 合并 call() 与 sendrecv() 系统调用
    [图示]
    IPC 几乎总是以请求-响应 RPC 的形式使用
    因此分别使用 send() 和 recv() 系统调用较为浪费
    客户端：call()：发送消息并等待响应
    服务端：sendrecv()：回复一个请求后等待下一个请求
    用户态/内核穿越次数减少 2 倍
  * 精心布局内核代码以最小化缓存占用
  结果：IPC 开销降低 20 倍

如何在微内核上构建完整的操作系统？
  记住，其思路是将大多数功能移入用户态服务器。
    文件系统、设备驱动、网络栈、进程控制等
  对于嵌入式系统，这可以相当简单。
  那么面向通用场景（如工作站、Web 服务器）的服务呢？
  真正需要与现有应用程序保持兼容性。
    例如，系统需要模拟类似 UNIX 的接口。
  将 UNIX 内核服务重新实现为大量用户态服务？
  或者：将现有的 Linux 内核作为一个进程运行在微内核之上。
    即"操作系统服务器"。
    也许不够优雅，但切实可行。
    这是走向普及的一条路径：
      用户可以从直接运行 Linux 应用开始。
      然后逐步利用底层微内核的各种可能性。

这引出了我们今天的论文：
  "The Performance of micro-Kernel-Based Systems",
  by Hartig et al, 1997

基本架构
  [diagram]
  L4 kernel
  Linux kernel server
  每个 Linux 进程对应一个 L4 任务
  系统调用通过 IPC 完成

在用户态运行 Linux 内核意味着什么？
  Linux 内核不过是一个程序！
  作者以多种方式修改了 Linux，
    将硬件访问替换为 L4 系统调用或 IPC。
  进程创建、配置用户页表、内存分配、
    系统调用处理、中断处理。

L4/Linux 对线程的使用
  每个 Linux 进程的用户代码拥有一个或多个 L4 线程
  Linux 服务器只有一个 L4 线程（加上等待中断的 L4 线程）
    空闲时等待携带系统调用的 IPC
  Linux 服务器在其各进程的内核线程之间切换自身的 L4 线程
    例如，文件系统代码调用 sleep() 等待磁盘读取时
    或 pipe 的 read() 调用 sleep() 等待写入时
    与 xv6 在内核线程间切换的方式类似。
  但 L4/Linux 的内核线程切换
    与用户进程切换无关
  相反，L4 单独在可运行的 L4 线程之间切换，
    这些线程实现了各个 Linux 进程
  因此 Linux 内核服务器可以在运行进程 P1 的内核线程的同时，
    当 L4 在另一个核心上运行进程 P2 时

为何不使用 L4 线程来实现 Linux 服务器的内核线程？
  因为这样做只会带来麻烦，没有任何好处。
  会在 Linux 内部引入并行性。
    但 Linux 2.0 不支持 SMP —— 例如没有自旋锁。
  而且他们的硬件只有一个核心，因此无论如何都不会有并行加速。

缺点：L4 负责调度用户线程
  因此 L4/Linux 无法强制执行 Linux 的优先级等概念

L4/Linux 服务器将所有用户内存映射到其地址空间中
  （实际上，它分配大量内存，然后将自身的内存交给用户进程使用）
  用于 copyin()/copyout()，以便从系统调用中解引用用户指针
  这使系统调用 IPC 保持精简 —— 传递数据地址，而非数据本身
  Linux 服务器还利用其内存访问来实现 fork() 和 exec()

示例：fork() 是如何工作的？
  进程 P1 调用 fork()（P1 实际上是一个 L4 任务）
  P1 的 libc 库将 fork() 转换为发往 L4/Linux 服务器的 IPC
  L4/Linux 请求 L4 创建一个新任务和线程 —— P2
  L4/Linux 分配内存页（数量与 P1 拥有的相同）
  L4/Linux 通过 IPC 通知 L4 将页面映射到 P2
  L4/Linux 将数据从 P1 的页面复制到 P2 的页面
  L4/Linux 向 P2 发送携带 SP 和 PC 的特殊 IPC，使其开始运行
  L4/Linux 通过 IPC 向 P1 发送回复

L4/Linux 服务器充当用户进程的分页器
  因此 L4 将进程的页错误转换为发往 Linux 服务器的 IPC
  用于例如写时复制 fork、惰性分配、内存映射文件等

缺点：L4 不允许直接控制页表
  因此 Linux 服务器无法切换其页表以包含用户虚拟地址
  直到近期 Linux 才使用此技巧来提升性能（避免页表切换），
    并便于解引用系统调用参数

L4/Linux 服务器直接使用 Linux 设备驱动，无需修改！
  因为 L4 允许其直接访问设备寄存器
  只是中断通过 L4 IPC 传递

目前的现状如何？
  微内核有时用于嵌入式计算
    微控制器、Apple "enclave" 处理器
    运行定制软件
  微内核本身从未在通用计算领域流行起来
    没有令人信服的理由说明为何要从 Linux 等系统切换过来
  微内核研究中的许多思想已被现代 UNIX 系统所采纳
    Mach 推动了成熟虚拟内存支持的采用
    虚拟机在一定程度上是对操作系统服务器理念的回应
    可加载内核模块是对可扩展性需求的回应
    客户端/服务器模式，如 DNS 服务器、窗口服务器
    MacOS 具有微内核风格的 IPC
