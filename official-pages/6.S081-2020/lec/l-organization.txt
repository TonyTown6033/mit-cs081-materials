传统内核背后的哲学是强大的抽象：
  便携式接口
    文件，而不是磁盘控制器寄存器
    地址空间，而不是 MMU 访问
  隐藏复杂性的简单界面
    所有 I/O 通过 FD 和读/写，并非专门针对每个设备 &c
    具有透明磁盘分页的地址空间
  抽象帮助内核管理和共享资源
    进程抽象让内核负责调度
    文件/目录抽象让内核负责磁盘布局
  抽象帮助内核加强安全性
    文件权限
    具有私有地址空间的进程
  很多间接的
    例如FD、虚拟地址、文件名、PID
    帮助内核虚拟化、隐藏、撤销、调度等

强大的抽象导致了大的“整体”内核
  内核是一个大程序，例如 xv6
  内核子系统易于协作——没有烦人的边界
    exec() 和 mmap() 是 FS 和 VM 系统的一部分
    相对容易添加符号链接、COW fork、mmap 等
  所有内核代码都以高权限运行——没有内部安全限制

传统内核有什么问题？
  big => complex => buggy/insecure
  也许过于笼统，因此速度缓慢
    通过 UNIX 管道发送一个字节需要执行多少代码？
    缓冲、锁、睡眠/唤醒、调度程序
  许多设计决策都是内置的，无法更改，可能会很尴尬
    也许我想等待一个不是我的孩子的进程
    也许我想更改另一个进程的地址空间
    也许 DB 比内核 FS 更擅长在磁盘上布置 B-Tree 文件
  很难创建其他人可以使用的内核“扩展”
    新的设备驱动程序、文件系统等

微内核——一种不同的方法
  大创意：将大多数操作系统功能移至用户空间服务进程
  [图：硬件、内核、服务（FS 磁盘 VM TCP NIC 显示）、应用程序]
  内核可以很小
    地址空间、线程、IPC（进程间通信）
    IPC让线程互相发送消息
  20 世纪 80 年代微内核设计研究爆发
    CMU 的 Mach 或许是最有影响力的
  如今用于嵌入式系统、电话芯片、汽车娱乐
  想法（特别是用户级服务器和 IPC）有影响力，例如Windows 和 MacOS

为什么对微内核感兴趣？
  专注、优雅、干净
  small -> more security -- less code means fewer bugs to exploit
  small -> verifiable (see seL4)
  small -> easier to optimize
    您无需为不使用的功能付费
  small -> avoid forcing design decisions on applications
  user-level -> may encourage modularity of O/S services
  user-level -> easier to extend / customize / replace user-level services
  user-level -> more robust -- restart individual user-level services
    大多数错误都存在于驱动程序中，请将它们从内核中删除！
  可以运行/模拟多个操作系统，例如 VMM

L4 基本抽象
  [图]
  地址空间（“任务”）
  线程
  工控机

L4系统调用：
  创建地址空间
  在[另一个]地址空间中创建/销毁线程
  通过 IPC 发送/接收消息（地址是线程 ID）
  将内存页面映射到另一个地址空间
    它必须同意
    这是通过 IPC 发生的——一个任务可以修改另一个任务的页表
    用于创建新任务、共享内存
  拦截另一个地址空间的页面错误——“pager”
    内核通过IPC传递
  访问设备硬件（不是系统调用，直接发生）
  处理设备中断
    内核通过IPC传递

注意 L4 内核几乎缺少 Linux 甚至 xv6 拥有的所有内容
  文件系统、fork()、exec()、管道、设备驱动程序、网络堆栈等
  如果你想要这些，它们必须是用户级代码
    库或服务器进程

L4线程切换是如何工作的？
  当前用户级线程可能因以下 3 个原因而屈服：
    IPC系统调用等待
    定时器中断
    yield() 系统调用
  L4内核保存用户线程寄存器，
    选择一个 RUNNABLE 线程来运行，
    恢复用户寄存器，
    切换页表，
    跳转到用户空间
  这里没有惊喜

L4 外部寻呼机如何工作？
  每个任务都有一个寻呼机任务
  1. 页面错误
  2. 内核挂起线程
  3. 内核将IPC中的故障信息发送给寻呼机
  4.寻呼机选择一个自己的页面
  5.寻呼机在IPC回复中发送虚拟页面地址给故障线程
  6.内核拦截IPS，映射到目标，恢复目标

L4 寻呼机可以用来做什么？
  分配内存——“sigma0”为早期任务分配错误
  写时复制分叉
    与撤销访问权限的系统调用相结合
  文件的映射

问题：IPC性能
  微内核程序执行大量 IPC！
  早期系统价格昂贵
    多个内核交叉、TLB 未命中、上下文切换等
  IPC 的成本导致许多人放弃微内核
  L4设计师在IPC性能上投入了大量精力

这是一个慢速 IPC 设计
  UNIX 管道上的图案
  [示意图，内核中的消息队列]
  发送（ID，消息）
    将 msg 添加到内核队列中，返回
  接收（&id，&数据）
    如果消息在队列中等待，则删除并返回
    否则睡眠（）
  称为“异步”和“缓冲”
  现在通常的请求响应模式（RPC）涉及：
    [图：第二个回复消息队列]
    4 system calls (user->kernel->user)
      send() -> recv()
      接收() <- 发送
      每个都可能干扰 CPU 的缓存（TLB、数据、指令）
    四份消息副本（两份用于请求，两份用于回复）
    两个上下文切换，两个通用调度

L4的快速IPC
  “通过内核设计改进 IPC”，Jochen Liedtke，1993 年
  * 同步
    [图]
    send() 等待目标线程的recv()
    常见情况：目标已经在recv()中等待
    send() 跳转到目标的用户空间，就像从 receive() 返回一样
      没有真正的上下文切换，没有调度程序循环
  * 无缓冲
    内核中没有队列
    由于同步，内核可以直接在用户缓冲区之间复制
  * 寄存器中的小消息
    内核 send() 路径不会干扰许多寄存器
      例如，没有上下文切换
    小消息无需复制
      因为 send() 与寄存器一起跳转到目标的用户空间
  * 作为虚拟内存授予的巨大消息
    同样，不需要复制，尽管内核 send() 代码必须更改页表
  * 组合call()和sendrecv()系统调用
    [图]
    IPC 几乎总是用作请求-响应 RPC
    因此使用单独的 send() 和 receive() 系统调用是浪费的
    client: call()：发送消息，等待响应
    服务器：sendrecv()：回复一个请求，等待下一个请求
    用户/内核交叉减少 2 倍
  * 仔细布局内核代码以最小化缓存占用空间
  结果：IPC 成本降低 20 倍

L4/Linux 对线程的使用
  每个 Linux 进程都有一个或多个用于其用户代码的 L4 线程
  Linux 服务器只有一个 L4 线程（加上等待中断的 L4 线程）
    At rest it is waiting for IPCs with system calls
  Linux 服务器在其进程的内核线程之间切换自己的 L4 线程
    当例如文件系统代码 sleep() 等待磁盘读取
    或者管道 read() sleep() 等待有人写入管道
    就像 xv6 在内核线程之间切换一样。
  但是 L4/Linux 内核线程切换有
    与用户进程切换无关
  相反，L4 在可运行的 L4 线程之间单独切换，
    实施Linux进程
  所以Linux内核服务器可以为进程P1运行一个内核线程，
    当 L4 正在另一个核心上运行进程 P2 时

为什么不使用L4线程来实现Linux服务器的内核线程呢？
  因为那会带来痛苦，却没有任何好处。
  将在 Linux 内部引入并行性。
    但 Linux 2.0 没有 SMP 支持——例如没有自旋锁。
  而且他们的硬件只有一个核心，因此无论如何都无法实现并行加速。

缺点：L4负责调度用户线程
  所以 L4/Linux 无法强制执行 Linux 的优先级概念

L4/Linux 服务器将所有用户内存映射到其地址空间
  （实际上，它分配大量内存，然后将自己的内存提供给用户进程）
  将其用于 copyin()/copyout()，以从系统调用中取消引用用户指针
  这使得系统调用 IPC 较小——数据地址，而不是数据本身
  Linux 服务器也将其内存访问用于 fork() 和 exec()

示例：fork() 是如何工作的？
  进程P1调用fork()（P1实际上是一个L4任务）
  P1的libc库将fork()变成IPC到L4/Linux服务器
  L4/Linux 要求 L4 创建新任务和线程——P2
  L4/Linux分配内存页（与P1一样多）
  L4/Linux 使用 IPC 告诉 L4 将页面映射到 P2
  L4/Linux 将数据从 P1 的页面复制到 P2 的页面
  L4/Linux 通过 SP 和 PC 向 P2 发送特殊的 IPC 使其运行
  L4/Linux 通过 IPC 向 P1 发送回复

L4/Linux 服务器充当用户进程的分页器
  所以L4将进程页面错误变成IPC到Linux服务器
  例如写时复制分叉、惰性分配、内存映射文件

缺点：L4 不允许直接控制页表
  因此 Linux 服务器无法切换其页表以包含用户 virt 地址
  直到最近 Linux 使用这个技巧来提高性能（没有页表切换），
    以及为了方便取消引用系统调用参数

L4/Linux服务器使用Linux设备驱动程序不变！
  因为 L4 允许直接访问设备寄存器
  除了通过 L4 IPC 到达的中断
