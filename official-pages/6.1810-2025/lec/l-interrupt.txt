6.1810 2025 第11讲：设备驱动、中断

主题：设备驱动
  CPU 需要连接各种设备：存储、通信、显示等
    操作系统的设备驱动负责控制这些设备
  设备处理可能很复杂：
    设备通常拥有严格且复杂的接口
    设备与 CPU 并行运行——存在并发问题
    中断
      硬件需要立即得到响应！
        例如，数据包到达
      软件必须暂停当前工作并作出响应
        在 RISC-V 上使用与系统调用和异常相同的陷阱机制
      中断可能在不合时宜的时刻到来
   生产内核中的大部分代码都是设备驱动
     你将为一块网卡编写一个驱动
      
设备在哪里？
  [CPU, bus, RAM, disk, net, uart]

设备编程：内存映射 I/O
  设备硬件拥有若干控制寄存器和状态寄存器
  设备寄存器位于某个物理"内存"地址
  对这些地址执行 ld/st 操作即可读写设备控制寄存器
  平台设计者决定各设备的地址

示例设备：UART
  通用异步收发传输器
  串行接口，支持输入和输出
  "RS232 端口"，例如 qemu 控制台
  UART 是硬件——由晶体管构成
  qemu 模拟常见的 16550 UART 芯片
    数据手册：课程表页面上的 16550.pdf 链接，或通过网络搜索获取
    数据手册详细描述了物理特性、电气特性和编程接口
  [rx wire, receive shift register, receive FIFO]
  [transmit FIFO, transmit shift register, tx wire]
  16 字节 FIFO
  内存映射的 8 位寄存器，物理地址为 UART0=0x10000000：
    （16550.pdf 第 9 页）
    0: RHR / THR -- receive/transmit holding register
    1: IER -- interrupt enable register, 0x1 is receive enable, 0x2 transmit
    ...
    5: LSR -- line status register, 0x1 is receive data ready

内核设备驱动如何使用这些寄存器？
  简单示例：kernel/uart.c 中的 uartgetc()
  ReadReg(RHR) 最终执行的是 *(char*)(0x10000000 + 0)

为什么 UART 要有 FIFO 缓冲区？

设备驱动必须应对设备未就绪的情况
  read() 但接收 FIFO 为空
  write() 但发送 FIFO 已满
  LSR 位：数据就绪（Data Ready）、发送器空闲（Transmitter Empty）

设备驱动应如何等待？

一种方式是"忙等循环"：
  while((LSR & 1) == 0)
    ;
  return RHR
若等待概率极低——输入必定很快到来时尚可接受
但对控制台而言太浪费了！
  FIFO 中常常没有待处理的输入（按键）
  许多设备都是如此——可能需要长时间等待 I/O

一种解决方案：中断
  当设备需要驱动处理时，设备触发一个中断
  UART 在以下情况触发中断：
    接收 FIFO 从空变为非空，或
    发送 FIFO 从满变为未满

内核如何感知中断？
  [在图中添加 PLIC，连接到地址总线和设备]
  device -> PLIC -> CPU -> trap -> usertrap()/kerneltrap() -> devintr()
  PLIC 负责选择源设备和目标核心，因为两者都可能不止一个
  trap.c devintr()
  scause 的高位表示该陷阱来自设备中断
  一个 PLIC 寄存器指示是哪个设备触发了中断
    即"IRQ"——UART 的 IRQ 为 10
    IRQ 由平台定义——此处为 qemu

中断通常只是设备状态可能已发生变化的一个提示
  真实情况需查看设备的状态寄存器
    设备驱动必须读取这些寄存器以决定是否采取行动
  对于 UART，检查 LSR 以判断接收 FIFO 是否非空、发送 FIFO 是否未满
    如 uartgetc() 中所示
    一次中断可能意味着需要处理多个动作

xv6 必须同时向设备和 RISC-V 请求开启中断：
  uartinit() uart.c:71
    WriteReg(IER, IER_TX_ENABLE | IER_RX_ENABLE);
  intr_on() / intr_off() riscv.h:289
    w_sstatus(r_sstatus() | SSTATUS_SIE);
    用于内核代码中不允许被中断打断的位置

通用设备驱动模式：下半部与上半部
  [图示：系统调用调用下半部，中断为上半部]
  下半部：
     由进程的系统调用调用，例如 write() 或 read()
     可能通知设备开始输出或输入
     可能等待输入就绪或输出完成
  共享信息（缓冲区）
  上半部：
     中断处理程序
     从设备硬件读取输入或向设备硬件发送更多输出
     与"下半部"进程交互
       将输入放置到下半部可以找到的位置
       通知下半部输入已到达
       或者可以发送更多输出
     *不*在下半部进程的上下文中运行
       可能在不同的核心上
       可能正在中断某个其他进程
     因此交互必须保持间接方式——缓冲区、sleep()/wakeup()

如果多个设备同时请求中断会怎样？
  PLIC 将中断分发给各个核心
    不同的中断可以在不同核心上并行处理
  每个中断由第一个调用 plic_claim() 的核心认领
  每个独立设备最多同时有一个中断在处理中
    PLIC 通过 plic_complete() 得知中断已完成
        
若中断已启用，设备中断可能发生在任意两条指令之间
  示例：
    假设内核正在用全局变量 n 计数
    下半部：n = n + 1
    中断上半部：n = n + 1
    n=n+1 对应的机器码如下：
      lw a4, n
      add a4, a4, 1
      sw a4, n
    如果中断发生在 lw 和 add 之间会怎样？
      且中断处理程序也执行 n = n + 1？
  一种解决方案：在下半部短暂禁用中断
    intr_off()
    n = n + 1
    intr_on()
    intr_off(): w_sstatus(r_sstatus() & ~SSTATUS_SIE);
  可行，但还不够：中断可能到达不同的 CPU
    更多内容见锁机制相关章节

当 SSTATUS_SIE 为零时，中断会怎样？
  PLIC/CPU 会记录待处理的中断
  在内核重新启用中断时再进行传递

生产与消费通常是解耦的——并发进行
  来自设备的输入：
    可能在读取方未等待时到达
    到达速度可能快于或慢于读取方的读取速度
    缓冲与批处理有助于匹配速度、提升效率
  向设备的输出：
    若设备较慢，需缓冲输出以便进程可以继续执行
    若设备较快，需批量发送以提高效率
  因此生产者/消费者缓冲区十分常见
  我们已在两个层面见过这种机制：
    UART 内部 FIFO，用于设备与驱动之间——加上中断
    cons.buf，用于下半部与上半部之间——加上 sleep/wakeup
  我们将再次看到这些内容：
    pipes
    net lab

中断会产生开销
  大约一微秒
  "开销" == 不包含有效设备驱动工作的纯额外代价
  CPU 陷阱、保存寄存器、可能还需要
    切换页表、判断是哪个设备，
    以及之后恢复所有状态并返回所需的时间
  流水线、大型寄存器组、缓存/TLB 缺失、慢速 RAM

如果中断频率很高怎么办？
  示例：以太网每秒可传送数百万个数据包
  在这种速率下，CPU 时间的很大一部分耗费在中断*开销*上
    
轮询：一种适用于高频率事件的通知策略
  告知设备（或 PLIC）不要为该设备生成中断
  定期检查输入，例如在 scheduler() 或定时器中断中检查
  然后处理自上次轮询以来积累的所有内容
  在高频率下比中断更高效
  可根据测量到的频率动态切换策略

DMA（直接内存访问）可以高效地移动数据
  xv6 的 uart 驱动程序在软件中每次读取一个字节
    CPU 并不擅长做这种事：
      片外访问、不可缓存、每次仅 8 位
    仅适用于低速设备
  大多数高速设备会自动将批量输入复制到 RAM —— DMA
    然后再触发中断
    输入数据已在普通 RAM 中
    CPU 对 RAM 的读写效率很高

中断的演进历程
  几十年前：
    中断开销只有几个时钟周期
    因此：硬件简单，软件复杂，中断频繁
  如今：
    开销高达数千个时钟周期
    因此：硬件智能化，每次中断完成大量工作

中断与设备处理是持续关注的领域
  专用快速中断路径（同样适用于缺页故障、系统调用）
  将设备工作分散到多个 CPU 上
  用户态设备驱动 —— 完全绕过内核
