主题：设备驱动程序
  CPU 需要附加设备：存储、通信、显示等
    操作系统设备驱动程序控制这些设备
  设备处理可能很困难：
    设备通常具有严格且复杂的接口
    设备和CPU并行运行——并发
    中断
      硬件现在需要关注！
        例如，pkt 到达
      软件必须搁置当前的工作并做出响应
        在 RISC-V 上使用与系统调用和异常相同的陷阱机制
      中断可能会在尴尬的时候到来
   生产内核中的大多数代码都是设备驱动程序

设备在哪里？
  [CPU、总线、RAM、磁盘、网络、UART]

编程设备：内存映射 I/O
  设备硬件有一些控制和状态寄存器
  设备寄存器位于物理“内存”地址
  ld/st 到这些地址读/写设备控制寄存器
  平台设计者决定设备的地址

示例设备：UART
  通用异步接收器和发送器
  串行接口、输入和输出
  “RS232 端口”，例如qemu控制台
  UART 是硬件——晶体管
  qemu模拟常见的16550 uart芯片
    数据表：时间表页面上的 16550.pdf 链接，或网络搜索
    数据表详细介绍了物理、电气和编程
  [rx线、接收移位寄存器、接收FIFO]
  [发送 FIFO、发送移位寄存器、tx 线]
  16 字节 FIFO
  物理地址 UART0=0x10000000 处的内存映射 8 位寄存器：
    （16550.pdf 第 9 页）
    0: RHR / THR -- 接收/发送保持寄存器
    1：IER——中断使能寄存器，0x1为接收使能，0x2为发送使能
    ...
    5：LSR——线路状态寄存器，0x1为接收数据就绪

内核设备驱动程序如何使用这些寄存器？
  简单的例子：kernel/uart.c 中的 uartgetc()
  ReadReg(RHR) 变成 *(char*)(0x10000000 + 0)

为什么UART有FIFO缓冲区？

设备驱动程序必须应对设备未准备就绪的情况
  read() 但 rx FIFO 为空
  write() 但 tx FIFO 已满
  LSR 位：数据就绪、发送器空

设备驱动程序应该如何等待？

也许是一个“繁忙循环”：
  while((LSR & 1) == 0)
    ;
  返回右心率
如果不太可能等待——如果输入肯定很快就会到达，那么就可以
但对于控制台来说太浪费了！
  通常 FIFO 中没有等待输入（击键）
  很多设备都是这样——I/O可能需要等待很长时间

解决办法：中断
  当设备需要驱动程序注意时，设备会引发中断
  UART 中断如果：
    rx FIFO 从空变为非空，或者
    tx FIFO 从已满变为未满

内核如何看到中断？
  [将PLIC添加到图中，连接到地址总线和设备]
  device -> PLIC -> CPU -> trap -> usertrap()/kerneltrap() -> devintr()
  PLIC 选择 src 设备和 dst 内核，因为两者都不止一个
  trap.c devintr()
  原因高位表示陷阱来自设备中断
  PLIC 寄存器指示哪个设备中断
    “IRQ”——UART 的 IRQ 为 10
    IRQ 由平台定义——本例中为 qemu

中断通常只是设备状态可能已更改的提示
  真正的真相在设备的状态寄存器中
    设备驱动程序必须读取它们来决定操作（如果有）
  对于 UART，检查 LSR 以查看 rx FIFO 是否非空、tx FIFO 是否未满
    如 uartgetc() 中所示
    一个中断可能会发出需要执行多项操作的信号

通用设备驱动程序模式：下半部和上半部
  [图：系统调用调用下半部，中断为上半部]
  下半部分：
     由进程的系统调用调用，例如写（）或读（）
     可以告诉设备开始输出或输入
     可能等待输入准备好或输出完成
  共享信息（缓冲区）
  上半部分：
     中断处理程序
     从设备硬件读取输入或向设备硬件发送更多输出
     与“下半部分”流程交互
       将输入放在下半部分可以找到的地方
       告诉下半部分输入已到达
       或者可以发送更多输出
     *不*在下半部进程的上下文中运行
       也许在不同的核心上
       可能会中断其他进程
     因此交互必须保持一定距离——缓冲区、sleep()/wakeup()

如果多个设备同时请求中断怎么办？
  PLIC 在内核之间分配中断
    不同的中断可以在不同的内核上并行处理
  每个中断由第一个内核调用 plic_claim() 声明
  每个单独的设备最多有一个正在运行的中断
    PLIC 知道通过 plic_complete() 完成
    
如果启用，设备中断可以发生在任意两条指令之间
  Example:
    假设内核正在计算全局变量 n 中的某些内容
    下半部分：n = n + 1
    中断上半部分：n = n + 1
    n=n+1 的机器代码如下所示：
      lw a4, n
      添加a4,a4,1
      sw a4, n
    如果lw和add之间发生中断怎么办？
      中断处理程序还说 n = n + 1？
  一种解决方案：暂时禁用下半部分的中断
    intr_off()
    n = n + 1
    intr_on()
    intr_off(): w_sstatus(r_sstatus() & ~SSTATUS_SIE);
  很好，但还不够：中断可能到达不同的 CPU
    当我们查看锁定时会对此进行更多了解

当 SSTATUS_SIE 为零时中断会发生什么？
  PLIC/CPU 记住挂起的中断
  当内核重新启用中断时传递

生产和消费通常是解耦的——并发的
  从设备输入：
    可以在读者不等待的时间到达
    到达速度可能比读者阅读的速度更快或更慢
    缓冲和批处理有助于匹配速度、提高效率
  输出到设备：
    如果设备速度慢，需要缓冲输出以便进程可以继续
    如果设备速度很快，希望分批发送以提高效率
  所以生产者/消费者缓冲区很常见
  我们在两个层面上看到了这一点：
    UART 内部 FIFO，用于设备和驱动程序 - 以及中断
    cons.buf，用于下半部和上半部——加上睡眠/唤醒

中断会产生开销
  大约一微秒
  "overhead" == cost *excluding* useful device driver work
  CPU 陷阱所需的时间，保存寄存器，也许
    切换页表，决定使用哪个设备，
    然后恢复一切并返回
  管道、大型寄存器集、高速缓存/TLB 未命中、慢速 RAM

如果中断率很高怎么办？
  示例：以太网每秒可以传送数百万个数据包
  按照这个速度，中断的 CPU 时间的很大一部分*开销*
  
轮询：高速率的事件通知策略
  告诉设备（或 PLIC）不要为设备生成中断
  定期检查输入，例如在 Scheduler() 或定时器中断中
  然后处理自上次轮询以来积累的所有内容
  比高速率中断更高效
  也许根据测量的速率切换策略

DMA（直接内存访问）可以有效地移动数据
  xv6 uart 驱动程序在软件中一次读取一个字节
    CPU 对此效率不高：
      片外，不可缓存，一次 8 位
    仅适用于低速设备
  大多数快速设备会自动将批量输入复制到 RAM——DMA
    然后中断
    输入已经在普通 RAM 中
    CPU 高效地读/写 RAM

随着时间的推移中断演变
  几十年前：
    中断开销是几个周期
    所以：简单的硬件，智能的软件，大量的中断
  Now:
    开销是 1000 个周期
    所以：智能硬件，为每个中断做很多工作

中断和设备处理是持续关注的领域
  特殊的快速中断路径（也适用于页面错误、系统调用）
  将设备工作分散到 CPU 上
  用户空间设备驱动程序——完全避免内核
