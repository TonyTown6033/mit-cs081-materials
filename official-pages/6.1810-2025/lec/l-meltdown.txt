这是攻击的核心（这是用户代码）：
1. 字符缓冲区[8192]

4. r2 = r2 & 1
5. r2 = r2 * 4096

（这些代表机器指令）

  加载会导致页面错误。

本文假设内核映射在每个用户页表中。

那么这段代码对攻击者有何用处呢？
  答案与一堆几乎隐藏的 CPU 实现细节有关。
  推测执行和 CPU 缓存。

首先，投机执行。
  这还不是安全问题。
  想象一下这个普通的代码。
  “r0”和c是寄存器，“*r0”是内存引用。

  r0 = <某个地址>
  r1 = load x // r1 是一个寄存器； x 是 RAM 中的变量
  if(r1 == 1){
    r2 = *r0
    r3 = r2 + 1
  } 否则{
    r3 = 0
  }

  如果必须从 RAM 中获取 x，则“r1 = x”需要 100 秒的周期。
  The "if(r1 == 1)" needs that RAM content.
  如果 CPU 必须暂停直到 RAM 读取完成，那就太糟糕了。
  相反，CPU 会预测分支可能走向哪个方向，
    并继续执行。
  这就是所谓的“投机”。
  So before the "r1 == 1" is resolved,
    CPU 可能预测它会是真的，
    并推测执行“r2 = *r0”，
    然后是“r3 = r2 + 1”。

如果 CPU 错误地预测了一个分支怎么办？ x 结果为零？
  推测指令的寄存器更新在提交之前是暂定的。
  如果 CPU 意识到分支是中间预测的，则它会放弃尝试性更新。
  并在“else”分支中重新开始执行。

推测执行有助于提高性能，因为它有助于
  当 CPU 等待慢速内存时，避免停顿。

What if the CPU predicts r1 == 1,
  并推测执行 r2 = *r0,
  但 r0 持有无效指针？
  If it turns out x == 1, the "r2 = *r0" should raise an exception.
  If it turns out x == 0, the "r2 = *r0" should not raise an exception.

CPU 仅在确定指令后才“退休”指令
  不会因为错误猜测而被取消。
  并且CPU按顺序退役指令，毕竟
    以前的指令已经失效，因为只有那时它才
    知道之前的指令没有错误。

因此，推测性指令的错误
  执行可能要等到指令完成后一段时间才会发生。

投机原则上是透明的。
  CPU 实现的一部分，但在规范中不可见。
  也就是说，投机的目的是为了提高性能，而不需要
    改变程序计算的结果。
  CPU 通过撤销寄存器使推测变得透明
    如果它意识到自己推测错误并且没有这样做
    从错误推测的指令中引发异常。

一些行话：
  “架构特性”——CPU手册中的东西，程序员可见。
  “微架构”——手册中没有，旨在隐形。
    这是芯片上数十亿个晶体管的大部分

另一个微架构特性：CPU 数据和 TLB 缓存。
  核心
  L1：弗吉尼亚州，宾夕法尼亚州 |数据/TLB：va |帕
  L2: 帕 |数据
  内存
缓存分为“缓存行”，例如64 字节。
如果加载失败，则会获取数据并将其放入缓存中。
L1（“一级”）高速缓存通过虚拟低位进行索引，以提高速度。
CPU 必须同时咨询 L1 和 TLB，后者获取权限
  以及 L1 关联性标签的物理地址，
  确定负载是否到达 L1。
  （英特尔 L1 是虚拟索引、物理标记 (VIPT)）
L1 缺失时：TLB 查找、使用 phys addr 进行 L2 查找。
Times:
  L1 命中——几个周期。
  L2 命中——十几个或两个周期。
  RAM——300 个周期。
  TLB 未命中——最多 100 个周期，遍历页表树。
  一个周期是 1/时钟频率，例如 0.5 纳秒。

系统调用返回用户空间后，将内核数据保留在一级缓存中。
  （假设页表有用户和内核映射）

为什么 L1 在执行用户代码时包含内核数据是安全的？
  用户程序可以直接从缓存中读取内核数据吗？

在现实生活中，微架构并不是完全看不见的。
  它影响指令和程序花费的时间。
  编写性能关键代码的人们对此非常感兴趣。
  以及编译器作者。
  英特尔&c 发布了优化指南、建议，但细节很少。

一个有用的技巧：感知某些内容是否被缓存。
  这就是本文的Flush+Reload。
  您想知道函数 f() 是否使用地址 Z 处的内存。
  1）确保Z没有被缓存。
     Intel CPU 有一条 clflush 指令。
     或者加载足够的内存位置以强制将其他所有内容从缓存中移出。
  2）调用f()
  3）记录时间。
     现代 CPU 允许您读取周期计数器。
     对于 Intel CPU，它是 rdtsc 指令。
  4）从地址Z加载一个字节
     （你需要内存栅栏来确保负载确实发生）
  5) 再次记录时间。
  6) 如果时间差 <（例如）50，则 #4 中的负载达到，
     这意味着 f() 可能使用了地址 Z 处的内存。
     否则不会。

Meltdown 如何用于现实世界的攻击？
  攻击者需要在受害者机器上运行他们的代码。
  分时：内核可能有其他用户的秘密，例如密码、密钥。
    并且内核可以映射所有物理内存，包括其他进程。
  云：某些容器和 VMM 系统可能容易受到攻击，
    这样您就可以从其他云客户那里窃取数据。
  您的浏览器：它在沙箱中运行不受信任的代码，例如插件，
    也许某个插件可以从您的内核中窃取您的密码。

如果它经常（甚至通常！）不起作用，为什么对攻击者有用？
  安全游戏规则：
    防守必须以 100% 的胜利为目标。
    如果攻击者的胜率只有 1%，那么对于防御来说就是一场灾难。
  例如如果攻击者只能窃取 1% 用户的密码。
  此外，攻击者可能能够影响缓存中的内容。
    例如进行系统调用，发送网络请求。

据了解，Meltdown 并未被用于任何实际攻击中。
  但它激发了很多补救措施。

防御呢？

软件修复：
  不要将内核映射到用户页表中。
    该报称此为“KAISER”； Linux 现在将其称为 KPTI。
  每个系统调用入口/出口都需要页表切换。
    这就是 RISC-V xv6 的工作原理。
  页表切换可能会很慢——它可能需要 TLB 刷新。
    PCID 可以避免 TLB 刷新，尽管仍然需要一些费用。
  Meltdown 出现后不久，许多内核就采用了 KAISER/KPTI。

硬件修复：
  仅从推测负载返回允许的数据！
    如果 PTE_U/R/V 清零，则返回零，而不是实际数据。
  这可能成本很低，因为 CPU 必须查看
    无论如何，每次 L1 命中都会在 PTE 和 TLB 中获得。
  AMD CPU 显然一直都是这样工作的。
  现代 Intel CPU 似乎就是这样做的（称为 RDCL_NO）。

这些防御措施已部署并被认为有效；但是：
