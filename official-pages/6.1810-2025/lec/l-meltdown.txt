6.1810 2025 第23讲：Meltdown

Meltdown：从用户态读取内核内存，Lipp 等人，2018年。

提示：安全是操作系统的顶层目标
  恶意用户代码是攻击的来源之一
  内核的主要策略：隔离
    用户态/特权态、页表、严格的系统调用、容器等
  如果一切配置正确，还可能出什么问题？

为什么要研究这篇 Meltdown 论文？
  它允许恶意用户代码在页表保护机制下读取内核内存。
  令人惊讶且令人不安
  是近年来一系列"微架构"攻击之一
    利用 CPU 隐藏的实现细节
  可修复，但人们担心会不断涌现类似的安全隐患
    Linux:  grep . /sys/devices/system/cpu/vulnerabilities/*

欢迎提问！
  这一问题十分复杂，且大部分细节对外不可见。
  只有 Intel 的设计者才了解攻击能否生效的具体原因。
  其余人只能进行推测。

以下是攻击的核心代码（这是用户代码）：
1.  char buf[8192]
2.  r1 = <a kernel virtual address>
3.  r2 = *r1
4.  r2 = r2 & 1
5.  r2 = r2 * 4096
6.  r3 = *(buf + r2)
（以上表示机器指令）

如果用户代码试图使用内核地址（如第3行），会发生什么？
  该加载操作将触发缺页异常。

本文假设内核被映射到每个用户页表中。
  且 PTE_U 位被清除。
  [diagram: 0 to 2^64]
  用户内存从零地址开始；内核位于高地址。
  在这些攻击被发现之前，这种方式几乎是通行做法。
  同时映射用户态和内核态可以加快系统调用的速度。
  关键在于：*r1 是有意义的，即使访问被禁止。

那么这段代码对攻击者有何用处？
  答案与一系列大多不可见的 CPU 实现细节有关。
  即投机执行与 CPU 缓存。

首先，介绍投机执行。
  这还不涉及安全问题。
  想象这段普通的代码。
  "r0" 等是寄存器，"*r0" 是内存引用。

  r0 = <some address>
  r1 = load x // r1 is a register; x is a variable in RAM
  if(r1 == 1){
    r2 = *r0
    r3 = r2 + 1
  } else {
    r3 = 0
  }

  如果 x 需要从 RAM 中读取，"r1 = x" 会花费数百个时钟周期。
  "if(r1 == 1)" 依赖于该 RAM 中的内容。
  如果 CPU 必须暂停等待 RAM 读取完成，代价将会很大。
  因此，CPU 会预测分支可能走向哪一侧，
    并继续执行。
  这被称为"推测执行"。
  所以在 "r1 == 1" 的结果确定之前，
    CPU 可能预测其为真，
    并推测性地执行 "r2 = *r0"，
    然后执行 "r3 = r2 + 1"。

如果 CPU 分支预测错误，例如 x 的值实际为零，会发生什么？
  推测指令对寄存器的更新在提交前是暂定的。
  如果 CPU 发现分支预测错误，则丢弃暂定的更新。
  并重新从 "else" 分支开始执行。

推测执行有助于提升性能，因为它可以
  避免 CPU 等待慢速内存时产生的停顿。

如果 CPU 预测 r1 == 1，
  并推测性地执行 r2 = *r0，
  但 r0 持有一个无效指针，会发生什么？
  若最终 x == 1，"r2 = *r0" 应触发一个异常。
  若最终 x == 0，"r2 = *r0" 则不应触发异常。

CPU 只有在确认指令不会因预测错误而需要取消时，
  才会"退休"（retire）该指令。
  并且 CPU 按顺序退休指令，只有在所有
    前序指令都已退休之后才处理当前指令，因为只有那时
    才能确认之前没有任何指令发生错误。

因此，一条推测执行的指令所引发的错误，
  可能在该指令执行完成后相当一段时间才会真正发生。

推测执行在原则上是透明的。
  CPU 实现的一部分，但在规范中不可见。
  也就是说，推测执行旨在提高性能，而不
    改变程序计算的结果。
  CPU 通过撤销寄存器
    赋值来使推测透明化，当其发现推测错误时，并且不会
    对错误推测的指令触发异常。

一些术语：
  "架构特性" —— CPU 手册中的内容，对程序员可见。
  "微架构" —— 不在手册中，旨在对外不可见。
    这占据了芯片上数十亿晶体管中的大部分

另一个微架构特性：CPU 数据缓存与 TLB 缓存。
  核心
  L1: va,pa | data / TLB: va | pa
  L2: pa    | data
  RAM
缓存被划分为若干"缓存行"，例如每行 64 字节。
若加载缺失，数据将被读取并放入缓存。
L1（"一级"）缓存以虚拟低位地址为索引，以提高速度。
CPU 必须同时查询 L1 和 TLB，后者用于权限检查
  以及获取 L1 关联性标签所需的物理地址，
  从而判断加载是否命中 L1。
  （Intel L1 采用虚拟索引、物理标签方式（VIPT））
L1 缺失时：查询 TLB，再以物理地址查询 L2。
时延参考：
  L1 命中 —— 几个时钟周期。
  L2 命中 —— 十几到二十几个时钟周期。
  RAM —— 300 个时钟周期。
  TLB 缺失 —— 最多数百个时钟周期，需遍历页表树。
  一个时钟周期为 1/时钟频率，例如 0.5 纳秒。

系统调用完成后，返回用户态时，内核数据仍留在 L1 缓存中。
  （假设页表同时包含用户态和内核的映射）

为什么在执行用户代码时，L1 中包含内核数据是安全的？
  用户程序能直接从缓存中读取内核数据吗？

在现实中，微架构并非完全不可见。
  它影响指令和程序的执行时间。
  它是编写性能敏感代码的人员的重点关注对象。
  也是编译器开发者的关注对象。
  Intel 等厂商发布了优化指南，提供建议但披露细节甚少。

一个有用的技巧：检测某内容是否已被缓存。
  这即论文中的 Flush+Reload 方法。
  你想知道函数 f() 是否访问了地址 Z 处的内存。
  1) 确保 Z 不在缓存中。
     Intel CPU 有一条 clflush 指令。
     或者加载足够多的内存地址，强制将其他所有内容驱逐出缓存。
  2) 调用 f()
  3) 记录当前时间。
     现代 CPU 允许读取循环计数器。
     对于 Intel CPU，使用的是 rdtsc 指令。
  4) 从地址 Z 加载一个字节
     （需要内存屏障以确保加载操作真正发生）
  5) 再次记录时间。
  6) 如果两次时间之差 < （比如）50，则第 4 步的加载命中缓存，
     这意味着 f() 可能访问了地址 Z 处的内存。
     否则则未命中。

回到 Meltdown —— 这次更加详细：

    // 位于用户内存中
    char buf[8192]

    // Flush+Reload 中的 Flush 阶段
    clflush buf[0]
    clflush buf[4096]

1.  r1 = <一个内核虚拟地址>
2.  r2 = *r1
3.  r2 = r2 & 1      // 推测执行
4.  r2 = r2 * 4096   // 推测执行
5.  r3 = *(buf+r2)   // 推测执行

    <*r1 最终触发故障；r2 和 r3 被回滚，但数据残留在缓存中>
    <处理页错误>

    // Flush+Reload 中的 Reload 阶段
    a = rdtsc
    r0 = buf[0]
    b = rdtsc
    r1 = buf[4096]
    c = rdtsc
    if c-b < b-a:
      低位很可能为 1

也就是说，用户代码可以根据两条用户缓存行中哪一条被加载（buf[0] 还是 buf[4096]），
推断出内核数据的最低位。
    
要点：来自 "r2 = *r1" 的故障会被延迟，直到该加载指令退休时才触发，
  这一过程可能耗费一定时间，从而为后续推测执行的
  指令提供了执行机会。

要点：显然 "r2 = *r1" 会执行加载操作，即使对应的 PTE
  禁止该操作，并将结果存入 r2，但这只是暂时的，因为
  会在退休时因错误而被撤销。

要点："r3 = buf[r2]" 会将 buf[] 的部分内容加载到缓存中，
  即使对 r3 的修改因误推测而被取消。
  因为 Intel 将缓存内容视为隐藏的微架构状态。

这种攻击确实有效，已有许多人复现了它。

Meltdown 在真实攻击中会如何被利用？
  攻击者需要在受害机器上运行其代码。
  分时共享：内核可能持有其他用户的机密，如密码、密钥。
    并且内核可能映射了全部物理内存，包括其他进程的内存。
  云环境：某些容器和 VMM 系统可能存在漏洞，
    因此可以窃取其他云用户的数据。
  浏览器：它在沙箱中运行不可信代码，例如插件，
    插件也许能从内核中窃取你的密码。

如果攻击经常（甚至通常！）失败，对攻击者有何用处？
  安全博弈的规则：
    防御方必须力求 100% 的时间内获胜。
    若攻击者有 1% 的成功率，对防御方而言已是灾难。
  例如，攻击者若能窃取 1% 用户的密码。
  此外，攻击者可能能够影响缓存中的内容。
    例如，发起系统调用、发送网络请求。

Meltdown 尚未被证实用于任何实际攻击。
  但它已促使各方付出大量补救努力。

防御措施如何？

软件修复方案：
  不将内核映射到用户页表中。
    该论文将其称为"KAISER"；Linux 现将其称为 KPTI。
  每次系统调用进入/退出时需要进行页表切换。
    RISC-V xv6 正是这样工作的。
  页表切换可能较慢——可能需要刷新 TLB。
    PCID 可以避免刷新 TLB，但仍有一定开销。
  许多内核在 Meltdown 被披露后不久便采用了 KAISER/KPTI。

硬件修复方案：
  对推测性加载只返回允许访问的数据！
    若 PTE_U/R/V 未置位，则返回零，而非实际数据。
  这样做的代价可能很小，因为 CPU 对每次
    L1 命中都需要查询 TLB 中的 PTE。
  AMD CPU 显然一直以来都是这样工作的。
  现代 Intel CPU 似乎也实现了这一点（称为 RDCL_NO）。

这些防御措施已部署并被认为有效；但是：
  令人不安的是，页保护机制竟然并不牢固！
  更多微架构层面的意外正在不断浮现。
  根本问题仅仅是可修复的漏洞？还是策略上的失误？
  请持续关注，此事仍在演进之中。
