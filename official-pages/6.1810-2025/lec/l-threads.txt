为什么要支持并发任务？
  分时复用：多个用户和/或多个运行中的程序。
  程序结构：shell、进程管道、find -exec 等。
  并行编程：充分利用多核硬件。

什么是线程？
  设想正在执行的代码
    以普通的串行方式运行
  假设我们想暂停它，将其搁置一旁，
    去做其他事情，之后再恢复该代码的执行？
  我们需要保存什么？
    内存、栈、CPU 寄存器、CPU 程序计数器
  "线程"在以下两种状态之间交替：
    执行代码，
    以及被挂起时，保存恢复所需的状态
  [简单的双线程交替示意图]
  线程系统负责管理各线程之间的切换

xv6 如何使用线程？
  [简单示意图]
  每个 xv6 进程拥有一个用户级线程，
    以及一个内核线程
  进程的内核线程负责执行系统调用的具体实现，
    并可能需要挂起自身以等待输入等事件，
    或让其他进程的线程运行
  xv6 内核线程共享内存——它们都运行
    在内核地址空间中，都使用内核数据结构，
    因此需要加锁
  进程的用户线程和内核线程并非相互独立！
    若正在内核中执行，用户线程则在等待陷阱返回
    若正在用户态执行，则不存在正在运行的内核线程
  本讲将"进程"与"线程"两个术语交替使用

若某个 xv6 进程未在执行
  它通常在等待某个事件——控制台、管道、磁盘等
    因为它通过系统调用（如 read()）进入了内核
    下一讲将深入探讨这一方面
  可能在复杂的内核系统调用实现执行到一半时挂起
    需要在内核系统调用代码中断处恢复执行
    因此其内核寄存器（及栈）必须被保存

xv6 进程/线程的保存状态
  用户内存
  用户保存的寄存器（位于陷阱帧（TF）中）
  内核栈
  内核保存的寄存器（"上下文"（CTX））
  内核 p->state

p->state 告诉调度器如何处理该进程
  RUNNING —— 当前正在某个 CPU 上执行（处于用户态或内核态）
  RUNNABLE —— 希望执行，但尚未执行（挂起，在内核中）
  SLEEPING —— 等待某个事件（挂起，在内核的 read()、wait() 等调用中）
  有助于避免同时在两个 CPU 上执行等错误

xv6 如何从一个进程切换到另一个进程 —— "上下文切换"
  例如：P1 调用 read() 后等待，P2 处于 RUNNABLE 状态
  [P1, TF1, KSTACK1, CTX1, swtch(),
   CTXs, STACKs, swtch(),
   CTX2, KSTACK2, TF2, P2]
  TF = trapframe = 保存的用户寄存器
  CTX = context = 保存的内核寄存器
  从一个用户进程切换到另一个涉及多次转换：
    用户态 -> 内核态；将用户寄存器保存到陷阱帧
    内核线程 -> 调度器线程；将内核线程寄存器保存到上下文
    调度器线程 -> 内核线程；从上下文中恢复内核线程寄存器
    内核态 -> 用户态；从陷阱帧中恢复用户寄存器

proc.h 中的 struct proc
  p->trapframe 保存用户线程的寄存器
  p->context 保存内核线程的寄存器
  p->kstack 指向该线程的内核栈
  p->state 为 RUNNING、RUNNABLE、SLEEPING 等
  p->lock 保护 p->state、哪个 CPU 正在运行 p 以及其他信息

proc.c 中的 proc[NPROC] 数组 —— 每个进程一项

为什么需要独立的调度器线程？
  以便始终有一个栈可供调度器循环运行
  例如：从一个正在退出的进程切换走
  例如：进程数少于 CPU 数

调度器线程详情
  每个 CPU 一个；各自拥有一个栈和一个 struct context
  内核线程始终切换到当前 CPU 的调度器线程
    再由调度器线程切换到另一个内核线程（如果有 RUNNABLE 的话）
    从不直接进行进程到进程的切换
  每个 CPU 的调度器线程持续扫描 proc[] 进程表
    直到找到一个 RUNNABLE 的线程
  如果没有 RUNNABLE 的线程，调度器处于"空闲"状态

如果用户代码一直计算而从不发起系统调用会怎样？
  这会阻止其他进程运行吗？
  CPU 的定时器硬件会强制周期性中断
    xv6 的定时器处理程序会执行切换（"让出"）
  "抢占"或"非自愿上下文切换"

Q: 为什么要在 swtch() 期间持有 p->lock？

p->lock 在以下步骤期间防止干扰：
  * p->state=RUNNABLE
  * 将寄存器保存到 p->context
  * 停止使用 p 的内核栈
  这样其他 CPU 的调度器在所有步骤完成之前不会开始运行 p

scheduler() 的循环遍历所有进程，找到一个处于 RUNNABLE 状态的进程
  持续循环直到找到为止——可能会空闲一段时间
  在本演示中，将会找到另一个 aaa/bbb 进程

内核中的定时器中断是否会引发 yield？
   即内核代码是否也可以像用户态代码一样被抢占？
   是的——kerneltrap() 会调用 yield()
   进程保存的寄存器在哪里？
     有三组保存的寄存器：
     * 用户寄存器保存在 trapframe 中，通过 trampoline 保存
     * 被中断的内核代码寄存器保存在栈上，通过 kernelvec 保存
     * 中断处理程序的寄存器保存在 p->context 中，通过 swtch() 保存

   [假设在系统调用执行期间发生抢占的示意图]
      aaa
      usertrap
      syscall
      kernelvec                  bbb
      kerneltrap                 usertrap
      yield         main         yield
      sched       scheduler      sched
      swtch  ->  swtch  swtch -> swtch

   内核中是否必须支持抢占？
     不必，因为内核中不存在无限循环的 CPU 密集型操作。
     但如果某些系统调用需要大量计算，抢占则很有价值。
     或者当我们需要严格的线程优先级机制时。

为什么不允许在上下文切换时持有自旋锁？
   p->lock 除外
   P1:
     acquire(L1)
     yield()
   P2:
     acquire(L2)
     acquire(L1)
   P2 持有 L2，因此 P2 在 acquire(L1) 中自旋时中断已关闭
     -> 定时器中断不会发生
     -> P2 不会让出 CPU
     -> P1 无法执行
     -> P1 永远不会释放 L1

我们能否去掉独立的每 CPU 调度器线程？
   sched() 能否直接 swtch() 到一个新线程？
   那样会更快——可以省去一次 swtch() 调用
   我们会将 scheduler() 的循环移入 sched()
   或许可以——但是：
     调度循环将在某个线程的内核栈上运行于 sched() 中
     如果该线程正在退出怎么办？
     如果线程数少于 CPU 数——即栈不够用怎么办？
   因此可能较为棘手

为什么 scheduler() 要通过 intr_on() 开启中断？
   （演示：注释掉 kernel/proc.c:scheduler 中的 intr_on、intr_off）
      make CPUS=1 qemu-gdb
      gdb
      (gdb) c
   可能不存在处于 RUNNABLE 状态的线程
     它们可能全都在等待 I/O，例如磁盘或控制台
   开启中断以便设备有机会发出完成信号
     从而唤醒某个线程
   否则，系统将会冻结

线程高效吗？
   内存开销：每个线程一个栈
   CPU 时间开销：swtch()
   通常足够高效——而且无疑很方便
   如果线程数量很多（内存压力）或切换频繁（CPU 压力），则会成为问题
   除线程外，还有其他技术可用于任务交错执行
     参见事件驱动编程或状态机
   线程并非最高效的方式，但它们很方便

用户态进程可以拥有多个用户态线程吗？
   xv6 不支持这一特性
   但其他系统支持，例如 Linux、MacOS
   通常每个用户态线程对应一个内核线程
