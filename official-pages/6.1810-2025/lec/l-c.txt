6.1810 2025 第2讲：用C语言编写xv6程序

为什么选择C？
  适合底层编程
    C语言与RISC-V指令之间映射关系简单直接
    C类型与硬件结构之间映射关系简单直接
      例如，设置设备硬件寄存器中的位标志
  运行时开销极小
    易于移植到其他硬件平台
    可直接访问硬件
  显式内存管理
    无垃圾回收机制
    内核完全掌控内存管理
  高效：编译执行（无需解释器）
    编译器将C语言编译为汇编代码
  广泛用于构建内核、系统软件等
    几乎在任何平台上都有良好的C语言支持
  为什么不选C？
    容易编写出错误的代码
    容易编写出存在安全漏洞的代码

示例：编译cat.c
  Makefile定义了编译方式
  gcc将源文件编译为.o文件
  ld将.o文件链接为可执行文件
    ulib.o是xv6的精简C库
  riscv64-linux-gnu-objdump -htr user/cat.o
    来自cat.c的已编译代码，含用于填入ulib的重定位记录
  可执行文件采用a.out格式，包含以下节：
    text（代码）、已初始化数据、符号表、调试信息等
  riscv64-linux-gnu-objdump -fp user/_cat
    各节由user.ld定义

探索 _cat 的 a.out
  riscv64-linux-gnu-objdump -S user/_cat
    与 user/cat.asm 相同
  0x0: cat
    如果我们同时运行两个 cat 程序会怎样？
    参见页表讲义
  0xf6: start
    user.ld 的默认入口点
  start 是什么？
    在 ulib.c 中定义，调用 main() 和 exit(0)
  数据内存在哪里？（例如 buf）
    在数据段/BSS 段中
    必须由内核初始化
  但我们知道 buf 应该在的地址
    riscv64-linux-gnu-nm -n user/_cat

C 指针
  指针是内存地址
    每个变量都有一个内存地址（即 p = &i）
    因此每个变量都可以通过其指针访问（即 *i）
    指针可以是变量（例如 int *p）
      因此也有内存地址，等等
  指针运算
    char *c;
    int *i;
    c+1 和 i+1 的值是多少？
  访问结构体的成员
    struct {
       int a;
       int b;
    } *p;
    p->a = 10
  [demo ptr.c]
    
C 数组
  存储相同数据类型（char、int 等）的连续内存
    无边界检查，不能动态增长
  访问数组的两种方式：
    通过下标：buf[0]、buf[1]
    通过指针：*buf、*(buf+1)
  [demo array.c]

C 链表（更多指针）
  单链表
    kernel/kalloc.c 实现了一个内存分配器
    维护一个空闲内存"页"的链表
      一页为 4096 字节
      free 将页插入链表头部
      kalloc 从链表头部取页
  双链表
    kernel/bio.c 实现了一个 LRU 缓冲区缓存
    brelse() 需要将一个 buf 移到链表头部
    见 buf.h
      两个指针：prev 和 next

按位运算符
  char/int/long/指针各有其位数（在 RISC-V 上分别为 8、32、64 位）。
  可以用 |、&、~、^ 对其进行操作
    10001 & 10000 = 10000
    10001 | 10000 = 10001
    10001 ^ 10000 = 00001
    ~1000 = 0111
  示例：
    user/usertests.c
    kernel/fcntl.h
    kernel/sysfile.c
  后续还有更有趣的示例
  
关键字：
  static：将变量的可见性限制在其声明所在的文件内
    但在文件内是全局的
  void："无类型"、"无值"、"无参数"

常见 C 语言错误
  释放后使用
  重复释放
  未初始化内存
    栈上的内存或由 malloc 返回的内存不为零
  缓冲区溢出
    写入超出数组末尾
  内存泄漏
  类型混淆
    错误的类型转换
