上一讲的要点：
  页面分配通常是惰性的（比 xv6 多得多）
  当程序启动时，其页表可能完全为空
  当它分配内存时，它的页表一般不会改变！
  当程序第一次*访问*页面时：
    页面错误
    内核分配物理页，初始化（零，或从文件读取）
    映射到页表
  why?
    透明快速启动
    程序可以请求大量内存而无需担心 RAM 大小

页表的最初用途：
  支持大于 RAM 的应用程序
  只有一个，或者很多，总数很大
  可以追溯到内存相对非常昂贵的时代
  仍然有用且值得了解（也是今天论文背景的一部分）
  “分页”或“分页到磁盘”

磁盘分页如何工作？
  即如何让程序认为它们拥有比 RAM 更多的内存？

玩具示例：机器只有两页 RAM，
  但一个程序想要使用 4 页数据

diagram:
  页表：4 个 PTE
  RAM：两页物理内存
    最初免费
  磁盘：4页“分页”存储，一页可执行文件

读取 va 0 上的页面错误
  内核透明地处理页面错误
  分配 phys 页#1
  从可执行文件中读取
  PTE0 -> pa1

在 va 2 上写入页错误（实际上是 va 0x2000，第 3 页）
  分配物理页#0
  将其归零
  PTE2 -> pa0

va 1 上写页错误
  没有可用 RAM：现在怎么办？
  选择一个非免费物理页面，假设物理页面#0
  将 phys 页 #0 写入磁盘页 2
    我们知道我们必须保存它，因为 PTE2 将设置脏位
    PTE2 -> invalid
    记住 va 2 在磁盘上的位置
    “驱逐”或“页出”或“替换”
  初始化 va 1 的 phys 页#0
  PTE1 -> pa0

va 2 上的页面错误（读或写）
  让我们逐出物理页 #1 (va 0)
    将页 #1 写入磁盘块 #1
    PTE0无效
  让我们将虚拟页面 2“分页”到物理页面 #1
  PTE2 -> pa1

我们使用 RAM 作为缓存，使用磁盘作为“后备存储”

现在的记忆是巨大的，为什么例如Linux 支持分页到磁盘吗？
  当分页发明时，内存很小（< 1 MB）并且昂贵
  现在电脑单机很便宜，有GB的内存
  但内存仍然是一项巨大的开支，例如在数据中心
    总内存成本通常高于 CPU
  程序和数据不断变大
  因此对于操作系统来说优化 RAM 使用仍然很重要
  页面替换仍然很重要：
    管理文件缓存
    非常大的程序
    内存映射大文件
    避免硬边

驱逐策略非常重要：
  如果我们驱逐一个本身即将被使用的页面，
    这将导致另一个页面错误和磁盘读取
  磁盘读取大约需要一毫秒
  那是一百万条指令！
  故障过程必须等待...
  糟糕的驱逐策略可能会导致大量耗时的页面错误

想法：驱逐从现在开始使用时间最长的页面
  遗憾的是，一般来说内核无法预测这将是哪个页面
  所以我们需要可以实施的驱逐启发法
  人们发明了很多驱逐策略

常见的驱逐策略：最近最少使用（LRU）
  内核保留所有物理页号的 LRU 列表
  内核定期扫描所有物理页
    查找每个 PTE，查看“已访问”位
    如果设置了 Accessed 位，则将页面移动到 LRU 列表的头部
    并清除访问位
  因此，如果一个页面被多次使用，它就会不断地被移动到 LRU 列表的头部
  当页面错误需要内存的物理页面时，
    从LRU链表尾部取出

驱逐页面时，需要使引用该页面的所有 PTE 无效
  可能不止一种：写时复制分叉、内存映射文件、共享内存
  通常内核有一个“反向映射”将 PA 映射到页表和 VA 列表

驱逐干净页面比驱逐脏页面更好
  clean == there's already an identical copy on the disk
    来自先前的页出，或者在只读可执行文件中
  我们可以重新使用干净的页面，而不必先将其写入磁盘
    只需要将其归零，然后调整新旧 PTE
  如果我们可以重新使用（逐出）干净页面，页面错误会更快

更详细的 LRU 方案（论文第 5.1 节中的 FreeBSD 方案）
  三个 LRU 列表：
    活跃
    不活跃
    缓存
  定期扫描；如果已访问（在任何列表上），则移至活动的头部
  如果内存紧张：
    将“活动”的尾部移至“非活动”
    将脏的非活动页写入磁盘
    将非活动列表的干净尾部移动到缓存列表
  所以缓存列表只包含一段时间没有使用的干净页面
    这是为页面错误分配的缓存页面

保持缓存列表非空对于快速页面错误很重要
  如果“内存压力”，扫描速度更快，更快地将脏页写入磁盘
  内存压力=缓存LRU列表太短

磁盘分页何时能正常工作？
  如果应用程序在任何给定时间仅使用其内存的一小部分
    这样活动内存就可以保存在 RAM 中，其余的则分页到磁盘
  “参考地点”
  “工作集”
  工作集可能会随着时间的推移而改变，但希望是缓慢的
  许多程序都是如此，但并非全部

如果程序的工作集太大怎么办？
  或者运行的程序太多？
  内核将驱逐即将需要的页面
  大量的内存访问会导致页面错误和磁盘读写
  磁盘比 RAM 慢得多，系统速度会显着变慢
  “殴打”

LRU 是一个好的计划吗？
  LRU is effectively a prediction: recently used => will be used again soon
  通常效果很好
  但有时很糟糕！
  示例：通过大内存重复顺序扫描
  该程序可能会在*每个*页面上出现错误
    最近最少使用的页面将是程序即将访问的页面！
  所以，对于这个程序，LRU 是一个糟糕的替换策略
  因此，有些系统使用随机替换，或将其作为选项提供

页面应该有多大？
  假设只有一种尺寸
  CPU 设计者选择页面大小，内核必须接受它
  很久以前：小，例如512字节
  现在经常是4096（但是纸质用8k，有的更大）
  为什么喜欢大？
    页表消耗的内存更少
      16 GB -> 32 MB of PTEs if 4k pages
    用于内核簿记的 CPU 和内存更少
      空闲列表、反向映射、VMA
    更少的页面错误（假设引用位置良好）
  为什么喜欢小的？
    仅部分使用的页面浪费的 RAM 更少
      因此对于给定的工作负载可能需要更少的 RAM
    PTE 访问和脏位的更细粒度
      这样内核就可以更精确地将所需的数据保存在 RAM 中
    每次页面输入和页面输出的磁盘 I/O 更少，因此页面错误延迟更低
  无论大小都有引人注目的特性
  今天的论文是关于操作系统对*两者*的支持

今天报纸的最后一个背景：TLB
  翻译后备缓冲区
  虚拟地址到物理地址转换的CPU缓存
  这是一张 VA、PA 表
  【图：核心、L1、L2、RAM，然后添加TLB】

每个内存引用都需要 va 到 pa 查找
  ld、st、取指令
  所以 CPU 需要能够在每个周期执行大约一个操作——纳秒

TLB 通常很小
  因为它一定非常快
  论文：128 条
  现代 CPU：128 个 L1 条目，1024 个 L2 条目

TLB 的“范围”是什么？
  128 个条目，4k 页：半兆字节！
  1024 个条目：4 兆字节
  对于 RAM >= 16 GB 的机器和程序来说，这是很小的
  经常使用更多内存的程序将在 TLB 中丢失

TLB 未命中的成本是多少？
  RISC-V CPU 遍历多级页表以获取叶 PTE
    （RISC-V 硬件处理 TLB 未命中，而不是内核）
  这是几次内存读取，每次最多 100 ns
    数百个周期（尽管 CPU 数据缓存可能有所帮助）
  CPU 可能会停止运行，直到 TLB 填满
  因此 TLB 未命中可能会使指令时间增加约 100 倍

更大的页面是增加 TLB 范围的一种方法
  128 个 TLB 条目 * 2MB 页 = 1/4 GB
  事实上，现代 CPU 的超级页面至少有那么大

但大页面会浪费大量 RAM！
  因为有些程序只使用每个页面的一小部分
  能够混合小页面和超级页面很有吸引力
  你们都熟悉基本思想了！
  
今天的报纸
  目标：内核自动在基页和超级页之间进行选择
    增加 TLB 到达范围，减少 TLB 未命中中浪费的时间
  适应程序特征，包括行为的变化
  应对大小程序、紧张和松散的内存压力
  透明地做到这一点——经典的内核策略

给进程一个 2MB 的超级页面实际上是一个预测：
  在不久的将来，进程将相当密集地使用这 2MB
  而不是例如仅使用 2MB 中的几千字节
  if wrong -> wasted RAM
  张力：较少的 TLB 未命中与浪费的 RAM

三个令人费解的设计问题
  今天的论文、后续研究、真正的内核，例如Linux

* 内核什么时候应该给应用程序一个超级页面（PTE 和 2MB RAM）？
  当应用程序调用 sbrk() 时？
    很难从 sbrk() 大小参数猜测情况。
    sbrk(2MB) 可能并不意味着进程将使用该内存。
    sbrk(4096) 可能是完整 2MB 分配中的第一页。
  当应用程序在 2MB 区域发生第一个页面错误时？
    （这是Linux的做法之一）
    至少我们知道它将使用一些 RAM
    但也许不是全部，导致内存浪费
    应用程序将立即从超级页面中受益
    这是一个赌注，超级页面通常是合适的
      可能是一个不错的计划，特别是如果有大量 RAM，一些大应用程序
  当应用程序在 2MB 区域中的所有页面上出现页面错误时？
    将区域转换为超级页面
    （这是论文的方法）
    好：我们知道它 100% 使用了 2 MB 超级页面
    坏：我们让它执行很长一段时间，没有超级页面的好处
    这是一种保守的方法，优先考虑不浪费内存

* 内核如何找到合适的2MB RAM 区域？
  必须是连续的、2MB 对齐且空闲
  2MB 长的免费运行很少是偶然发生的！
    phys mem 通常是“碎片化的”——已使用的和空闲的 4k 页面散布在其中
    4k 页面没问题，如果同时使用 4k 和 2MB 则问题大
  在启动时分配一些 2MB 的 RAM 区域？
    （为简单起见，这是实验室的建议）
    但有多少？
    如果需要更多或更少怎么办？
  需要时移动（复制）物理页以清除 2MB？
    “压缩”或“碎片整理”
    并修补移动页面的 PTE
    （这是Linux的做法之一）
    导致分配或首次使用缓慢，使用CPU进行压缩

该论文提出了一个巧妙的分配计划（第 4.1 节）
  在新的 2MB 区域出现第一次故障时，
    创建一个普通的 PTE，仅分配并初始化一页
  而且还从 LRU“缓存”列表中保留 2MB 的页面
    这些是一段时间没有使用的干净页面
  该论文实际上并未分配或初始化或映射这些页面
    所以他们仍然保留缓存的内容
    如果使用它们的原始映射
  随着超级页面中出现更多错误，分配更多
    那些保留的页面，并初始化它们
  当2MB区域中的所有普通页都出现故障时，升级
    到超级页面
  问题：为什么这样的安排是好的？

* 内核有时需要降级超级页面
  如果内存紧张；较小的页面可能需要较少的 RAM
    哪些超级页面应该被降级？
  problem:
    2MB 粒度访问位使得很难判断真正在使用什么
    因此，分解超级页面以获得更细粒度的访问位
  also:
    也许一个进程写入超级页面
    不希望单次写入（稍后）导致整个 2MB 页面调出
    所以读保护超级页，在第一次写入时降级，然后
      可以从更细粒度的脏位中受益

目前状况？
  Linux 最容易跟踪；网上有很多帖子。
  对于某些应用非常有价值。
  但“透明大页”在其他情况下会浪费大量内存，
    因为实际只使用了 2MB 的一小部分。
  因此，随着时间的推移，设计细节发生了很大变化。
    谨慎的应用程序通常会显式分配其超级页面。
  仍在积极发展。
  也许根本问题是收益往往相当可观
    适度，但成本（内存浪费）可能非常大。
