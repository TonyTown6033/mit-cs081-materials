6.1810 2025 L9：磁盘分页与超级页

超级页的实际、透明操作系统支持，
Navarro、Iyer、Druschel 与 Cox，OSDI 2002。

提纲：
  经典操作系统分页
  TLB 相关考虑
  本节论文

上节课的重要内容：
  页分配通常是惰性分配（远比 xv6 中更为普遍）
  程序启动时，其页表可能完全为空
  程序分配内存时，其页表通常不会发生变化！
  当程序首次*访问*某页时：
    发生缺页错误
    内核分配一个物理页，进行初始化（清零，或从文件读取）
    映射到页表中
  为什么这样设计？
    透明快速启动
    程序可以申请大量内存，而无需担心 RAM 容量

页表的原始用途：
  支持大于 RAM 容量的应用程序
  单个应用或多个应用的总量超出 RAM
  起源于内存相对非常昂贵的年代
  至今仍然实用且值得了解（也是本节论文的背景之一）
  "分页"或"磁盘分页"

磁盘分页如何工作？
  即如何让程序认为其拥有的内存多于实际 RAM？

简单示例：机器仅有两页 RAM，
  但程序希望使用 4 页数据

示意图：
  页表：4 个 PTE
  RAM：两页物理内存
    初始为空闲状态
  磁盘：4 页"分页"存储空间，一个单页可执行文件

对虚拟地址 va 0 发生读缺页错误
  内核透明地处理该缺页错误
  分配物理页 #1
  从可执行文件读取内容
  PTE0 -> pa1

对虚拟地址 va 2（实际为 va 0x2000，第 3 页）发生写缺页错误
  分配物理页 #0
  将其清零
  PTE2 -> pa0

对虚拟地址 1 发生写页错误
  没有空闲内存：现在怎么办？
  选择一个非空闲的物理页，假设选择物理页 #0
  将物理页 #0 写入磁盘页 2
    我们知道必须保存它，因为 PTE2 的脏位已置位
    PTE2 -> 无效
    记住虚拟地址 2 在磁盘上的位置
    "驱逐"或"换出"或"页面置换"
  为虚拟地址 1 初始化物理页 #0
  PTE1 -> pa0

对虚拟地址 2 发生页错误（读或写）
  驱逐物理页 #1（虚拟地址 0）
    将页 #1 写入磁盘块 #1
    PTE0 置为无效
  将虚拟页 2"换入"到物理页 #1
  PTE2 -> pa1

我们将内存用作缓存，磁盘用作"后备存储"

现在内存已经很大了，为什么 Linux 等系统仍然支持换页到磁盘？
  换页技术发明时，内存极小（< 1 MB）且价格昂贵
  如今计算机单价低廉，内存已达 GB 级别
  但内存在数据中心等场景中仍是巨大的开销
    总内存成本通常超过 CPU
  而且程序和数据持续增长
  因此操作系统优化内存使用仍然至关重要
  页面置换依然重要：
    管理文件缓存
    超大型程序
    内存映射大文件
    避免硬性边界

驱逐策略至关重要：
  如果我们驱逐的页面本身即将被使用，
    将会引发另一次页错误和一次磁盘读取
  一次磁盘读取大约需要一毫秒
  这相当于一百万条指令的时间！
  发生页错误的进程必须等待……
  糟糕的驱逐策略会导致大量耗时的页错误

思路：驱逐下次被使用时间距现在最远的页面
  遗憾的是，内核通常无法预测哪个页面满足此条件
  因此我们需要可实际实现的驱逐启发式策略
  人们发明了许多页面换出策略

一种常见的换出策略：最近最少使用（LRU）
  内核维护一个包含所有物理页号的 LRU 列表
  内核定期扫描所有物理页
    为每个物理页找到对应的 PTE，查看"Accessed"位
    若 Accessed 位已置位，则将该页移至 LRU 列表头部
    并清除 Accessed 位
  因此，若某页被频繁使用，它会不断被移到 LRU 列表头部
  当缺页错误需要一个物理内存页时，
    从 LRU 列表尾部取出一页

换出页面时，需要使所有指向该页的 PTE 失效
  可能不止一个：写时复制 fork、内存映射文件、共享内存
  通常内核维护一张"反向映射"表，将物理地址（PA）映射到页表及虚拟地址（VA）的列表

优先换出干净页而非脏页
  干净页 == 磁盘上已存在相同副本
    来自之前的页面换出，或只读可执行文件中的内容
  复用干净页无需先将其写入磁盘
    只需将其清零，并调整新旧 PTE
  若能复用（换出）干净页，缺页错误的处理会更快

一种更精细的 LRU 方案（论文第 5.1 节中的 FreeBSD 方案）
  三条 LRU 列表：
    Active（活跃）
    Inactive（非活跃）
    Cache（缓存）
  定期扫描；若 Accessed 位已置位（无论在哪条列表），移至 Active 列表头部
  若内存紧张：
    将 Active 列表尾部的页移至 Inactive 列表
    将 Inactive 中的脏页写入磁盘
    将 Inactive 列表尾部的干净页移至 Cache 列表
  因此 Cache 列表只包含一段时间内未被使用的干净页
    缺页错误所需的页从 Cache 列表中分配

保持 Cache 列表非空对快速处理缺页错误至关重要
  若"内存压力"增大，则加快扫描速度，更快地将脏页写入磁盘
  内存压力 = Cache LRU 列表过短

磁盘换页在什么情况下效果较好？
  若应用程序在任意时刻只使用其内存的一小部分
    从而使活跃内存可以保留在 RAM 中，其余部分换出到磁盘
  "引用局部性"
  "工作集"
  工作集可能随时间变化，但希望变化缓慢
  这对许多程序成立，但并非所有程序都如此

如果程序的工作集太大会怎样？
  或者运行的程序太多？
  内核会驱逐即将被需要的页面
  大量内存访问将引发页面错误及磁盘读写
  磁盘比内存慢得多，系统将会显著变慢
  "抖动"

LRU 是个好策略吗？
  LRU 本质上是一种预测：最近使用过 => 不久后还会再次使用
  通常效果不错
  但有时会很糟糕！
  例如：对大块内存反复进行顺序扫描
  程序很可能会在*每一个*页面上都触发缺页错误
    最久未使用的页面恰恰是程序即将访问的那个！
  因此，对于这类程序，LRU 是一种糟糕的替换策略
  所以一些系统采用随机替换，或将其作为可选策略

页面应该多大？
  假设只有一种大小
  CPU 设计者决定页面大小，内核必须接受它
  早期：较小，例如 512 字节
  现在通常为 4096（但论文使用 8k，有些更大）
  为何倾向于大页面？
    页表占用的内存更少
      16 GB -> 若使用 4k 页，则 PTE 占用 32 MB
    内核簿记所需的 CPU 和内存开销更少
      空闲链表、反向映射、VMAs
    缺页错误更少（假设具有良好的局部性）
  为何倾向于小页面？
    对于仅部分使用的页面，浪费的内存更少
      因此给定工作负载所需的内存可能更少
    PTE 的 Accessed 位和 Dirty 位粒度更细
      内核可以更精确地只将所需数据保留在内存中
    每次换入/换出的磁盘 I/O 更少，缺页延迟更低
  大页面和小页面各有其令人信服的特性
  今天的论文讨论的是操作系统对*两者*的支持

今天论文的最后一个背景知识：TLB
  Translation Lookaside Buffer（旁路转换缓冲）
  CPU 对虚拟地址到物理地址转换的缓存
  它是一张 va、pa 对照表
  [图示：核心、L1、L2、内存，再加上 TLB]

每次内存访问都需要进行虚拟地址到物理地址的查询
  ld、st、取指令
  因此 CPU 需要能够大约每个时钟周期完成一次——纳秒级

TLB 通常很小
  因为它必须极快
  论文中：128 个条目
  现代 CPU：128 个 L1 条目，1024 个 L2 条目

TLB 的"覆盖范围"是多少？
  128 个条目，4k 页：半兆字节！
  1024 个条目：四兆字节
  对于内存 >= 16 GB 的机器和程序而言，这非常小
  频繁使用更多内存的程序将会在 TLB 中发生缺失

TLB 缺失的代价是什么？
  RISC-V CPU 遍历多级页表以获取叶节点 PTE
    （RISC-V 硬件处理 TLB 缺失，而非内核）
  这需要进行几次内存读取，每次最多耗时 100 ns
    数百个时钟周期（不过 CPU 数据缓存可能有所帮助）
  CPU 可能会停顿，直到 TLB 填充完毕
  因此一次 TLB 缺失可能使指令执行时间增加约 100 倍

更大的页是扩大 TLB 覆盖范围的一种方法
  128 个 TLB 条目 * 2MB 页 = 1/4 GB
  现代 CPU 确实支持至少这么大的超级页

但是大页可能会浪费大量内存！
  因为某些程序只使用每页中很小一部分
  能够混合使用小页和超级页是很有吸引力的
  你们都熟悉这个基本思路！
    
今天的论文
  目标：内核自动在基本页和超级页之间做出选择
    以扩大 TLB 覆盖范围，减少 TLB 缺失所浪费的时间
  适应程序特性，包括行为的变化
  应对大型和小型程序，以及宽松和紧张的内存压力
  以透明方式实现——这是内核的经典策略

为进程分配一个 2MB 的超级页实际上是一种预测：
  进程在近期将相当密集地使用这 2MB 内存
  而不是例如只使用这 2MB 中的几千字节
  若预测错误 -> 浪费内存
  权衡：减少 TLB 缺失 vs 浪费内存

三个令人困惑的设计问题
  由今天的论文、后续研究以及 Linux 等实际内核加以解决

* 内核何时应为应用程序分配超级页（PTE 及 2MB 内存）？
  当应用程序调用 sbrk() 时？
    难以从 sbrk() 的大小参数推断实际情况。
    sbrk(2MB) 不一定意味着进程会使用该内存。
    sbrk(4096) 可能是完整 2MB 分配中的第一页。
  当应用程序在一个 2MB 区域内发生第一次缺页错误时？
    （这是 Linux 的方法之一）
    至少那时我们知道它会使用一些内存
    但也许不会全部使用，导致内存浪费
    应用程序将立即从超级页中受益
    这是一个赌注，即超级页通常是合适的
      这可能是一个好策略，尤其是在内存充足、应用程序较少的情况下
  当应用程序在一个 2MB 区域内的所有页上都发生了缺页错误时？
    将该区域转换为超级页
    （这是论文的方法）
    好处：我们知道它使用了 100% 的 2MB 超级页
    坏处：我们让它在没有超级页优势的情况下执行了相当长的时间
    这是一种保守的方法，优先考虑不浪费内存

* 内核如何找到合适的 2MB 内存区域？
  必须是连续的、2MB 对齐的且空闲的
  2MB 长的连续空闲区域很少偶然出现！
    物理内存通常是"碎片化"的——已用和空闲的 4k 页交错分布
    对 4k 页没有问题，但如果同时使用 4k 和 2MB 页则问题很大
  在启动时分配一些 2MB 的内存区域？
    （这是实验建议的方式，为了简单起见）
    但需要多少？
    如果需要更多或更少怎么办？
  移动（复制）物理页以在需要时清理出 2MB 空间？
    "压缩"或"去碎片化"
    并修补被移动页的页表项
    （这是 Linux 的方法之一）
    导致分配或首次使用变慢，并消耗 CPU 进行压缩

论文提出了一种巧妙的分配方案（第 4.1 节）
  在一个新的 2MB 区域内发生第一次缺页错误时，
    创建一个普通的页表项，仅分配并初始化该一个页
  同时从 LRU "Cache" 列表中预留 2MB 的页
    这些是近期未被使用的干净页
  论文实际上并不分配、初始化或映射这些页
    因此它们仍然保存着各自的缓存内容
    以防其原始映射被使用
  随着超级页区域内发生更多缺页错误，分配更多
    这些预留的页并对其进行初始化
  当 2MB 区域内的所有普通页都发生缺页错误后，将其提升
    为一个超级页
  核心问题：为什么这种安排是好的？

* 内核有时需要降级超级页
  如果内存紧张；较小的页可能需要较少的内存
    哪些超级页应该被降级？
  问题：
    2MB 粒度的 Access 位难以准确反映实际使用情况
    因此将超级页拆分以获得更细粒度的 Access 位
  另外：
    如果一个进程写入超级页
    不希望单次写操作（之后）导致整个 2MB 被换出
    因此对超级页设置写保护，在首次写时降级，然后
      可以受益于更细粒度的 Dirty 位

当前状态如何？
  追踪 Linux 最为方便，网上有大量相关文章。
  对某些应用程序非常有价值。
  但"透明大页"在其他场景下会浪费大量内存，
    原因在于 2MB 中实际使用的只是一小部分。
  因此相关设计细节随时间变化了很多。
    谨慎的应用程序通常会显式分配超级页。
  目前仍在持续演进中。
  或许根本问题在于：收益往往相当有限，
    而代价（内存浪费）却可能非常巨大。
