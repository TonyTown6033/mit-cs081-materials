以太网地址
  每块以太网网卡都有一个内置的唯一以太网地址
    由网卡制造商分配
    <24 位制造商 ID，24 位序列号>
  早期以太网通过电缆广播
    主机通过目标地址判断数据包是否真正发给自己
  现代以太网局域网使用交换机，每台主机各连一根线
    交换机通过目标地址决定将数据包发送给哪台主机

我们能否将以太网地址用于一切？
  1. 不行：以太网并非唯一的底层地址类型
  2. 不行："扁平"地址使广域路由变得困难
  因此：使用 32 位 IP 地址，并在高位嵌入路由信息

IP 头部
  [kernel/net.h, struct ip]
  以太网类型 0x0800
  包含很多字段，但地址是最关键的
  一个 32 位 IP 地址足以路由到互联网上的任意一台计算机
  高位包含"网络号"，帮助路由器
    了解如何在互联网中转发数据包
  协议号告知目的端如何处理该数据包
    即将其交给哪个上层协议（通常是 UDP 或 TCP）

[tcpdump -t -n -xx ip | more]

注意：
  模式：将上层数据包"嵌套"在下层数据包中
  [diagram: eth | ip | udp | DNS]
  某一层的载荷以下一层的首部开始
  因此通常会看到一系列首部依次排列

UDP 首部
  [kernel/net.h, struct udp]
  数据包到达正确主机后，应交给哪个应用程序？
  UDP 首部位于 IP 数据包内部
  包含源端口号和目的端口号
  应用程序使用"socket API"系统调用告知
    内核它希望接收发往某一特定端口的所有数据包
  某些端口是"知名端口"，例如 53 号端口保留给 DNS 服务器
  其他端口按需分配给连接的客户端
  UDP 首部之后为载荷，例如 DNS 请求或响应

[tcpdump -t -n udp]

典型内核中的网络代码是什么样的？
  设计对性能和过载处理至关重要

控制流
  * 网卡硬件（通常不止一块网卡！）
    网卡内部缓冲区
  * 网卡 DMA 引擎
    DMA 接收环
  * 接收中断处理程序，将数据从网卡复制到软件输入队列
    IP 输入队列
  * 网络线程
    IP 等协议处理
    可能转发
    可能写入 socket 队列
  * 应用程序
  * 输出处理
  - IP 输出队列
  * 发送中断处理程序
  - 释放已完成的网卡 TX DMA 环槽位
  - 将数据从软件输出队列复制到 TX 环
  * NIC

网络实验是这一架构的子集

注意事项：
  -- 数据包进入时，每一层负责解析、验证并剥除首部
     若数据包损坏或队列过长则丢弃
  -- 数据包发出时，每一层负责在前面加上首部
    
为什么需要这些数据包队列？
  吸收临时的输入突发流量，避免在软件繁忙时被迫丢包
  在计算过程中保持输出 NIC 持续工作
  允许独立的控制流（NIC、网络线程与应用程序之间）
    在边界处设置队列

其他架构方案也是可行的，有时效果更好
  例如，用户态协议栈
  例如，用户直接访问 NIC（参见 Intel 的 DPDK）
  例如，轮询方式，如今日论文所述

作者 Mogul 与 Ramakrishnan，1996 年

我们为什么阅读这篇论文？
  为了研究内核网络栈结构中的若干权衡取舍
  这是一篇著名且具有深远影响的论文

问题所在：
  网卡中断的优先级高于所有其他处理。
  随着输入速率的增长，中断最终会占用 100% 的 CPU。
  此时 CPU 没有时间用于其余的 IP 处理。
    （只有一个核心！）
  IP 输入队列增长至允许的最大长度。
  网卡中断随后读取每个数据包，发现队列已满，丢弃数据包。

从更高层次来看：
  软件浪费时间对那些
    最终会被丢弃的数据包进行部分处理。

论文的解决方案是什么？
  不设 IP 输入队列
  网卡接收中断仅用于唤醒网络线程
    然后将该网卡的中断*禁用*
  线程完成所有处理，
    重新检查网卡是否有更多输入，
    仅在没有待处理输入时才重新启用中断。

从更高层次来看：
  丢弃操作尽可能早地发生（在网卡中）。
  CPU 不会浪费时间去部分处理注定被丢弃的数据包。

为什么"轮询（无配额）"效果很差？
  输入处理使发送完成处理得不到执行（饥饿）

为什么"无配额"会急剧下降，而不是逐渐降低？
  在丢弃之前做了更多处理，使活锁问题更加严重
  即每个多余的接收数据包消耗了许多发送数据包的 CPU 时间

解释图 6-4
  （此时每个数据包都要经过一个用户态程序）
  为什么"轮询，无反馈"表现很差？
    screend 前面有一个队列
    若发生过载，100% 的时间给网络线程，0% 给 screend
  为什么"轮询加反馈"表现良好？
    当 screend 队列接近满时，网络线程进入睡眠
    当队列接近空时唤醒

总体思路：轮询循环是施加调度控制的地方
  配额、反馈

通用原则？
  如果启动新工作可能妨碍已有工作的完成，则不要启动新工作
  需要丢弃时，尽可能早地执行丢弃操作
  设计应使效率随负载增加而提升，
    而不是下降。例如，论文中在高负载下从
    中断切换为轮询。

解决同一问题的其他方法
  中断合并
  多核与多网卡队列
  将网卡 DMA 环直接暴露给用户代码（DPDK）

类似现象在系统的其他领域中同样存在
  网络中的超时加重传，随连接数增长
  自旋锁，随核心数增长

一个通用教训：复杂（多阶段）系统若要在过载下存活，
  需要对资源进行精心的调度
