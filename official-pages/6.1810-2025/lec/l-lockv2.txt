6.1810 2025 第12讲：锁

为什么要讲锁？
  应用程序希望利用多核处理器实现并行加速
  因此内核必须处理并行的系统调用
  进而需要并行访问内核数据（缓冲区缓存、进程等）
  锁有助于正确共享数据
  锁可能限制并行加速效果

如果没有锁会出现什么问题
  案例分析：删除 kalloc.c 中 kfree() 里的 acquire/release

会出现什么问题？
  示例：同时调用 kfree() -> 页丢失
  [示意图：core1、core2、总线、RAM]

启动，运行 usertests
  能运行相当长一段时间！
  为何崩溃？
    r->next = freelist
      kalloc()
    freelist = r
    因此已分配的页仍留在空闲链表中！
      很快会被二次分配，在使用过程中被覆盖
    尽管 kalloc() 有锁保护
  问题所在：
    我们需要锁来保证正确性
    但会损失性能（kfree 被串行化）
        
锁的抽象：
  锁 l
  acquire(l)
    x = x + 1 -- "临界区"
  release(l)
  锁本身是一个对象
  若多个线程调用 acquire(l)
    只有一个线程会立即返回
    其余线程等待 release() —— "阻塞"
  程序通常拥有大量数据和大量锁
    若不同线程使用不同数据，
    则它们很可能持有不同的锁，
    从而可以在多核上并行执行——完成更多工作。
  注意：锁 l 并不与数据 x 绑定
    程序员必须自行规划二者之间的对应关系

决定何时需要加锁的保守原则：
  只要两个线程可能访问同一内存位置，且至少有一个是写操作
  因此：除非持有正确的锁，否则不要访问共享的读写数据！

为什么说"保守"？
  有时过于严格：程序逻辑有时可以排除共享的情况
  有时过于宽松：printf() 并不总是简单的锁与数据的对应关系

锁能否自动化？
  也许语言可以为每个数据对象关联一把锁
    编译器在每次使用时自动添加 acquire/release
    程序员就不容易忘记了！
  但编译器难以判断数据是否在多个核之间共享
  而且"保护单个对象的使用"并不是一个充分的视角
    假设 kfree() 写成这样
      acquire
      r->next = freelist;
      release
      acquire
      freelist = r;
      release
    每次内存访问都被锁保护了！
    但代码仍然是错误的。
  因此程序员通常需要对以下方面进行显式控制
    持有锁的代码区域
    以便隐藏不正确的中间状态

思考锁所实现目标的几种方式
  原子性的多步操作——隐藏中间状态
    读-改-写
  避免更新丢失（x = x + 1，或链表头插）
  维护不变量
    假设操作开始时不变量成立
    操作使用锁来隐藏对不变量的临时违反
    操作在释放锁之前恢复不变量
    如果某个函数在无并行时是正确的，通常可以
      通过在其外围加锁，使其在并行情况下也正确。

问题：死锁
  rename(f1, f2) 必须持有两把锁，分别对应两个目录
  如果出现以下情况：
    核 A              核 B
    rename(d1/x, d2/y)  rename(d2/a, d1/b)
      lock d1             lock d2
      lock d2 ...         lock d1 ...
  解决方案：
    程序员为所有锁确定一个顺序
    所有代码必须按照该顺序获取锁
    即：预判所需的锁，排序后再获取——较为复杂！

锁与模块化
  锁使得在模块内部隐藏细节变得困难
  为了避免死锁，我需要知道所调用函数所获取的锁
  并且可能需要在调用之前就先获取这些锁，即使我并不直接使用它们
  即，锁通常不是单个模块的私有事务

锁与并行性
  锁*阻止*并行执行
  为了实现并行性，通常需要对数据和锁进行拆分
    使得每个核心通常使用不同的数据和锁
    "细粒度锁"
  选择最优的数据/锁拆分方式是一项设计挑战
    整个文件系统；目录/文件；磁盘块
    整个内核；各子系统；各对象
  可能需要重新设计代码以使其在并行环境下良好运行
    示例：将单一空闲内存链表拆分为每个核心各自的空闲链表
      若线程频繁等待单一空闲链表的锁，此方法有助于提升性能
    可能需要大量的分析和编程工作！

锁粒度建议
  从粗粒度锁开始，例如用一把锁保护整个模块
    死锁风险更低，因为同时持有两把锁的机会更少
    对不变量/原子性的推理要求也更少
  通过测量来判断是否存在性能问题
    粗粒度锁通常已经足够——也许在该模块上花费的时间很少
  仅在必要时才重新设计为细粒度锁

让我们来看看 xv6 中的锁机制。

锁的典型用法：uart.c 输出
  这是许多操作系统设备驱动程序的典型组织方式
  示意图：
    user processes, kernel, UART, uartwrite()
    uartintr()
  并发来源：进程、中断
  注意中断处理程序可能会在 acquire() 中阻塞！
    等待另一个核心上的 uartwrite
  tx_lock 保护什么？
    * 进程/进程：避免输出内容相互混杂
    * 进程/进程：原子地执行 write(THR) 和 tx_busy=1
    * 进程/中断：不变量 tx_busy=1 => 中断将会到来
    * 进程/中断：原子地执行 read(LSR) 和 tx_busy=0

如何实现锁？
  考虑以下方式：
    struct lock { int locked; }
    acquire(l) {
      while(1){
        if(l->locked == 0){ // A
          l->locked = 1;    // B
          return;
        }
      }
    }

让我们来试试（这是关键问题）：
  将 acquire() 循环中的原子 test-and-set 替换为非原子操作
    while(*(volatile int *) &lk->locked != 0)
      ;
    lk->locked = 1;
  结果：启动时出现 "panic: release"
  两个 acquire() 都看到 locked == 0，都将 locked 置为 1（出错）
    （一个核的 wakeup() 与另一个核的 scheduler() 之间的竞争）
  其中一个释放锁，将 locked 置为 0
  第二个 release 发现锁已经释放，触发 panic

我们如何将检查 locked == 0 与设置 locked = 1 合并为原子操作？

RISC-V 原子交换指令：
  在 kernel/kernel.asm 中查看 acquire()：

  a5 = 1
  s1 = &lk->locked
  amoswap.w.aq a5, a5, (s1)

  硬件执行过程如下：
    在内存系统中锁定 *s1
    temp = *s1
    *s1 = a5
    a5 = temp
    解锁 *s1
  RISC-V 硬件内部具有锁定某个内存位置的机制
    不同的 CPU 有不同的实现方式
    示意图：核、总线、内存、总线仲裁器
    或通过缓存一致性协议实现
    因此我们实际上是将问题下推到了硬件层面
  内存锁保证并发的 amoswap 逐一执行，而不会交错进行

查看 xv6 自旋锁的实现
  acquire(l){
    while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
      ;
  }
  如果 l->locked 原本已经为 1，
    sync_lock_test_and_set 将其再次置为 1，返回值为 1，
    循环继续自旋
  如果 l->locked 原本为 0，最多只有一个 lock_test_and_set 能看到该 0；
    它将设置为 1 并返回 0；
    其他 test_and_set 将返回 1
  这是一种"自旋锁"，因为等待的核心在 acquire 循环中"自旋"

push_off() 的作用是什么？
  为什么要禁用中断？
  如果发生设备中断，而中断处理程序需要同一把锁，会怎样？
  就像 uart 代码中那样……

release()：
  将 lk->locked 设置为 0
  并重新启用中断

细节：内存读写顺序
  代码如此编写还有一个额外的错误原因：
    locked = 1  (aquire)
    x = x + 1
    locked = 0  (release)
  编译器和 CPU 都会对内存访问进行重排序！
    即它们不遵守源程序中内存引用的顺序
    例如，编译器可能为核心 A 生成如下代码：
      locked = 1
      locked = 0
      x = x + 1
      即将自增操作移到临界区之外！
    合法的行为集合称为"内存模型"
  release() 中对 __sync_synchronize() 的调用可防止重排序
    编译器不会将内存引用移过 __sync_synchronize()
    并且（可能）发出"内存屏障"指令来通知 CPU
  acquire() 中对 __sync_synchronize() 的调用具有类似效果
  如果使用锁，就无需理解内存排序规则

为什么使用*自旋*锁？
  acquire() 在等待时难道不会浪费 CPU 吗？
  为什么不放弃 CPU 并切换到另一个进程，让它运行？
  自旋锁使用准则：
    持有自旋锁的时间应非常短暂
    持有自旋锁时不要让出 CPU
  系统为较长的临界区提供"阻塞"锁
    等待的线程会让出 CPU
    但开销通常更高
    稍后你将看到一些 xv6 的阻塞方案

建议：
  如果可能，避免共享
  从少量粗粒度锁开始
  进行测量——哪些锁阻碍了并行性？
  仅在需要并行性能时才使用细粒度锁
  使用自动化竞争条件检测器
