为什么要谈论锁定？
  应用程序希望使用多核处理器进行并行加速
  所以内核必须处理并行系统调用
  从而并行访问内核数据（缓冲区高速缓存、进程等）
  锁有助于正确共享数据
  锁会限制并行加速

锁抽象：
  锁l
  获取(l)
    x = x + 1 --“临界区”
  释放(l)
  锁本身就是一个对象
  如果多个线程调用 acquire(l)
    只有一个人会立即返回
    其他人将等待release()——“阻塞”
  一个程序通常有大量数据、大量锁
    如果不同的线程使用不同的数据，
    那么他们可能持有不同的锁，
    因此它们可以在多核上并行执行——完成更多工作。
  请注意，锁 l 不与数据 x 绑定
    程序员必须有一个通信计划

决定何时需要锁定的保守规则：
  任何时候两个线程可以使用一个内存位置，并且至少有一个是写操作
  因此：除非您持有正确的锁，否则不要触摸共享读/写数据！

思考锁的用途的方法
  原子多步操作——隐藏中间状态
    read-modify-write
  避免丢失更新（x = x + 1，或列表前置）
  维持不变量
    假设不变量在操作开始时为真
    操作使用锁来隐藏临时违反不变量的情况
    操作在释放锁之前恢复不变量
    如果某些函数在没有并行性的情况下是正确的，通常可以
      通过用锁包围使其在并行性下正确。

问题：死锁
  rename(f1, f2) 必须在两个目录上持有两个锁
  如果：
    核心A 核心B
    重命名（d1/x，d2/y） 重命名（d2/a，d1/b）
      锁 d1 锁 d2
      锁定 d2 ... 锁定 d1 ...
  solution:
    程序员为所有锁制定一个顺序
    所有代码必须按该顺序获取锁
    即预测锁、排序、获取——复杂！

锁与模块化
  锁使得隐藏模块内的细节变得困难
  为了避免死锁，我需要知道我调用的函数获取的锁
  即使我不使用它们，我也可能需要在打电话之前获取它们
  即锁往往不是各个模块的私有业务

锁和并行性
  锁*防止*并行执行
  为了获得并行性，您通常需要拆分数据和锁
    使得每个核心通常使用不同的数据和锁
    “细粒度锁”
  选择数据/锁的最佳分割是一个设计挑战
    整个FS；目录/文件；磁盘块
    整个内核；每个子系统；每个对象
  您可能需要重新设计代码以使其并行运行良好
    示例：将单个空闲内存列表分解为每个核心的空闲列表
      如果线程在锁上长时间等待单个空闲列表，则有帮助
    可能需要大量的分析和编程！

锁定粒度建议
  从大锁开始，例如一锁保护整个模块
    由于持有两个锁的机会较少，因此死锁较少
    需要更少的关于不变量/原子性的推理
  测量一下是否有问题
    大锁通常就足够了——也许在该模块上花费很少的时间
  仅在必要时才重新设计细粒度锁定

How can we make locked == 0 atomic with locked = 1?

RISC-V原子交换指令：
  如果你查看 kernel/kernel.asm 中的 acquire() ：

  a5 = 1
  s1 = &lk->locked
  amoswap.w.aq a5, a5, (s1)

  在硬件中执行此操作：
    将 *s1 锁定在内存系统中
    温度 = *s1
    *s1 = a5
    a5 = 温度
    解锁*s1
  RISC-V h/w 内部有一个锁定内存位置的概念
    不同的CPU有不同的实现
    图表：内核、总线、RAM、总线仲裁小工具
    或通过缓存一致性协议
    所以我们确实将问题归咎于硬件
  内存锁强制并发amoswap一次运行一个，而不是交错运行

看一下xv6自旋锁的实现
  获取(l){
    while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
      ;
  }
  if l->locked was already 1,
    sync_lock_test_and_set 设置为 1（再次），产生 1，
    循环继续旋转
  if l->locked was 0, at most one lock_test_and_set will see the 0;
    它将设置为 1 并返回 0；
    其他 test_and_set 将返回 1
  这是一个“自旋锁”，因为等待核心在获取循环中“自旋”

详细信息：内存读/写顺序
  像这样的附加原因代码已损坏：
    锁定 = 1（获取）
    x = x + 1
    锁定 = 0（释放）
  编译器和CPU重新排序内存访问！
    即它们不遵守源程序的内存引用顺序
    例如编译器可能会为核心 A 生成以下代码：
      锁定 = 1
      锁定 = 0
      x = x + 1
      即，将增量移到临界区之外！
    法律行为被称为“记忆模型”
  release() 对 __sync_synchronize() 的调用可防止重新排序
    编译器不会将内存引用移过 __sync_synchronize()
    并且（可能）发出“内存屏障”指令来告诉CPU
  acquire() 对 __sync_synchronize() 的调用也有类似的效果
  如果使用锁，则无需了解内存排序规则
