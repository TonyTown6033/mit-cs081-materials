今天的主题：

Background:
  摩尔定律于 2000 年左右结束：单核性能停止提高
    参见 rcu/moore.pdf
  CPU 从单核设计转向多核设计
  内核必须利用并行性才能获得良好的性能

Puzzle:
  内核有很多天然的并行性。
    不同进程的系统调用在高层上通常是独立的。
    分叉，读/写缓存、管道、套接字等中的不同文件。
  但内核的共享资源常常阻碍并行性。
    例如内存分配器、调度程序、磁盘缓存、i 节点缓存等。
    通常的症状是 CPU 时间浪费在 acquire() 中旋转。
  在生产内核中付出巨大努力来消除并行瓶颈。
  许多设计模式，适合不同的情况。

      N个核上的线程调用r_acquire(l)；没有作家。
      All N cores fetch rwlk->n, see rwlk->n == 0, execute atomic_compare_exchange
      只有一次compare_exchange成功。
      其余的都失败了，必须重新执行。
      但是原子的compare_exchange一次执行一个——不是并行的。
      因此，一个 CPU 获取读锁的时间为 O(N)。
      其他N-1个核心全部重试读取和CAS；再次，只有一个人获胜。
      因此，所有 N 个核心获取共享读锁的总时间为 O(N^2)。

Disappointing:
  如果缓存的话，列表本身读取可能需要几十个周期。
    即使有很多核心正在读取。
  但 r_acquire() 可能需要 100 或 1000 个周期（如果它很流行的话）。
  More cores -> *less* performance.

r_acquire()/r_release 的根本问题是：它的*写入*成本很高。

读取-复制更新 (RCU)。
  快速读取：读取器不锁定（因此不写入）。
  写入速度较慢：写入者必须锁定，并做额外的工作来帮助读取。
  在许多情况下有助于读取大量共享数据（但不是全部）。
  在 Linux 内核中广泛使用。

RCU 是一组供读者和作者使用的规则和模式。
  再加上一些机制。

RCU 理念 1：编写者不要就地修改数据；相反，准备一份新副本。
  Head  ->  E1  ->  E2  ->  E3  ->  nil
  假设 writer 想要改变 n 和 refcnt
  1. 锁
  2. e = 分配()
  3. e->next = E2->next
  4. e->n = 10
  5. e->refcnt = 1;
  6. E1->next = e
  7. 解锁
  如果另一个核心上的读者遍历该列表呢？
    At some point reader will read E1->next.
    在步骤 6 之前或之后（这是一个简化，请参见下文）。
    如果之前，读者看到旧的 E2 和旧的 n 和 refcnt
    如果之后，读者看到 new n 和 refcnt
    Either way, reader will see ...->next pointing to E3.
  要点：读者不会看到部分 e（例如，n 已更新但未 refcnt）
    即使读者没有锁定。

思考这个想法的一个好方法是：
  Update of E1->next is a "committing write".
  之前，读者看不到任何变化。
  之后，*所有*更改都变得可见。
  开发者必须先做4+5再做6！
  这避免了读者看到部分完整更新的问题。
  RCU 最适合单指针写入提交的数据结构。
    例如列表和树。

要求 64 位写入和读取是原子的。
  I.e. reader won't see mix of old and new bits in the E1->next pointer.
  我所知道的所有 64 位 CPU 都是如此。
    用于对齐负载/存储。

RCU 想法 2：读取器和写入器必须使用内存屏障来强制执行顺序。
  我们不希望编译器或机器将步骤 3、4 或 5 移到步骤 6 之后。
  作家必须在第 6 步之前设置障碍。
  Reader may need a barrier between Rx = E1->next,
    并取消引用 Rx 以读取元素内容。
  rcu_dereference() 确保了这一点

下一个问题：当编写者 free() 删除一个已删除的列表元素时会发生什么？
  删除可见引用会阻止*新*读者，但是
  并发读者可能仍在查看已删除的元素！
    例如，上面的旧 E2
  释放后使用是一场潜在的灾难：
    可能会被重新分配+覆盖以供其他用途。
  作者需要给读者时间来完成——一个“宽限期”。
    之后它删除了对该元素的可见引用。
    作者要等多久？
  可以使用 GC 或引用计数，但它们很昂贵。

RCU 想法 3（宽限期）：
  1. 规则：读取器不能跨上下文切换保存指向 RCU 数据的指针。
     程序员负责遵守这条规则。
  2. Writer 延迟释放，直到所有 CPU 都完成上下文切换。
  编剧还得等
    但假设写入很少。
  如何实现这个延迟呢？
    每个核心都对上下文切换进行计数，写入器监视也进行计数。
    同步rcu()
    （有很多方法可以实现宽限期。）

rcu_read_lock/unlock 几乎不执行任何操作。
  尽管有名字，但它们不会上锁。
  禁用定时器中断以防止抢占。

  作为文档。

注意：代码只允许在rcu_read_lock/unlock中使用e！
  它不能例如返回(e)
  并且不允许在按住 e 的同时进行上下文切换。

rcu_dereference(e) 有什么作用？
  告诉编译器只计算一次指针。
    而不是例如将 e 替换为 head 进行第一次迭代。
  然后是一个屏障，以确保读取 CPU 看到写入。

  免费（旧）

RCU 性能与读/写锁的比较？
  致读者：
    RCU 的读取成本几乎为零。
    r/w 锁可能需要 100 秒或 1000 秒的周期（图 8，上面的线）。
    此外，RCU 可以在写入过程中进行读取！
    而且，RCU 读取不容易出现死锁！
  对于作家：
    由于synchronize_rcu()，RCU 可能需要更长的时间。
    因此，当写入很少或对时间不敏感时，RCU 就有意义。

示例：删除 NMI 处理程序；论文第 4.1 节；图 4.
  NMI 是无法禁用的中断。
    用于 CPU 分析、严重硬件错误、看门狗定时器。
  内核代码可以注册在 NMI 期间调用的处理程序。
  还可以取消注册处理程序，并释放包含处理程序代码的内存。
  NMI 很频繁；注册/注销很少见；因此读取 >> 写入。
  如果调用取消注册时某些核心位于 NMI 代码中怎么办？
  图4的解决方案，在unregister_nmi_handler()中：
    1. 删除 NMI 处理程序列表条目（这样以后的中断将看不到它）。
    2.synchronize_rcu()等待当前所有中断完成。
       因为核心在离开中断之前不会进行上下文切换。
    3.（未显示）释放保存 NMI 处理程序代码的内存。
  此示例使用 RCU 推迟释放，直到所有使用都完成。
  一个有趣的皱纹：
    NMI 无法禁用。
    所以自旋锁无法阻止 NMI。
    所以一般不能允许 NMI 获取锁（死锁...）。
    所以这里 RCU 不仅比读卡器锁定更快，
      但实际上在锁定不起作用的地方有效。

示例：IP 选项；第 4.2 节；图 6.

  该论文将其称为“引用计数”，但没有引用计数。
    “延迟免费”或“垃圾收集”可能是一个更好的术语。
  
RCU 并不普遍适用。
  对写作没有帮助。
  仅在读取>>写入时提高性能。
  不适用于必须在yield/sleep 中保存引用的代码（但可以修复）。
  如果数据结构不适合单次提交写入，则很难应用。
    例如如果读者扫描双向链表的两个方向。
    或者如果需要就地更新。
  读者可以看到陈旧的数据。
    例如图 6 中的 udp_sendmsg() 可能会使用旧的 IP 选项进行发送。
    这里不是问题；可能在少数情况下（例如数据库事务）。
  RCU 增加了编写者的复杂性。
    在网络上搜索“RCU 补丁审查清单”
  RCU 需要频繁进行上下文切换，并且需要了解它们。
    在内核中很容易，但用户空间不知道*核心*开关。

如何高效地实现synchronize_rcu()？
  这是 McKenney 和 Slingwine 论文中的设计
    http://www2.rdrop.com/users/paulmck/RCU/rclockpdcsproof.pdf
    第3.5.4节
  每核心数据：
    该核心的上下文切换计数。
    等待的synchronize_rcu()和call_rcu()列表。
  每个核心会定期处理整批（列表）的 RCU 编写器：
    保存列表，清空它。
    记录所有其他核心的计数。
    每次上下文切换，都会再次查看其他核心的计数。
    如果所有内容都已更改，则唤醒/运行已保存列表上的所有内容。

如果您共享写入量大的数据怎么办？
  最好：重新设计，不共享。
  其次：以某种方式对数据进行分区，并锁定每个分区。
    示例：锁定实验室中的 kalloc -- 按核心分区。
    示例：统计计数器。
      每个核心在单独的自旋锁下保留自己的计数。
      要写入，获取本地锁，增加本地计数。
        如果仅从一个核心使用自旋锁，那么它很便宜。
      要读取，请获取“所有”锁，读取所有计数并对其求和。
        昂贵，但我们假设写入量很大。
  
RCU总结
  在加速对共享内核数据的读取访问方面非常成功。
    在现代 Linux 中广泛使用。
  完全消除了读者的锁定成本。
  允许读取器与写入器并行执行。
  关键思想是类似 GC 的宽限期来推迟释放对象。
