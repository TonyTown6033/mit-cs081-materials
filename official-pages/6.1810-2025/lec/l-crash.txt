计划
  问题：崩溃恢复
    崩溃导致磁盘上的文件系统不一致
  解决方案：
    预写日志

# 为什么需要崩溃恢复

什么是崩溃恢复？
  进程创建文件、目录等
  然后电源断电
  系统重启
  文件系统是否仍可正常使用？

文件系统回顾
  文件系统是一种磁盘上的数据结构
    包含文件的目录树
    每个文件由一个 inode 和数据块树组成
  xv6 中的磁盘布局：
    0: 未使用
    1: 超级块（大小、inode 数量）
    2: 事务日志（31 个块）
    33: inode 数组，每个 64 字节，每块存放 16 个
    46: 块使用位图（0=空闲，1=已用）
    47: 文件/目录内容块...
  对文件系统的修改需要多次磁盘写入
    删除文件 f 涉及：
      - 将 inode 标记为空闲
      - 将其数据块标记为空闲
      - 更新目录以移除 f

问题：在写入多个块的系统调用过程中发生崩溃
  风险：可能导致文件系统不变式被破坏
    例如，在 unlink 过程中崩溃
      inode 被标记为空闲，但文件仍存在于目录中
  重启后：
    糟糕情况：由于文件系统损坏而再次崩溃
    更糟情况：未崩溃，但读写了错误的数据

示例：
  创建文件：
    
    $ echo > x
    // 上一讲中 create 的跟踪记录：
    log_write: block 34 by ialloc   // 在第2个 inode 块中分配 inode
    log_write: block 34 by iupdate  // 更新 inode（例如，设置 nlink）
    log_write: block 47 by writei   // 写目录项，通过 dirlink() 添加 "x"
    log_write: block 33 by iupdate  // 更新目录 inode，因为 inode 可能已更改
    log_write: block 34 by iupdate  // itrunc 新 inode

    在 iupdate 和 writei 之间崩溃
      分配文件 inode
      崩溃：inode 未释放但未使用——问题不大

    如果文件系统先将数据写入 47 和 33，再写入 34
      即先创建目录项，再创建文件
      若在 33 和 34 之间崩溃，则目录项指向空闲 inode——灾难性错误！
      再次崩溃，或更糟：若该 inode 已被分配给其他内容

    真实的文件系统会将一批写操作一起提交到磁盘以提高性能
      因此崩溃后，部分写操作可能已完成，部分尚未完成

  write:
    inode addrs[] 和 len
    间接块
    块内容
    块空闲位图
    崩溃：inode 引用了空闲块——灾难性错误！
    崩溃：块未释放但未使用——问题不大
        
  unlink:
    释放块
    释放 inode
    清除目录项
    崩溃：目录项引用了空闲 inode——灾难性错误！

我们能期望什么？
  重启并运行恢复代码后
  1. 文件系统内部不变量得以维护
     例如，没有任何块同时出现在空闲列表和某个文件中
  2. 除最后几个操作外，其余操作均已持久化到磁盘
     例如，昨天写入的数据得以保留
     但崩溃时正在写入的数据可能未能保留
     因此用户可能需要检查最后几个操作
  3. 无操作顺序异常
     echo 99 > result ; echo done > status

正确性与性能往往相互冲突
  磁盘写操作很慢！
  安全性 => 尽快写入磁盘
  速度 => 尽量不写磁盘（例如：批量写入、写回缓存）

崩溃恢复是一个反复出现的问题
  在所有存储系统中均会出现，例如数据库
  多年来人们在解决方案上投入了大量工作
  涌现出许多兼顾性能与正确性的巧妙权衡方案

# Logging solution

最流行的解决方案：日志（即 journaling）
  目标：系统调用相对于崩溃具有原子性
  目标：快速恢复（无需耗时数小时的 fsck）

将分两步介绍日志机制
  首先介绍 xv6 的日志，它仅提供安全性与快速恢复
  然后介绍 Linux EXT3，它在正常运行时同样高效

日志机制背后的基本思想
  你希望实现原子性：要么执行系统调用的所有写操作，要么一个都不执行
    将这样的原子操作称为"事务"
    内核开发者必须标记事务的开始与结束
  将系统调用*将要*执行的所有写操作记录到磁盘上的日志中（log）
  然后在磁盘上记录"完成"标志（commit）
    此操作本身必须是原子的
    提交要么发生，要么不发生（不存在半途提交）
  然后执行文件系统的磁盘写入（install）
  崩溃后恢复时：
    若日志中存在"完成"标志，则重放日志中的所有写操作
    若不存在"完成"标志，则忽略日志
  这就是预写式日志（WRITE-AHEAD LOG）

预写式日志规则
  在事务的所有写操作均已写入磁盘日志，
  且已标记为已提交之前，
  不得将事务中的*任何*写操作安装到磁盘。

为何要遵循该规则？
  一旦我们将某个写操作安装到磁盘上的文件系统，
  就必须完成该事务的*所有*其他
  写操作——这样事务才具有原子性。我们必须
  为第一次安装写操作之后发生崩溃的情况做好准备，
  因此其余写操作在崩溃后必须仍然可用
  ——即保存在日志中。

日志机制堪称神奇
  对复杂可变数据结构进行崩溃恢复通常非常困难
  日志往往可以作为一层叠加在现有存储系统之上
  并且与高性能兼容（下次课的主题）

# Overview of xv6 logging

xv6 日志的表示形式
  [图示：缓冲区缓存、内存中日志块号数组、
            磁盘上的文件系统树、磁盘上的日志头和日志块]
  写入时将块号添加到内存数组中
  将数据本身保留在缓冲区缓存中（已固定）
  提交时：
    将缓冲区写入磁盘上的日志
    等待磁盘完成写入（"同步"）
    将日志头扇区写入磁盘
      块号
      非零的 "n"
  提交后：
    将日志中的块安装（写入）到文件系统中的原始位置
    解除块的固定
    将磁盘上日志头中的 "n" 写为零

磁盘上日志头中的 "n" 值表示提交状态
  非零 == 已提交，日志内容有效且构成完整事务
  零 == 未提交，可能不完整，恢复时应忽略日志
  写入非零 "n" 是"提交点"
    
我们来看一个例子。
  我修改了 log_write() 和 bwrite()，使其打印底层磁盘写入信息，
  即事务提交期间发生的磁盘写入。

  $ echo > x
  log_write 34
  log_write 34
  log_write 47
  log_write 33
  log_write 34
  // 提交之前不会有磁盘写入！
  bwrite 3    // 包含 x 的 inode 34 的块
  bwrite 4    // 目录块 47
  bwrite 5    // 包含目录 inode 33 的块
  bwrite 2    // 提交
  bwrite 34   // 安装 x 的 inode
  bwrite 47   // 安装目录内容
  bwrite 33   // 更新目录 inode
  bwrite 2    // 将日志标记为空
  // 对同一块的多次写入合并为一次写入
  // 每个块写入两次：日志写入和安装写入

如果我们在事务执行期间崩溃会发生什么？
  内存丢失，只留下崩溃时磁盘上的内容
  内核在启动时、使用文件系统之前调用 recover_from_log()
    如果日志头块显示 "done"：
      将日志中的块复制到磁盘上的实际位置
  磁盘上的日志中有什么内容？
    提交前崩溃
    提交过程中崩溃——提交点
      bwrite 2 必须是原子的；单个扇区
      因此，要么已提交，要么未提交
    在 install_trans() 执行期间崩溃
    重启后，在 recover_from_log() 执行期间立即崩溃
  注意：多次重放日志是允许的！
    只要中间没有其他活动介入
    
让我们查看代码并逐步分析 create 事务
  sysfile.c: sys_open()
    begin_op/end_op: 标记事务
  sysfile.c: create
    ialloc() 分配 inode
      log_write

  log.c 中的 begin_op():
    需要指明哪一组写操作必须是原子的！
    需要检查日志是否正在提交
    需要检查我们的写操作是否能放入日志的剩余空间
  log_write():
    将扇区号添加到内存数组中
    bpin() 将把块固定在缓冲区缓存中，以防止 bio.c 将其驱逐
  end_op():
    如果没有未完成的操作，则提交
  commit():
    将已更新的块从缓存复制到磁盘上的日志
    在磁盘日志头中记录扇区号和"done"标志
    安装写操作——从磁盘日志复制到磁盘文件系统
      bunpin() 将取消固定缓存——此后该块可被驱逐
    从日志中清除"done"标志

注意：xv6 假设磁盘是故障停止（fail-stop）的
  磁盘要么正确完成写操作，要么根本不执行写操作
    即：例如因断电导致最后一次写操作无法完成
  因此：
    不存在部分写入（每次扇区写入是原子的）
    不存在野写
    不存在扇区数据损坏（无读取错误）
    不存在读取错误扇区的情况

# 挑战
    
挑战：防止缓存回写
  系统调用可以安全地更新*缓存*中的块，
    但该块在事务提交之前
    不能写入文件系统
  这很棘手，例如缓存可能耗尽空间，
    并可能被诱导驱逐某些条目，以便
    读取并缓存其他数据。
  考虑 create 示例：
    将脏 inode 写入日志
    将目录块写入日志
    驱逐脏 inode
    提交
  xv6 解决方案：
    确保缓冲区缓存足够大
    将脏块固定在缓冲区缓存中
    提交后，取消固定该块
    
挑战：系统调用的数据必须能放入日志
  xv6 解决方案：
  - 计算每个系统调用写入块数的上界
    设置日志大小 >= 上界
  - 将某些系统调用拆分为多个事务
    例如，较大的 write()
    因此：较大的 write() 不是原子的
      但崩溃后将保留写入内容的一个正确前缀
		
挑战：允许并发系统调用
  必须允许来自多个调用的写入存在于日志中
  提交时必须将它们全部写入
  但不能写入仍处于事务中的调用的数据

xv6 解决方案
  若新系统调用的数据可能无法放入日志，则不允许其启动
    必须等待当前调用完成并在日志中留出足够空间
    或者，等待并发调用完成提交，从而释放日志空间
  当进行中的调用数量降为零时
    提交
    释放日志空间
    唤醒等待中的调用

挑战：一个块可能在一个事务中被多次写入
  log_write() 仅影响内存中已缓存的块
  因此一个已缓存的块可能反映多个未提交的事务
  但安装（install）仅在没有进行中的事务时发生
    因此已安装的块仅反映已提交的事务
  有利于性能："写吸收"

挑战：孤立的文件/目录
  inode 的引用计数为 0，但某个进程仍持有其打开的文件描述符
    暂时不能删除
  但崩溃可能发生在 close(fd) 之前
    文件存在于磁盘上，但没有任何目录项指向它

xv6 的解决方案：
  ireclaim：重启时检查孤立文件

挑战：进程如何知道其写入已落盘？
  例如，当 write() 返回时，更新可能尚未提交
    另一个事务正在进行中，延迟了提交

典型解决方案：sync() 系统调用
  仅当所有脏块都已写入磁盘时才返回
  xv6 没有 sync 调用
        
# 总结

xv6 日志设计的优点是什么？
  由于预写日志而保证正确性
  良好的磁盘吞吐量：日志天然地对写入进行批处理
    但数据磁盘块会被写入两次
  并发性
    
xv6 日志的缺点是什么？
  效率不高：
    每个块被写入两次（写入日志和安装）
    即使只修改了几个字节，也会记录整个块
    每个日志块都是同步写入的
      可以批量写入日志块，仅同步写入日志头
    日志写入和安装写入都是即时（eager）的
      两者都可以是惰性的，以吸收更多写入
      但仍必须先写日志
  操作大小超出日志容量时会出现问题
    unlink 在截断文件时可能会使许多块变脏
