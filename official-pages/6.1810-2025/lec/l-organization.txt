6.1810 2025 L4：操作系统组织结构与微内核

主题：
  内核应该做什么？
  它的抽象层/系统调用应该是什么样的？
  是否存在多种可行方案？
  本主题更侧重于思想，而非具体机制

"传统方法"——UNIX、Linux、xv6
  1) 大型抽象，以及
  2) "宏内核"实现

大型抽象
  示例：具有命名、目录、权限等功能的文件系统
  对程序员而言：提供便利性与可移植性
    例如：相较于直接操作裸磁盘
  对内核而言：有助于共享和管理资源
    例如：由内核负责将磁盘空间分配给不同程序
  对内核而言：有助于安全性
    例如：文件权限

大型抽象导致了庞大的"宏内核"
  内核是一个大型程序，如 xv6
  内核子系统之间易于协作——无需处理繁琐的边界问题
    exec() 与内核的进程、内存和文件代码深度集成
  所有内核代码均以高特权级运行——内部无安全限制

宏内核/大型抽象存在哪些问题？
  体积大 => 结构复杂 => 可能存在漏洞/安全隐患
  过度通用 => 可能性能低下
    通过 UNIX 管道发送一个字节需要执行多少代码？
      缓冲、锁、sleep/wakeup、调度器
  大型抽象隐藏/强制了大量设计决策，有时显得笨拙
    也许我想等待一个并非我子进程的进程
    也许我想修改另一个进程的地址空间
    也许数据库比内核文件系统更擅长在磁盘上布局 B 树文件

微内核——一种不同的方法——例如 L4、Mach
  主要目标：尽可能精简内核
  主要技术：将大部分操作系统功能迁移至用户态服务进程
  [示意图：硬件、内核、应用程序、服务（FS disk VM TCP NIC display）]
  内核提供什么？
    地址空间、内存管理、线程、IPC
    IPC = 进程间通信
  1980 年代掀起了微内核设计研究的热潮
    CMU 的 Mach 或许是其中影响最深远的

人们希望从微内核中获得什么？
  从零开始设计 -> 更加优雅
  小巧 -> 更少的漏洞 -> 更安全
  小巧 -> 可验证（参见 seL4）
  小巧 -> 更易于优化
  小巧 -> 对应用程序强加的设计决策更少
  用户态 -> 促使操作系统服务更加模块化
  用户态 -> 更易于扩展 / 定制 / 替换用户态服务
  用户态 -> 更健壮 —— 可单独重启各个用户态服务
    大多数漏洞存在于驱动程序中，将它们移出内核！

设计挑战？
  最小可用功能集是什么？
    最小功能集是否不止一种？
  它是否能掌握足够的信息来实施安全策略？
    例如，在不了解用户信息的情况下？
  程序是否能够共享磁盘和网络等资源？
    在没有提供 file/directory/socket 抽象的内核的情况下？
  没有宏内核的集成优势，性能是否仍然良好？
  内核是否能掌握足够的信息来合理分配资源？
    哪些进程应获得 CPU、内存、磁盘访问权限等

现实层面的考量
  目标平台是什么？用户工作站？Web 服务器？嵌入式设备？
  现有应用程序需要完整的操作系统，例如 UNIX、Windows 等
    在微内核上重新实现 UNIX 接口可能需要大量工作
  如何说服用户迁移到新的微内核？

L4
  历经多次演进，存在多个版本与重新实现
  目前已商业化应用，广泛用于手机和嵌入式控制器
  是微内核方法的典型代表
  强调最小化原则：
    仅有数十个系统调用（Linux 有 300 个以上）
    13,000 行代码

L4 基本抽象
  [diagram]
  地址空间（"任务"）
  页映射
  线程
  IPC（进程间通信）

与 Linux 等相比，L4 内核中缺少什么？
  几乎所有东西！
  文件系统、fork()、exec()、管道、设备驱动、网络协议栈等
  若需要这些功能，必须以用户态代码的形式实现
    以库或服务进程的方式提供
    并基于 L4 所提供的少量原语来构建

L4 系统调用：
  创建任务 / 地址空间
  创建/销毁线程
  通过 IPC 发送/接收消息（地址为线程 ID）
  拦截另一个地址空间的缺页错误——"pager"
    并修改目标的映射关系
  访问设备硬件
  通过 IPC 接收设备中断

示例：在 L4 上执行 exec()
  一个已存在的任务 T1 想要创建一个新任务
    并让它执行来自某个文件的指令
  假设存在一个用户态的文件系统服务
  1. T1 创建新任务 T2——T2 将没有任何内存！
  2. T1 告知 L4 从 PC=0 开始执行 T2
  3. T2 将立即访问无效内存并触发缺页错误
  4. L4 内核通过 IPC 将缺页信息发送给 T1
  5. T1 通过 IPC 请求文件系统服务器读取文件块
  6. T1 此时已在自己的内存中获得该文件块
  7. T1 告知 L4 将文件块映射到 T2 的内存中，并恢复 T2 的执行
  （由缺页错误驱动的文件访问通常称为"按需分页"）

问题：IPC 性能
  微内核程序会进行大量 IPC 操作！
  在早期系统中代价高昂
    多次内核穿越、缓存缺失、上下文切换等
  IPC 的高开销使许多人否定了微内核
  L4 设计者在提升 IPC 性能上投入了大量精力

这是一种低效的 IPC 设计
  以 UNIX 管道为模型
  [图示：内核中的消息队列]
  send(id, msg)
    将消息复制到内核中的队列，然后返回
  recv(&id, &data)
    若队列中有等待的消息，则将其复制到用户态并返回
    否则等待 send()
  称为"异步"且"带缓冲"的方式
  常见的请求-响应模式（RPC）将是：
    [图示：用于回复的第二条消息队列]
    4 次系统调用（用户态 -> 内核态 -> 用户态）
      send()
      recv()
               recv()
               send()
      （recv() 返回）
    或者说八次用户态/内核态或内核态/用户态的穿越
      每个都很慢！
    四次消息拷贝（请求两次，回复两次）

L4的快速IPC
  "Improving IPC by Kernel Design," Jochen Liedtke, 1993
  * 合并了 call() 和 sendrecv() 系统调用
    IPC 几乎总是用作请求-响应式 RPC
    因此分别使用 send() 和 recv() 系统调用较为浪费
    [diagram]
    客户端：call()：发送消息并获取响应
    服务端：sendrecv()：回复一个请求后等待下一个
    用户态/内核态切换次数减少 2 倍
  * 同步
    [diagram]
    call() 等待目标线程的 sendrecv()
    常见情形：目标线程已在 sendrecv() 中等待
    call() 返回至目标线程，如同从 sendrecv() 返回一般
  * 无缓冲
    同步 => 源与目标的用户缓冲区地址均已知 => 直接拷贝
    无需向内核缓冲区拷贝或从中拷贝
  * 小消息通过寄存器传递，而非内存
  * 大消息以页面映射方式传递
    send() 将发送方的页面映射到目标的地址空间
    recv() 在目标中指定地址
    同样，无需拷贝
  * 精心布局内核代码以最小化缓存占用
  结果：IPC 开销降低 20 倍

在这种情况下，简洁确实带来了优化——很好。

如何在微内核之上构建完整的操作系统？
  需要一组用户态服务器。
    文件系统、设备驱动、网络栈等
  对于嵌入式系统，这可以相当简单。
  对于通用场景（如工作站、Web 服务器）又该怎么办？
  确实需要与现有应用程序的兼容性。
    例如，系统需要模拟类似 UNIX 的接口。
  将 UNIX 内核服务重新实现为大量用户态服务任务？

想法：将现有 Linux 内核作为一个进程运行在微内核之上。
  一个"操作系统服务器"。
  也许并不优雅，但很务实。
  通向推广应用的一条路径：
    用户可以从仅运行 Linux 应用开始。
    然后逐步利用底层微内核的各种可能性。

基本概念图

在用户态运行 Linux 内核意味着什么？
  Linux 内核只是一个程序！
  作者对 Linux 进行了少量修改
    用 L4 系统调用或 IPC 替换了硬件访问。
    包括进程创建、配置用户页表、用户内存分配、
      系统调用处理、中断处理。
  未修改 Linux 文件系统、网络协议、设备驱动等。

通过 IPC 实现的 L4/Linux 系统调用
  每个 Linux 进程是一个 L4 任务
  Linux 服务器主要是单个 L4 线程，等待 IPC
  系统调用流程：
    向 Linux 服务器发送 IPC（进程阻塞，等待 IPC 回复）
    Linux 服务器执行系统调用的实现
    发送 IPC 回复（L4 负责传递，进程可恢复执行）
    Linux 服务器等待下一个系统调用 IPC

L4/Linux 服务器分配所有内存，并分发给各进程
  因此所有用户内存也映射到 Linux 服务器的地址空间中
  用于 copyin()/copyout()，以便从系统调用中解引用用户指针
  这使系统调用 IPC 保持精简——传递数据地址，而非数据本身
  Linux 服务器还利用其内存访问权限实现 fork() 和 exec()

示例：L4/Linux 的 fork() 如何工作？
  进程 P1 调用 fork()（P1 本质上是一个 L4 任务）
  P1 的 libc 库将 fork() 转换为发送给 L4/Linux 服务器的 IPC
  L4/Linux 为 P2 分配部分页面，复制 P1 的内存
  L4/Linux 请求 L4 创建一个新任务——P2
  L4/Linux 向 P2 发送特殊 IPC，携带 SP 和 PC 以使其开始运行
  L4/Linux 从 P2 获取外部页面错误，逐页映射

IPC 微基准测试
  表 2 —— getpid() 系统调用的开销
    Linux:       1.68 us
    L4/Linux:    3.95 us
    Mach Linux: 15.41 us
  getpid() 在原生 Linux 上是一次系统调用
    但在 L4/Linux 中需要两次 L4 系统调用（call、sendrecv）才能到达 Linux 服务器任务
    对应两条 IPC 消息（请求、回复）
  令人满意的结果：在 L4/Linux 上仅耗费略多于 2 倍的时间
  远快于 Mach+LinuxServer
    Mach 为何慢？遗憾的是论文并未说明。

整体系统基准测试：AIM
  图 8
  AIM 创建大量进程
  每个进程随机使用磁盘、分配内存、使用管道、执行计算等
    以完成固定总量的工作
  x 轴表示并发 AIM 进程数量的[某种函数]
    即工作总量
  y 轴表示完成所有工作所需的时间
  只有斜率真正重要
    斜率代表单位工作所需时间，越低越好
    原生 Linux 最优，但 L4Linux 仅稍慢一些
    Mach+Linux 的效率明显较低
  结论：
    2倍的 IPC 时间似乎对整体性能影响不大
    L4+Linux 仅比 Linux 略慢
    L4+Linux 明显快于 Mach+Linux

这些结果本身并不构成使用 L4 的理由
  但它们反驳了以性能问题为由拒绝 L4 的说法

当前情况如何？
  微内核有时用于嵌入式计算
    微控制器、Apple"飞地"处理器

  微内核从未在通用计算领域流行起来
