草案设计：无操作系统
  [sh, echo | CPU, RAM, disk]
  应用程序直接与硬件交互
  高效！灵活！有时也不失为一个好方案。

无操作系统的主要问题：缺乏隔离
  资源隔离：
    某个应用占用过多内存、独占 CPU，或耗尽磁盘空间
  内存隔离：
    某个应用的 bug 覆写了其他应用的内存

Unix 系统调用接口通过限制应用程序的行为来实现隔离
  通常通过对硬件资源进行抽象来实现
  fork() 与进程对处理器核心进行抽象
    操作系统在进程间透明地切换核心
    强制要求进程主动让出核心
    进程数量可以超过核心数量
  exec()/sbrk() 与虚拟地址对 RAM 进行抽象
    每个进程拥有"独立"的内存——一个地址空间
    操作系统决定应用程序在内存中的放置位置
    操作系统将进程限制在其自身内存范围内
  文件对磁盘块进行抽象
    操作系统确保不同使用之间不发生冲突
    操作系统强制执行权限控制
  管道对内存共享进行抽象

系统调用接口经过精心设计以实现隔离
  同时仍允许受控共享与可移植性

隔离既关乎安全性，也关乎程序错误的防范

操作系统设计者对安全性有哪些假设？
  我们假设用户代码是主动恶意的
    主动尝试突破隔离
    主动尝试欺骗系统调用去执行愚蠢的操作
    主动尝试干扰其他程序
  我们假设内核代码是可信的
    我们假设内核开发者是善意且有能力的
    我们不太担心内核代码滥用其他内核代码。
    当然，内核中仍然存在漏洞
  因此内核必须谨慎处理所有用户交互
  => 需要具备安全思维
    内核中的任何漏洞都可能成为安全漏洞利用点
  [用安全术语来说，内核属于可信计算基（TCB）]

内核如何防御用户代码的攻击？
  两个主要组成部分：
    针对用户指令的硬件级控制
    严谨的系统调用接口与实现

硬件级隔离
  CPU 与内核协同设计
  - 用户态/特权态模式
  - 虚拟内存
    
用户态/特权态模式（也称内核模式）
  特权态：可以执行"特权"指令
    例如，访问设备硬件
    例如，修改页表
  用户态：不能执行特权指令
  内核运行在特权态，应用程序运行在用户态
  [RISC-V 还有一种 M 模式，我们基本上忽略不计]

处理器提供虚拟内存
  页表将虚拟地址（VA）映射到物理地址（PA）
  限制用户进程可以使用的内存范围
  操作系统配置页表，使每个应用程序只能访问自己的内存
    而无法访问内核的内存
  页表只能在特权态下修改
  我们将花大量时间研究虚拟内存……

RISC-V 指令集手册第二卷：特权架构
  仅限特权态的指令与寄存器 —— 第 11 页
  页表

系统调用是如何工作的？
  应用程序运行在用户态
  系统调用必须在内核的特权态下执行
  必须以某种方式允许应用程序访问特权资源！

解决方案：以受控方式切换模式的指令
  open():
    ecall <n>
  ecall 做了几件事
    切换到超级用户模式
    从内核代码中的已知入口点开始执行
  内核预期在其代码的该入口点处接管控制权
  涉及一些细节，将在后续课程中讨论

补充：是否可以在没有硬件支持的
  超级用户/用户模式和虚拟内存的情况下实现进程隔离？
  可以！使用强类型编程语言
    例如，参见 Singularity O/S
    但用户只能使用经过批准的语言/编译器
  不过，硬件用户/超级用户模式仍是最流行的方案

宏内核
  [diagram]
  内核是一个实现所有系统调用的单一大型程序
  xv6 采用这种设计，Linux 等系统也是如此。
  内核接口 == 系统调用接口
  - 优点：子系统之间易于协作
    文件系统与虚拟内存共享同一缓存
  - 缺点：交互关系复杂
    容易引发漏洞
    内核内部缺乏隔离，例如设备驱动之间

内核漏洞有多普遍？

让我们具体来看 xv6

xv6 仅运行在 RISC-V CPU 上
  并要求特定的外围设备配置——即开发板
  以 "SiFive HiFive Unleashed" 开发板为原型
  hifive.pdf
  一块简单的开发板（例如，没有显示器）
    - 搭载 4 核的 RISC-V 处理器
    - RAM（128 MB）
    - 用于控制台的 UART
    - 类磁盘存储设备
    - 以太网
    - 此类开发板价格较低，但性能有限
  Qemu 模拟该 CPU 及一组类似的板载设备
    - 称为 "virt"，即 "qemu -machine virt"
      https://github.com/riscv/riscv-qemu/wiki
    - 与 SiFive 开发板（https://www.sifive.com/boards）接近
      但磁盘使用 virtio

这块开发板上的 RISC-V 芯片内部是什么？
  四个核心，每个核心包含
    32 个寄存器
    ALU（加法、乘法等）
    MMU
    控制寄存器
    定时器、中断逻辑
    总线接口
  各核心基本相互独立，例如每个核心拥有各自的寄存器
    它们共享 RAM
    它们共享板载设备

什么是模拟？
  一个忠实模拟硬件行为的 C 程序
  例如，RISC-V CPU：
    uint64 reg[32];
    for (;;) {
      read RISC-V instruction 
      decode RISC-V instruction (ld, add, sub)
      execute RISC-V instruction (add reg[0] <- reg[0] + 7, for ld t0, 7)
    }

让我们来看看 xv6 中的系统调用
  qemu 启动 xv6 的 kernel/kernel（参见 -kernel 标志）
    main() 初始化 xv6 内核和硬件
    userinit() 创建一个进程
      内核从 forkret 处启动该进程
      forkret 调用 exec("/init")，然后"返回"到用户态
    init
      顶层进程
      控制台文件描述符，0 和 1
      发起系统调用以启动 shell
  init 是如何发起系统调用的？
    让我们来看看 open()；参见 user/usys.S
    使用某个编号执行 ecall（SYS_open）；参见 kernel/syscall.h（15）
    观察：
      open 并不直接调用内核中的某个函数
      系统调用本质上是一个编号
  init/sh 会发起哪些系统调用？
    修改 kernel/syscall.c:syscall
    查看系统调用的追踪记录
  让我们来看看 exec（SYS_exec，7）
    sys_exec
      获取参数（路径名和 argv）
      调用 kernel/exec.c:kexec
    kexec：
      一个复杂的系统调用
      从磁盘读取文件
      "ELF" 格式
      文本段、数据段
      严格防御，包含大量检查
      不能被欺骗而覆盖内核内存！
      分配栈空间
      将参数写入栈上
