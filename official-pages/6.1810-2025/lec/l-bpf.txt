6.1810 2025 第22讲：通过 BPF 实现内核可扩展性

注：本讲的演示示例可在以下地址获取：
  https://pdos.csail.mit.edu/6.1810/2025/lec/bpf/

论文："The BSD Packet Filter"，作者：McCanne, Jacobson

动机：监控原始网络数据包
  用户态进程需要检查传入的网络数据包
    而非某条特定的 TCP 连接 / UDP 端口
    多种应用程序：tcpdump、arpwatch、rarpd……
  每个进程希望获取不同类型的数据包
    内核开发者事先无法知道应将哪些数据包传递给用户态

[ 演示：tcpdump ]
  # tcpdump -n -i wlan0 udp
  # tcpdump -n -i wlan0 udp and port 123

挑战：性能
  将每个数据包发送到用户态的开销很大
    需要在内核中复制数据包
    需要将数据包发送给用户态应用程序
  应用程序会丢弃它不关心的数据包
    复制这些数据包属于无效工作

目标：指定内核应复制或丢弃哪些数据包
  在内核中基于指定规则进行检查
  若应用程序不需要该数据包，则避免复制开销
  论文：提出一种高效且通用的过滤器指定方式

论文的思路：将过滤器表示为一种简单字节码语言（"BPF"）编写的程序
  应用程序可将自身需求转译为过滤器程序
  字节码语言灵活，可表达多种不同类型的数据包规则
  内核可高效地执行过滤器程序
  可在接收数据包时于中断处理程序中运行过滤器

[ 演示：tcpdump bpf ]
  # tcpdump -n -i wlan0 -d udp

[ 示意图：tcpdump 将表达式转译为 BPF，发送给内核，内核运行 BPF ]

事实证明，这是一种扩展内核的强大方案
  为内核执行用户提供的代码提供了灵活、安全、低开销的方式
  与常规进程级隔离不同的隔离模型
    有时称为"软件故障隔离"
    与 WebAssembly、甚至 JavaScript 等系统使用相同的通用技术
  与进程相比存在一些限制
    代码必须使用 BPF 语言编写
    代码必须立即返回（不能睡眠，不能使用线程，……）
    无虚拟内存
    无标准系统调用
  这些限制带来的巨大收益：性能提升，开启新的使用场景

  $ cd bpf
  $ make seccomp.bpf

  $ bwrap --bind / / --seccomp 5 5<seccomp.bpf -- sh

实现这一功能所面临的有趣技术挑战
  如何确保过滤程序不会崩溃（破坏内存）？
  如何确保过滤程序不会泄漏（读取其他数据）？
  如何确保过滤程序不会永久运行？
  如何以高性能执行过滤程序？

那么，内核如何安全且高效地运行 BPF？

方案一：编写一个解释器。
  类似于论文中所讨论的内容。
  循环遍历指令，对每条指令使用 switch 语句处理。
  我们来看一个仅包含少量指令的 BPF 简化版本。

[ demo: bpf interp ]
  $ cd bpf/engine
  $ cat bpf.h
  $ cat interp.c

解释器需要进行哪些安全检查？
  不能访问超出数据包缓冲区大小的内存。
  不能执行超出有效指令范围的 BPF 操作码。
  不能执行未知操作码。
  必须初始化状态（a=0），否则可能读取到内核中的残留数据。

我们如何确保 BPF 解释器一定会结束？
  跳转使用无符号 8 位偏移量，因此始终向前跳转 0 或更多步。
  每条指令将 PC 推进 1（跳转指令可能推进更多）。
  若 PC 超出 BPF 程序末尾，解释器将捕获错误。
  解释器执行的 BPF 操作码数量有界（最多 nins 条）。
  每条操作码执行一个简单的有界步骤。
  因此，解释器执行整个 BPF 程序将"很快"结束。

[ demo: bpf interp perf ]
  $ cat main.c
  $ time ./run_interp ../seccomp.bpf
  bpf_run: 0x7fff0000

  real	0m2.392s
  user	0m2.384s
  sys	0m0.002s

已经相当不错了：每次调用约 24 纳秒。
  作为对比，切换到用户态（例如 getpid）大约需要 ~100 纳秒。
  这就是 BPF 对该论文作者来说意义重大的原因。
  对于 seccomp 使用场景同样表现出色：比系统调用开销更低！

方案 2：通过避免关键路径上的检查来加速解释器。
  解释器速度慢的部分原因在于它正在执行检查操作。
  但这些检查与我们正在过滤的数据包无关！

[ 演示：bpf 快速解释器 ]
  $ cat fast_interp.c

为什么 bpf_run 跳过内存加载、PC 等检查是安全的？
  预先验证 BPF 程序：bpf_prepare()。

验证规则：
  至少必须有 1 条指令（以便我们能够开始运行）。
  最后一条指令必须是返回指令（以防运行超出末尾）。
  内存加载必须在数据包边界范围内。
    内核在拿到数据包之前就已知晓数据包缓冲区的大小。
  跳转指令不得越过指令序列的末尾。

[ 演示：bpf 快速解释器性能 ]
  $ time ./run_fast_interp ../seccomp.bpf
  bpf_run: 0x7fff0000

  real	0m1.650s
  user	0m1.645s
  sys	0m0.002s

显著提升：从 24 纳秒缩短至 16 纳秒！
  如果程序会运行多次，预先验证是值得的。

方案 3：将 BPF 字节码翻译为硬件指令（"JIT"）。
  BPF 字节码本身已与真实 CPU 指令十分相似。
  我们能否将 BPF 指令翻译为 CPU 指令并直接运行？
  这与 qemu 为在 x86 或 ARM 上运行 RISC-V 所采用的方式类似。

[ 演示：bpf jit ]
  $ cat jit.c
  $ seccomp-tools disasm ../seccomp.bpf   (in another terminal on the right)
  $ gdb --args ./run_jit ../seccomp.bpf
  (gdb) b bpf_run
  (gdb) r
  (gdb) p runner->f
  (gdb) x/20i runner->f

需要事先规划好各寄存器存放哪些状态。
  在 x86-64 中，函数调用的第一个参数存入 %rdi。
  我们用它来存储指向数据包的指针。
  在 x86-64 中，函数的返回值存入 %eax。
  将 return 操作码的值存放在那里。
  在 x86-64 中，%eax 寄存器由被调用者保存（即函数可以修改它）。
  因此，我们用它来存储 BPF 的"A"寄存器。

我们如何确定指令的编码方式？

[ 演示：汇编代码片段，在旁边另开一个终端 ]
  $ vi snippets.S
  $ objdump -d snippets.o | less

JIT 需要做什么？
  仍然需要与快速解释器相同的安全检查。
  对于每条指令，需要填入对应的 x86 代码。
    需要将特定的常量和偏移量编码到指令中。
  需要知道跳转目标的位置。
    BPF 代码指定的是 BPF 指令编号。
    生成的 x86 代码需要的是 x86 代码偏移量。
    需要两趟处理来填入正确的跳转偏移量。
    第一趟，生成 x86 代码，跳转目标可能有误，但指令大小正确。
    记录每条 BPF 指令对应的 x86 指令偏移量。
    第二趟，再次生成 x86 代码，这次填入正确的跳转目标。
  需要在开头填入 x86 代码，将 %eax 寄存器清零。
    否则，BPF 代码（及生成的 x86 代码）可能读取未初始化的 %eax。
  JIT 设置完成后，运行过滤器只需跳转到生成的代码即可。
    bpf_run。

[ 演示：bpf jit 性能测试 ]
  $ time ./run_jit ../seccomp.bpf
  bpf_run: 0x7fff0000

  real	0m0.380s
  user	0m0.377s
  sys	0m0.002s

相比解释器大幅提升：3.8 纳秒，而非 16 纳秒！

还有进一步优化的空间吗？
  可以使用更高效的指令编码（短跳转）。
  可以省去对 %eax 的清零操作。
    需要在每条执行路径上检查 BPF 程序在使用前已完成加载。
    这是一种不同类型的分析遍：取决于分支选择。

Linux 支持一种更复杂的 BPF 版本，称为 eBPF。
  更丰富的操作码以提升性能（支持多个寄存器）。
  允许一定程度的循环（需要更复杂的验证器）。
  允许访问某些共享状态（如哈希表）。
  允许调用某些内核代码（同样需要复杂的验证器）。
  通过 JIT 即时编译为本机代码以提升性能。
