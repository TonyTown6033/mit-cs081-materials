6.1810 2025 第1讲：操作系统概述

概述

* 什么是操作系统？
  [用户态/内核态示意图]
  - 硬件：CPU、RAM、磁盘、网络等
  - 用户应用程序：sh、cc、数据库等
  - 内核服务：文件系统、进程、内存、网络等
  - 系统调用

* 操作系统的目的是什么？
  - 在多个应用程序之间复用硬件资源
  - 隔离应用程序以保障安全性并限制错误蔓延
  - 在协作应用程序之间共享数据
  - 对硬件进行抽象以实现可移植性与便利性

* 设计上的矛盾使操作系统设计颇具挑战性
  - 高效 vs 抽象/可移植/通用
  - 功能强大 vs 接口简洁
  - 灵活 vs 安全
  - 可移植 vs 充分利用新硬件与新接口

* 如果你有以下情况，本课程将对你大有裨益……
  * 对计算机系统的工作原理充满好奇
  * 需要追踪调试错误或安全问题
  * 关注高性能

UNIX 系统调用简介

* 应用程序通过"系统调用"与操作系统交互。
  你将在第一个实验中使用系统调用。
  并在后续实验中对其进行扩展和改进。

* 我将展示一些应用示例，并在 xv6 上运行它们。
  xv6 是我们专为本课程创建的操作系统。
  xv6 仿照 UNIX 设计，但简单得多。
  为什么选择 UNIX？
    它是当今许多操作系统的前身。
    例如 Linux 和 MacOS。
    学习 xv6 将帮助你理解许多其他操作系统。
  xv6 足够小，你将能够阅读并理解其全部代码。
    配套教材解释了 xv6 的工作原理及其设计原因
  xv6 在 6.1810 中承担两个角色：
    核心机制的示例
    大多数实验的起点
  xv6 运行在 RISC-V CPU 上，与 6.1910（6.004）相同
  你将在 qemu 机器模拟器中运行 xv6

* 示例：ex1.c，将输入复制到输出
  从输入读取字节，并将其写入输出
  % make qemu
  $ ex1
  你可以通过网站上的课程安排找到这些示例程序
  ex1.c 使用 C 语言编写
    C 语言可能是操作系统内核中最常用的语言
  read() 和 write() 是系统调用
    它们看起来像函数调用，但实际上会跳转进入内核。
    其方式能够保持用户态与内核的隔离。
  read()/write() 的第一个参数是"文件描述符"（FD）
    传递给内核，告知其对哪个"已打开文件"进行读/写
    一个 FD 连接到一个文件/管道/套接字/等
    该 FD 必须已事先被打开
    一个进程可以打开多个文件，拥有多个 FD
  UNIX 惯例：fd 0 为"标准输入"，1 为"标准输出"
    程序无需知道输入来自何处，或输出去往何处
    只需对 FD 0 和 1 进行读/写即可
  read() 的第二个参数是用于存储读取数据的内存地址
  第三个参数是要读取的字节数
    read() 实际读取的字节数可能少于该值，但不会超过
  返回值：实际读取的字节数，出错时返回 -1
  read()/write() 不关心数据的格式
    UNIX I/O 以 8 位字节为单位
    数据的解释由应用程序决定，例如数据库记录、C 源码等
  如何创建一个新的文件描述符？

  open() 在磁盘上创建（或打开）一个文件，
    返回一个文件描述符（出错时返回 -1）
  FD 是一个小整数
  FD 索引到由内核维护的每个进程的表中
  [用户态/内核态示意图]
  $ ex2
  $ cat out
  不同进程拥有各自独立的 FD 命名空间
    因此 FD 3 对不同进程通常具有不同的含义
  这些示例忽略了错误处理——实际编写时切勿如此粗心！

* 当程序调用 open() 或 write() 等系统调用时会发生什么？
  看起来像函数调用，但实际上是一条特殊指令
    CPU 保存部分用户态寄存器
    CPU 提升特权级别
    CPU 跳转到内核中已知的"入口点"
  此时在内核中运行 C 代码
  内核调用系统调用的具体实现
    sys_open() 在文件系统中查找文件名
    可能需要等待磁盘
    更新内核数据结构（文件块缓存、FD 表）
  恢复用户态寄存器
  降低特权级别
  跳回程序中的调用点，程序继续执行
  课程后续将详细介绍

* 我一直在使用 UNIX 的命令行界面——shell。
  shell 打印出 "$" 提示符。
  shell 是一个普通的用户程序，并非内核的一部分。
  shell 让你运行 UNIX 命令行工具
    适用于系统管理、文件操作、开发和脚本编写
    $ ls
    $ ls > out
    $ grep x < out
  UNIX 也支持其他交互方式
    图形界面、服务器、路由器等。
  但通过 shell 进行分时使用是 UNIX 最初的核心功能。

* 示例：ex3.c，创建新进程
  shell 为你输入的每条命令创建一个新进程
    进程是正在运行的程序，拥有内存、栈和内核状态
    与其他进程相互隔离，以防止错误蔓延
  ex3.c
  fork() 系统调用用于创建新进程
  内核会复制调用进程的内容
    包括指令、数据、寄存器、文件描述符和当前目录
    分为"父"进程和"子"进程
  [图示：ex3 与子进程]
  因此子进程和父进程在初始时完全相同！
    区别在于：fork() 在父进程中返回子进程的 pid，在子进程中返回 0
  pid（进程 ID）是一个整数；内核为每个进程分配不同的 pid
  $ ex3
  因此：
    ex3.c 中的"fork() returned"会在*两个*进程中都执行
    "if(pid == 0)" 使代码能够判断自己是父进程还是子进程
    两个进程在 fork 之后都会继续运行
  好，fork() 让我们可以创建新进程
    那我们如何在该进程中运行一个程序呢？

* 示例：ex4.c，用可执行文件替换调用进程
  shell 是如何运行一个程序的，例如
    $ echo a b c
  程序以文件形式存储：包含指令和初始内存
    由编译器和链接器生成
  因此存在一个名为 echo 的文件，其中包含指令
    在你自己的电脑上：ls -l /bin/echo
  ex4.c
  exec() 用一个可执行文件替换当前进程
    丢弃原有的指令内存和数据内存
    从文件中加载指令和初始内存
    保留文件描述符
  $ ex4
  exec(filename, argument-array)
    argument-array 存放命令行参数；exec 将其传递给 main()
    cat user/echo.c
    echo.c 展示了程序如何查看其命令行参数
  exec() 若执行成功则不会返回！

* 示例：ex5.c，用 fork() 创建新进程，用 exec() 执行程序
  shell 不能直接调用 exec()！
    因为那样它自身就不再运行了
    就无法接受多条命令了
  ex5.c 展示了 shell 如何处理这个问题：
    用 fork() 创建子进程
    子进程调用 exec()
    父进程用 wait() 等待子进程结束
  $ ex5
  shell 对你输入的每条命令都执行这套 fork/exec/wait 流程
    wait() 返回后，shell 打印下一个提示符
  exit(status) -> wait(&status)
    status 允许子进程向父进程传回 32 位信息
    status 约定：0 表示成功，1 表示命令遇到错误
  注意：fork() 会复制内存，但 exec() 会丢弃这些复制的内存
    这看起来似乎很浪费
    你将在"写时复制"实验中消除这种浪费

* 示例：ex6.c，重定向命令的输出
  shell 对以下命令做了什么？
    $ echo hello > out
  答：fork，子进程修改文件描述符 1，子进程 exec echo
  $ ex6
  $ cat out
  注意：open() 总是选择编号最小的空闲文件描述符；此处为 1，因为执行了 close(1)。
  注意：exec 会保留文件描述符
  fork、文件描述符与 exec 配合良好，共同实现了 I/O 重定向
    先 fork 后 exec 的分离设计，给了子进程修改文件描述符的机会
      在 exec() 交出控制权之前
      且不会影响父进程的文件描述符
  文件描述符提供了一层间接性
    命令只需使用文件描述符 0 和 1，无需知道它们实际指向哪里
  因此：只有 sh 需要了解 I/O 重定向，各个程序本身无需关心

* 值得追问设计决策背后的"为什么"：
  为何选择这些 I/O 和进程抽象？为何不采用其他方式？
  为何提供文件系统？为何不让程序以自己的方式直接使用磁盘？
  为何使用文件描述符？为何不直接把文件名传给 write()？
  为何不把 fork() 和 exec() 合并为一个调用？
  UNIX 设计得很好，但也存在其他优秀的设计方案！
