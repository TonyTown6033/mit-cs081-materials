6.1810 2025 第17讲：文件系统

为什么文件系统有用？
  重启后数据持久保存
  命名与组织
  程序和用户之间的共享
  设备无关性（硬盘、闪存、EBS）

为什么有趣？
  崩溃恢复
  性能
  安全
  API 的泛化：管道、设备、/proc、/afs、Plan 9
    使得面向文件系统的应用可以操作多种类型的对象
  两个实验的主题

API 影响设计与实现。
  示例——UNIX/Posix/Linux/xv6/&c：
  fd = open("x/y", -);
  write(fd, "abc", 3);
  link("x/y", "x/z");  -- 现在文件有两个名字！
  unlink("x/y");
  write(fd, "def", 3);
  close(fd);
  // file y/z contains abcdef

UNIX 文件系统 API 中可见的高层设计选择
  对象：文件（而非原始磁盘空间、数据库记录）
  内容：字节数组（而非行/列、B树）
  大小：可随时追加；磁盘空间无需预先分配
  命名：人类可读（而非对象ID）
  组织：目录层次结构
  同步：无（无锁、无版本控制）
    不阻止应用程序并发修改！
  上述每一项决策在某些其他文件系统中都有不同的选择！

API 的几点含义：
  fd 引用某个对象
    即使文件名发生变化，该引用仍然有效
    或者文件在打开期间被删除，引用依然有效！
  一个文件可以有多个"硬"链接
    即出现在多个目录中
    其中没有哪一个出现是特殊的
    因此文件信息必须存储在目录以外的地方
  由此：
    文件系统将文件信息记录在磁盘上的"inode"中
    文件系统通过 i-number 引用 inode
    inode 必须包含链接计数（用于判断何时释放）
    inode 必须记录已打开文件描述符的计数
    inode 的释放推迟到最后一个链接和文件描述符均消失后才执行

磁盘上的数据意味着数据是持久化的
  持久化 = 即使断电数据也能保留
    （RAM 中的数据在断电后会丢失）
  "磁盘"的多种形式：
    机械硬盘（容量大但速度慢，价格低廉）
    固态硬盘（容量较小，但速度快，价格更贵）
  通用接口：扇区数组，通常每扇区 512 字节

机械硬盘（HDD）
  磁盘以恒定速率旋转（例如 7200 RPM）
  同心磁道
  每条磁道由一系列扇区组成
  读写一个块的过程：
    将磁头寻道至正确的磁道
    等待目标扇区旋转到磁头下方
    随机访问速度慢（5 到 10 毫秒，源于寻道与旋转延迟）
    顺序访问速度快得多（100 MB/秒）
      因为磁盘上的位密度非常高
  每个扇区有 ECC 纠错（Reed-Solomon，数百位）
  只能整扇区读写
  因此：子扇区写入速度慢（需先读取再修改再写入）

固态硬盘（SSD）
  非易失性"闪存"存储
  随机访问：100 微秒
  顺序访问：500 MB/秒
  内部结构复杂——通常对外不可见，但有时会影响性能
    闪存在重新写入前必须先擦除，且以大块为单位进行
    闪存块的可写入次数存在上限
    SSD 在内部维护一层间接映射——对块进行重新映射

对于 HDD 和 SSD：
  接口兼容——均以块数组形式呈现
  顺序访问的吞吐量远高于随机访问
  大读写操作比小读写操作更快
  这两点都会影响文件系统的设计与性能
    
块大小
  大多数操作系统的文件系统使用大块，例如 4 KB 块 = 8 个扇区
  以减少簿记开销和寻道开销
  xv6 使用 1024 字节的块（2 个扇区）

磁盘上的布局
  xv6 将磁盘视为块的数组
  0: 未使用
  1: 超级块（大小、inode 数量）
  2: 事务日志（31 个块）
  33: inode 数组，每个 64 字节，每块紧凑存储 16 个
  46: 块使用位图（0=空闲，1=已用）
  47: 文件/目录内容块……
  具体数字取决于 inode 数量和块数量

"元数据"
  磁盘上除文件内容以外的所有内容
  超级块、inode、位图、目录内容

xv6 的 mkfs 程序为空文件系统生成此布局
  该布局在文件系统的整个生命周期内保持静态
  mkfs 将内核所需的大小等信息写入超级块

超级块
  [kernel/fs.h]
  日志、inode、位图及内容区域的大小与位置
  内核在启动时读取超级块

磁盘上的 inode
  [kernel/fs.h]
  类型（空闲、文件、目录、设备）
  nlink
  size
  addrs[12+1]

直接块与间接块
  间接块存储 256 个块号
  因此文件最大为 12+256 个块，即 268 KB

示例：
  如何找到文件第 8000 字节所在的磁盘块号？
  逻辑块 7 = 8000 / BSIZE（=1024）
  inode.addrs[7] 存储磁盘块号

每个 inode 都有一个 inode 编号
  根据 i-number 可以轻松在磁盘上找到 i-node
  inode 长度为 64 字节
  磁盘上的字节地址：33*BSIZE + 64*inum

目录内容
  目录以类型为 T_DIR 的 i-node 实现
    与文件共享大量实现
  内容为 dirent 数组
  dirent：
    [kernel/fs.h]
    inum
    14 字节的文件名
  若 inum 为零，则该 dirent 为空闲项
  应用程序可以读取目录以获取文件名
    应用程序不能直接写入目录

根目录（/）的 i-number 为 1，由 mkfs 创建
  因此 xv6 知道从哪里找到它

你应该将文件系统视为一种磁盘上的数据结构
  [树形结构：根 inode、dirent、inode、数据块]
  具有两个分配池：inode 池和数据块池

xv6 的磁盘布局在硬盘上性能较低
  假设你在一个包含大量文件的目录中执行 grep（搜索）操作
  i-node 与文件内容之间、以及连续文件块之间的寻道距离很长
  存在更好的布局方式
    例如：将文件的各个数据块分配在彼此相邻的位置
    例如：将 i-node 分散存储在磁盘各处，靠近对应内容

既然磁盘速度如此缓慢，缓存方面是如何处理的？
  xv6 文件系统在两个层级进行缓存：
    bio.c 中对磁盘块的缓存
    fs.c 中对活跃 i 节点的缓存

来看看 bio.c 中的块缓存
   块缓存仅保存少量最近使用的块
   bcache 位于 bio.c 开头

文件系统调用 bread，bread 再调用 bget
   bget 检查该块是否已在缓存中
   若已存在，则加锁（可能等待）并返回该块
     可能在睡眠锁处等待，直到当前使用该块的进程释放锁
     睡眠锁在已被锁定的情况下会使调用者进入睡眠
   若不存在，则复用一个已有的缓冲区
   b->refcnt++ 防止在等待期间缓冲区被回收
   不变式：内存中每个磁盘块只保留一份副本

这里有两层锁
  bcache.lock 保护缓存内容的描述信息
  b->lock 仅保护单个缓冲区

Q: 块缓存的替换策略是什么？
   prev ... head ... next
   bget 复用 bcache.head.prev —— 即"尾部"块
   brelse 将块移动到 bcache.head.next

路径名查找
  逐个解析路径名中的各个分量
  可能涉及多个块：
    顶层目录的 inode
    顶层目录的数据块
    下一级目录的 inode
    …… 以此类推 ……
  每一个都可能导致缓存未命中
    磁盘访问代价高昂
  => 允许并行路径名查找
    若某进程阻塞在磁盘 I/O 上，另一进程可继续执行查找
    挑战：unlink 可能与查找并发发生

来看 namex()（kernel/fs.c）
  ilock()：锁定当前目录
  查找下一级目录的 inode
  然后解锁当前目录
  另一进程可能会 unlink 下一个 inode
    但该 inode 不会被删除，因为其引用计数 refcnt > 0
  风险：next 指向与 current 相同的 inode（查找"."时）
    在获取 next 的锁之前先解锁 current
    关键思路：引用的获取与加锁分开进行
