回顾 #1：为什么在 swtch() 期间持有 p->lock？
   该规则影响 xv6 中的许多情况
   yield()                     scheduler()
   -------                     -----------
   acquire(&p->lock);
   p->state = RUNNABLE;
   swtch();
                               swtch();
                               release(&p->lock);

问：为什么在 swtch() 期间持有 p->lock？
  1. 防止其他核心的调度器看到 p->state == RUNNABLE
     直到原始核心完成寄存器保存之后
     直到原始核心停止使用线程栈之后
  2. 防止定时器中断在 swtch() 期间调用 yield()
     （注意：acquire() 会关闭中断）
     第二次 swtch() 会覆盖已保存在上下文中的寄存器

回顾 #2：为什么 xv6 在让出 CPU 时从不持有自旋锁？
   （p->lock 除外）
   在单核机器上，设想如下场景：
     P1           P2
     acq(x)
     sched()
                  acq(x)

问：在单核机器上，这里存在什么问题？
   P2 将永远等待：
     P2 将自旋等待 P1 释放 x
     P2 在自旋前关闭中断（设备中断……）
     没有时钟中断，P2 不会调用 yield()，P1 也不会运行
     因此 P1 永远不会释放 x
   即使在多核机器上，涉及更多锁/线程时也可能发生
   解决方案：禁止在让出 CPU 时持有锁！
     （p->lock 除外）

# 主题：序列协调
  线程经常等待特定事件／"条件"：
    磁盘读取完成（由中断通知）
    管道有数据可读（由另一个进程写入）
    子进程已退出

# 协调是线程编程的基本构建块。
  但需要注意遵循一些规则。

# 问：为什么不直接用 while 循环自旋，直到条件为真？
  管道读取：
    while buffer is empty {
    }
  管道写入：
    put data in buffer

# 更好的方案：让出 CPU 的协调原语
  操作系统使用多种机制
    e.g. barriers, semaphores, event queues, condition variables.
  xv6 使用 sleep 与 wakeup
    被许多系统所采用
    类似于条件变量

# 示例：kernel/uart.c 中的 uartwrite() 与 uartintr()
  回顾：UART 是连接到控制台的设备硬件
    UART 硬件每次只接受一个字节的输出
    硬件发送每个字节需要较长时间，可能长达一毫秒
  基本思路：
    向控制台写入的进程必须等待 UART 发送完上一个字符
    UART 硬件在发送完每个字符后会产生中断
      写入线程在等待中断期间应让出 CPU
  write() 以一个输出缓冲区调用 uartwrite()
    uartwrite() 写入第一个字节（如果可以）
    uartwrite() 调用 sleep() 等待 UART 的中断
    uartintr() 调用 wakeup()

sleep/wakeup 术语说明
  sleep(wait_chan, lock)
  wakeup(wait_chan)
  sleep 让出 CPU
  wakeup 唤醒所有以相同 wait_chan 调用 sleep() 的进程
  "&tx_chan" 参数用于关联 sleep 与 wakeup
    "等待通道"
    仅是一个数字，告知 wakeup 应唤醒哪些正在睡眠的线程
    可以是对睡眠方和唤醒方都方便的任意值
  sleep/wakeup 并不知道我们在等待什么事件
  程序员知道：
    tx_busy == 0 是 uartwrite() 等待的"条件"
    由 uartwrite() 设置；由 uartintr() 清除
  简单且灵活

# 为什么 sleep() 需要锁参数？
  遗憾的是，sleep() 的设计无法像你期望的那样简洁
  sleep() 不能简单地实现为"等待 wakeup() 被调用"
  这个问题被称为"丢失的唤醒"
  以下是详细说明

# 假设只有 sleep(chan)；我们该如何实现？
  以下是一个有缺陷的 sleep/wakeup
  [在黑板上，不在 vi 中]
  broken_sleep(chan)
    acquire(&p->lock)
    p->state = SLEEPING;
    p->chan = chan;
    swtch(...);
    (此时 scheduler() 不会运行它——因为不是 RUNNABLE 状态)
  wakeup(chan)
    for each p:
      acquire(&p->lock);
      if p->state == SLEEPING && p->chan == chan:
        p->state = RUNNABLE
  wakeup 唤醒所有在 chan 上睡眠的线程
    可能会唤醒不止一个线程

# uart 代码如何使用这个（有缺陷的）sleep/wakeup？
  uartwrite(buf):
    for each char c:
      while tx_busy:
        broken_sleep(&tx_chan)
      send c
      busy = 1
  uartintr():
    tx_busy = 0
    wakeup(&tx_chan)

# 那么 UART 操作的加锁问题呢？
  - 驱动的数据结构，例如 tx_busy
  - UART 硬件
  uartwrite() 和 uartintr() 都需要加锁
  Q: uartwrite() 是否应该在其整个生命周期内持有锁？
     不行：否则 uartintr() 无法获取锁并清除 tx_busy
  也许 uartwrite() 可以在 sleep() 之前释放锁？
  我们来尝试一下——修改 uart.c 以调用 broken_sleep()
    release(&tx_lock);
    broken_sleep(&tx_chan);
    acquire(&tx_lock);
  Q: 会出什么问题？
  make qemu
  cat README

问题所在：
  uartwrite() 发现 tx_busy = 1（UART 尚未处理完上一个字节）
  释放 tx_lock
    从而启用中断
  中断发生！
    uartintr() 将 tx_busy 置为 0
    uartintr() 调用 wakeup()——但此时没有任何进程需要唤醒！
  随后 uartwrite() 调用 sleep()
  uartwrite() 进入睡眠，尽管 UART TX 中断已经完成
    且 tx_busy 已为零……
  现在没有任何机制能唤醒 uartwrite()，它将永远沉睡
    实际上，直到一个 UART *输入* 中断才会被唤醒

这就是"丢失唤醒"问题。

我们需要消除 uartwrite() 检查条件与 sleep() 将进程标记为睡眠状态之间的时间窗口。
    
  我们将使用锁来防止 wakeup() 在整个时间窗口内运行。

我们将修改 sleep() 的接口及其使用方式。
  sleep() 将要求提供一个"条件锁"，以防止
    条件发生变化，并要求调用
    sleep() 和 wakeup() 的调用方都持有该锁
  sleep(chan, lock)
    调用方必须持有锁
    sleep 释放锁，返回前重新获取
  wakeup(chan)
    调用方必须持有锁

sleep 并不知晓条件的具体内容，也不知道锁与条件的关联关系
  但该锁必须能阻止所等待条件的变化！
  且该锁必须传递给 sleep()
  且在调用 wakeup() 时必须持有该锁

(repair uart.c)

让我们来看 proc.c 中的 wakeup(chan)
  它扫描进程表，查找状态为 SLEEPING 且 chan 匹配的进程
  它获取每个 p->lock
  调用方在调用 wakeup() 之前已获取条件锁
  因此 wakeup() 同时持有条件锁和每个 p->lock

问：为什么仅将 p->state 设置为 RUNNABLE 就足够了？
   这为何能使该线程（最终）得以运行？

让我们来看 proc.c 中的 sleep()
  注意：sleep 必须释放条件锁
    因为调用 swtch() 时不能持有锁，除了 p->lock
    并且唤醒者需要持有条件锁才能修改条件
  Q: 如何防止 sleep() 释放条件锁之后 wakeup() 趁机运行？
     条件锁？
  A: 在释放条件锁*之前*先获取 p->lock
     因此，在整个过程中，sleep() 持有 lk、p->lock 或两者之一
  由于 wakeup() 同时持有*两把*锁，sleep() 只需持有*任意一把*即可
    迫使 wakeup() 自旋等待，而不是去查看正在调用 sleep() 的进程
  现在 wakeup() 必须等到 sleep() 的 swtch() 完成后才能继续执行
    因此 wakeup() 保证能看到 p->state==SLEEPING 且 p->chan==chan
  从而：不会丢失唤醒！
    wakeup() 无法在检查条件与调用 sleep() 之间趁虚而入

[时序图，或口述，锁的时间线]
  uartwrite()         uartintr()
  -----------         ----------
  acq tx_lock         acq tx_lock
  check tx_busy       tx_busy = 0
  sleep()             wakeup()
    acq p->lock         acq p->lock
    rel tx_lock         check SLEEPING / chan
    SLEEPING            rel p->lock
    swtch()             rel tx_lock
      rel p->lock

关键点：重叠持有的锁防止了 wakeup 在释放 tx_lock 与进入睡眠之间趁虚而入，
  即在释放 tx_lock 与进入睡眠之间趁虚而入。
  从而避免了丢失唤醒的问题。

Q: 为什么 uartwrite() 要将 sleep() 包在一个循环中？
  即 sleep() 返回后重新检查条件，可能再次进入睡眠
  原因有两点：
    1. 可能有多个等待者，另一个线程可能已将 tx_busy 置位
    2. kill() 会唤醒进程，即使条件并不成立
  所有对 sleep 的调用都包在循环中，以便重新检查条件

# 另一个示例：pipe.c 中的 piperead()
  条件是有数据等待读取（nread != nwrite）
  条件锁是管道的 pi->lock
  pipewrite() 在末尾调用 wakeup()
  如果 piperead() 使用了 broken_sleep()，竞争条件是什么？
    即先释放锁，再调用 sleep
    丢失唤醒不只发生在中断场景中！
  注意 sleep() 外层的循环
    多个进程可能同时读取同一个管道
  Q: 为什么 piperead() 末尾也要调用 wakeup()？

# sleep/wakeup 的接口与规则稍显复杂
    -> sleep() 需要条件锁
  但是，sleep() 不需要理解条件本身
  sleep/wakeup 相当灵活，尽管属于较低层次的机制

# 另一个协调难题——如何关闭一个线程？

# xv6 有两种销毁进程的方式：exit() 和 kill()

# exit() 难题：线程无法释放自身的所有资源
  例如自身的 proc[] 槽位
  例如自身的栈，而它仍在使用中

# exit()：
  我们希望最终达到的状态：
    p->state = UNUSED，以便将来的 fork() 可以使用该 proc[] 槽位
    并且所有资源均已释放
  策略：
    exit() 释放部分资源，但并非全部，例如内核栈不释放
    父进程的 wait() 完成最终的释放工作

# proc.c 中的 kexit()：
    进行部分清理
    唤醒正在 wait() 的父进程
    p->state = ZOMBIE
      还不能设为 UNUSED！
        仍在使用内核栈和 proc[] 条目
      ZOMBIE 表示已准备好等待父进程的 wait()
        但 fork() 不会分配它（因为不是 UNUSED）
        调度器也不会运行它（因为不是 RUNNABLE）
    swtch() 切换到调度器

# proc.c 中的 kwait()（父进程最终应调用）：
  扫描 proc[] 表，查找任何 p->state==ZOMBIE 的子进程
  调用 freeproc()
    （持有 p->lock 期间……）
    trapframe、pagetable、……、p->state=UNUSED
  子进程在 kexit() 将 p->state 设为 ZOMBIE 之后是否仍可能在执行？
    不会：kexit() 在此期间持有 p->lock
    因此可以安全地释放子进程的栈和 struct proc
  因此：wait() 不仅是为应用程序提供便利，对操作系统本身也是必要的

#  什么机制避免了 exit()->wait() 唤醒的丢失？
   若子进程在父进程检查 ZOMBIE 之后、父进程调用 sleep() 之前调用了 exit()
   条件是什么？
     某个子进程处于 ZOMBIE 状态
   条件锁是什么？
   不能是子进程的 p->lock，因为父进程的 wait() 不知道
     它在等待哪个子进程！
   所以：wait_lock 就是条件锁
     它是全局变量，而非每个进程各自持有
   wait()：
     在扫描 proc[] 查找 ZOMBIE 子进程时持有 wait_lock
     wait_lock 是 wait() 传递给 sleep() 的条件锁
   exit()：
     在执行 p->state=ZOMBIE 和 wakeup(p->parent) 时持有 wait_lock
   所以：子进程的 exit() 必须等待父进程完成 ZOMBIE 检查并进入睡眠
   所以：父进程不会在检查 ZOMBIE 与进入睡眠之间错过唤醒信号
   更好的设计可能是为每个父进程单独维护一把 wait_lock

# kill() 难题：线程 X 不能直接销毁线程 Y
  如果 Y 正在另一个核上执行怎么办？
    不能直接释放它的内核栈或用户内存！
  如果 Y 持有锁怎么办？
  如果 Y 正在对重要数据结构进行复杂更新的中途怎么办？
    必须让它执行完！
  所以：kill() 不能直接销毁目标进程。

# kill() 解决方案：
  kill() 仅设置 p->killed 标志，不做其他操作
  目标进程自身检查 p->killed 标志
    并自行调用 kexit()
  在 usertrap() 中查找 "if(killed(p)) kexit(-1);"
    此处不处于任何操作的中途，且没有持有锁
    因此退出是安全的

# 如果 kill() 的目标处于 SLEEPING 状态——在 sleep() 中——怎么办？
  此时它不持有锁，也没有在执行！
  kill() 立即销毁目标进程是否可行？
  不行：如果正在文件创建的中途等待磁盘怎么办？

# xv6 对 kill() 作用于 sleep() 中进程的解决方案
  参见 proc.c 中的 kill()
    将 SLEEPING 改为 RUNNABLE——类似于 wakeup()
    这样 sleep() 将返回，可能在条件满足之前就返回了
  部分 sleep 循环会检查 p->killed
    例如 piperead()、consoleread()
    否则已被 kill 的进程的读操作可能会无限期挂起
  部分 sleep 循环不检查 p->killed
    例如 virtio_disk.c
    不能直接退出，因为可能处于文件系统更新的中途
    影响不大，因为磁盘读取速度相当快
  因此被 kill() 的进程可能还会继续运行一段时间
    但 usertrap() 会在系统调用完成后调用 exit()

# xv6 关于 kill 的规范
  如果目标进程处于用户态
    则下次发起系统调用或触发时钟中断时才会终止
  如果目标进程处于内核中
    目标进程将不再执行任何用户态指令
    但可能还会在内核中继续运行一段时间
