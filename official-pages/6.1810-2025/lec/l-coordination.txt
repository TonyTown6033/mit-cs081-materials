Q: why is p->lock held across swtch()?
  1. prevent another core's scheduler from seeing p->state == RUNNABLE
     直到原始核心完成寄存器保存后
     直到原始核心停止使用线程堆栈之后
  2.防止定时器中断在swtch()期间调用yield()
     （记住：acquire() 关闭中断）
     第二个 swtch() 将覆盖上下文中已保存的寄存器

问：在单核机器上，这里有什么问题？
   P2将永远等待：
     P2将旋转等待P1释放x
     P2 在旋转之前禁用中断（设备中断...）

sleep 不知道条件是什么，也不知道锁与它有何关系

  并且锁必须传递给 sleep()

让我们看看proc.c中的wakeup(chan)
  它扫描进程表，寻找 SLEEPING 和 chan
  it grabs each p->lock
  调用者在调用wakeup()之前获得条件锁
  so wakeup() holds BOTH the condition lock AND each p->lock

Q: why is it enough to just set p->state = RUNNABLE?
   为什么这会导致线程（最终）运行？

让我们看看 proc.c 中的 sleep()
  嗯：睡眠*必须*释放条件锁
    since we can't hold locks when calling swtch(), other than p->lock
    唤醒器需要它来修改条件
  问：如何防止 sleep() 释放后 waitup() 运行
     条件锁？
  A: acquire p->lock *before* releasing condition lock
     so, throughout, sleep() holds either lk, p->lock, or both
  由于wakeup()持有*两个*锁，所以sleep()持有*任一*就足够了
    强制wakeup()旋转而不是查看调用sleep()的进程
  现在，直到 sleep() 的 swtch() 完成后，wakeup() 才能继续
    so wakeup() is guaranteed to see p->state==SLEEPING and p->chan==chan
  因此：不会丢失唤醒！
    wakeup() 不能潜入条件检查和 sleep() 之间

要点：重叠的锁可以防止唤醒偷偷摸摸
  在释放 tx_lock 和进入睡眠之间。
  从而避免唤醒丢失。

问：为什么 uartwrite() 将 sleep() 包裹在一个循环中？
  即在 sleep() 返回后重新检查条件，可能会再次睡眠
  两个原因：
    1. 可能有多个等待者，另一个线程可能设置了 tx_busy
    2. 即使条件不成立，kill() 也会唤醒进程
  所有对 sleep 的调用都包含在循环中，因此它们会重新检查

# another coordination challenge -- how to shut down a thread?

# xv6 has two ways to get rid of processes: exit() and kill()

# exit() puzzle: a thread cannot free all of its own resources
  例如它自己的 proc[] 槽
  例如它自己的堆栈，它仍在使用

# exit():
  我们想要结束的地方：
    p->state = UNUSED, so a future fork() can use this proc[] slot
    并且所有资源都是免费的
  策略：
    exit() 释放了一些东西，但不是全部，例如内核堆栈
    父级的 wait() 执行最后的释放

# kexit() in proc.c:
    一些清理工作
    唤醒等待（）的父母
    p->state = ZOMBIE
      还不能未使用！
        仍然使用内核堆栈和 proc[] 条目
      ZOMBIE 表示已准备好等待父级的 wait()
        但 fork() 不会分配它（不是未使用的）
        并且调度程序不会运行它（不可运行）
    swtch() 到调度程序

# kwait() in proc.c (parent should eventually call):
  scans proc[] table for any child with p->state==ZOMBIE
  调用 freeproc()
    (p->lock held...)
    trapframe, pagetable, ..., p->state=UNUSED
  could child still be executing, perhaps after kexit() set p->state to ZOMBIE?
    no: kexit() held p->lock during that time
    所以释放孩子的堆栈和结构过程是安全的
  因此： wait() 不仅是为了应用程序方便，也是为了操作系统

#  what avoids a lost exit()->wait() wakeup?
   如果子进程 exit() 在父进程检查 ZOMBIE 和父进程 sleep() 之间
   条件是什么？
     有些孩子是僵尸
   条件锁是什么？
   can't be child's p->lock, since parent wait() doesn't know
     它在等哪个孩子！
   so：wait_lock是条件锁
     它是一个全局变量，而不是每个进程
   等待（）：
     扫描 proc[] 中的 ZOMBIE 子进程时持有 wait_lock
     wait_lock 是 wait() 传递给 sleep() 的条件锁
   退出（）：
     holds wait_lock around p->state=ZOMBIE and wakeup(p->parent)
   所以：子进程 exit() 必须等待父进程完成 ZOMBIE 检查并睡眠
   所以：父母不能在检查 ZOMBIE 和睡觉之间错过唤醒
   更好的设计可能每个父级都有一个单独的 wait_lock

# kill() puzzle: thread X cannot just destroy thread Y
  如果 Y 在另一个核心上执行怎么办？
    不能只是释放其内核堆栈或用户内存！
  如果 Y 持有锁怎么办？
  如果 Y 正在对重要数据结构进行复杂更新怎么办？
    必须让它结束！
  所以：kill()不能直接摧毁目标。

# kill() solution: 
  kill() sets p->killed flag, nothing else
  the target process itself checks for p->killed
    并调用 kexit() 本身
  寻找“if(killed(p)) kexit(-1);”在用户陷阱()中
    不在任何东西中间，也没有锁
    所以可以安全退出

# what if kill() target is SLEEPING -- in sleep()?
  在这种情况下，它不会持有锁，并且不会执行！
  Kill() 可以立即摧毁目标吗？
  否：如果在文件创建过程中等待磁盘怎么办？

# xv6 solution to kill() of sleep()ing process
  参见 proc.c 中的kill()
    将 SLEEPING 更改为 RUNNABLE - 就像wakeup()
    所以 sleep() 可能会在条件成立之前返回
  some sleep loops check for p->killed
    例如管道读取()、控制台读取()
    否则 read 可能会因被终止的进程而无限期挂起
  some sleep loops don't check p->killed
    例如virtio_disk.c
    无法退出，因为可能是文件系统更新中途
    还不错，因为磁盘读取速度非常快
  所以一个被kill()ed的进程可能会持续一段时间
    但 usertrap() 将在系统调用完成后 exit()

# xv6 spec for kill
  如果目标位于用户空间
    将在下次进行系统调用或进行定时器中断时死亡
  如果目标在内核中
    目标永远不会执行另一个用户指令
    但可能会在内核中花费一段时间
