6.1810 2025 L21：容器与虚拟机

论文：融合容器与虚拟机：对
Firecracker 与 gVisor 的研究（VEE 2020），作者 Anjali 等人。

目标："监禁"不可信代码
  操作系统隔离基于内核 + 进程 + 虚拟内存
    内核被攻破则隔离失效
  现代操作系统具有宽泛的系统调用接口
    系统调用共享许多命名空间（fs、pid 等）
  本文综述了实现更强隔离的技术
    减少对系统调用和命名空间的访问
    
动机：无服务器计算
  租户向提供商提交应用程序
  提供商希望在同一服务器上运行多个应用以实现高利用率
  隔离挑战：代码任意，需隔离来自不同租户的应用
  性能挑战：负载可能大幅波动
    可从机器的一小部分扩展到多台机器
    变化可能很快，因此需要迅速启动新实例
  许多具体的隔离技术也被更广泛地使用。
    Android 手机、Web 服务器、Chrome 浏览器、OpenSSH……

隔离方案
  Linux 进程与 chroot
  容器，使用 Linux 命名空间 + cgroups
  "用户态内核"或"库操作系统"（gVisor、Drawbridge）
  虚拟机

Linux 进程
  用户 ID
  文件级权限
  旨在用户间细粒度共享，而非粗粒度隔离
  注意：xv6 没有用户 ID 和权限机制

为什么 Linux 中的隔离具有挑战性？
  内核中存在大量共享状态（"资源"）。
  系统调用通过命名来访问共享状态。
    PID。
    文件名。
    IP 地址 / 端口。
    （甚至某种形式的用户 ID。）
  典型的访问控制围绕用户 ID 展开（例如文件权限）。
    难以用权限来强制隔离两个应用程序。
    大量文件各有权限。
    应用程序会无意或故意创建共享文件（例如全局可写文件）。

Unix/Linux 机制：chroot <dir>
  将进程的根目录更改为目录 <dir>
    / 命名 <dir>
  优点：对进程实施"监狱"隔离
    限制某个应用程序可以命名的文件范围
      即使应用程序意外创建了全局可写文件也无关紧要
        被关押的进程无法访问它
  挑战：不允许进程逃脱监狱
    风险：..、符号链接等
  是实现更好隔离的良好起点，但存在不足
    监狱中仍有许多系统调用可访问其他共享资源
    例如：kill <pid>
  
命名空间提供了一种对系统调用中可命名资源进行作用域限定的方式
  [[ Ref: https://blog.quarkslab.com/digging-into-linux-namespaces-part-1.html ]]
  进程属于某个特定的命名空间（对应每种命名空间类型）
    新进程继承父进程的命名空间
    例如，PID 命名空间限制了进程可以命名的 PID 范围
  命名空间类型：PIDs、IPC（共享内存等）、NET、UTS（主机名）、USER 等
  粗粒度隔离，不受应用程序行为的影响
  针对不同类型资源（不仅限于文件系统）设计更合理的 chroot

挑战：监狱中的进程需要正常运行
  它需要：
    动态链接库
    配置文件（时区等）
    可能还需要 python 解释器或其他程序
    ..
  它需要一个 Linux 环境
  解决方案：Open Container Initiative (OCI) 提供了标准容器格式。
    [[ Ref: https://opencontainers.org/ ]]
    例如：Alpine Linux，一个轻量级 Linux 环境
  流行方案：Linux 容器、gvisor 和 Firecracker 均采用该格式

Linux 容器
  命名空间可控制哪些文件、进程等是可见的。
  为每个进程的 Linux 环境提供容器镜像
  Cgroups 控制资源使用，实现性能隔离。
  注意"容器"一词有两种含义
  - 容器镜像（OCI 格式）
  - 使用命名空间和 cgroups 的隔离技术

容器为被关押的进程提供其"专属"的 Linux 环境
  拥有自己的动态链接库等。
  即使不用于隔离也很有用：如果两个应用需要不同版本的 libssl 怎么办？
    Open Container Initiative (OCI) 提供了标准容器格式。
    Docker 容器可在 Linux 容器隔离或 gVisor 下运行。
      甚至支持在 Firecracker 上运行 Docker 容器。
      [[ Ref: https://github.com/weaveworks/ignite ]]
  容器隔离基于两种 Linux 机制：命名空间（namespaces）和控制组（cgroups）。

Linux cgroups。
  对资源使用进行限制 / 调度。
  内存、CPU、磁盘 I/O、网络 I/O 等。
  作用于进程，类似于命名空间。
    新进程继承父进程的 cgroup。
  不是安全边界，但对于防止 DoS 攻击很重要。
    例如，某个进程或虚拟机试图独占所有 CPU 或内存。

为什么命名空间/容器可能还不够？
  共享 Linux 内核。
  攻击面很广：350+ 个系统调用，ioctl 下还有许多专用功能……
  大量代码，使用 C 语言编写。
    漏洞（缓冲区溢出、释放后使用……）持续被发现。
    Linux 内核自身内部没有隔离。
  内核漏洞使攻击者得以逃脱隔离（"本地权限提升"，即 LPE）。
    较为常见：每年都会出现新的 LPE 漏洞。

额外的安全机制：seccomp-bpf。
  思路：过滤进程可以调用的系统调用。
    参见本学期早些时候的 Janus 课程
  可能有助于我们应对 Linux 内核的广泛攻击面。
  常见规律：较少使用的系统调用或功能更容易存在漏洞。
  每个进程（可选地）关联一个系统调用过滤器。
    过滤器以 BPF 字节码语言编写的小程序形式呈现。
    Linux 内核在每次系统调用被调用前，先运行该过滤器，再执行系统调用。
    过滤器程序可以决定是否允许该系统调用。
    可以查看系统调用编号、参数等。
    新进程继承父进程的系统调用过滤器："粘性"继承。
  可使用 seccomp-bpf 阻止访问可疑的系统调用。
  被部分容器实现所采用。
    设置 bpf 过滤器以禁止可疑系统调用。
  为什么这可能还不够？
    限制系统调用可能会降低兼容性。
    可能导致使用非常规系统调用的应用程序无法正常运行。
    但对于安全性而言仍可能不足（常见系统调用中存在大量代码/漏洞）。
  容器：所有系统调用，除了 44 个（见表 1）。

挑战：减少可用的系统调用数量
  约束：应用程序应能正常运行
  思路：为容器提供独立的 Linux 内核
  两种方式：gvisor 和虚拟机（VM）（见图2和图3）
  VM 和 gvisor 向宿主机发出系统调用，但被隔离的应用程序不会
    见表1：实现 firecracker VM 需实现 36 个系统调用

什么是虚拟机？
  对计算机的仿真，精确到足以运行操作系统
  示意图：硬件、宿主机/VMM、客户 Linux 及应用程序
    VMM 可以独立运行，或
    VMM 可以运行在宿主操作系统中，例如 Linux
  为什么这比容器更好？
    攻击面更小：无需复杂的系统调用，仅需 x86 加虚拟设备。
    漏洞更少：VM 逃逸漏洞的发现频率低于每年一次。

虚拟机有着悠久的历史
  1960年代：IBM 使用虚拟机共享昂贵的大型机
  1980年代：（计算机变得小巧且廉价）
         （随后机房变得拥挤不堪）
  1990年代：VMWare 重新推广了虚拟机，用于 x86 硬件
  2000年代：在云计算和企业领域得到广泛应用

慢速虚拟机：模拟硬件
  VMM 逐条解释客户指令
  为客户维护虚拟机状态
    32个寄存器、satp、模式、RAM、磁盘、网络等
  优点：可以工作；我们在实验中使用它
    xv6 内核运行在 QEMU 之上
    虚拟机的用途不限于隔离
      例如，在 Linux 上运行 Windows（或反之亦然）
  缺点：速度慢

思路：在 CPU 上直接执行客户指令——速度快！
  观察：客户操作系统和应用程序使用相同的指令集（x86）
    [对 xv6 不适用]
  用 CPU 的 add 指令执行加法，而非模拟
    速度快！
  如果客户内核执行特权指令会怎样？
    例如，客户将新的页表加载到 satp

思路：在用户态运行客户内核
  类似于将客户内核作为用户进程运行
    当然，客户内核假设自己处于超级用户模式
  普通指令正常工作
    两个寄存器相加、函数调用等
  x86/RISC-V 特权指令在用户态是非法的
    将触发陷阱，转交给 VMM
  VMM 的陷阱处理程序模拟特权指令
    可能将特权操作应用于"虚拟状态"
      例如，读/写 sepc
    也许转换后应用到真实硬件
      例如，对 satp 的赋值操作
  "陷阱与模拟"
     较好但仍然较慢：大量陷阱进入 VMM

示例：RISC-V 陷阱与模拟
  客户机用户代码执行 ecall 进行系统调用？
  [图示：客户机用户态、客户机内核、VMM、虚拟状态、真实 sepc]
  CPU 陷入 VMM（ecall 始终产生陷阱）
    硬件将客户机的 PC 保存在（真实）sepc 中
  VMM 陷阱处理程序：
    检查客户机指令
    虚拟 sepc <- 真实 sepc
    虚拟模式 <- supervisor
    虚拟 scause <- 8 "系统调用"
    真实 sepc <- 虚拟 stvec
    [[ 暂时忽略页表；如何处理客户机内核中非 PTE_U 的条目？ ]]
    sret：从陷阱返回（将真实模式设置为用户态）

VT-x/VMX/SVM：硬件支持的虚拟化
  现代 Intel（和 AMD）CPU 在硬件层面支持虚拟化
    客户机可以无需陷阱地执行特权指令！
    可以修改控制寄存器、更改页表、处理异常！
    可以切换到用户态，并接收系统调用陷阱
    等等。
  比陷阱与模拟更快，VMM 软件也更简单
  广泛用于实现虚拟机（例如 KVM）

（这怎么可能是安全的？）

一些术语
  每个 CPU 处于 root 模式——运行宿主机
    或处于 non-root 模式——运行客户机（内核 + 用户进程）
    执行在两者之间来回切换
  VMCS（VM 控制结构）
    配置，
    客户机特权状态的保存/恢复
      例如，虚拟 sepc、mode、scause、stvec
  特殊指令用于切换 VT-x 模式
    VMLAUNCH/VMRESUME：宿主机 -> 客户机
      CPU 使用客户机的 sepc、mode、scause、stvec
      系统调用无需切换回宿主机！
    VMCALL：客户机 -> 宿主机

VMCS 内存区域保存宿主机的已保存状态
  VMLAUNCH 和 VMRESUME 保存宿主机所有特权状态（寄存器等）
  并恢复客户机所有（先前保存的）状态
  从客户机退出到宿主机时恢复宿主机的状态
    因此客户机无法干扰宿主机的特权状态
  因此：如果宿主机正确配置，客户机便无法逃脱
    宿主机能否允许客户机使用宿主机的 satp？
    VT-x 必须防止宿主机读写其内存范围之外的内容！

VT-x 的 EPT（扩展页表）限制客户机的内存访问
  问题：
    我们希望让客户机内核控制自己的页表，
    同时又希望将客户机限制在其允许的物理内存范围内，
  CPU 的 MMU 在 VT-x 客户机模式下有 *两层* 地址转换
    第一层，%cr3/satp 页表将客户机虚拟地址映射到客户机物理地址（与通常相同）
    第二层，EPT 将客户机物理地址映射到宿主机物理地址
  VMM 配置 EPT，使其仅包含客户机自身内存的映射
  客户机无法查看或修改 EPT
  因此：
    客户机可以自由读写 %cr3、修改 PTE、读取 D 位等
    VMM 仍可通过 EPT 实现隔离

Linux KVM（基于内核的虚拟机）。
  [[ Ref: https://lwn.net/Articles/658511/ ]]
  [[ Ref: https://www.kernel.org/doc/html/latest/virt/kvm/api.html ]]
  用于使用硬件虚拟化支持的抽象层。
  管理虚拟 CPU 和虚拟内存。
  对应的硬件支持：扩展页表。
  QEMU：
    实现虚拟设备
    实现纯虚拟设备（virtio）。
    实现 CPU 指令的模拟。
      在使用硬件支持时大多不需要。
      但仍用于硬件不原生支持的指令。
      例如，CPUID、INVD 等。
      [[ Ref: https://revers.engineering/day-5-vmexits-interrupts-cpuid-emulation/ ]]
    提供部分 BIOS 实现以启动虚拟机。

虚拟机的缺点是什么？
  启动开销大：启动虚拟机需要较长时间
  运行开销高：每个运行中的虚拟机占用大量内存
  资源分配与共享粗放且不灵活（虚拟机内存、虚拟磁盘、vCPU）
  VMM 本身（QEMU）可能存在漏洞：共 140 万行 C 代码。

Firecracker 设计。
  论文中的图 3。
  使用 KVM 实现虚拟 CPU 和内存。
  用 Rust 重新实现 QEMU。
  支持最小化设备集合。
    virtio 网络、virtio 块设备（磁盘）、键盘、串口。
  使用块设备而非文件系统：实现更强的隔离边界。
    文件系统具有复杂的状态。
      目录、可变长度文件、符号链接/硬链接。
    文件系统具有复杂的操作。
      创建/删除/重命名文件、移动整个目录、读/写范围、追加……
    块设备则简单得多：
      4 KByte 的块。
      块从 0 到 N 编号，N 即磁盘大小。
      读写整个块。（也许还有刷新/屏障操作。）
  不支持指令模拟。
    （除 CPUID、VMCALL/VMEXIT 等必要指令外。）
  完全不支持任何 BIOS。
    仅在初始化时将内核加载到虚拟机中并开始运行。

Firecracker 实现：Rust。
  内存安全语言（"unsafe" 代码除外）。
  5 万行代码：远少于 QEMU。
  使 VMM 实现出现缓冲区溢出等漏洞的可能性大大降低。
  [[ Ref: https://github.com/firecracker-microvm/firecracker ]]

Firecracker VMM 运行在"jail"进程中。
  chroot 限制 VMM 可访问的文件。
  namespaces 限制 VMM 访问其他进程和网络。
  以独立用户 ID 运行。
  seccomp-bpf 限制 VMM 可调用的系统调用。
  所有这些措施都是为了确保即使 VMM 中的漏洞被利用，攻击者也难以进行权限提升。

gVisor 方案：在独立的用户态进程中重新实现操作系统的系统调用接口。
  见论文图 2。
  拦截容器内进程发起的系统调用（使用 ptrace 或 KVM）。
  由用 Go 编写的用户态进程来实现这些系统调用。
    同样，相比 C 语言，Go 能更好地避免缓冲区溢出等错误。
  优点：Go 代码出现内存管理漏洞的可能性更低。
  优点：漏洞不在内核代码中，通常受 Linux 进程隔离机制约束。
    使用 seccomp-bpf 限制 gVisor 模拟器可调用的系统调用。
  优点：更细粒度的共享。
    可共享特定文件或目录。
  优点：更细粒度的资源分配。
    不必使用整块虚拟磁盘或整个虚拟机的内存分配。
    对于在隔离环境中运行小型应用程序尤为重要。
  缺点：性能开销可能较为显著。
    每个系统调用都必须重定向到 gVisor 进程。
    上下文切换开销、数据复制开销等。
  潜在缺点（或优点）：兼容性问题（真实 Linux 与 gVisor 之间的差异）。
    gVisor 在忠实实现 Linux 系统调用方面表现出色！
    可以实现在旧宿主机上模拟新系统调用

安全性比较：可访问的系统调用。
  系统调用总数约 350 个
  LXC（Docker）：屏蔽 44 个系统调用（允许 300+ 个）
  Firecracker：VMM 允许 36 个系统调用
  gVisor：Sentry 允许 53-68 个系统调用

各平台有哪些潜在的优点或缺点？
  Linux：简单，执行代码最少，开销最小。
  LXC：隔离与容器抽象，灵活共享，接近原生性能。
  gVisor：强隔离但仍可灵活共享，资源分配。
  Firecracker：强隔离，性能优于 gVisor，但
  粒度较粗。
