为什么 Linux 中的隔离具有挑战性？
  内核中有很多共享状态（“资源”）。
  系统调用通过命名来访问共享状态。
    PIDs.
    文件名。
    IP 地址/端口。
    （甚至是某种形式的用户 ID。）
  典型的访问控制围绕用户 ID（例如文件权限）。
    很难使用权限来强制两个应用程序之间的隔离。
    很多具有权限的文件。
    应用程序无意中或有意创建共享文件（例如，全局可写）。

Unix/Linux 机制：chroot <dir>
  将进程的根目录更改为目录 <dir>
    / 名称 <目录>
  好处：“监禁”进程
    限制一个应用程序可以命名的文件
      如果应用程序意外创建了全局可写文件也没关系
        被监禁的进程无法访问它
  挑战：不允许进程越狱
    风险：..、符号链接等。
  更好隔离的良好起点，但存在缺点
    许多系统调用在监狱中仍然可用，可以访问其他共享资源
    例如，杀死 <pid>
 
命名空间提供了一种确定可在系统调用中命名的资源范围的方法
  [[参考：https://blog.quarkslab.com/digging-into-linux-namespaces-part-1.html]]
  进程属于特定的命名空间（对于每种命名空间类型）
    新进程继承父进程的命名空间
    例如，PID 命名空间限制进程可以命名的 PID
  命名空间：PID、IPC（共享内存等）、NET、UTS（主机名）、USER 等
  粗粒度隔离，不受应用程序可能执行的操作的影响
  针对不同类型的资源（不仅仅是文件系统）设计更好的 chroot

挑战：监狱中的进程需要运行

Linux容器
  命名空间可以控制哪些文件、进程等可见。
  每个进程 Linux 环境的容器镜像
  Cgroup 控制资源使用以实现性能隔离。
  注意“容器”一词有两种含义
  - 容器镜像（OCI 格式）
  - 使用命名空间和 cgroup 的隔离技术

容器为被监禁的进程提供“自己的”Linux 环境
  自己的动态链接库等
  即使没有隔离也很有用：如果两个应用程序需要不同的 libssl 版本怎么办？
    开放容器倡议 (OCI) 具有标准容器格式。
    Docker 容器可以与 Linux 容器隔离或 gVisor 一起运行。

  容器隔离建立在两种 Linux 机制之上：命名空间和 cgroup。

Linux cgroup。
  资源使用的限制/调度。
  内存、CPU、磁盘I/O、网络I/O等
  适用于进程，就像命名空间一样。
    新进程继承父进程的cgroup。
  不是安全边界，但对于防止 DoS 攻击很重要。
    例如，一个进程或虚拟机试图独占所有 CPU 或内存

为什么命名空间/容器还不够？
  共享 Linux 内核。
  广泛的攻击面：350+系统调用，ioctl下的许多专门函数...
  代码量大，用C语言编写。
    错误（缓冲区溢出、释放后使用等）不断被发现。
    Linux 内核本身没有隔离。
  内核错误让攻击者能够逃脱隔离（“本地权限升级”或 LPE）。
    相对常见：每年都会出现新的 LPE 错误。

附加安全机制：seccomp-bpf。
  思路：过滤进程可以调用哪些系统调用。
    请参阅本学期早些时候的 Janus 讲座
  可能会帮助我们解决 Linux 内核的广泛攻击面。
  常见模式：很少使用的系统调用或功能更有可能出现错误。
  每个进程（可选）与系统调用过滤器关联。
    过滤器用 BPF 字节码语言编写为一个小程序。
    Linux 内核在运行系统调用之前在每个系统调用调用上运行此过滤器。
    过滤器程序可以决定是否允许系统调用。
    可以查看系统调用#、参数等。
    新进程继承父进程的系统调用过滤器：“sticky”。
  可以使用 seccomp-bpf 来防止访问可疑的系统调用。
  由一些容器实现使用。
    设置 bpf 过滤器以禁止可疑的系统调用。
  为什么这可能不够好？
    限制系统调用可能会限制兼容性。
    可能会破坏使用不常见系统调用的应用程序代码。
    但对于安全性来说仍然可能不够（常见系统调用中存在大量代码/错误）。
  容器：所有系统调用，除了 44（参见表 1）

挑战：减少可用系统调用的数量
  限制：应用程序应该可以工作
  想法：给容器自己的Linux内核
  两种方法：gvisor 和 VM（见图 2 和图 3）
  虚拟机和 gvisor 对主机进行系统调用，但被监禁的应用程序不会
    参见表1：实现firecracker VM的36个系统调用

什么是虚拟机？

一些术语
  每个CPU都处于任一根模式——运行主机
    或在非root模式下——运行来宾（内核+用户进程）
    执行来回切换
  VMCS（VM控制结构）
    配置，
    保存/恢复访客特权状态
      例如，虚拟 sepc、模式、原因、stvec
  特别说明切换VT-x模式
    VMLAUNCH/VMRESUME: host -> guest
      CPU 使用客人规格、模式、原因、stvec
      系统调用不需要切换到主机！
    VMCALL: guest -> host

VMCS 内存区域保存已保存的主机状态
  VMLAUNCH 和 VMRESUME 保存所有主机特权状态（寄存器和c）
  并恢复所有客人的（之前保存的）状态
  从访客退出到主机恢复主机状态
    所以客人不能打扰主人的特权状态
  因此：如果主机配置正确，访客就无法逃脱
    主机可以允许访客使用主机的 satp 吗？
    VT-x 必须防止主机在其内存之外读取/写入！

VT-x 的 EPT（扩展页表）限制 guest 内存访问
  problem:
    我们想让客户内核控制它自己的页表，
    我们还想限制来宾仅使用其允许的物理内存，
  CPU 的 MMU 在 VT-x 访客模式下具有“两层”地址转换
    first, %cr3/satp page table maps guest va -> guest pa (as usual)
    second, EPT maps guest pa -> host pa
  VMM 将 EPT 设置为仅具有来宾自己的内存的映射
  访客无法查看或更改 EPT
  so:
    来宾可以自由读取/写入 %cr3、更改 PTE、读取 D 位等
    VMM 仍然可以通过 EPT 提供隔离

VM 有什么缺点？
  启动成本高：虚拟机启动时间长
  高开销：每个正在运行的虚拟机都会消耗大量内存
  刚性/粗略的资源分配和共享（VM内存；虚拟磁盘；vCPU）
  VMM 本身 (QEMU) 中的潜在错误：140 万行 C 代码。

鞭炮设计。
  论文中的图3。
  使用KVM虚拟CPU和内存。
  用 Rust 重新实现 QEMU。
  支持最少的设备集。
    virtio 网络、virtio 块（磁盘）、键盘、串行。
  块设备代替文件系统：更强的隔离边界。
    文件系统具有复杂的状态。
      目录、可变长度文件、符号链接/硬链接。
    文件系统的操作比较复杂。
      创建/删除/重命名文件，移动整个目录，读/写范围，追加，...
    块设备要简单得多：
      4 KB 块。
      块编号为 0 到 N，这是磁盘的大小。
      读取和写入整个块。 （也许齐平/屏障。）
  不支持指令仿真。
    （除了必要的指令，如 CPUID、VMCALL/VMEXIT 等）
  根本不支持任何BIOS。
    只需在初始化时将内核加载到VM中并开始运行即可。

Firecracker 实现：Rust。
  内存安全语言（模“不安全”代码）。
  50K 行代码：比 QEMU 小得多。

Firecracker VMM 在“被监禁”的进程中运行。
  chroot 以限制 VMM 可以访问的文件。
  命名空间以限制 VMM 访问其他进程和网络。
  作为单独的用户 ID 运行。
  seccomp-bpf 用于限制 VMM 可以调用的系统调用。
  所有这些都是为了确保，如果 VMM 中的错误被利用，攻击很难升级。

gVisor计划：在单独的用户空间进程中重新实现操作系统系统调用接口。
  论文中的图2。
  拦截来自容器中运行的进程的系统调用（使用 ptrace 或 KVM）。
  实现这些系统调用的用户空间进程，用 Go 编写。
    同样，在避免缓冲区溢出和其他错误方面，这是比 C 更好的语言。
  好处：Go 代码中不太可能出现内存管理错误。
  好处：错误不在内核代码中，可能包含在 Linux 进程中。
    使用 seccomp-bpf 限制 gVisor 模拟器可以调用的系统调用。
  好处：更细粒度的共享。
    可以共享特定的文件或目录。
  好处：更细粒度的资源配置。
    不仅仅是单一虚拟磁盘或整个虚拟机内存分配。
    也许对于独立运行小型应用程序很重要。
  缺点：性能开销可能很大。
    每个系统调用都必须重定向到 gVisor 进程。
    上下文切换开销、数据复制开销等。
  可能的缺点（或优点）：兼容性（真正的 Linux 与 gVisor）
    不过，gVisor 在忠实地实现 Linux 系统调用方面做得非常可靠！
    可以在旧主机上模拟新的系统调用

安全性比较：系统调用可访问。
  总共约 350 个系统调用
  LXC (Docker)：阻止 44 个系统调用（因此允许超过 300 个）
  Firecracker：VMM 允许 36 个系统调用
  gVisor：Sentry 允许 53-68 个系统调用

每个平台有哪些潜在的优点或缺点？
  Linux：简单，执行的代码最少，开销最小。
  LXC：隔离和容器抽象、灵活共享、接近原生的性能。
  gVisor：强隔离但仍然灵活的共享、资源分配。
  Firecracker：隔离性强，性能比 gVisor 好，但是
  coarse-grained.
