实验：系统调用

在上一个实验中，您使用系统调用编写了一些实用程序。在本实验中，您将为 xv6 添加一个新的系统调用，这将帮助您了解它们的工作原理，并向您展示 xv6 内核的一些内部结构。您将在后面的实验中添加更多系统调用。

在开始编码之前，请阅读本书的第 2 章 xv6 书，以及第 4 章的 4.3 和 4.4 节，以及相关源文件：

  • 将系统调用路由到内核的用户空间“存根”位于 user/usys.S，它是由生成的 user/usys.pl 当你跑步时 make。声明位于 user/user.h
  • 将系统调用路由到实现它的内核函数的内核空间代码位于 kernel/syscall.c 和 kernel/syscall.h.
  • 流程相关的代码是 kernel/proc.h 和 kernel/proc.c.

要开始实验，请切换到系统调用分支： 

  $ git fetch
  $ git checkout syscall
  $ make clean

沙箱命令

在此作业中，您将“沙箱”一个进程以限制它可以进行的系统调用。例如，可以对进程进行沙箱处理以禁止打开文件。您将创建一个新的 interpose 系统调用将指定内核应从调用进程中拒绝哪些系统调用。 interpose 应该有两个参数：一个整数掩码和一个路径。掩码的位指定要拒绝哪些系统调用。您将在下一个作业中使用的第二个参数，在此作业中它始终是 "-"。例如，为了让进程阻止自己使用 open 系统调用，它应该调用 interpose(1 << SYS_open, "-"), 其中 SYS_open 是来自的系统调用号 kernel/syscall.h。您的实现应该导致掩码被 fork 的子级继承，以便子级继承父级的限制。
我们为您提供了 user/sandbox.c 分叉、调用的用户程序 interpose() 在子级中，然后在子级中执行程序。当你完成实施后 interpose()，您应该看到如下输出： 
$ sandbox 32768 - cat README
cat: cannot open README
$

在这个例子中， cat README 是正在沙盒中的命令。 32768是拒绝系统调用的掩码；在这个例子中是 1<<SYS_open。如果您的解决方案正确，您应该看到“cat：无法打开自述文件”。

如果您通过了测试，您的解决方案将获得满分 grade-lab-syscall sandbox_mask: 

$ ./grade-lab-syscall sandbox_mask
== Test sandbox_mask == sandbox_mask: OK (1.5s)

一些提示：

  • 添加 $U/_sandbox 到 Makefile 中的 UPROGS

  • 运行 make qemu 你会看到编译器无法编译 user/sandbox.c，因为用户空间存根 interpose 系统调用尚不存在：添加原型 interpose 到 user/user.h，一个存根 user/usys.pl，以及一个系统调用号 kernel/syscall.h。 Makefile 调用 perl 脚本 user/usys.pl，这会产生 user/usys.S，实际的系统调用存根，使用 RISC-V ecall 指令转换到内核。解决编译问题后，运行 sandbox 32768 - cat README 在 xv6 外壳中；它会失败，因为你还没有在内核中实现系统调用。

  • 添加一个 sys_interpose() 函数于 kernel/sysproc.c 通过将掩码参数记录在新的字段中来实现新的系统调用 proc 结构（见 kernel/proc.h）。从用户空间检索系统调用参数的函数位于 kernel/syscall.c，您可以在中查看它们的使用示例 kernel/sysproc.c。添加您的新 sys_interpose 到 syscalls 数组中 kernel/syscall.c.

  • 修改 kfork() （见 kernel/proc.c) 将掩码从父进程复制到子进程。

  • 修改 syscall() 函数于 kernel/syscall.c 检查系统调用是否必须被拒绝。

攻击xv6

xv6内核将用户程序相互隔离，并将内核与用户程序隔离。正如您在上面的作业中看到的，应用程序不能直接调用内核或另一个用户程序中的函数；相反，交互仅通过系统调用发生。但是，如果内核的系统调用实现存在错误，则攻击者可能能够利用该错误来打破隔离边界。为了了解如何利用错误，我们在 xv6 中引入了一个错误，您的目标是利用该错误从另一个进程窃取秘密。

错误是调用 memset(mem, 0, sz) 在 uvmalloc() 在 kernel/vm.c 编译本实验时，省略了清除新分配的页面的操作。同样，编译时 kernel/kalloc.c 对于本实验，使用的两条线 memset 将垃圾放入空闲页面的操作被省略。省略这 3 行的净效果（全部由 ifndef LAB_SYSCALL）是新分配的内存保留了以前使用的内容。因此，一个应用程序调用 sbrk() 分配内存可能会收到包含先前使用的数据的页面。尽管删除了 3 行，xv6 大部分工作正常；它甚至通过了大部分 usertests.

user/secret.c 在其内存中写入一个秘密字符串，然后退出（这会释放其内存）。您的目标是添加几行代码 user/attack.c 找到先前执行的秘密 secret.c 写入内存，并单独将秘密打印在一行上。

你的 attack.c 必须与未修改的 xv6 和未修改的一起使用 secret.c。您可以更改任何内容以帮助您进行实验和调试，但必须在最终测试和提交之前恢复这些更改。

的 secret 程序将秘密作为参数。您可以测试您的 attack 通过运行程序 secret 有一些争论，然后运行 attack，并查看是否 attack 准确打印传递给的参数 secret。这是一次成功的运行： 
$ secret xyzzy
$ attack
xyzzy
$

根据您实施攻击的具体方式，您可能需要运行 attack 第二次是为了让它发现这个秘密。分级机运行 attack 两次，以防万一，如果其中一个产生了秘密，则满意。

从 xv6 外部，您可以使用 ./grade-lab-syscall attack, 或 make grade，看看您的攻击是否通过了我们的测试。测试生成的秘密字符串保证仅包含数字和大小写字母。

与此示例一样，不直接影响正确性的错误有时可能会被利用来破坏安全性。仔细的编程和广泛的测试可以减少错误的数量，但不能保证不存在错误。 xv6 过去曾出现过错误，并且可能还有更多未被发现的错误。真实内核的代码比 xv6 多得多，此类错误由来已久。例如，参见公众号 Linux 漏洞 和 如何报告漏洞.
