实验：网络驱动

在本实验中，你将为网络接口卡（NIC）编写一个 xv6 设备驱动，然后编写以太网/IP/UDP 协议处理栈的接收部分。

获取本实验的 xv6 源代码并切换到 net branch: 

  $ git fetch
  $ git checkout net
  $ make clean

背景

在编写代码之前，您可能会发现阅读教材中的"第6章：中断与设备驱动"会有所帮助。 xv6 书.

你将使用一种名为 E1000 的网络设备来处理网络通信。对于 xv6（以及你编写的驱动程序）而言，E1000 看起来就像一块连接到真实以太网局域网（LAN）的真实硬件。实际上，你的驱动程序所交互的 E1000 是由 qemu 提供的模拟设备，连接到一个同样由 qemu 模拟的局域网。在这个模拟局域网中，xv6（"guest"）的 IP 地址为 10.0.2.15。Qemu 将运行 qemu 的计算机（"host"）以 IP 地址 10.0.2.2 的形式呈现在局域网中。当 xv6 使用 E1000 向 10.0.2.2 发送数据包时，qemu 会将该数据包传递给 host 上相应的应用程序。

您将使用 QEMU 的"用户态网络栈"。QEMU 的文档中有更多关于用户态栈的内容 此处。我们已更新 Makefile，以启用 QEMU 的用户态网络栈和 E1000 网卡仿真。

Makefile 配置 QEMU 将所有传入和传出的数据包记录到文件 packets.pcap 在您的实验目录中。查看这些录制内容可能有助于确认 xv6 正在发送和接收您预期的数据包。要显示录制的数据包： 

tcpdump -XXnr packets.pcap

我们已为本次实验向 xv6 代码仓库添加了一些文件。该文件 kernel/e1000.c 包含 E1000 的初始化代码，以及用于发送和接收数据包的空函数，你将对其进行补全。 kernel/e1000_dev.h 包含 E1000 定义的寄存器及标志位，这些内容均在 Intel E1000 软件开发人员手册. kernel/net.c 和 kernel/net.h 包含一个简单的网络栈，实现了 IP, UDP以及 ARP 协议； net.c 包含用户进程发送 UDP 数据包的完整代码，但缺少大部分接收数据包并将其传递到用户态的代码。最后， kernel/pci.c 包含 xv6 启动时在 PCI 总线上搜索 E1000 网卡的代码。

第一部分：网卡（NIC）

你的任务是补全 e1000_transmit() 和 e1000_recv()，两者均位于 kernel/e1000.c，使驱动程序能够发送和接收数据包。完成以下内容即视为完成本部分： make grade 表明你的解决方案通过了 "txone" 和 "rxone" 测试。

在编写代码时，你将参考 E1000 软件开发人员手册，特别是：

  • 第3.2节介绍了数据包接收（但跳过3.2.8和3.2.9小节）。
  • 第 3.3.1、3.3.2、3.3.3 和 3.4 节介绍了数据传输。
  • 第13节描述了E1000的寄存器（可按需参考；无需通读全文）。

该 软件开发人员手册 描述了几种密切相关的以太网控制器。QEMU 模拟的是 82540EM。你需要熟悉上述第 3 章中标注的各节内容。其他章节主要涵盖 E1000 中你的网络驱动无需交互的部分。一开始不必纠结于细节，只需大致了解文档的结构，以便日后查找所需内容。E1000 具有许多高级特性，其中大部分可以忽略。完成本实验只需用到一小部分基本功能。

该 e1000_init() 我们在其中为你提供的函数 e1000.c 将 E1000 配置为从 RAM 中读取待发送的数据包，并将接收到的数据包写入 RAM。这种技术称为 DMA（直接内存访问），指的是 E1000 硬件直接向 RAM 写入或从 RAM 读取数据包。

因为数据包可能以突发方式到达，其速度超过驱动程序的处理速度， e1000_init() 为 E1000 提供多个缓冲区，E1000 可将接收到的数据包写入其中。E1000 要求这些缓冲区由内存中的一个"描述符"数组来描述；每个描述符包含一个内存地址，E1000 可将接收到的数据包写入该地址。 struct rx_desc 描述了描述符格式。描述符数组被称为接收环，或接收队列。它是一个循环环，即当网卡或驱动到达数组末尾时，会回绕到数组开头。 e1000_init() 使用以下方式分配数据包缓冲区 kalloc() 供 E1000 进行 DMA 写入。此外还有一个发送环，驱动程序应将希望 E1000 发送的数据包放入其中。 e1000_init() 将两个环的大小配置为 RX_RING_SIZE 和 TX_RING_SIZE.

当 net.c 中的网络协议栈需要发送数据包时，它会调用 e1000_transmit() 并传入一个指向待发送数据包缓冲区的指针； net.c 使用以下方式分配该缓冲区 kalloc()。你的发送代码必须将指向数据包数据的指针放入 TX（发送）环中的一个描述符内。 struct tx_desc 描述了描述符的格式。你需要确保每个缓冲区最终被传递给 kfree()，但必须在 E1000 完成数据包发送之后（E1000 会在描述符中设置 E1000_TXD_STAT_DD 位来表示这一状态）。

当 E1000 从以太网接收到每个数据包时，它会通过 DMA 将数据包写入以下指针所指向的内存中 addr 在下一个 RX（接收）环描述符中。如果 E1000 中断尚未挂起，E1000 会在中断启用后立即请求 PLIC 传递一个中断。您的 e1000_recv() 代码必须扫描 RX 环，并通过调用 net.c将每个新数据包传递给网络协议栈（在 net_rx()）。然后您需要分配一个新的缓冲区并将其放入描述符中，以便当 E1000 再次到达 RX 环中的该位置时，能找到一个新的缓冲区用于 DMA 接收新数据包。

除了读写 RAM 中的描述符环之外，您的驱动还需要通过 E1000 的内存映射控制寄存器与其交互，以检测何时有接收到的数据包可用，并通知 E1000 驱动已在某些 TX 描述符中填入了待发送的数据包。全局变量 regs 保存指向 E1000 第一个控制寄存器的指针；您的驱动可以通过将 regs 作为数组索引来访问其他寄存器。您将特别需要使用索引 E1000_RDT 和 E1000_TDT 。

e1000 提示

对于 e1000_transmit:

  • 从添加打印语句开始， e1000_transmit() 和 e1000_recv()，以及（在 xv6 中）运行 nettest txone。你应该能从你的打印语句中看到 nettest txone 生成对 e1000_transmit.
  • `net.h` 中的描述符定义 e1000_dev.h 使用"legacy"发送描述符格式（第 3.3.3 节）。
  • 首先通过读取 E1000_TDT 控制寄存器。
  • 然后检查环形缓冲区是否已溢出。如果 E1000_TXD_STAT_DD 未在由 E1000_TDT索引的描述符中设置，说明 E1000 尚未完成对应的上一次发送请求，因此返回错误。
  • 否则，使用 kfree() 释放从该描述符最后一次发送的缓冲区（如果存在的话）。
  • 然后填写描述符。设置必要的 cmd 标志位（参见 E1000 手册第 3.3 节）。
  • 最后，将 E1000_TDT 对其取模后加一，更新环形缓冲区的当前位置。 TX_RING_SIZE.

对于 e1000_recv:

  • 首先通过读取 E1000_RDT 控制寄存器并对其结果加一后取模，向 E1000 查询下一个待接收数据包（如有）在环形缓冲区中的索引位置。 RX_RING_SIZE.
  • 然后通过检查 E1000_RXD_STAT_DD 位于 status 描述符的相应部分。如果没有，则停止。
  • 通过调用以下函数将数据包缓冲区传递给网络栈 net_rx().
  • 然后使用以下函数分配一个新缓冲区 kalloc() 以替换刚刚交给 net_rx()的那个。将描述符的状态位清零。
  • 最后，更新 E1000_RDT 寄存器为最后处理的环形描述符的索引。
  • e1000_init() 用缓冲区初始化 RX 环，建议参考其实现方式，并可适当借用相关代码。
  • 在某些情况下，曾经到达的数据包总数可能会超过环的大小（16）；请确保你的代码能够处理这种情况。
  • e1000 每次中断可能会传递多个数据包；你的 e1000_recv 应能处理这种情况。

你需要使用锁来应对以下情况：xv6 可能从多个进程同时使用 E1000，或者在中断到达时内核线程正在使用 E1000。

第二部分：UDP 接收

UDP（用户数据报协议）允许不同互联网主机上的用户进程交换单独的数据包（数据报）。UDP 构建于 IP 之上。用户进程通过指定一个 32 位 IP 地址来指明要将数据包发送到哪台主机。每个 UDP 数据包包含源端口号和目标端口号；进程可以请求接收发往特定端口号的数据包，也可以在发送时指定目标端口号。因此，不同主机上的两个进程只要知道彼此的 IP 地址和各自监听的端口号，就可以通过 UDP 进行通信。例如，Google 在 IP 地址为 8.8.8.8 的主机上运行 DNS 名称服务器，监听 UDP 端口 53。

在本任务中，你需要在 kernel/net.c 中添加代码，以接收 UDP 数据包、将其加入队列，并允许用户进程读取它们。 net.c 已包含用户进程发送 UDP 数据包所需的代码（e1000_transmit() 除外，该函数由你实现）。

你的任务是补全 ip_rx(), sys_recv()以及 sys_bind() 在 kernel/net.c的实现。当 make grade 显示你的解答通过所有测试时，即表示完成。

本实验的 UDP 系统调用 API 规范如下：

  • send(short sport, int dst, short dport, char *buf, int len)：此系统调用向 IP 地址为 dst，以及（在该主机上）监听端口 dport。数据包的源端口号将是 sport （该端口号会被报告给接收进程，以便其能够回复发送方）。UDP 数据包的内容（"载荷"）将是 len 地址处的字节 buf。返回值在成功时为 0，失败时为 -1。
  • recv(short dport, int *src, short *sport, char *buf, int maxlen)：此系统调用返回目标端口为 dport。如果在调用 recv()，它应该立即返回最早等待的数据包。如果没有数据包在等待， recv() 应等待直到收到发往 dport 的数据包。 recv() 应按到达顺序查看到达指定端口的数据包。 recv() 将数据包的 32 位源 IP 地址复制到 *src，将数据包的 16 位 UDP 源端口号复制到 *sport，最多复制 maxlen 字节的数据包 UDP 载荷到 buf，并将该数据包从队列中移除。系统调用返回已复制的 UDP 载荷字节数，出错时返回 -1。
  • bind(short port)：进程应在调用 bind(port) 之前先调用 recv(port, ...)。若到达的 UDP 数据包的目标端口未曾传递给 bind(), net.c 则应丢弃该数据包。此系统调用的目的是初始化所需的数据结构 net.c 为存储后续到达的数据包所需的 recv() 调用。
  • unbind(short port)：您无需实现此系统调用，因为测试代码不使用它。但如果您希望与 bind().

传递给这些系统调用的参数以及由其返回的所有地址和端口号，必须采用主机字节序（见下文）。

您需要提供系统调用的内核实现，但 send()除外。程序 user/nettest.c 使用此 API。

为使 recv() 正常工作，您需要向 ip_rx()添加代码，该函数 net_rx() 对每个接收到的 IP 数据包进行调用。 ip_rx() 应判断到达的数据包是否为 UDP，以及其目标端口是否已传递给 bind()；如果两者均为真，则应将数据包保存至 recv() 可以找到它。但是，对于任何给定的端口，保存的数据包不应超过 16 个；如果已有 16 个数据包在等待 recv()，该端口收到的数据包应当被丢弃。此规则的目的是防止发送速度过快或恶意的发送方迫使 xv6 耗尽内存。此外，如果某个端口因已有 16 个数据包待处理而丢弃数据包，不应影响其他端口收到的数据包。

数据包缓冲区 ip_rx() 包含一个 14 字节的以太网头部，后跟一个 20 字节的 IP 头部，再跟一个 8 字节的 UDP 头部，最后是 UDP 有效载荷。你可以在以下位置找到这些结构的 C 语言结构体定义： kernel/net.h。Wikipedia 上有对 IP 头部的描述 此处，以及 UDP 此处.

生产级的 IP/UDP 实现较为复杂，需要处理协议选项并验证各项不变量。你只需要做到足以通过 make grade。你的代码需要查看 IP 头中的 `ip_p` 和 `ip_src`，以及 UDP 头中的 `dport`、`sport` 和 `ulen`。

你需要注意字节序问题。以太网、IP 和 UDP 头部中包含多字节整数的字段在数据包中将最高有效字节放在最前面。而 RISC-V CPU 在内存中存储多字节整数时，将最低有效字节放在最前面。这意味着，当代码从数据包中提取多字节整数时，必须重新排列字节顺序。这适用于 short（2 字节）和 int（4 字节）字段。你可以使用 ntohs() 和 ntohl() 分别用于 2 字节和 4 字节字段的函数。请查看 net_rx() 可参考解析 2 字节以太网类型字段时的相关示例。

如果您的 E1000 代码存在错误或遗漏，这些问题可能只在 ping 测试期间才会显现。例如，ping 测试发送和接收的数据包数量足以使描述符环索引发生回绕。
