背景

在编写代码之前，您可能会发现查看“第 6 章：中断和设备驱动程序”很有帮助。 xv6 书.

您将使用名为 E1000 的网络设备来处理网络通信。对于 xv6（以及您编写的驱动程序）来说，E1000 看起来就像一个连接到真实以太网局域网 (LAN) 的真实硬件。事实上，您的驱动程序将与之通信的 E1000 是 qemu 提供的仿真，连接到也由 qemu 仿真的 LAN。在此模拟 LAN 上，xv6（“来宾”）的 IP 地址为 10.0.2.15。 Qemu 安排运行 qemu 的计算机（“主机”）出现在 IP 地址为 10.0.2.2 的 LAN 上。当 xv6 使用 E1000 将数据包发送到 10.0.2.2 时，qemu 将数据包传送到主机上的相应应用程序。

您将使用 QEMU 的“用户模式网络堆栈”。 QEMU 的文档有更多关于用户模式堆栈的信息 这里。我们更新了 Makefile 以启用 QEMU 的用户模式网络堆栈和 E1000 网卡模拟。

Makefile 配置 QEMU 将所有传入和传出数据包记录到文件中 packets.pcap 在您的实验室目录中。查看这些记录可能会有助于确认 xv6 正在传输和接收您期望的数据包。显示记录的数据包：

我们已为本实验的 xv6 存储库添加了一些文件。该文件 kernel/e1000.c 包含 E1000 的初始化代码以及用于发送和接收数据包的空函数（您将填写这些代码）。 kernel/e1000_dev.h 包含由 E1000 定义并在 Intel E1000 中描述的寄存器和标志位的定义 软件开发人员手册. kernel/net.c 和 kernel/net.h 包含一个简单的网络堆栈，它实现了 知识产权, UDP协议, 和 ARP 协议； net.c 具有用户进程发送UDP数据包的完整代码，但缺少接收数据包并将其传递到用户空间的大部分代码。最后， kernel/pci.c 包含当 xv6 引导时在 PCI 总线上搜索 E1000 卡的代码。

的 e1000_init() 我们为您提供的功能 e1000.c 配置E1000从RAM中读取待发送的报文，并将接收到的报文写入RAM中。这种技术称为 DMA，即直接内存访问，指的是 E1000 硬件直接向 RAM 写入数据包或从 RAM 读取数据包的事实。

因为数据包突发的到达速度可能比驱动程序处理它们的速度快， e1000_init() 为E1000提供多个缓冲区，E1000可以将接收到的报文写入其中。 E1000 要求这些缓冲区由 RAM 中的“描述符”数组来描述；每个描述符都包含 RAM 中的一个地址，E1000 可以将接收到的数据包写入其中。 struct rx_desc 描述描述符格式。描述符数组称为接收环或接收队列。从某种意义上说，它是一个圆环，当卡或驱动程序到达阵列的末尾时，它会回绕到开头。 e1000_init() 分配数据包缓冲区 kalloc() 为E1000转DMA进去。还有一个传输环，驱动程序应将其希望 E1000 发送的数据包放入其中。 e1000_init() 配置两个环的大小 RX_RING_SIZE 和 TX_RING_SIZE.

当网络堆栈进入 net.c 需要发送一个数据包，它调用 e1000_transmit() 带有指向保存要发送的数据包的缓冲区的指针； net.c 分配这个缓冲区 kalloc()。您的发送代码必须在 TX（发送）环的描述符中放置一个指向数据包数据的指针。 struct tx_desc 描述描述符格式。您需要确保每个缓冲区最终都传递到 kfree()，但只有在 E1000 发送完数据包后（E1000 设置 E1000_TXD_STAT_DD 描述符中的位来指示这一点）。

当E1000从以太网接收到每个数据包时，它会将数据包DMA到由 addr 在下一个 RX（接收）环描述符中。如果 E1000 中断尚未挂起，则一旦启用中断，E1000 就会要求 PLIC 立即传送中断。你的 e1000_recv() 代码必须扫描 RX 环并将每个新数据包传送到网络堆栈（在 net.c）通过调用 net_rx()。然后，您需要分配一个新的缓冲区并将其放入描述符中，以便当 E1000 再次到达 RX 环中的该点时，它会找到一个新的缓冲区来将新数据包 DMA 到其中。

除了在 RAM 中读取和写入描述符环之外，您的驱动程序还需要通过其内存映射控制寄存器与 E1000 进行交互，以检测接收到的数据包何时可用，并通知 E1000 驱动程序已使用要发送的数据包填充了一些 TX 描述符。全局变量 regs 保存指向 E1000 第一个控制寄存器的指针；您的驱动程序可以通过索引获取其他寄存器 regs 作为一个数组。您需要使用索引 E1000_RDT 和 E1000_TDT 特别是。

e1000 提示

对于 e1000_transmit:

  • 首先添加打印语句 e1000_transmit() 和 e1000_recv()，并运行（在 xv6 中） nettest txone。您应该从打印语句中看到 nettest txone 生成一个调用 e1000_transmit.
  • 描述符定义在 e1000_dev.h 使用“传统”传输描述符格式（第 3.3.3 节）。
  • 首先通过读取 E1000 的 E1000_TDT 控制寄存器。
  • 然后检查环是否溢出。如果 E1000_TXD_STAT_DD 未在索引的描述符中设置 E1000_TDT时，E1000 还没有完成相应的上一次传输请求，因此返回错误。
  • 否则，使用 kfree() 释放从该描述符传输的最后一个缓冲区（如果有）。
  • 然后填写描述符。设置必要的 cmd 标志（请参阅 E1000 手册中的第 3.3 节）。
  • 最后，通过添加 1 来更新环位置 E1000_TDT 模数 TX_RING_SIZE.

对于 e1000_recv:

  • 首先向 E1000 询问下一个等待接收的数据包（如果有）所在的环索引，方法是获取 E1000_RDT 控制寄存器并加一模 RX_RING_SIZE.
  • 然后通过检查是否有新的数据包可用 E1000_RXD_STAT_DD 位在 status 描述符的一部分。如果没有，就停下来。
  • 通过调用将数据包缓冲区传递到网络堆栈 net_rx().
  • 然后使用分配一个新的缓冲区 kalloc() 替换刚刚给的那个 net_rx()。将描述符的状态位清零。
  • 最后，更新一下 E1000_RDT 注册为最后处理的环描述符的索引。
  • e1000_init() 使用缓冲区初始化 RX 环，您需要了解它是如何做到这一点的，也许还需要借用代码。
  • 在某个时刻，到达的数据包总数将超过环大小 (16)； make sure your code can handle that.
  • e1000 每次中断可以传送多个数据包；你的 e1000_recv 应该处理这种情况。

您需要锁来应对 xv6 可能从多个进程使用 E1000，或者当中断到达时可能在内核线程中使用 E1000 的可能性。

第二部分：UDP 接收

UDP（用户数据报协议）允许不同 Internet 主机上的用户进程交换单独的数据包（数据报）。 UDP 位于 IP 之上。用户进程通过指定 32 位 IP 地址来指示它要将数据包发送到哪个主机。每个UDP数据包包含一个源端口号和一个目的端口号；进程可以请求接收到达特定端口号的数据包，并且可以在发送时指定目标端口号。因此，如果不同主机上的两个进程知道彼此的 IP 地址和各自侦听的端口号，则它们可以使用 UDP 进行通信。例如，Google 在 IP 地址为 8.8.8.8 的主机上运行 DNS 名称服务器，监听 UDP 端口 53。

在此任务中，您将添加代码 kernel/net.c 接收 UDP 数据包，将它们排队，并允许用户进程读取它们。 net.c 已包含用户进程传输 UDP 数据包所需的代码（您提供的 e1000_transmit() 除外）。

您的工作是填写以下内容的实施 ip_rx(), sys_recv(), 和 sys_bind() 在 kernel/net.c。当你完成时 make grade 说你的解决方案通过了所有测试。

本实验室的 UDP 系统调用 API 规范如下所示：

  • send(short sport, int dst, short dport, char *buf, int len)：该系统调用向具有IP地址的主机发送UDP数据包 dst，以及（在该主机上）侦听端口的进程 dport。数据包的源端口号将是 sport （这个端口号被报告给接收进程，以便它可以回复发送者）。 UDP 数据包的内容（“有效负载”）将 len 地址处的字节数 buf。成功时返回值为 0，失败时返回值为 -1。
  • recv(short dport, int *src, short *sport, char *buf, int maxlen)：此系统调用返回通过目标端口到达的 UDP 数据包的有效负载 dport。如果一个或多个数据包在调用之前到达 recv()，它应该立即返回最早等待的数据包。如果没有数据包在等待， recv() 应该等到一个数据包 dport arrives. recv() 应该按到达顺序查看给定端口的到达数据包。 recv() 将数据包的 32 位源 IP 地址复制到 *src，将数据包的 16 位 UDP 源端口号复制到 *sport, 最多复制 maxlen 数据包的 UDP 负载字节 buf，并将数据包从队列中删除。系统调用返回复制的 UDP 有效负载的字节数，如果出现错误，则返回 -1。
  • bind(short port): 一个进程应该调用 bind(port) 在它调用之前 recv(port, ...)。如果 UDP 数据包到达时的目标端口尚未传递到 bind(), net.c 应该丢弃该数据包。该系统调用的原因是初始化任何结构 net.c 需要存储到达的数据包以供后续使用 recv() call.
  • unbind(short port)：您不需要实现此系统调用，因为测试代码不使用它。但如果你愿意的话，你可以为了提供对称性 bind().

作为参数传递给这些系统调用并由它们返回的所有地址和端口号都必须采用主机字节顺序（见下文）。

您需要提供系统调用的内核实现，但以下情况除外 send()。该计划 user/nettest.c 使用这个API。

使 recv() 工作，您需要添加代码 ip_rx()，其中 net_rx() 调用每个收到的 IP 数据包。 ip_rx() 应判断到达的数据包是否为 UDP，以及其目标端口是否已传递到 bind();如果两者都为真，则应将数据包保存在何处 recv() 可以找到它。然而，对于任何给定端口，不应保存超过 16 个数据包；如果 16 人已经在等待 recv()，应该丢弃该端口的传入数据包。该规则的目的是防止快速或滥用的发送者迫使 xv6 耗尽内存。此外，如果一个端口的数据包因已有 16 个数据包等待而被丢弃，则不会影响到达其他端口的数据包。

数据包缓冲 ip_rx() 看起来包含一个 14 字节的以太网标头，后面跟着一个 20 字节的 IP 标头，后面跟着一个 8 字节的 UDP 标头，最后是 UDP 负载。您将在以下位置找到其中每个结构体的 C 结构定义： kernel/net.h。维基百科有关于IP头的描述 这里，和UDP 这里.

生产 IP/UDP 实现非常复杂，需要处理协议选项并验证不变量。你只需要做足够的事情就能通过 make grade。您的代码需要查看 IP 标头中的 ip_p 和 ip_src，以及 UDP 标头中的 dport、sport 和 ulen。

您必须注意字节顺序。包含多字节整数的以太网、IP 和 UDP 标头字段将最高有效字节放在数据包的前面。 RISC-V CPU 在内存中布置多字节整数时，会将最低有效字节放在前面。这意味着，当代码从数据包中提取多字节整数时，它必须重新排列字节。这适用于短（2 字节）和整型（4 字节）字段。您可以使用 ntohs() 和 ntohl() 分别用于 2 字节和 4 字节字段的函数。看看 net_rx() 查看 2 字节以太网类型字段时的示例。

如果您的 E1000 代码中存在错误或遗漏，它们可能只会在 ping 测试期间开始导致问题。例如，ping 测试发送和接收足够的数据包，描述符环索引将环绕这些数据包。

一些提示：

  • 创建一个结构体来跟踪绑定端口及其队列中的数据包。
  • 请参阅 sleep(void *chan, struct spinlock *lk) 和 wakeup(void *chan) 功能于 kernel/proc.c 实现等待逻辑 recv().
  • 目的地地址 sys_recv() 将数据包复制到虚拟地址；您必须从内核复制到当前用户进程。
  • 确保释放已复制或已丢弃的数据包。

  • 在本实验中，网络堆栈使用中断来处理入口数据包处理，但不处理出口数据包处理。一种更复杂的策略是在软件中对出口数据包进行排队，并且在任何时候仅向 NIC 提供有限数量的数据包。然后，您可以依靠 TX 中断来重新填充传输环。使用这种技术，可以对不同类型的出口流量进行优先级排序。
  • 提供的网络代码仅部分支持 ARP。实施全面 ARP缓存.
  • E1000支持多个RX和TX环。配置 E1000 为每个核心提供一个环对，并修改网络堆栈以支持多个环。这样做有可能增加网络堆栈可支持的吞吐量并减少锁争用。 ，但难以测试/测量
  • ICMP 可以提供失败的网络流的通知。检测这些通知并将它们作为错误传播到用户进程。
  • E1000支持多种无状态硬件卸载，包括校验和计算、RSC和GRO。使用其中一项或多项卸载来提高网络堆栈的吞吐量。 ，但很难测试/测量
  • 本实验室中的网络堆栈很容易受到活锁的影响。使用讲座中的材料和阅读作业，设计并实施解决方案来解决这个问题。 ，但很难测试。
  • 实现一个最小的 TCP 堆栈并下载网页。

其中一些挑战旨在以在 QEMU 下可能不明显或无法衡量的方式提高性能。
