实验：锁

在本实验中，您将获得重新设计代码以提高并行性的经验。多核机器上并行性差的一个常见症状是高锁争用。提高并行性通常涉及更改数据结构和锁定策略以减少争用。您将为 xv6 内存分配器和块缓存执行此操作。

内存分配器

程序 user/kalloctest 强调 xv6 的内存分配器：三个进程增大和缩小其地址空间，导致多次调用 kalloc 和 kfree. kalloc 和 kfree 获得 kmem.lock。 kalloctest 打印（如“#test-and-set”）循环迭代次数 acquire 由于尝试获取另一个核心已经持有的锁，对于 kmem 锁和其他一些锁。循环迭代次数 acquire 是锁争用的粗略度量。的输出 kalloctest 在开始实验之前看起来与此类似：

acquire 对于每个锁，维护调用的计数 acquire 对于该锁，以及循环次数 acquire 尝试设置锁但失败。 kalloctest 调用一个系统调用，使内核打印 kmem 锁（这是本实验的重点）和 5 个竞争最激烈的锁的计数。如果存在锁争用的数量 acquire 循环迭代将会很大。系统调用返回 kmem 锁的循环迭代次数总和。

对于本实验，您必须使用具有多个内核的专用卸载计算机。如果您使用正在执行其他操作的机器，则 kalloctest 打印的计数将是无意义的。您可以使用专用的 Athena 工作站或您自己的笔记本电脑，但不要使用拨号计算机。

kalloctest 中锁争用的根本原因是 kalloc() 有一个空闲列表，由一个锁保护。要消除锁争用，您必须重新设计内存分配器以避免单个锁和列表。基本思想是为每个 CPU 维护一个空闲列表，每个列表都有自己的锁。不同CPU上的分配和释放可以并行运行，因为每个CPU将在不同的列表上操作。主要挑战是处理一个CPU的空闲列表为空，但另一个CPU的列表有空闲内存的情况；在这种情况下，一个 CPU 必须“窃取”另一个 CPU 的空闲列表的一部分。窃取可能会导致锁争用，但希望这种情况不会频繁发生。

您的工作是实现每个 CPU 的空闲列表，并在 CPU 的空闲列表为空时进行窃取。您必须给出所有以“kmem”开头的锁名称。也就是说，你应该打电话 initlock 对于每个锁，并传递一个以“kmem”开头的名称。运行 kalloctest 来查看您的实现是否减少了锁争用。要检查它是否仍然可以分配所有内存，请运行 usertests sbrkmuch。您的输出将类似于下图所示，尽管具体数字会有所不同，但 kmem 锁的争用总数大大减少。确保所有测试都在 usertests -q pass. make grade 应该说 kalloctests 通过了。

读写锁

这一半的作业与前半部分是独立的；无论您是否完成了前半部分，您都可以完成这半部分（并通过测试）。

考虑xv6的 sys_pause 和 sys_uptime 函数，读取全局 ticks 变量。由于该变量可能会同时更新 clockintr，这两个函数获取 tickslock 读取之前的自旋锁 ticks。重要的是，这可以防止 clockintr 来自同时修改 ticks，但这也阻止了多核读取 ticks 同时，这样就好了。在后一种情况下，自旋锁不必要地降低了性能。

解决这个问题的常见方法是使用读写锁。读写锁引入了两种锁持有者的概念：读者和作者。一次最多可以有一个写入者（当有写入者时，就不能有读者），但可以同时有多个读者（只要没有写入者）。典型的读写锁API如下（参见 kernel/defs.h): 

void            initrwlock(struct rwspinlock*);
void            read_acquire(struct rwspinlock*);
void            read_release(struct rwspinlock*);
void            write_acquire(struct rwspinlock*);
void            write_release(struct rwspinlock*);

读写锁可能出现的一个微妙问题是，如果有很多读取者，那么写入者可能永远没有机会运行。换句话说，即使读者不断获取和释放锁，也永远不会有真正零读者的时刻，因此写入者可能永远无法获取锁。为了解决这个问题，读写锁通常会实现写入者优先方案：一旦写入者尝试获取锁，后续读取者必须等待，直到写入者成功获取并释放锁（当然，要等待当前读取者释放锁才允许写入者获取）。

遵循上述 API 和语义，在 xv6 中实现读写自旋锁。确保读者不会让写者挨饿：如果有任何待处理的写者，则没有更多的读者可以获得锁。

您需要填写读写自旋锁 API 的存根函数 kernel/spinlock.c，并可能改变 a 的定义 struct rwspinlock 在 kernel/spinlock.h.

一些提示：

  • 看看 sys_rwlktest 在 kernel/spinlock.c 第一；您应该能够分阶段测试您的实施。
  • 如果你跑 rwlktest 在 xv6 中而不修改任何内容 kernel/spinlock.c，内核将打印 panic: acquire 因为最初的自旋锁实现只允许锁一次被一个线程持有。您需要将调用替换为 acquire() 和 release() 在 write/read_acquire_inner 和 write/read_release_inner 用你自己的锁实现。
  • Be careful about possible interleavings.例如，如果读者看到没有挂起的写入者并想要获取锁进行读取，那么您如何知道获取锁仍然安全？
  • 阅读有关原子操作的内置 gcc 函数可能会有所帮助；看到 https://gcc.gnu.org/onlinedocs/gcc/_005f_005fatomic-Builtins.html.
