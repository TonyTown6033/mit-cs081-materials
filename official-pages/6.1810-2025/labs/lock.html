实验：锁

在本实验中，你将通过重新设计代码来积累提高并行性的经验。在多核机器上，并行性差的常见表现是锁竞争激烈。提高并行性通常需要同时改变数据结构和加锁策略，以减少竞争。你将对 xv6 的内存分配器和块缓存进行此类优化。

在编写代码之前，请确保阅读以下内容，来自 xv6 书 :

  • 第 7 章：「锁」及其对应代码。
  • 第 3.5 节：「代码：物理内存分配器」

内存分配器

程序 user/kalloctest 对 xv6 的内存分配器施加压力：三个进程反复扩大和收缩其地址空间，从而产生大量对 kalloc 和 kfree. kalloc 和 kfree 的获取 kmem.lock调用。kalloctest 打印（标记为 "#test-and-set"）在 acquire 中，由于尝试获取已被其他核持有的锁而导致的循环迭代次数，针对 kmem 锁及其他若干锁。在 acquire 中的循环迭代次数是衡量锁竞争程度的粗略指标。在开始本实验之前， kalloctest 的输出类似如下：

acquire 对每个锁维护调用 acquire 对于该锁，以及 acquire 尝试但未能成功获取锁。kalloctest 调用一个系统调用，使内核打印出 kmem 锁（本实验的重点）以及争用最激烈的 5 个锁的相关计数。如果存在锁争用，则 acquire 循环迭代次数将会很大。系统调用返回所有 kmem 锁的循环迭代次数之和。

在本实验中，你必须使用一台专用的、空闲的多核机器。如果你使用一台正在运行其他任务的机器，kalloctest 打印的计数将毫无意义。你可以使用专用的 Athena 工作站，或者你自己的笔记本电脑，但不要使用拨号机器。

`kalloctest` 中锁竞争的根本原因是 kalloc() 有一个单一的空闲链表，由一个单独的锁保护。为了消除锁争用，你需要重新设计内存分配器，以避免使用单一的锁和链表。基本思路是为每个 CPU 维护一个空闲链表，每个链表有其自己的锁。不同 CPU 上的分配和释放操作可以并行运行，因为每个 CPU 将操作不同的链表。主要挑战在于处理某个 CPU 的空闲链表为空、但另一个 CPU 的链表中仍有空闲内存的情况；在这种情况下，该 CPU 必须从另一个 CPU 的空闲链表中"窃取"一部分内存。窃取操作可能会引入锁争用，但这种情况应该不会频繁发生。

你的任务是实现每个 CPU 的空闲链表，并在某个 CPU 的空闲链表为空时从其他 CPU 窃取。你必须为所有锁命名，且名称须以 "kmem" 开头。也就是说，你应该调用 initlock 对于你的每个锁，传入一个以 "kmem" 开头的名称。运行 kalloctest 检查你的实现是否减少了锁争用。要验证仍然能够分配所有内存，请运行 usertests sbrkmuch。你的输出结果将与下方所示类似，kmem 锁上的总体争用将大幅减少，尽管具体数字会有所不同。请确保 usertests -q 通过。 make grade 应显示 kalloctests 通过。

读写锁

本作业的后半部分与前半部分相互独立；无论你是否完成了前半部分，都可以单独完成后半部分（并通过相应测试）。

考虑 xv6 的 sys_pause 和 sys_uptime 函数，它们读取全局 ticks 变量。由于该变量可能被 clockintr并发更新，这两个函数在读取前会先获取 tickslock 自旋锁，然后再读取 ticks。重要的是，这可以防止 clockintr 同时修改 ticks，但这也阻止了多个核心同时读取 ticks ，而同时读取本是完全可行的。在后一种情况下，自旋锁会不必要地降低性能。

解决此问题的常见方案是使用读写锁。读写锁引入了两种锁持有者的概念：读者和写者。同一时刻最多只能有一个写者（且有写者时不能有读者），但可以同时存在多个读者（前提是没有写者）。典型的读写锁 API 如下（参见 kernel/defs.h): 

void            initrwlock(struct rwspinlock*);
void            read_acquire(struct rwspinlock*);
void            read_release(struct rwspinlock*);
void            write_acquire(struct rwspinlock*);
void            write_release(struct rwspinlock*);

读写锁可能出现的一个微妙问题是：如果读者持续不断，写者可能永远得不到运行机会。换句话说，即使读者不断地获取和释放锁，实际读者数量从未降为零，导致写者可能永远无法获取锁。为解决此问题，读写锁通常实现写者优先策略：一旦有写者尝试获取锁，后续读者必须等待，直到该写者成功获取并释放锁（当然，需等待当前读者释放锁后，写者才能获取）。

在 xv6 中按照上述 API 和语义实现一个读写自旋锁。确保读者不会使写者饥饿：若存在任何待等待的写者，则不允许新的读者获取锁。

你需要在以下文件中填写读写自旋锁 API 的桩函数 kernel/spinlock.c，并可能需要修改 struct rwspinlock 在 kernel/spinlock.h.

一些提示：

  • 先看看 sys_rwlktest 在 kernel/spinlock.c ；你应该能够分阶段测试你的实现。
  • 如果您运行 rwlktest 在不修改 xv6 内部任何内容的情况下 kernel/spinlock.c，内核将打印 panic: acquire ，因为原始的 spinlock 实现每次只允许一个线程持有锁。你需要将对 acquire() 和 release() 在 write/read_acquire_inner 和 write/read_release_inner 的调用替换为你自己的锁实现。
  • 请注意可能存在的交错执行情况。例如，若一个读者发现没有待处理的写者并希望获取读锁，你如何确保此时获取锁仍然是安全的？
  • 阅读有关 gcc 内置原子操作函数的资料可能会有所帮助；参见 https://gcc.gnu.org/onlinedocs/gcc/_005f_005fatomic-Builtins.html.
