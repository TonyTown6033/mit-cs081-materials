实验：陷阱

本实验探讨如何使用陷阱实现系统调用。你将首先完成一个关于栈的热身练习，然后实现一个用户态陷阱处理的示例。

开始编写代码之前，请阅读 xv6 书以及相关源文件：

  • kernel/trampoline.S：从用户态切换到内核态再返回所涉及的汇编代码
  • kernel/trap.c：处理所有中断的代码

要开始本实验，请切换到 trap 分支：

  $ make clean

回溯

为了调试，回溯（backtrace）往往非常有用：它是一个函数调用列表，记录了从错误发生点往上的整个调用栈。为了支持回溯，编译器会生成机器码，在栈上为当前调用链中的每个函数维护一个栈帧。每个栈帧由返回地址和指向调用者栈帧的"帧指针"组成。寄存器 s0 包含一个指向当前栈帧的指针（它实际上指向栈上已保存的返回地址加 8 的地址）。你的 backtrace 应使用帧指针遍历栈，并打印每个栈帧中保存的返回地址。

实现一个 backtrace() 函数，位于 kernel/printf.c。在 sys_pause中插入对该函数的调用，然后运行 bttest，它调用了 sys_pause。你的输出应该是一个返回地址列表，格式如下（但具体数字可能不同）： 

    backtrace:
    0x0000000080002cda
    0x0000000080002bb6
    0x0000000080002898
在 bttest 退出 qemu。在终端窗口中：运行 addr2line -e kernel/kernel （或 riscv64-unknown-elf-addr2line -e kernel/kernel），并将你的回溯中的地址粘贴进去，如下所示： 
    $ addr2line -e kernel/kernel
    0x0000000080002de2
    0x0000000080002f4a
    0x0000000080002bfc
    Ctrl-D
你应该会看到类似如下的内容： 
    kernel/sysproc.c:74
    kernel/syscall.c:224
    kernel/trap.c:85

一些提示：

  • 为你的 backtrace() 至 kernel/defs.h 添加原型声明，以便你可以调用 backtrace 在 sys_pause.
  • GCC 编译器将当前正在执行的函数的帧指针存储在寄存器 s0中。在 #ifndef __ASSEMBLER__ ... #endif 标记的部分内，将以下函数添加到 kernel/riscv.h: 
    static inline uint64
r_fp()
{
  uint64 x;
  asm volatile("mv %0, s0" : "=r" (x) );
  return x;
}
    并在 backtrace 以读取当前帧指针。 r_fp() 使用 内联汇编 以读取 s0.
  • 这些 讲义 中有栈帧布局的示意图。注意，返回地址位于栈帧帧指针的固定偏移量（-8）处，而保存的帧指针位于帧指针的固定偏移量（-16）处。
  • 你的 backtrace() 需要一种方法来识别已到达最后一个栈帧，并应停止回溯。一个有用的事实是，每个内核栈所分配的内存由一个页对齐的单页组成，因此某个栈的所有栈帧都位于同一页上。你可以使用 PGROUNDDOWN(fp) （参见 kernel/riscv.h）来确定帧指针所指向的页。

一旦你的回溯功能正常工作，请在 panic 在 kernel/printf.c 中调用它，以便在内核发生 panic 时显示回溯信息。

Alarm

在本练习中，你将为 xv6 添加一项功能，使其能够在进程使用 CPU 时间时周期性地发出提醒。这对于希望限制自身 CPU 占用的计算密集型进程，或者在执行计算的同时希望周期性执行某些操作的进程来说非常有用。更广泛地说，你将实现一种用户态中断/故障处理程序的基本形式；例如，你可以使用类似的机制在应用程序中处理缺页错误。如果你的解决方案能够通过 alarmtest 和 `usertests -q`，则说明解答正确。

您应该添加一个新的 sigalarm(interval, handler) 系统调用。如果应用程序调用 sigalarm(n, fn)，然后在每次 n "ticks" 是程序消耗的 CPU 时间单位，内核应触发应用程序函数 fn 被调用。当 fn 返回时，应用程序应从中断处继续执行。tick 是 xv6 中一个相当任意的时间单位，由硬件定时器产生中断的频率决定。如果应用程序调用 sigalarm(0, 0)，内核应停止生成周期性的警报调用。

你将找到一个文件 user/alarmtest.c 在你的 xv6 代码仓库中。将其添加到 Makefile。在你添加 sigalarm 和 sigreturn 系统调用（见下文）。

alarmtest 调用 sigalarm(2, periodic) 在 test0 请求内核强制调用 periodic() 每隔 2 个时钟滴答触发一次，然后自旋一段时间。你可以在 user/alarmtest.asm 中查看 alarmtest 的汇编代码，这对调试很有帮助。当满足以下条件时，你的解决方案即为正确： alarmtest 产生如下输出，且 usertests -q 也能正确运行：

完成后，你的解决方案只需几行代码，但要正确实现可能有些棘手。我们将使用原始仓库中的 alarmtest.c 版本来测试你的代码。你可以修改 alarmtest.c 来辅助调试，但请确保原始的 alarmtest 显示所有测试均通过。

test0：调用处理程序

通过修改内核以跳转到用户态的报警处理程序来开始，这将使 test0 打印出 "alarm!"。暂时不必担心输出 "alarm!" 之后会发生什么；如果你的程序在打印 "alarm!" 后崩溃，目前也是可以接受的。以下是一些提示：

  • 您需要修改 Makefile 以使 alarmtest.c 将被编译为一个 xv6 用户程序。
  • 应放入的正确声明位于 user/user.h are: 
        int sigalarm(int ticks, void (*handler)());
    int sigreturn(void);
  • 更新 user/usys.pl（用于生成 user/usys.S）、kernel/syscall.h 和 kernel/syscall.c，以允许 alarmtest 用于调用 sigalarm 和 sigreturn 系统调用。
  • 目前，您的 sys_sigreturn 应直接返回零。
  • 你的 sys_sigalarm() 应将报警间隔和处理函数指针存储在 proc 结构体（位于 kernel/proc.h).
  • 你需要跟踪自上次调用（或距下次调用）进程报警处理函数以来经过的 tick 数；你还需要在 struct proc 中为此新增一个字段。你可以在 proc 中的字段在 allocproc() 在 proc.c.
  • 每个 tick，硬件时钟强制触发一个中断，该中断在 usertrap() 在 kernel/trap.c.
  • 仅当存在定时器中断时，才应操作进程的报警 tick；你需要类似这样的逻辑： 
        if(which_dev == 2) ...
  • 仅当进程有待处理的定时器时才调用报警函数。注意，用户报警函数的地址可能为 0（例如，在 user/alarmtest.asm 中， periodic 位于地址 0）。
  • 你需要修改 usertrap() 使得当进程的报警间隔到期时，用户进程能够执行处理函数。当 RISC-V 上的陷阱返回用户态时，是什么决定了用户态代码恢复执行时的指令地址？
  • 如果让 QEMU 仅使用一个 CPU，用 gdb 查看陷阱会更方便，可以通过运行以下命令实现： 
        make CPUS=1 qemu-gdb
  • 如果 alarmtest 打印出 "alarm!"，则说明你已成功。

test1/test2()/test3()：恢复被中断的代码

alarmtest 很可能在打印 "alarm!" 后于 test0 或 test1 中崩溃，或者 alarmtest（最终）打印 "test1 failed"，或者 alarmtest 在未打印 "test1 passed" 的情况下退出。要解决此问题，你必须确保当警报处理程序执行完毕后，控制权能返回到用户程序最初被定时器中断时所在的指令处。你必须确保寄存器内容恢复为中断发生时的值，以便用户程序能够在不受干扰的情况下继续运行。最后，你应在每次警报触发后"重置"警报计数器，以便处理程序能被周期性地调用。

作为起点，我们已为你做出了一个设计决策：用户警报处理程序在完成后须调用 sigreturn 系统调用。请参阅 periodic 在 alarmtest.c 中的示例。这意味着你可以在 usertrap 和 sys_sigreturn 中添加代码，相互配合，使用户进程在处理完警报后能正确恢复执行。

一些提示：

  • 你的解决方案需要保存和恢复寄存器——为了正确恢复被中断的代码，你需要保存和恢复哪些寄存器？（提示：数量会很多。）
  • 让 usertrap 在定时器触发时将足够的状态保存到 struct proc 中，以便 sigreturn 能够正确返回到被中断的用户代码。
  • 防止对处理程序的重入调用——如果处理程序尚未返回，内核不应再次调用它。 test2 对此进行测试。
  • 确保恢复 a0。 sigreturn 是一个系统调用，其返回值存储在 a0 中。

一旦你通过 test0, test1, test2以及 test3 运行 usertests -q 以确保你没有破坏内核的其他部分。
