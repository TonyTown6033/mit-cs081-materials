实验：mmap

该 mmap 和 munmap 系统调用允许 UNIX 程序对其地址空间进行精细控制。它们可用于在进程间共享内存、将文件映射到进程地址空间，以及作为用户态缺页故障方案（如课堂上讨论的垃圾回收算法）的组成部分。在本实验中，你将添加 mmap 和 munmap 到 xv6，专注于内存映射文件。

获取本实验的 xv6 源代码并切换到 mmap branch: 

  $ git fetch
  $ git checkout mmap
  $ make clean

`man 2 mmap`) describes the POSIX `mmap()` function. xv6 doesn't have many features that `mmap` requires; for example, it doesn't support `MAP_PRIVATE` and may lack file system features. We've provided you with starter code in `kernel/sysfile.c` that you should use as a starting point. 手册页（运行 `man 2 mmap`）描述了 POSIX `mmap()` 函数。xv6 缺少 `mmap` 所需的许多特性；例如，它不支持 `MAP_PRIVATE`，也可能缺少文件系统特性。我们在 `kernel/sysfile.c` 中为你提供了起始代码，你应以此作为起点。 man 2 mmap）展示了该声明，内容为 mmap: 

void *mmap(void *addr, size_t len, int prot, int flags,
           int fd, off_t offset);

mmap 可以通过多种方式调用，但本实验只需实现与文件内存映射相关的功能子集。你可以假设 addr 将始终为零，表示内核应自行决定将文件映射到哪个虚拟地址。 mmap 返回该地址，若失败则返回 0xffffffffffffffff。 len 是要映射的字节数；它可能与文件的长度不同。 prot 指示内存是否应被映射为可读、可写和/或可执行；你可以假设 prot 的值为 PROT_READ 或 PROT_WRITE 或两者兼有。 flags 将是以下两者之一 MAP_SHARED，这意味着对映射内存的修改应写回文件，或 MAP_PRIVATE，意味着它们不应该。你不必实现 flags. fd 是要映射的文件的打开文件描述符。你可以假设 offset 为零（这是文件中开始映射的起始偏移量）。

你的实现应当以惰性方式填充页表，以响应缺页错误。也就是说， mmap 本身不应分配物理内存或读取文件。而应在缺页错误处理代码中（或由其调用的函数中）完成这些操作， usertrap，就像在写时复制实验中一样。采用惰性方式的原因是为了确保 mmap 大文件时速度很快，以及 mmap 大于物理内存的文件是可行的。

映射同一个 MAP_SHARED 文件的进程 不 共享物理页面是可以接受的。

We've provided you with starter code in `kernel/sysfile.c` that you should use as a starting point. 手册页（运行 `man 2 mmap`）描述了 POSIX `mmap()` 函数。xv6 缺少 `mmap` 所需的许多特性；例如，它不支持 `MAP_PRIVATE`，也可能缺少文件系统特性。我们在 `kernel/sysfile.c` 中为你提供了起始代码，你应以此作为起点。 man 2 munmap）展示了该声明，内容为 munmap: 

int munmap(void *addr, size_t len);

munmap 应删除指定地址范围内的 mmap 映射（如有）。如果进程已修改该内存且以 MAP_SHARED方式映射，则应先将修改写入文件。 munmap 调用可能只覆盖 mmap 区域的一部分，但可以假设它只会在区域的开头、结尾或整个区域取消映射（不会在区域中间打孔）。当进程退出时，它对 MAP_SHARED 区域所做的任何修改都应写入相应文件，就如同进程调用了 munmap.

你需要实现足够的 mmap 和 munmap 功能，以使 mmaptest 测试程序能够正常运行。如果 mmaptest 未使用某个 mmap 特性，则无需实现该特性。你还必须确保 usertests -q 仍能正常工作。

以下是一些提示：

  • 从添加开始 _mmaptest 至 UPROGS以及 mmap 和 munmap 系统调用，以便获得 user/mmaptest.c 编译。目前，只需从以下位置返回错误： mmap 和 munmap. 我们定义了 PROT_READ 等供您使用 kernel/fcntl.h. 运行 mmaptest，这将在第一次 mmap 调用时失败。
  • 记录 mmap 为每个进程映射了哪些内容。定义一个与"面向应用程序的虚拟内存"讲座中所描述的 VMA（虚拟内存区域）相对应的结构体。该结构体应记录由以下操作创建的虚拟内存范围的地址、长度、权限、文件等信息。 mmap由于 xv6 内核中没有可变大小的内存分配器，可以声明一个固定大小的 VMA 数组，并按需从中分配。大小为 16 应该足够。
  • 实现 mmap：在进程的地址空间中找到一块未使用的区域用于映射文件，并向进程的已映射区域表中添加一条 VMA。该 VMA 应包含一个指向 struct file 用于被映射的文件； mmap 应增加文件的引用计数，以确保在文件关闭时该结构不会消失（提示：参见 filedup）。运行 mmaptest：第一个 mmap 应成功，但首次访问 mmap 映射的内存时将引发页错误并终止 mmaptest.
  • 添加代码，使 mmap 映射区域中发生缺页错误时，能够分配一页物理内存，将相关文件的 4096 字节读入该页，并将其映射到用户地址空间。使用以下方式读取文件： readi，该函数接受一个偏移量参数用于指定在文件中的读取位置（但你需要对传入的 inode 进行加锁/解锁 readi）。不要忘记正确设置页面的权限。运行 mmaptest；它应该到达第一个 munmap.
  • 实现 munmap：找到该地址范围对应的 VMA 并取消映射指定页面（提示：使用 uvmunmap）。如果 munmap 移除之前所有的 mmap，应当递减相应的引用计数 struct file。若已取消映射的页面已被修改，且文件以 MAP_SHARED方式映射，则需将该页面写回文件。参考 filewrite 以获取灵感。
  • 理想情况下，您的实现应仅写回 MAP_SHARED 程序实际修改过的页面。RISC-V PTE 中的脏位（D）表示该页面是否已被写入。但是， mmaptest 不会检查未被修改的页面是否被写回；因此，即使不查看 D 位，也可以直接写回页面。
  • 修改 exit 以取消进程的已映射区域，效果等同于调用 munmap 。运行 mmaptest；所有测试通过至 test mmap two files 应该通过，但可能不包括 test fork.
  • 修改 fork 以确保子进程拥有与父进程相同的映射区域。不要忘记为 VMA 的 struct file增加引用计数。在子进程的缺页处理程序中，分配一个新的物理页而非与父进程共享页面是可以接受的。后者更为优雅，但需要更多的实现工作。运行 mmaptest；它应该通过所有测试。

运行 usertests -q 以确保所有功能仍然正常工作。

可选挑战

  • 如果两个进程 mmap 了同一个文件（如 fork 测试中所示），则共享它们的物理页。你需要对物理页维护引用计数。
  • 你的实现可能会为从 mmap 文件中读取的每一页分配一个新的物理页，即使这些数据已经存在于内核的缓冲区缓存中。修改你的实现，改为使用那些已有的物理内存，而不是分配新页。这要求文件块的大小与页面大小相同（将 BSIZE 设置为 4096）。你需要将 mmap 的块固定在缓冲区缓存中，并需要处理引用计数问题。修复这种双重缓存的一个好处是，它还有助于使 read() 和 write() 与 mmap保持一致。也就是说，如果某些 mmap通过内存映射修改的文件数据， read 应返回这些修改内容，同样地，如果应用程序调用 write，该写入应出现在该文件的任何活跃内存映射中。您可能会发现阅读以下论文很有趣： 统一缓冲区缓存.
  • 消除你的惰性分配实现与 mmap 文件实现之间的冗余。（提示：为惰性分配区域创建一个 VMA。）
  • 修改 exec 以便为二进制文件的不同段使用 VMA，从而实现按需分页的可执行文件。这将使程序启动更快，因为 exec 将不需要从文件系统中读取任何数据。
  • 实现页面换出与换入：当物理内存不足时，让内核将进程的某些部分移至磁盘；当进程访问已换出的内存时，再将其换入。
